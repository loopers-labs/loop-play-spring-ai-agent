# 1주차 - 프롬프트 정량 비교

> 1단계가 끝나고도 마음에 안 풀려서 남겨둔 게 있었어요.
> "SYSTEM_PROMPT 손본 게 진짜 효과가 있는 건가" 를 어떻게 확인할 수 있는가.

## 1단계가 남긴 찝찝함

1단계 회고 끝에 적어둔 미해결이 두 가지였어요.
하나는 `confidenceLevel` 이 실제로 추측인 케이스에서 LOW 를 솔직하게 뱉는지 모른다는 거,
다른 하나는 카테고리를 일곱 개로 자른 게 적절한지 분류 로그를 봐야 알겠다는 거였습니다.

근데 이 두 개 다 "한 번 호출해보고 답이 맞으면 OK" 로는 검증이 안 되더라고요.
같은 문의를 LLM 에 다섯 번 던지면 카테고리가 다섯 번 다 똑같이 나오는가, 아니면 흔들리는가 — 거기부터 본 다음에야 어디까지 신뢰할지 정해질 것 같았어요.
`application.yml` 에 `temperature: 0.3` 으로 잡혀 있어서 완전 결정론은 아니고, 같은 입력에 응답이 어느 정도 흔들리는 게 정상입니다.
그래서 2단계는 "정답을 맞췄는가" 가 아니라 "흔들림이 얼마나 큰가" 를 먼저 보기로 했어요.

## categoryConsistency 가 정확히 뭘 측정하는가

스타터 코드에 이미 `PromptLabResult.from()` 이 있어서 계산식이 박혀 있었어요.

```text
categoryConsistency = maxCategoryCount / totalRuns
```

이게 무엇을 측정하느냐 — "같은 입력 N번 돌렸을 때 가장 많이 뽑힌 카테고리가 차지하는 비율" 입니다.
1.0 이면 N번이 다 같은 카테고리, 0.2 이면 5번 호출에서 카테고리가 죄다 다르게 흩어졌다는 뜻.

근데 이건 "안정성" 만 보는 지표지 "정답" 을 보는 지표가 아니에요.
모델이 어떤 입력에 대해 다섯 번 다 자신 있게 `ETC` 로 분류해도 categoryConsistency 는 1.0 이 나옵니다.
사실은 `SAFETY` 였어야 할 입력인데도요.

그래서 이 지표를 "프롬프트 좋아졌는가" 의 단일 기준으로 쓰면 안 될 것 같아요.
정답 라벨을 사람이 붙인 골든 셋이 따로 있어야 정밀도/재현율 같은 진짜 분류 지표가 나옵니다.
이번 2단계는 거기까진 못 가고, 그래도 흔들림 자체는 보고 싶었던 거예요.

## 구현 결정 몇 가지

엔드포인트는 `POST /api/v1/prompt-lab` 으로 시스템 프롬프트와 메시지, 반복 횟수를 받게 했어요.
한 번 요청 안에서 `ChatClient.Builder` 의 `defaultSystem(...).build()` 는 한 번만 호출하고, 그 `ChatClient` 로 `repeat` 번 호출하게 묶었습니다.
요청마다 system prompt 가 달라지니까 1단계처럼 컨트롤러 생성자에서 한 번만 빌드해두는 패턴은 못 써요 — 그래도 한 요청 안에서는 한 번 빌드 후 재사용으로 정리했습니다.

`repeat == 0` 또는 음수면 LLM 을 부르지 않고 빈 결과를 돌려주게 했어요.
의도가 모호한 입력으로 모델에 부담을 주는 게 싫었습니다.
이건 학습 환경이라 비용 부담은 작지만, 운영을 생각하면 이런 가드는 처음부터 들이는 게 손에 익을 것 같아서 같이 넣었어요.

`@RequiredArgsConstructor` 는 빼고 명시 생성자를 썼어요.
1단계 `SupportController` 때부터 정한 톤인데, 생성자에서 로직이 들어갈 가능성이 있는 컴포넌트는 Lombok 으로 가리지 않는 게 차후 확장 때 덜 헷갈리겠더라고요.

## 테스트로 잡은 가드레일

`PromptLabControllerTest` 에 네 케이스를 넣었어요.

1. `experiment_callsLlmRepeatTimes_andBuildsChatClientOnce` — repeat=3 일 때 `ChatClient.Builder.build()` 가 1회, `.entity()` 가 3회 호출되는지 (한 요청 안에서 빌드 재사용 확인용)
2. `experiment_categoryConsistency_isMaxCountOverTotal_whenResponsesDiffer` — 3회 호출에 ORDER 2회, ETC 1회 답이 섞이면 consistency 가 `2/3` 으로 떨어지는지
3. `experiment_repeatZero_doesNotCallLlm_andReturnsEmptyStats` — repeat=0 이면 빌더에 한 번도 손이 안 가는지
4. `experiment_negativeRepeat_isTreatedAsZero` — 음수 repeat 도 0 과 같이 다루는지

`./gradlew test --rerun-tasks` 결과는 `build/test-results/test/TEST-com.baedal.support.PromptLabControllerTest.xml` 의 `<testsuite>` 속성에 `tests="4" skipped="0" failures="0" errors="0"` 로 기록됐고, 1단계 `SupportControllerTest` 의 `tests="2" failures="0" errors="0"` 도 동일 디렉토리에서 회귀 없는 게 확인됐어요.
실제 LLM 응답이 아니라 ChatClient 체인이 mock 인 상태에서의 검증이라, "ChatClient 가 의도된 횟수로 호출되고 집계 식이 맞다" 까지만 보장하는 가드입니다.

## 안 풀린 채로 두는 것들

가장 큰 게 실측이에요.
이 컨트롤러는 단위 테스트만 통과한 상태고, 실제 Ollama `qwen2.5` 에 1단계 SYSTEM_PROMPT 와 "단순 프롬프트" 를 각각 5회 돌려서 categoryConsistency 를 비교해본 결과는 아직 없습니다.
이건 모델 띄워두고 직접 `curl` 로 두드려본 다음에 README 든 05번 회고든 한쪽에 숫자랑 같이 적을 영역이에요.

두 번째는 `temperature` 조작.
`application.yml` 에 `temperature: 0.3` 으로 박혀 있는데, 이걸 0.0 으로 떨어뜨리면 consistency 가 1.0 에 더 붙을 가능성이 큽니다.
그런데 그건 "프롬프트가 좋아져서" 가 아니라 "샘플링이 좁아져서" 라, 비교 실험할 땐 temperature 를 고정해두고 SYSTEM_PROMPT 만 바꾸는 게 맞을 것 같아요.
이 결정도 실측을 한 번 본 다음에 다시 정리하려고요.

세 번째는 정답 라벨.
위에 적은 대로 consistency 만 보고는 "프롬프트가 더 정확해졌나" 를 못 봅니다.
사람이 손으로 라벨링한 골든 셋 (한 20건이라도) 이 같이 있어야 정밀도 비교가 됩니다.
당장은 못 만들고, 3단계 (Streaming) 끝낸 다음에 작은 셋부터 시도해볼 생각이에요.

## 실측해보고 적어두는 부록

PromptLab 의 `systemPrompt` 만 두 가지로 갈아끼우면서 같은 메시지에 `repeat: 3` 으로 호출해봤어요.
하나는 "당신은 친절한 한국 배달 고객 상담사입니다. 고객 문의에 친절하게 답하세요." 한 줄짜리, 다른 하나는 1단계에서 보강한 `BaedalPrompt.SYSTEM_PROMPT` 전체.
이걸 SIMPLE / ENRICHED 라고 적어두고 메시지 세 개를 돌렸습니다.

첫 메시지가 "음식에 머리카락이 나왔어요. 너무 화가 납니다." 였어요.
SIMPLE 쪽은 세 번 다 QUALITY + HIGH 로 일관적으로 떨어졌고, ENRICHED 쪽은 QUALITY 한 번 + SAFETY 두 번 + 모두 CRITICAL 로 갈렸습니다.
이게 좀 당황스러웠는데, 회고 본문에서 "이물질 = QUALITY, 식중독·알레르기 = SAFETY" 로 단정해서 카테고리를 나눴거든요.
근데 모델 쪽에선 머리카락 이물질을 식품안전 사고에 더 가깝게 본 거예요.
회고에 적어둔 SOP 분할이 모델 분류 기준과 항상 일치하진 않는다는 게 잡혔습니다.

그리고 묘한 게, SIMPLE 쪽이 consistency 1.0 으로 더 안정적으로 보였어요.
근데 이건 SIMPLE 이 더 정확해서 그런 게 아니라 SIMPLE 프롬프트엔 카테고리 정의 자체가 없으니까 모델이 자기 사전 분류로 가서 그렇다고 봐요.
정답 라벨 없이 consistency 만 보면 잘못된 정답에 일관적인 경우랑 진짜 정답을 안정적으로 뱉는 경우가 구분이 안 되는데, 회고 본문에 추측으로 적어둔 그 한계가 이 한 케이스에서 그대로 노출됐어요.

두 번째 메시지가 "어제 시킨 거 먹고 토했어요. 새우 알레르기인 거 같아요." 였습니다.
이 케이스의 SIMPLE 쪽이 HTTP 500 으로 깨졌어요.
모델이 JSON 으로 답할 의무가 없으니까 자유롭게 자연어로 답했고, `.entity(SupportResponse.class)` 의 BeanOutputConverter 가 JSON 추출에 실패한 거예요.
사실 4단계 내내 막연히 걱정했던 게 이거였습니다.
ENRICHED 프롬프트의 "JSON 외 다른 텍스트는 출력하지 않습니다" 라는 한 줄이 형식 지시 한 줄로 보였는데, 빠지면 엔드포인트 자체가 깨진다는 게 실측으로 잡혔어요.
ENRICHED 쪽은 같은 입력을 세 번 다 SAFETY 로 분류했고 urgency 만 HIGH 두 번 CRITICAL 한 번으로 갈렸는데, 이 정도는 temperature 0.3 의 자연스러운 흔들림으로 봤습니다.

세 번째 메시지가 "주문 취소하고 싶어요." 였는데, 여기선 SIMPLE / ENRICHED 가 ORDER + NORMAL 로 똑같이 떨어졌어요.
입력에 단서가 너무 명확해서 어떤 프롬프트로 가도 같은 분류가 나오는 거예요.
회고 본문에서 의도적으로 안 적었던 부분인데, 모든 입력에서 ENRICHED 가 우월한 게 아니라 모호한 입력에서만 차이가 보이는 거였습니다.

세 메시지를 통째로 보고 나서 정리되는 게, ENRICHED 의 본 효과는 두 가지였어요.
하나는 JSON 강제로 `.entity()` 가 깨지지 않게 잡아주는 거고, 다른 하나는 SAFETY 가드레일이 발화하는 거.
반대로 "ENRICHED 가 더 정확하다" 는 단정은 못 하겠습니다. 머리카락 케이스에서 SOP 분류가 흔들리는 게 실측에 그대로 잡혀서요.
회고 본문에 적어뒀던 categoryConsistency 의 한계도 머리카락 SIMPLE 케이스가 그대로 보여줍니다 — 잘못된 정답에도 1.0 이 나오니까요.
다음 라운드에 정답 라벨 셋이 진짜 필요하겠다는 생각이 굳어진 자리예요.
