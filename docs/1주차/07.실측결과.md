# 1주차 - 실측 결과 정리

> 03~06 회고에 적어둔 "왜" 를 실측으로 두드려보고, 어디가 그대로 작동했고 어디가 흔들렸는지 한 자리에 모았어요.
> 세부 데이터는 각 회고 끝 "실측해보고 적어두는 부록" 에 같이 적었으니, 이 글은 가로질러 보는 자리로 봐 주세요.

## 어떤 환경에서 두드렸는가

Ollama 에 `qwen2.5:latest` (4.7GB) 받아두고, `application.yml` 의 `temperature: 0.3`, `base-url: http://localhost:11434` 설정 그대로 사용했어요.
`./gradlew bootRun` 으로 8080 띄우고 `curl` 로 직접 두드렸고, raw 응답은 `/tmp/baedal-실측/` 에 저장했습니다 (커밋 대상은 아니에요).

## 회고가 그대로 작동한 부분

가장 마음에 든 게 SAFETY 가드레일이었어요.
"어제 시킨 거 먹고 두드러기가 났어요" 같은 한 줄에 대해 category=SAFETY, urgency=CRITICAL, nextAction 에 "의료기관 방문을 권유합니다" 가 그대로 떨어졌습니다.
회고 03 의 [규칙] 에 적어둔 "직접 진단하지 않고 의료기관 방문을 권유한다" 가 그대로 작동한 거예요.
이거 하나는 시스템 프롬프트 손본 보람이 있구나 싶었어요.

또 한 가지는 회고 04 에서 SIMPLE vs ENRICHED 비교에서 잡힌 거예요.
"어제 시킨 거 먹고 토했어요" 입력에 대해 SIMPLE 프롬프트는 HTTP 500 으로 깨졌고, ENRICHED 는 세 번 다 SAFETY 로 일관 분류됐습니다.
ENRICHED 의 "JSON 외 다른 텍스트는 출력하지 않습니다" 한 줄이 단순한 형식 지시가 아니라 엔드포인트의 안정성을 결정하는 가드라는 게 데이터로 잡혔어요.

advisor 의 null 검사도 이번 실측에선 다섯 건 다 안 발화했어요 (회고 06 부록).
qwen2.5 가 usage 메타데이터를 항상 잘 채워주는 모델이라는 뜻이고, null 검사가 다른 모델이나 다른 옵션을 대비한 방어 코드라는 위치가 좀 더 분명해졌습니다.

## 회고에 단정으로 적어둔 게 흔들린 부분

confidenceLevel 부터 적어둘게요.
회고 03 본문에서 "근거가 부족하면 LOW 로 낮춥니다" 라는 지시를 시스템 프롬프트에 박아두고 그게 작동할 거라고 적었는데, 다섯 건 실측에서 다 MEDIUM 으로만 떨어졌어요.
주문번호가 명시된 ORDER 케이스도 MEDIUM, 단서가 거의 없는 PAYMENT 케이스도 MEDIUM 으로 묶였습니다.
모델이 자기 확신도를 안전하게 가운데 값에 던지는 습관이 있다는 가설이 새로 생겼는데, 다섯 건만으론 단정 못 하고 의심 짙어진 채로 다음 라운드로 넘어갑니다.

estimatedResolutionMinutes 도 다섯 건 다 null 이었어요.
회고에서 "모르면 null 허용" 으로 적어둔 게 실측에선 "항상 null" 이었습니다.
이 필드를 살리려면 카테고리별 typical resolution time 을 시스템 프롬프트에 같이 박거나 few-shot 예시를 보여줘야 할 것 같다는 새 가설이 생긴 자리예요.

카테고리 분할이 흔들린 건 회고 04 의 머리카락 케이스예요.
회고 03 에서 "이물질 = QUALITY, 식중독·알레르기 = SAFETY" 로 단정해서 카테고리를 나눴는데, 모델은 머리카락 이물질을 ENRICHED 프롬프트에선 SAFETY 쪽으로 더 자주 분류했습니다 (세 번 중 두 번).
회고에 적어둔 SOP 분할이 모델 분류 기준과 항상 일치하진 않는다는 게 데이터로 잡혔어요.

회고 05 에서 미해결로 남겨둔 "트리아지 (JSON) vs 스트리밍 (자연어) 의 균형이 어색하다" 도 실측에서 그대로 보였습니다.
JSON 강제 SYSTEM_PROMPT 와 `.stream()` 이 만나니까 JSON 한 글자 한 글자가 SSE 청크로 떨어지는 모양이 됐고, 클라이언트가 부분 JSON 청크를 쓸 방법이 없으니 사실상 `.call()` 이랑 사용성이 같아졌어요.

## 회고에 안 적었던 부분 — 단순 입력에선 차이가 없다

회고 04 비교에서 "주문 취소하고 싶어요" 케이스는 SIMPLE / ENRICHED 가 ORDER + NORMAL 로 똑같이 떨어졌어요.
입력에 단서가 너무 명확하면 프롬프트 보강의 효과가 0 입니다.
회고 본문에서 의도적으로 안 적었던 부분인데, 모든 입력에서 ENRICHED 가 우월한 게 아니라 모호 케이스에서만 차이가 보이는 거였어요.

## 토큰 비용은 어디서 흘러나오는가

회고 06 부록에 적어둔 대로 promptTokens 가 1149~1159 사이에서 거의 안 흔들렸어요.
SYSTEM_PROMPT 본문이 ~1130 토큰을 차지하니까 매 호출마다 이게 깔리는 거예요.
지금은 학습 환경이라 비용 부담이 작지만 운영을 가정하면 그대로 둘 수 없을 것 같고, 다음 라운드에 캐싱이나 축약을 봐야 할 자리로 잡혔습니다.

## 다음 라운드로 미루는 것들

회고 본문 끝마다 적어둔 미해결 목록을 가로질러 보면, 1주차 시점에서 이번 라운드 안에 안 푼 게 정리되어요.

정답 라벨 셋이 가장 큰데, 한 20건이라도 사람이 손으로 라벨링한 데이터가 있어야 categoryConsistency 외에 정밀도/재현율 비교가 됩니다.
이게 없으면 머리카락 SIMPLE 케이스처럼 잘못된 정답에도 consistency 1.0 이 나오는 상황을 잡을 수가 없어요.

stream 용 시스템 프롬프트 분리도 다음 자리로 넘어갔어요.
자연어 답변 + 짧은 안내 톤만 살린 별도 시스템 프롬프트가 필요하고, 트리아지 (JSON) 모드랑 시스템 프롬프트 자체를 분리해야 사용성이 살아납니다.

PromptLab / StreamingChatController 에 advisor 적용도 같이 넘어갔어요.
회고 04 의 18 LLM 호출에 토큰/시간 데이터가 같이 잡혀야 비교 실험이 진짜 의미를 가집니다.

마지막으로 advisor 실패 경로가 정작 잘 작동하는지는 이번 실측에선 못 봤어요.
Ollama 끄거나 모델 이름 틀린 상태에서 한 번 두드려봐야 `log.warn("LLM call failed ...")` 가 의도대로 떨어지는지 확인이 가능합니다.
