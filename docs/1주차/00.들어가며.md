# 1주차 - 들어가며

> 강의 첫 시간 "왜 지금 Agentic AI인가"를 듣고 정리한 메모입니다.
> 강의 자료를 그대로 옮기기보다는, 슬라이드를 보면서 든 생각을 그때그때 적어 두려고 했어요.

## "Generative AI는 끝났다"는 한 줄에 멈췄던 이유

첫 슬라이드에 AWS·Google·Microsoft 키노트 톤이 비슷하다는 얘기가 나왔습니다.
"Generative AI는 끝났고, 이제 Agentic AI다."

처음엔 "또 새 키워드인가" 하는 마음이 살짝 들었어요.
LLM, MLOps, 데이터 메시처럼 매년 도는 키워드들이 있어서, 이번에도 비슷한 사이클일 수도 있겠다 싶었습니다.

그런데 이어서 나온 Gartner 두 줄을 보고는 잠깐 멈췄어요.

> 2024년에 1% 미만이었던 비중이 2028년에 33%가 된다.

4년에 30배.
이게 그대로 맞는 숫자라고 보진 않지만, 적어도 "그냥 또 하나의 키워드"라고 흘려보내긴 어려운 기울기인 것 같았습니다.
클라우드 전환이나 모바일 전환과 한 줄에 놓고 봐도 어색하지 않은 정도라, 한 번쯤 들여다볼 만하다는 생각이 들었어요.

📌 **이 부분에서 살짝 바뀐 생각**: "또 한 번 도는 키워드겠지" → "적어도 백엔드 입장에서 안 봐도 되는 흐름은 아닌 것 같다".

## 통계보다 마음에 와닿은 건 제 책상이었어요

강의 중간에 Claude Code·Cursor·Copilot Workspace 이야기가 나왔습니다.
저한테는 이쪽이 통계보다 더 자연스럽게 와닿았어요.

저는 이미 Cursor 없이 코드를 짜는 게 어색해진 지 좀 됐고, Claude Code로 리팩토링을 돌린 다음 결과만 검토하는 날이 늘었습니다.
"코드를 제안하는 단계는 진작에 넘어섰다"는 강의자의 말이, 미래 시제가 아니라 그냥 지금 제 모습에 가까웠어요.

그러다 보니 Agentic AI라는 단어가 막 새롭게 들리지는 않았습니다.
백엔드 쪽으로 넘어오는 시점이 늦었을 뿐, 흐름 자체는 이미 옆에서 돌아가고 있던 거 같아요.

📌 **저한테 가장 와닿은 부분**: 시장 예측이 아니라 "지난주에 내가 뭘 썼나" 를 돌아보는 쪽. 이 부분이 가장 거짓말이 안 통하는 자료라는 생각이 들었어요.

## AgentCore 컴포넌트 분해를 보고 마음이 편해진 부분

강의 후반에 AWS Bedrock AgentCore가 나왔습니다.
처음엔 "또 새 서비스인가" 싶었는데, 컴포넌트 분해 슬라이드를 보고는 분위기가 좀 바뀌었어요.

Memory · Identity · Gateway · Observability.
이름을 보자마자 "이거 우리가 매일 다루는 것들과 꽤 닮았네" 하는 생각이 들었습니다.
캐시와 세션, OAuth2, API Gateway, OpenTelemetry — 이름만 살짝 바꿔서 매핑하면 거의 그대로 Spring 백엔드에서 다루는 영역이에요.

강의자가 "AgentCore가 새로 발명한 게 아니라, 기존 백엔드 베스트 프랙티스를 에이전트라는 워크로드에 맞게 재조립한 쪽에 가깝다"라고 했는데, 들으면서 꽤 공감이 갔어요.
AWS가 이 정도로 컴포넌트를 분해해서 공개했다는 건, 적어도 엔터프라이즈가 에이전트를 "데모"보다는 "운영해야 할 시스템"으로 보고 있다는 정도의 신호로 읽혔습니다.

📌 **이 슬라이드에서 마음이 편해진 이유**: 새로 배워야 할 게 생각보다 많지 않을 수도 있겠다는 생각. 이미 익숙한 영역 위에 얇은 레이어 하나가 더 올라가는 정도라면, 백엔드 개발자가 빠르게 따라잡기에 그렇게 멀어 보이지 않았어요.

## "Python 진영이 더 빠른데 왜 Spring AI냐"에 대한 제 생각

강의 마지막에 자연스럽게 떠오른 질문이었어요.
강의자는 운영 측면을 강조했는데, 듣다 보니 저도 비슷한 결론에 닿게 됐습니다.

Python 진영(LangChain, LlamaIndex)이 자료 양과 속도 면에선 분명 앞서 있는 것 같아요.
새 모델이나 새 기법이 나오면 PyPI에 빠르게 패키지가 올라오니까요.
다만 운영까지 같이 생각하면 이야기가 조금 달라지는 것 같습니다.
트랜잭션, 인증, 로깅, 헬스체크, 메트릭, SLO처럼 이미 Spring 쪽에서 손에 익은 것들을 Python으로 다시 짜는 비용이 만만치 않게 느껴졌어요.

이미 운영 중인 Spring 시스템이 있는 입장에서는, 그 안에 LLM 호출 한 줄 얹는 쪽이 훨씬 짧은 경로일 것 같다는 생각이 들었습니다.
`@Tool`로 기존 서비스 메서드를 LLM 도구로 노출하고, `VectorStore` 추상화로 PGVector나 Redis를 같은 API로 다루고, Observation으로 LLM 호출을 추적합니다.
결국 익숙한 부품들 위에 호출 대상 하나가 추가되는 정도라, 부담이 그렇게 크지 않을 것 같아요.

📌 **이 시점에서 제가 받아들인 트레이드오프**: Python 생태계의 풍부함을 조금 내려놓고, 대신 이미 굴러가는 시스템 안으로 곧장 들어갈 수 있는 경로를 골랐습니다. 이게 정답이라기보다는, 지금 상황에서 가장 합리적인 선택지 같았어요.

## 강의를 듣고 남은 두 가지 질문

강의가 끝난 뒤에도 머릿속에 남은 게 두 가지 있어요.
6주차까지 천천히 답을 찾아보고 싶습니다.

**하나, AgentCore의 Observability를 Spring AI Observation으로 정말 자연스럽게 대응시킬 수 있을지.**
강의자는 가능하다고 했는데, 멀티 에이전트 시나리오에서 추적 컨텍스트가 어떻게 흐를지는 직접 해봐야 감이 올 것 같아요.

**둘, "LLM은 판단자, 실행은 우리 서버"라는 경계선이 실제로 깔끔하게 그어지는지.**
강의에서 가장 강조한 메시지였는데, Tool Calling이 들어오는 2주차부터는 이 경계가 조금씩 흐려질 수도 있겠다 싶었습니다.
LLM이 "실행" 쪽에 더 발을 들이려고 할 때 어디서 멈추게 할지가, 이번 6주차에서 가장 흥미롭게 볼 지점이지 싶어요.
