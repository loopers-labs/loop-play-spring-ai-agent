# 1주차 - 스트리밍 구현

> 01.블로킹.md 에서 풀어두긴 했는데, 글로 푼 거랑 손으로 구현하는 건 또 달랐어요.

## 01 에서 풀어둔 게 다는 아니었습니다

01 회고 끝에 "WebFlux 로 갈아엎는 게 아니라 MVC 위에서도 `Flux` 반환이 된다" 까지는 정리해뒀어요.
그래서 3단계 시작할 땐 "그냥 `.call()` 자리에 `.stream().content()` 만 끼우면 되는 거 아닌가" 정도로 만만하게 봤습니다.
실제로 코드만 보면 정말 그게 다였어요.

```java
return chatClient.prompt()
        .user(req.message())
        .stream()
        .content();
```

근데 손이 멈춘 건 그 위의 `@PostMapping(produces = MediaType.TEXT_EVENT_STREAM_VALUE)` 였어요.
스타터에 이미 적혀 있어서 그냥 넘어갈 뻔했는데, 이게 왜 SSE 미디어 타입이어야 하는지 한 박자 짚고 가는 게 맞다 싶었어요.

## produces = text/event-stream 이 왜 필요한가

`Flux<String>` 을 반환한다고 자동으로 토큰 단위 스트리밍이 되는 건 아니더라고요.
이게 1주일 전의 저를 헷갈리게 했던 부분인데, 응답을 어떤 미디어 타입으로 직렬화할 거냐에 따라 클라이언트가 받는 모양이 완전히 달라집니다.

기본 `application/json` 으로 두면 Jackson 이 `Flux` 를 통째로 모아서 배열로 직렬화해버려요.
모든 토큰이 다 모인 다음에 한 덩어리로 떨어집니다.
그러면 백엔드는 토큰을 흘려보내는데 클라이언트는 결국 한 번에 받는, 의도와 정반대 상황이 됩니다.

`text/event-stream` 으로 바꾸면 SSE 직렬화 경로로 들어가서 `Flux` 가 emit 할 때마다 `data: ...\n\n` 형식으로 한 청크씩 흘려보내요.
브라우저든 `curl -N` 이든 받자마자 한 청크씩 표시할 수 있게 되는 거죠.

이게 정확한지는 사실 직접 두 가지 produces 로 응답 모양을 본 다음에 다시 정리해야 할 영역이긴 한데, 일단 SSE 미디어 타입을 명시한 이유는 그 차이 때문이라고 정리해뒀어요.

## ChatClient 는 또 생성자에서 한 번만 빌드했어요

`SupportController` 1단계에서 정해둔 패턴 그대로 가져갔습니다.

```java
public StreamingChatController(ChatClient.Builder builder) {
    this.chatClient = builder
            .defaultSystem(BaedalPrompt.SYSTEM_PROMPT)
            .build();
}
```

`PromptLabController` (2단계) 는 요청마다 system prompt 가 바뀌니까 매 요청 빌드인데, 이 컨트롤러는 1단계와 같은 트리아지 프롬프트를 그대로 쓰니까 한 번 빌드해두고 재사용하는 게 자연스러웠어요.

테스트에 `builder.build()` 가 1회만 호출되는지 확인하는 케이스를 또 하나 넣었는데, 이게 매번 작성하기 번거롭긴 합니다.
그래도 일단 컨트롤러마다 가드는 두기로 했어요. 빌드 비용이 크진 않지만, 매 요청마다 빌드되는 컨트롤러가 섞여 있으면 운영에서 보고 헷갈리니까요.

## 단위 테스트로 잡힌 가드와 못 잡는 것

`StreamingChatControllerTest` 에 케이스 두 개를 넣었어요.

1. `chatStream_appliesSystemPrompt_andEmitsTokensInOrder` — SYSTEM_PROMPT 가 `defaultSystem` 으로 전달되고, `Flux.just("주문", "번호", "확인", "필요")` 가 그대로 순서대로 emit 되는지
2. `chatStream_doesNotBuildChatClientPerRequest` — 같은 컨트롤러 인스턴스로 두 번 호출해도 `builder.build()` 가 1회만 도는지

`./gradlew test --rerun-tasks` 결과는 `build/test-results/test/TEST-com.baedal.support.StreamingChatControllerTest.xml` 의 `<testsuite>` 가 `tests="2" skipped="0" failures="0" errors="0"`.
같은 디렉토리의 `SupportControllerTest` 와 `PromptLabControllerTest` 도 각각 `tests="2"` / `tests="4"` 에 `failures="0" errors="0"` 로 회귀 없는 게 확인됐어요.

근데 솔직히 말하면, 이 단위 테스트로 "스트리밍이 잘 동작한다" 를 보장하긴 어려워요.
제가 한 건 `Flux.just(...)` 로 stub 한 리액터 스트림이 컨트롤러 밖으로 그대로 빠져나오는지 본 거고, 진짜로 본 게 아닙니다 — TTFT 가 짧은지, Tomcat 의 async 처리가 풀려나는지, SSE 형식으로 직렬화돼서 클라이언트 화면에 한 글자씩 떨어지는지.

이 영역은 단위 테스트로는 못 보고 `curl -N` 으로 직접 두드리면서 봐야 의미가 있어요.
지금은 아직 그걸 안 했고, Ollama `qwen2.5` 를 띄워서 직접 받아본 다음에 글을 한 번 더 손볼 영역이에요.

## 안 풀린 채로 두는 것들

가장 거슬리는 게 클라이언트가 중간에 끊었을 때예요.
사용자가 페이지를 닫거나 네트워크가 끊기면 `Flux` 가 cancel 신호를 받는데, 모델은 그 시점에 토큰을 계속 만들고 있을 수도 있습니다.
이 케이스에서 LLM 호출이 제대로 중단되는지, 토큰 비용은 어디서 끊기는지는 솔직히 모르겠어요.
Spring AI 가 cancel 신호를 모델로 전파하는지부터 봐야 할 영역.

또 하나는 부분 응답 로깅이에요.
4단계 `PerformanceLoggingAdvisor` 에서 토큰 수랑 응답 시간을 찍기로 했는데, 스트리밍 응답에서는 "응답 시간" 이 두 개로 쪼개집니다 — 첫 토큰까지 (TTFT) 와 마지막 토큰까지 (전체 응답 시간).
사용자 체감으론 TTFT 가 더 중요한데, 이게 Advisor 레벨에서 잡히는지 별도로 측정해야 하는지는 4단계에서 다시 봐야 할 것 같아요.

마지막으로 `Flux<String>` 으로 흘려보내는 게 트리아지 컨트롤러 (`SupportController`) 와의 균형이 좀 어색합니다.
한쪽은 구조화된 JSON 한 덩어리, 한쪽은 자연어 토큰 스트림.
같은 SYSTEM_PROMPT 를 쓰면서 출력 모양이 두 갈래로 갈라지는데, 클라이언트는 둘을 어떻게 묶어 쓸지 (예: 구조화된 분류 결과를 받은 다음 자연어 답변을 스트리밍으로 받는다거나) 가 아직 안 잡혔어요.
이건 미션의 범위 밖이지만, 운영 그림 그릴 때 한 번 더 정리해야 할 영역으로 남깁니다.

## 실측해보고 적어두는 부록

`curl -N -X POST /api/v1/chat/stream -d '{"message":"주문번호 2024-1234 배달 어디쯤에 있어요?"}'` 로 직접 두드려봤어요.

흘러나온 첫 십수 줄을 보고 솔직히 좀 멍했습니다.

```text
data:{
data:
data: 
data: "
data:summary
data:":
data: "
data:고
data:객
data:님
data: 말씀
```

회고 본문 끝에서 "트리아지 (JSON) 와 스트리밍 (자연어) 의 균형이 어색하다" 라고 적어둔 게 가설이 아니라 그냥 실측 그림이었어요.
`StreamingChatController` 가 `BaedalPrompt.SYSTEM_PROMPT` 를 그대로 쓰니까 모델은 JSON 으로 답하고, `.stream()` 은 그걸 토큰 단위로 흘려보내니까, 결과적으로 JSON 한 글자 한 글자가 SSE 청크로 떨어지는 모양이 됩니다.
클라이언트가 받아도 부분 JSON 은 파싱이 안 되니까, 결국 다 받아서 합쳐야 의미가 생겨요.
그러면 `.call()` 이랑 사실상 같아지고, TTFT 만 좀 짧아질 뿐 사용성 이득은 사라집니다.

전체를 모아 보면 응답 자체는 정확했어요 (DELIVERY + NORMAL + neededInfo 빈 배열 + confidenceLevel HIGH).
근데 지원 다섯 건 실측에선 confidenceLevel 이 다 MEDIUM 으로만 나왔는데, 이번 stream 호출 한 건은 HIGH 가 떨어졌습니다.
표본이 한 건이라 뭐라 단정은 못 하고, 그저 회고 03 끝에서 의심 짙어진 채로 적어둔 "confidenceLevel 이 잘 갈라지지 않는다" 가 한 번 더 흔들리는 그림으로 봤어요.

이번 실측으로 분명해진 거 하나만 적어두면, stream 용 시스템 프롬프트는 따로 분리해야 할 것 같다는 거예요.
지금 SYSTEM_PROMPT 의 "JSON 외 다른 텍스트는 출력하지 않습니다" 한 줄이 `SupportController` 쪽에선 엔드포인트 안정성을 잡아주는 가드인데 (회고 04 에 적어둔 SIMPLE 프롬프트 HTTP 500 사건), stream 에선 정반대로 사용성을 깎는 자리가 됩니다.
자연어 답변 + 짧은 안내 톤만 살린 별도 시스템 프롬프트가 필요하다는 게 다음 라운드 영역으로 굳어졌어요.
한 가지 같이 확인된 건 SSE 직렬화 자체는 의도대로 작동했다는 거 — produces 가 `text/event-stream` 이라 청크마다 `data:` prefix 가 붙어 흘러나왔고, 첫 청크가 호출 시작 시점에 가까웠어요.
