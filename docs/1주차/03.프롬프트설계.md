# 1주차 - 프롬프트 설계

> `BaedalPrompt.SYSTEM_PROMPT` 뼈대를 한참 들여다보다, 결국 거의 새로 썼습니다.

## 뼈대를 그대로 두기가 어려웠어요

스타터 코드의 `SYSTEM_PROMPT` 가 [역할]/[규칙]/[금지]/[응답 포맷] 으로 잘 나뉘어 있긴 한데, 막상 배달 상담 큐에 들어오는 문장을 머릿속에서 몇 개 굴려보니까 그대로는 못 쓰겠더라고요.

처음 떠올린 게 "음식에 머리카락 나왔어요" 였습니다.
이걸 어디로 보내야 하나 — 카테고리에 보이는 게 `ORDER / DELIVERY / REFUND / PAYMENT / ETC` 다섯 개라, 결국 `ETC` 입니다.
근데 "ETC로 분류된 이물질 문의" 는 큐에서 사실상 잃어버린 거예요.
그 다음에 떠올린 게 "어제 시킨 거 먹고 두드러기 났어요" 였는데, 이것도 `ETC` 로 가게 됩니다.
같은 `ETC` 카테고리에 단순 기타 문의랑 식품 안전 사고가 같이 묶이면 상담사가 매번 뒤져야 합니다.

## 카테고리는 SOP 기준으로 잘랐습니다

처음엔 카테고리를 LLM이 분류하기 쉬운 단위로 잡을까 고민했어요.
근데 그건 LLM 입장의 편의지 상담사 입장은 아니다 싶었습니다.
실제로 처리하는 사람이 누구냐, 처리하는 방식이 갈라지냐 — 그 기준으로 다시 잘랐어요.

`QUALITY` (음식 품질/맛/양/이물질) 와 `SAFETY` (식중독/알레르기) 를 분리했습니다.
같은 "음식에 문제 있어요" 도 매장 컴플레인 트랙이냐 의료기관 안내 트랙이냐가 다르니까, 한 카테고리에 묶으면 안 될 것 같았어요.
`PAYMENT` 와 `REFUND` 도 굳이 같이 두지 않았습니다 — 결제 오류는 PG 로그를 봐야 하고 환불은 사장님 합의가 필요한데, 처리하는 사람이 다르니까요.

이게 정답이라고 단정하긴 좀 그렇고, 일단 이 일곱 개 (`ORDER / DELIVERY / QUALITY / SAFETY / PAYMENT / REFUND / ETC`) 로 두고 실제 분류 결과를 보면서 손보려고 합니다.

## 금지 규칙은 글자 말고 이유를 적었어요

뼈대에 있던 금지 3개 (타사 추천 / 개인정보 노출 / 보상 약속) 는 그대로 가져갔는데, 각 줄 옆에 "왜 금지인지" 를 한 줄씩 같이 적었습니다.

처음엔 사유까지 적으면 프롬프트가 너무 길어지는 거 아닌가 망설였어요.
근데 LLM 동작을 한 번 더 생각해보니까, 모델은 글자 그대로 매칭보다 "이 규칙의 의도" 를 따라가는 쪽이 더 안정적이었던 기억이 있었습니다.
"매장 사장님 연락처 알려주세요" 라는 변종 질문이 들어왔을 때 글자만 적어두면 "개인정보" 라는 단어가 안 들어간 케이스에서 새 가능성을 봐버릴 수 있는데, 사유까지 적어두면 라이더 연락처 같은 변종에도 같은 원칙이 적용됩니다.
이건 어디서 읽은 거라기보단 그동안 모델 튜닝하면서 손에 익은 직관이라, 정량 비교는 2단계에서 해볼 생각이에요.

여기에 한 줄을 더 추가했는데, 식품 안전 호소는 직접 진단하지 않고 의료기관 방문을 권유한다는 가드레일입니다.
"식중독 같은데요?" 라는 답을 LLM이 하면 안 됩니다.

## confidenceLevel 필드를 새로 단 이유

`SupportResponse` 에 `confidenceLevel` (LOW/MEDIUM/HIGH) 을 추가했는데, 이게 1단계에서 가장 망설인 결정이에요.

LLM 응답을 그대로 상담사한테 넘기면, 상담사 입장에서는 그 분류가 사실 기반인지 추측인지가 안 보입니다.
주문번호 없이 한 줄짜리 문의에 모델이 그럴듯한 카테고리를 뽑아내면, 바쁜 상담사는 그걸 그냥 쓰기 쉬워요.
그 결과가 식품 안전 사고였을 때를 생각하면 좀 무서운 그림이에요.

`confidenceLevel` 은 모델이 자기 답이 추측이라는 사실을 표면화하게 강제하는 장치인데, 솔직히 이게 실제로 잘 작동할지는 아직 모르겠어요.
모델한테 "추측이면 LOW로 낮춰라" 라고 적어둬도 LLM은 잘 모르겠는 케이스도 HIGH로 자신 있게 답하는 경향이 있어서, 이 필드가 진짜 안전망이 되는지는 2단계 비교 실험에서 같이 봐야 합니다.

## 컨트롤러 배선에서 잡은 거

`SupportController` 를 처음엔 매 요청마다 `builder.defaultSystem(...).build()` 를 하게 짤 뻔했어요.
근데 그러면 요청마다 `ChatClient` 빈을 새로 만드는 셈이라, 생성자에서 한 번 빌드해두고 필드로 들고 있게 바꿨습니다.

```java
public SupportController(ChatClient.Builder builder) {
    this.chatClient = builder
            .defaultSystem(BaedalPrompt.SYSTEM_PROMPT)
            .build();
}
```

이게 진짜 한 번만 빌드되는지가 신경 쓰여서, 테스트에 `builder.build()` 가 한 번만 호출되는지 확인하는 케이스를 일부러 하나 더 넣어뒀어요.

## useJUnitPlatform 빠져있던 거

테스트 돌리니까 `BUILD SUCCESSFUL` 떨어지는데 정작 `build/test-results/test/` 안에 XML 리포트가 없어서 한참 봤어요.
`build.gradle` 에 `tasks.named('test') { useJUnitPlatform() }` 한 줄이 빠져있어서 JUnit 5 테스트가 아예 발견조차 안 된 상태였습니다 — Gradle 기본 test runner 는 JUnit 4 가 잡혀서, `@Test` (org.junit.jupiter.api) 어노테이션이 달린 클래스는 통째로 스킵돼요.

한 줄 추가한 뒤 `./gradlew test --rerun-tasks` 를 다시 돌리니까 `build/test-results/test/TEST-com.baedal.support.SupportControllerTest.xml` 가 생겼고, 그 안의 `<testsuite>` 속성이 `tests="2" skipped="0" failures="0" errors="0"` 로 기록됐습니다.
즉, `SupportControllerTest` 의 두 케이스 (`triage_appliesSystemPromptAndReturnsStructuredResponse`, `triage_doesNotBuildChatClientPerRequest`) 가 둘 다 실행돼서 통과했다는 증거를 그 XML 한 곳에서 확인한 거예요.
이런 건 다음번엔 처음부터 확인 항목에 넣어둬야겠습니다.

## 안 풀린 채로 두는 것들

`confidenceLevel` 이 실제로 LOW 를 솔직하게 뱉는지가 가장 큰 미해결입니다.
2단계 프롬프트 정량 비교에서 "이 필드를 빼고 동일 입력 돌렸을 때 응답이 어떻게 바뀌는가" 를 같이 보려고요.

카테고리도 일곱 개로 잘랐는데, 실제 트래픽에 돌려보면 분명 어딘가 어색한 게 나올 거예요.
초반엔 너무 잘게 자른 것 같기도 하고, 반대로 `SAFETY` 안에 알레르기/식중독을 따로 둬야 하나 싶은 생각도 듭니다.
이건 실제 분류 로그를 며칠 보고 다시 손볼 영역으로 미뤘어요.

## 실측해보고 적어두는 부록

`./gradlew bootRun` 으로 Ollama `qwen2.5` 띄워두고 `/api/v1/support` 에 다섯 건을 직접 두드려봤어요.
응답 본문이랑 같이 bootRun 쪽에 `PerformanceLoggingAdvisor` 가 elapsedMs 랑 토큰 수를 박아주는데, 이걸 같이 보면서 메모를 남깁니다.

가장 마음에 든 게 "어제 시킨 거 먹고 두드러기가 났어요. 새우 알레르기인지 모르겠어요." 한 줄이었어요.
이게 SAFETY 로 분류되면서 urgency 가 CRITICAL 로 올라가고, nextAction 이 "의료기관 방문을 권유합니다" 로 떨어졌습니다.
회고 본문에서 [규칙] 에 적어둔 "식중독 의심, 알레르기 반응은 긴급으로 분류하고 의료기관 방문을 권유합니다. 직접 진단하지 않습니다" 가 사실상 그대로 작동한 거고, 이거 하나는 시스템 프롬프트 손본 보람이 있구나 싶었어요.

반대로 본문에 단정 톤으로 적어둔 부분이 흔들렸습니다.

`confidenceLevel` 이 다섯 건 다 MEDIUM 으로만 떨어진 게 좀 답답해요.
주문번호가 명시된 ORDER 케이스는 솔직히 HIGH 가 더 자연스럽고, 단서가 거의 없는 PAYMENT 케이스는 LOW 가 어울렸을 거라 생각했는데 둘 다 똑같이 MEDIUM 으로 묶였습니다.
시스템 프롬프트에 "근거가 부족하거나 추측이 섞이면 LOW 로 낮춥니다" 라고 적어둔 건 사실상 안 먹혔어요.
모델이 자기 답변의 확신도를 항상 가운데 값으로 던지는 습관이 있는 게 아닐까 싶은데, 다섯 건만 본 거라 단정은 못 하고 일단 의심 짙어진 상태로 적어둡니다.

`estimatedResolutionMinutes` 도 다섯 건 다 null 이었어요.
모델이 분 단위 추정을 한 번도 안 뱉었습니다. 본문에서 "모르면 null 허용" 으로 적어둔 게 실제로는 "항상 null" 이었던 거라, 이 필드가 살려둘 가치가 있는지부터 다시 봐야 할 것 같아요.
시스템 프롬프트에 카테고리별 typical resolution time 을 같이 박거나 few-shot 으로 예시를 한두 개 보여줘야 모델이 시도라도 할 것 같다는 가설이 새로 생겼는데, 이건 다음 라운드에 두드려볼 영역이에요.

토큰 수는 promptTokens 가 1149~1159 사이에서 거의 안 흔들렸습니다.
SYSTEM_PROMPT 본문이 ~1130 토큰을 차지하니까 user 메시지가 짧은 한 자연스러운 수치예요. 그런데 이게 매 호출마다 깔린다는 게 보이고 나니까 운영 그림 그릴 때 캐싱이나 축약을 안 보면 안 되겠다는 생각이 같이 들었어요.
completion 쪽은 84~126 으로 답변 길이에 따라 갈렸고, neededInfo 가 비어 있던 PAYMENT 가 가장 짧고 SAFETY 쪽이 길었어요.
응답 시간은 워밍업 직후 한 번이 ~10초였고 나머지 네 건은 3~4초 안에 들어왔습니다.
