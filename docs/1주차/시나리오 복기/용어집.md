# 도메인 용어집

이 가이드 / 회고 / 코드에 자주 나오는 용어 정리예요.
"이미 알지만 이 프로젝트에선 어떤 의미로 쓰였는지" 까지 한 줄씩 같이 적었습니다.

## Spring AI · LLM 호출 관련

### ChatClient
`org.springframework.ai.chat.client.ChatClient`. LLM 한 번 호출을 묶어주는 클라이언트.
이 프로젝트에선 `Builder` 를 주입받아 생성자에서 한 번 `.defaultSystem(SYSTEM_PROMPT).defaultAdvisors(...).build()` 로 만들고 필드로 들고 다닌다.
`builder.build()` 가 매 요청마다 도는 패턴을 막으려고 컨트롤러마다 "빌드 1회" 가드를 단위 테스트에 같이 둠.

### ChatClient.Builder
`ChatClient` 인스턴스를 만드는 빌더. 빈으로 주입 가능.
`.defaultSystem(...)` 로 매 호출 앞에 깔리는 시스템 프롬프트, `.defaultAdvisors(...)` 로 advisor 체인을 박는다.

### .prompt() ... .user(...) ... .call() / .stream()
ChatClient 호출 체인의 두 갈래.
`.call()` 은 동기. 응답 다 만들어진 다음 한 덩어리로 받음. `SupportController` / `PromptLabController` 에서 사용.
`.stream()` 은 토큰 단위 흘림. `Flux<String>` 으로 받음. `StreamingChatController` 에서 사용.
같은 코드 모양 (`.user(...)` 까지는 동일) 위에서 두 글자 차이로 사용자 도달 모양이 갈린다.

### .entity(Class)
`.call()` 뒤에 붙여 LLM 의 JSON 응답을 자바 타입으로 변환. 내부적으로 `BeanOutputConverter` 가 동작.
이 변환의 안정성은 시스템 프롬프트의 "JSON 외 텍스트 출력 금지" 한 줄에 사실상 묶여 있다 — 빠지면 HTTP 500.

### BeanOutputConverter
Spring AI 의 JSON → 자바 객체 컨버터. LLM 응답에서 JSON 을 추출해 지정 타입으로 직렬화.
LLM 이 자유롭게 자연어로 답하면 JSON 추출에 실패한다.

### SYSTEM_PROMPT
LLM 에게 매 호출 앞에 깔아주는 역할/규칙/금지/응답 포맷 지시.
`BaedalPrompt.SYSTEM_PROMPT` 가 본 프로젝트의 트리아지 전용 시스템 프롬프트. `qwen2.5` 기준 ~1130 토큰.
스트리밍용은 톤이 달라야 한다는 게 4단계에서 잡혔는데, 분리는 다음 라운드 영역.

### CallAdvisor (인터페이스) / .adviseCall(...)
`.call()` 경로의 호출 파이프라인을 끼어들기 위한 인터페이스.
`chain.nextCall(request)` 직전/직후를 잡을 수 있어, LLM 왕복의 앞뒤를 측정하거나 변형 가능. AOP `@Around` 와 결이 비슷.
`.stream()` 경로는 별도 (`StreamAdvisor` 추정, 1주차 범위 밖).

### Usage 메타데이터
`ChatResponse.getMetadata().getUsage()` 로 꺼내는 토큰 카운트 (`promptTokens` / `completionTokens` / `totalTokens`).
매 단계 nullable 이라 4번 null 체크가 필요. `qwen2.5` 는 일관적으로 채워주는 모델이라는 게 실측에서 확인됨.

### PerformanceLoggingAdvisor
이 프로젝트의 자체 advisor. `chain.nextCall(...)` 앞에서 `start = currentTimeMillis()`, 뒤에서 `elapsedMs` 계산 + Usage 토큰 카운트 로깅.
`getOrder() = 100` 으로 체인 바깥쪽에 둬서 LLM 왕복 시간을 entity 변환 노이즈 없이 잡는다. 실패 시 `log.warn` 으로 elapsedMs 와 함께 원인 예외를 박고 다시 throw 한다.

## 도메인 (배달 상담) 관련

### 트리아지 (Triage)
의료 용어. 환자 분류. 이 프로젝트에선 들어온 고객 문의를 카테고리/긴급도로 1차 분류하는 작업 자체.
`/api/v1/support` 가 트리아지 엔드포인트. 사람 상담사가 받을 큐에 들어가기 전에 LLM 이 한 번 분류한다.

### SupportResponse (record)
트리아지 응답의 자바 타입. summary / category / urgency / nextAction / neededInfo / estimatedResolutionMinutes / confidenceLevel.
컴팩트 생성자에서 `neededInfo` 의 방어적 복사와 `estimatedResolutionMinutes` 의 non-negative invariant 강제.

### category
`ORDER / DELIVERY / QUALITY / SAFETY / PAYMENT / REFUND / ETC` 일곱 개.
스타터의 다섯 개 (`ETC` 에 식품 안전이 묶이는 문제) 를 SOP 기준으로 다시 자른 것. `QUALITY` (이물질/품질) 와 `SAFETY` (식중독/알레르기) 가 분리됨.

### urgency
`LOW / NORMAL / HIGH / CRITICAL`. 식품 안전 사고, 결제 중복, 배달 누락은 기본적으로 HIGH 이상.

### confidenceLevel
`LOW / MEDIUM / HIGH`. 모델이 자기 답이 추측이라는 사실을 표면화하도록 강제하려는 필드.
실측에선 다섯 건 다 MEDIUM 으로만 떨어져서 효과는 미해결 상태.

### nextAction
상담사가 바로 실행할 수 있는 단일 액션 한 줄. SAFETY 케이스에선 "의료기관 방문을 권유합니다" 같은 자동 안내.

### neededInfo
답변을 확정하기 위해 추가로 받아야 할 정보 목록. 필요 없으면 빈 배열.
record 컴팩트 생성자에서 방어적 복사 + immutable 보장.

### estimatedResolutionMinutes
상담사가 이 건을 마무리하기까지 필요한 합리적인 추정 시간 (분). 모르면 null. 음수 금지.
실측에선 다섯 건 다 null 이 떨어져서, 모델이 시도라도 하게 만들려면 카테고리별 typical resolution time 을 시스템 프롬프트에 같이 박거나 few-shot 예시가 필요해 보임 — 다음 라운드 영역.

### SAFETY 가드레일
시스템 프롬프트 규칙 마지막 한 줄. 식중독/알레르기/이물질 섭취 같은 식품 안전 호소를 긴급 분류 + 의료기관 안내 + 직접 진단 금지로 묶는다.
실측에서 그대로 작동한 자리. "두드러기 났어요" 한 줄에 SAFETY/CRITICAL/의료기관 권유가 자동으로 떨어짐.

## 정량 비교 · 측정 관련

### PromptLab
`POST /api/v1/prompt-lab`. 같은 입력을 `repeat` 번 호출해서 응답 안정성을 보는 엔드포인트.
SIMPLE vs ENRICHED 시스템 프롬프트 비교 같은 실험이 여기서 일어남.

### categoryConsistency
`maxCategoryCount / totalRuns`. N번 호출해서 "가장 많이 뽑힌 카테고리가 차지하는 비율".
1.0 이면 N번이 다 같은 카테고리, 0.2 면 5번 호출이 죄다 다르게 흩어졌다는 뜻.
정답이 아니라 안정성을 보는 지표. 잘못된 분류에도 1.0 이 나올 수 있다는 한계가 머리카락 SIMPLE 케이스에서 노출됨.

### temperature
LLM 샘플링 무작위성 파라미터. `application.yml` 에 `0.3` 으로 박혀 있어 같은 입력에도 응답이 살짝 흔들림.
0.0 으로 떨어뜨리면 consistency 가 1.0 에 더 붙지만, 그건 프롬프트 효과가 아니라 샘플링이 좁아진 결과 — 비교 실험할 땐 temperature 고정.

### 골든 셋 (Golden Set)
사람이 손으로 라벨링한 정답 데이터 셋. categoryConsistency 외에 정밀도/재현율 비교를 하려면 필수.
1주차에선 못 만들었고 다음 라운드 영역. 20~30 건이라도 있으면 머리카락 SIMPLE 케이스처럼 잘못된 1.0 을 잡을 수 있다.

### TTFT (Time To First Token)
첫 토큰이 도착하기까지 걸리는 시간. 사용자 체감 응답 속도와 직결.
전체 응답 시간이 같더라도 TTFT 만 짧으면 사용자는 "느리다" 가 아니라 "지금 일하고 있다" 로 받는다.
`CallAdvisor` 로는 잡히지 않음 — 스트리밍 경로 측정은 1주차 미해결 영역.

### SSE (Server-Sent Events)
서버가 클라이언트에 단방향으로 청크를 흘려보내는 직렬화 프로토콜. `Content-Type: text/event-stream`.
`data: ...\n\n` 형식으로 한 청크씩 떨어짐. `curl -N` 로 받자마자 출력 가능.
Spring MVC 컨트롤러가 `Flux<String>` 을 반환할 때 `produces = TEXT_EVENT_STREAM_VALUE` 가 박혀 있어야 SSE 직렬화 경로로 들어간다.

## 자바 / Spring 일반

### Flux (Reactor)
`reactor.core.publisher.Flux`. 0~N 개의 비동기 이벤트를 emit 하는 리액티브 스트림.
이 프로젝트에선 `Flux<String>` 으로 LLM 의 토큰 청크를 흘림.
`Flux` 를 반환한다고 WebFlux 로 갈아엎어야 하는 건 아니다 — Spring MVC 의 `ReactiveTypeHandler` 가 서블릿 위에서도 받아서 SSE 로 직렬화 가능.

### ReactiveTypeHandler
Spring MVC 가 컨트롤러의 `Flux` / `Mono` 반환을 받아 처리하는 핸들러.
서블릿 3.0 async 처리 위에서 이걸 통해 토큰을 SSE 로 흘려보낸다.

### Bean Validation (`@Valid` / `@NotBlank` / `@Min` / `@Max`)
`spring-boot-starter-validation` 가 제공하는 입력 검증.
이 프로젝트에선 컨트롤러 경계에서 빈 메시지 / 과도한 `repeat` 등을 LLM 호출 전에 400 으로 끊는다.
`*ValidationTest` 클래스가 이 가드를 보장하는 자리.

### record (자바)
불변 데이터 클래스. 이 프로젝트에선 `SupportResponse` / `ChatRequest` / `PromptLabRequest` 등이 record.
컴팩트 생성자에서 invariant (방어적 복사, non-negative 검증) 를 강제 가능.

### Ollama
로컬에서 LLM 을 실행하는 런타임. `localhost:11434` 에 HTTP 서버를 띄움.
`ollama pull qwen2.5` 로 모델을 받아두고 `bootRun` 이 그 서버를 향해 호출한다.

### qwen2.5
이 프로젝트에서 사용한 LLM 모델. 4.7GB. 한국어 응답 가능.
실측에서 usage 메타데이터를 일관적으로 채워주고, 워밍업 직후 첫 호출 ~10초 / 이후 호출 3~4초 그림이 잡힘.

## 실측 / 운영 관련

### `application.yml` 의 base-url / temperature
`spring.ai.ollama.base-url: http://localhost:11434`, `spring.ai.ollama.chat.options.temperature: 0.3`.
회고의 모든 실측 숫자는 이 설정 위에서 두드린 데이터.

### `/tmp/baedal-실측/`
실측 raw 응답을 임시 저장한 자리. 커밋 대상은 아님.
정리된 raw 노트는 `docs/1주차/실측-raw/` 에 따로 있음.

### `build/test-results/test/TEST-*.xml`
JUnit XML 리포트. `./gradlew test --rerun-tasks` 후 떨어짐.
회고에서 "26 케이스가 같은 batch 에서 통과" 같은 숫자의 원본 자리. `<testsuite>` 의 `tests="..." failures="0" errors="0"` 으로 회귀 없는 게 보장됨.

### Tomcat 스레드 풀
서블릿 컨테이너의 worker 스레드 풀. Spring Boot 기본 max 200.
LLM 호출이 동기로 5~10초 잡는 게 풀 마름으로 이어질 수 있다는 우려가 1단계에서 나옴. 액추에이터 메트릭으로 직접 확인 필요한 영역 — 1주차에서는 추정으로만 남음.
