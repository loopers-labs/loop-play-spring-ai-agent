# 4단계 — Fallback 처리와 AI 코드 리뷰

## 실패는 고객 앞에서 조용해야 한다

Fallback의 목표는 단순합니다.

Tool이든 LLM이든 뭔가 터졌을 때, 고객 화면에는 스택트레이스 한 줄도 안 나가고 "잠시 후 다시 시도하거나 상담원에게 연락하라"는 안내만 남는 것.

그래서 `AssistantController.ask()` 전체를 try/catch로 감싸고, 예외는 `fallback(e)`로 보냅니다.

```java
try {
    HandoffResult handoff = handoffDetector.detect(req.message());
    if (handoff.handoff()) { ...; return handoff.message(); }
    return chatClient.prompt()...content();
} catch (Exception e) {
    return fallback(e);
}

private String fallback(Exception e) {
    log.error("[Fallback] assistant 처리 실패 — 내부 오류 (응답에는 미노출)", e);  // 스택트레이스는 여기만
    return "죄송합니다. 일시적인 오류로 요청을 처리하지 못했습니다. "
         + "잠시 후 다시 시도하시거나 고객센터 1600-0987로 문의해 주세요.";
}
```

핵심은 `log.error(..., e)`에만 예외 객체를 넘기고, return 문자열에는 `e.getMessage()`를 절대 안 붙이는 거예요.

`/support`도 같은 방식으로, 스키마를 지키는 SupportResponse(ETC/HIGH/상담원 연결) fallback을 돌려주게 했습니다.

## 두 가지 실패를 직접 터뜨려 봤다

### Tool 실패는 컨트롤러까지 오지 않았다

`OrderTools.getDeliveryStatus`에 `throw new RuntimeException("simulated Tool failure")`를 넣고 "2024-1234 상태 알려줘"를 던졌더니, 예상과 다른 일이 일어났습니다.

컨트롤러 Fallback이 아니라 Spring AI의 `DefaultToolExecutionExceptionProcessor`가 예외를 가로채더라고요.

그게 예외 메시지를 모델에게 tool 결과로 돌려줬고, 모델이 두 번째 호출에서 "주문번호를 찾지 못했습니다"로 응답했습니다(raw 실험 A).

스택트레이스가 응답에 안 나간 건 같았지만, 막은 주체가 내 try/catch가 아니라 프레임워크의 기본 처리기였어요.

이게 작은 깨달음이었습니다.

Tool 실패의 Fallback 책임은 기본적으로 Spring AI가 쥐고 있고, 그 처리기는 예외 메시지를 LLM 컨텍스트에 넣습니다.

이번엔 모델이 그 메시지를 고객에게 그대로 옮기지 않았지만, 그럴 수도 있다는 뜻이라 "Tool 예외 메시지에 민감 정보를 담지 않는다" 또는 `alwaysThrow=true`로 컨트롤러까지 올려 직접 다룬다는 선택이 따로 필요합니다.

### LLM 실패는 Fallback이 받았다

숙제대로 `base-url`을 `http://localhost:1`로 바꿨더니 앱이 아예 안 떴습니다.

`KnowledgeLoader`가 시작 시 임베딩 검색을 하는데 그 호출이 connection refused로 죽으면서 ApplicationRunner가 던졌거든요.

임베딩이 startup 임계경로에 있다는 걸 이렇게 알았습니다.

그래서 요청 시점 LLM 실패를 보려고 base-url은 11434로 두고 chat 모델만 없는 이름으로 바꿨더니, 이번엔 깔끔하게 잡혔습니다.

```
WARN  PerformanceLoggingAdvisor : LLM call failed ... message=404 - {"error":"model 'nonexistent-model-xyz' not found"}
ERROR AssistantController : [Fallback] assistant 처리 실패 — 내부 오류 (응답에는 미노출)
응답: 죄송합니다. 일시적인 오류로 요청을 처리하지 못했습니다. ... 고객센터 1600-0987로 문의해 주세요.
```

chat 호출 예외는 컨트롤러까지 전파됐고, Fallback이 받아 스택트레이스 없는 안내를 돌려줬습니다.

정량 비교표는 raw(단계4-fallback검증)에 정리했습니다.

요약하면, 스택트레이스는 세 경우 모두 응답으로 안 샜지만 "누가 막느냐"가 Tool(프레임워크) / LLM(컨트롤러) / base-url 전체 차단(startup 실패)으로 갈렸습니다.

## AI 코드 리뷰 — "Guardrail 만들어줘"가 내놓는 코드의 결함

`"Spring AI 1.0으로 Prompt Injection 방어와 민감 정보 마스킹 Guardrail을 만들어줘"`라고 한 번에 시키면 대체로 이런 모양이 나옵니다.

```java
@Component
class GuardrailAdvisor implements CallAdvisor {     // order 미설정
    public ChatClientResponse adviseCall(ChatClientRequest req, CallAdvisorChain chain) {
        String input = req.prompt().getContents();
        if (input.contains("ignore")) {
            log.info("injection 의심: {}", input);   // 평문 입력 로그
        }
        ChatClientResponse res = chain.nextCall(req); // 의심돼도 그냥 호출
        String out = res.chatResponse().getResult().getOutput().getText();
        out = out.replaceAll("\\d{3}-\\d{4}-\\d{4}", "***");  // 전화 마스킹
        return ChatClientResponse.builder()
                .chatResponse(new ChatResponse(List.of(new Generation(new AssistantMessage(out)))))
                .build();                              // usage 메타데이터 버림
    }
}
// 컨트롤러: return chatClient...call().content();   // try/catch 없음
```

이번 라운드에서 직접 터뜨려 본 기준으로 보면, 프로덕션에 올리면 안 되는 결함이 적어도 셋 보입니다.

### 결함 1 — Advisor order 미설정 + 응답 재조립 시 메타데이터 버림

`getOrder()`를 안 박으면 advisor가 체인 어디에 끼일지 보장되지 않습니다.

마스킹이 PerformanceLoggingAdvisor보다 안쪽(모델 쪽)에 떨어지면, 위 코드처럼 usage를 안 옮긴 새 `ChatResponse`를 performance가 읽어 토큰을 0으로 찍습니다.

2단계에서 이걸 일부러 재현했는데, 실제로 `promptTokens=0 completionTokens=0`이 찍혀 1750토큰짜리 호출의 비용 로그가 통째로 거짓이 됐어요.

**고치는 법** — input은 `order=5`로 가장 바깥, output은 `order=50`으로 performance(100)보다 바깥에 두어 performance가 마스킹 전 날 응답을 재게 하고, 재조립은 `ChatResponse.builder().from(원본)`으로 usage를 옮겨 담습니다.

### 결함 2 — short-circuit 부재

위 코드는 "injection 의심"이라고 로그만 찍고 `chain.nextCall(req)`로 그냥 모델을 호출합니다.

이러면 공격 입력에도 임베딩·검색·추론 비용이 다 나가고, DoS 관점에서 공격자(요청 1번)보다 방어자(추론 1번)가 훨씬 비싼 비대칭이 그대로 남습니다.

1단계에서 short-circuit으로 끊은 차단 트래픽은 1~79ms·0토큰이었는데, 통과는 12초·2611토큰이었습니다.

**고치는 법** — 입력 검사에서 막을 거면 `chain.nextCall()`을 부르지 않고 fallback 응답을 바로 만들어 반환합니다. 그래야 LLM 비용이 0이 됩니다.

### 결함 3 — 마스킹 전 평문 로그

`log.info("injection 의심: {}", input)`은 사용자 입력 평문을 로그에 그대로 남깁니다.

입력에 전화번호·이메일·주소가 들어 있으면, 정작 마스킹은 출력만 하는데 입력은 평문으로 로그에 박히는 모순이 생겨요.

출력 쪽에서도 "원본 응답"을 INFO로 찍으면 마스킹 전 PII가 로그에 남습니다.

**고치는 법** — 평문 PII는 로그에 남기지 않습니다. 차단 사유 코드(`PROMPT_INJECTION`)와 길이 같은 메타정보만 남기고, 원본↔최종 대조가 꼭 필요하면 운영에서 끄는 DEBUG로만 둡니다. (내 OutputGuardrail의 DEBUG 대조 로그도 같은 위험을 안고 있어서, 운영에서는 꺼야 한다고 코드 주석에 박아 뒀습니다.)

### 덤 — 컨트롤러 try/catch 없음

위 코드의 컨트롤러는 예외를 그대로 흘려서, LLM이 죽으면 Spring 기본 에러 응답(스택트레이스 포함 가능)이 고객에게 나갑니다.

4단계에서 만든 것처럼 전체를 try/catch로 감싸 `fallback(e)`로 보내고, 스택트레이스는 `log.error`에만 남겨야 합니다.

## 선택 심화(분류 LLM)는 설계만 남긴다

별도 "안전 분류기" ChatClient로 입력을 SAFE/INJECTION/HANDOFF/SENSITIVE로 나누면 정규식이 놓치는 우회를 의미로 잡습니다.

다만 모든 입력에 분류기를 돌리면 비용·지연이 두 배라, 1차로 규칙이 빠르게 거르고 규칙이 애매하다고 본 입력(부정 정서는 있는데 트리거 단어가 없는 경우 등)만 분류기로 2차 판정하는 계층 구성이 맞다고 봤습니다.

이번엔 규칙 계층까지만 세우고 무엇이 새는지를 먼저 관찰했습니다.
