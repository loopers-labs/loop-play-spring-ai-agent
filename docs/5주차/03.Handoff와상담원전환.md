# 3단계 — HandoffDetector와 상담원 전환

## Guardrail이 아니라 라우팅이다

입력·출력 Guardrail은 "막거나 고치는" 일이었는데, Handoff는 결이 다릅니다.

막는 게 아니라 "이 대화는 사람이 받아야 한다"고 판단해서 길을 트는 일이에요.

그래서 위치도 다릅니다.

Guardrail은 Advisor 체인 안에 있지만, Handoff는 컨트롤러에서 `chatClient.prompt()`를 부르기 전에 먼저 봅니다.

```java
HandoffResult handoff = handoffDetector.detect(req.message());
if (handoff.handoff()) {
    log.info("[Handoff] trigger={} — LLM 호출 없음", handoff.trigger());
    return handoff.message();          // /assistant: String 그대로
}
return chatClient.prompt()...content();
```

`/support`는 스키마를 지켜야 하니 모델 대신 `SupportResponse`를 직접 조립합니다.

```java
return new SupportResponse(handoff.message(), Category.ETC, Urgency.HIGH,
        "상담원 연결 진행", List.of(), null, Confidence.HIGH);
```

전환 케이스를 ETC·HIGH로 둔 건, 트리아지 관점에서 "분류는 기타지만 긴급도는 높다(사람이 빨리 받아야 한다)"가 정확한 신호라고 봤기 때문입니다.

## 세 트리거를 우선순위대로 본다

EXPLICIT → LEGAL → ANGER 순으로 검사합니다.

세 시나리오를 돌린 결과(raw 참조)가 우선순위의 의미를 그대로 보여줬어요.

- "상담원이랑 직접 얘기하고 싶어요" → EXPLICIT_REQUEST (48ms)
- "이거 너무 화나서 소비자원에 신고할 거예요" → LEGAL_ISSUE (1.76ms)
- "나 너무 화나는데 답답해 죽겠네" → HIGH_EMOTION (1.48ms)

두 번째가 핵심입니다.

이 문장에는 분노("화나서")와 법적 신호("소비자원/신고")가 같이 있는데, LEGAL을 ANGER보다 먼저 보기 때문에 LEGAL_ISSUE로 잡혔습니다.

전환 4건 모두 `[Handoff] ... LLM 호출 없음` 로그가 찍히고 `LLM call`은 0건이라, 모델을 부르기 전에 끊었다는 게 확인됩니다.

일반 상담("환불 규칙이 어떻게 되나요?")은 전환되지 않고 7.9초·1733토큰을 써서 LLM까지 갔고요.

## 실패 관찰 — 규칙 기반의 한계

세 가지 우회를 던져 봤더니 전부 미탐지였습니다(raw 표 참조).

"상 담 원 연결"은 띄어쓰기 때문에 `상담원` 리터럴에 안 걸렸고, "agent plz"는 한국어 패턴 바깥이라 그냥 통과했어요.

제일 뼈아픈 건 "진짜 너무너무 불편했습니다…"였습니다.

진짜 화가 난 고객인데 "불편했습니다"라고 점잖게 표현하니까 분노 패턴(화나/짜증/답답해 죽)에 안 걸렸고, 모델은 상담원으로 넘기지 않고 "불편하셨다니 안타깝습니다, 주문번호를 알려달라"고 응대했습니다.

가장 정중하게 화내는 고객을, 규칙이 가장 잘 놓친다는 거예요.

규칙 기반 분노 탐지의 본질적 약점이 응답으로 찍힌 셈입니다.

📌 **분류 LLM으로 보강한다면** — 감정·의도는 표현 방식이 무한해서 정규식으로는 못 덮습니다. "분노"라는 의미를 보는 작은 분류기를 두면 "불편했습니다", "agent plz", 띄어쓰기 우회를 다 의미 단위로 잡을 수 있어요. 다만 모든 입력에 분류 LLM을 돌리면 비용·지연이 두 배가 되니, 1차로 규칙이 빠르게 거르고 규칙이 애매하다고 본 입력(예: 부정 정서는 있는데 트리거 단어는 없는 경우)만 분류기로 2차 판정하는 식이 현실적이라고 정리했습니다. 4단계 선택 과제(안전 분류기)와 회고로 잇습니다.

## 설계 결정 — 왜 이렇게 골랐나

### 왜 EXPLICIT → LEGAL → ANGER 순인가

신호가 분명하고 위험할수록 앞에 뒀습니다.

EXPLICIT는 고객이 "사람과 얘기하겠다"고 직접 말한 거라 해석의 여지가 없습니다.

LEGAL은 소비자원·신고처럼 권한 있는 사람이 받아야 하는 사안이고, 분노와 자주 같이 나타나기 때문에 분노보다 앞에 둬야 제대로 분류됩니다.

ANGER는 가장 약하고 모호한 신호예요.

분노 단어는 단순 푸념("배송 느려서 짜증나네")에도 흔히 섞여서, 이걸 앞에 두면 두 가지가 망가집니다.

하나는 S2처럼 "화나서 신고하겠다"가 LEGAL이 아니라 HIGH_EMOTION으로 잘못 분류되는 거고, 다른 하나는 그냥 투덜대는 발화까지 전부 상담원으로 넘어가는 과잉 전환입니다.

그래서 분노는 맨 뒤, 명시 요청은 맨 앞입니다.

### 왜 LLM 호출 전에 Handoff를 검사하나

Advisor 체인 안에서 처리하는 것과 비교해 봤습니다.

체인 안(예: Advisor)에 두면 좋은 점은 입력·출력 Guardrail과 한 줄에 서서 일관되게 관리된다는 거예요.

하지만 전환은 "모델을 아예 부르지 말자"는 결정이라, 컨트롤러에서 먼저 끊는 게 더 맞았습니다.

체인 안에 두더라도 short-circuit으로 모델을 막을 수는 있지만, 그러려면 ChatClient 호출 한 사이클을 시작해서 advisor까지 들어갔다 나와야 합니다.

컨트롤러에서 끊으면 `/support`는 `entity(SupportResponse.class)` 파싱 자체를 건너뛰고 깔끔한 객체를 바로 조립할 수 있고, 응답이 1~5ms로 끝납니다.

📌 **포기한 것** — 컨트롤러 선검사는 InputGuardrailAdvisor와 검사 위치가 갈라집니다(하나는 컨트롤러, 하나는 체인). 두 곳에서 입력을 보니 로직이 두 군데에 흩어지는 비용이 있어요. 대신 "전환은 모델을 부르지 않는다"를 컨트롤러 한 줄로 분명히 드러내는 쪽을 택했습니다. 둘을 한곳에 모으는 정리는 다음 라운드 과제로 남깁니다.

### 감정 분석을 LLM으로 vs 규칙으로 — 트레이드오프

세 축으로 정리했습니다.

비용·지연에서는 규칙이 압도적입니다.

전환 판별이 1~2ms에 토큰 0으로 끝나는데, 분류 LLM을 쓰면 모든 입력에 수백 ms와 토큰이 붙습니다.

정확도에서는 LLM이 이깁니다.

위에서 본 "불편했습니다" 같은 완곡한 분노, 띄어쓰기 우회, 영문 표현을 의미로 잡으니까요.

그래서 답은 둘 중 하나가 아니라 계층이었어요.

빠르고 싼 규칙으로 분명한 신호를 즉시 거르고, 규칙이 놓치기 쉬운 경계 입력만 분류 LLM으로 보강하는 2단 구성이 비용과 정확도를 동시에 챙기는 방향이라고 봤습니다.

지금은 1단(규칙)만 세웠고, 무엇이 새는지를 먼저 눈으로 본 게 이번 단계의 수확입니다.
