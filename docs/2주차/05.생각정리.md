# 2주차 - 생각정리

> 단계 1~4 끝나고 묶어서 한 번 더 생각해본 메모예요. "내가 배운 것 / 안 풀린 채로 남은 것 / 3주차에 시도하고 싶은 것" 세 갈래로 정리했습니다.

## 두 줄이 머리에 남았어요

2주차 시작에 강의 자료에서 본 두 줄이 있었어요.

> 판단은 LLM, 실행은 Spring Bean.
> description 은 LLM 에게 보여주는 유일한 API 문서다.

처음엔 둘 다 당연한 얘기 같았는데, 단계 1~4 두드리고 나서 다시 보면 톤이 좀 달라져요.

"판단은 LLM, 실행은 Spring Bean" 은 사실 더 정확히는 "호출 결정은 LLM, 실행은 Spring Bean, 결과 해석은 다시 LLM" 이에요.
한 번의 사용자 발화 안에 LLM 이 두 번 발화합니다. 첫 발화에서 어떤 Tool 을 어떤 인자로 부를지 결정하고, 두 번째 발화에서 Tool 결과를 자연어로 변환해요.
이 두 번 발화 사이에 우리 Spring 코드가 한 번 끼어드는 거고, 우리가 통제할 수 있는 건 그 한 번뿐입니다. 그 한 번 안에서 멱등성, View DTO, outcome 분기를 다 처리해야 해요.

"description 은 LLM 에게 보여주는 유일한 API 문서" 는 단계 3 정량 비교에서 직접 확인됐는데, 좀 의외였던 게 description 이 결정하는 건 호출 라우팅 까지였어요.
응답 생성 (2차 round) 시점에는 실제 Tool 결과 JSON 이 description 보다 더 강한 신호로 작용합니다.
"description 이 거짓말이어도 응답은 멀쩡할 수 있다 (단계 3 버전 C)" 가 그 증거예요. 그러니까 description 은 유일한 API 문서 인 동시에 호출 라우팅 전용 문서 입니다. 응답 가공의 정확성은 데이터 자체에 박혀야 해요.

## 단계별로 다시 짚어보면

단계 1: 도메인과 Tool 뼈대.
가장 큰 발견은 `cancelOrder` 가 LLM 경로로는 한 번도 호출되지 않았다는 거였어요.
read 계열 Tool (`getOrderDetail`, `getDeliveryStatus`) 은 잘 호출되는데 변경 계열은 안 되는 거, qwen2.5 (7B) 의 학습 분포 한계로 추정합니다.
이 때문에 단계 2 멱등성 검증을 LLM 경로로만 했다간 데이터가 안 만들어질 위험이 있어 단위 테스트로 갔어요.

단계 2: 멱등성 설계.
`Outcome` 4분기 (CANCELED / ALREADY_CANCELED / NOT_CANCELABLE / NOT_FOUND) 를 박고, 한 분기씩 빼면 무엇이 깨지는지 raw 로 캡처했어요.
케이스 A (ALREADY_CANCELED 만 제거): 데이터 무결성 OK, 메시지 의미 가 깨짐.
케이스 B (둘 다 제거): canceledReason 덮어쓰임 + canceledAt 흔들림.
"한 분기씩 빠질 때 다른 차원이 깨진다" 는 게 멱등성 분기가 여러 겹 가드레일이라는 증거였어요.

단계 3: description 정량 비교.
A (기준) 3/5, B (빈약) 2/5, C (오해 유발) 4/5.
가장 의외였던 게 C 가 A 보다 호출률이 높았던 거예요.
가설: description 의 첫 한두 줄 키워드가 사용자 발화의 토큰과 매칭되는 강도가 호출 결정에 가장 결정적이다.
description 4요소 (무엇 / 언제 / 입력 / 실패) 를 본인 우선순위로 다시 매기면 언제, 무엇, 실패, 입력 순이에요.

단계 4: Observability + AI 코드 리뷰.
같은 발화 "주문번호 2024-1234 배달 어디?" 가 round 1 50 토큰, round 2 2803 토큰, 56배 차이.
1차 LLM 호출의 promptTokens 가 advisor 에 안 잡히는 게 발견됐고, 진짜 비용은 4150 토큰 (1349 + 2803) 정도로 추정.
AI 가 만든 cancel Tool 코드에서 결함 3개 (멱등성 없음 / 예외 throw / 내부 엔티티 노출) 를 골라 단계 1~2 의 작업으로 어떻게 고칠지 매핑.

## 두드리면서 손에 잡힌 것

Tool 의 경계는 메서드 시그니처가 아니다.
강의 자료의 한 줄 ("Tool 의 경계를 설계하는 훈련") 이 처음엔 추상적이었는데, 실제로 짜보니 (a) `isCancelable()` 의 상태 경계, (b) outcome 분기의 멱등성 경계, (c) View DTO 의 데이터 경계, (d) description 의 호출 라우팅 경계, 적어도 네 겹의 경계가 한 Tool 안에 있어요.
시그니처 한 줄 짜는 시간보다 이 네 경계를 정하는 시간이 훨씬 길었고, 그게 사실 본 작업이었습니다.

LLM 인터페이스에선 enum 분기를 통합하는 게 위험하다.
일반 자바 코드는 enum 값을 줄이고 boolean 으로 통합하는 게 좋을 때가 많은데, LLM 인터페이스는 반대예요.
`Outcome.FAILED` 하나로 묶으면 LLM 이 사용자에게 무엇을 안내할지 알 수 없어요.
`ALREADY_CANCELED`, `NOT_CANCELABLE`, `NOT_FOUND` 가 각각 다른 자연어 응답을 가능하게 합니다.
LLM 입장에선 분기 늘리는 게 곧 응답 정확성, 이게 강의 자료에 직접 적혀 있진 않았는데 두드리면서 손에 잡혔어요.

Tool 없는 LLM 은 그럴듯한 거짓말을 한다.
round 1 chat 에 "주문번호 2024-1234 배달 어디?" 를 보냈을 때 "배달사와 연락하세요" 라고 답한 게 가장 무서웠어요. 우리가 배달사인데요.
Tool 의 가치 명제가 사실 이 한 줄에 다 있어요. Tool 은 정확성을 만들기 위해 있다.

advisor 패턴의 한계도 같이 봐야 한다.
1주차에 advisor 한 줄로 다 측정될 줄 알았는데, 2주차에 와서 advisor 가 chain 의 마지막 LLM call 만 캡처한다는 걸 발견했어요.
1차 round 의 토큰 비용이 시각적으로 안 잡히면 운영 비용 추정이 무너집니다.
이건 advisor 를 chain 의 각 단계에 끼우는 방법을 찾아야 하는데, 단계 4 회고에서 미뤄둔 영역이에요.

## 아직 안 풀린 채로 두는 것들

1. cancelOrder 가 LLM 경로로 안 부르는 문제가 description 으로 풀리는가, 아니면 모델 크기 문제인가?
가설 셋 (모델 7B 한계 / description 의 동사 강도 / Spring AI Ollama 통합) 중 어느 게 우세한지를 단계 3 description 실험만으로는 못 풀었어요.
다음 라운드에서 description 의 첫 줄을 "고객의 취소 요청을 받아 주문을 취소 처리한다" 같은 사용자 의도 어휘로 바꿔서 한 번 더 두드려보고 싶어요.

2. description A/B/C 정량 비교가 표본 5회로 충분한가?
A 3/5, B 2/5, C 4/5 인데, 운으로 ±1 흔들릴 수 있는 표본이에요.
3주차에 PromptLab 류 batch 호출 인프라를 같이 다듬으면서 description 변형도 N=20 정도로 다시 돌려볼 생각이에요.

3. Tool 동시 호출 시 순서와 트랜잭션은?
LLM 이 한 응답에 여러 Tool 을 동시에 호출하는 경우 (parallel tool calls) 가 가능해요.
지금 우리 Mock 은 단일 스레드 가정인데, 동시에 같은 주문에 `getDeliveryStatus` + `cancelOrder` 가 호출되면 어떻게 되는지, race 가능성이 있어요.
이건 4주차 외부 시스템 연동 영역에서 다뤄야 할 것 같습니다.

4. AI 가 만든 코드의 결함 분포가 모델마다 어떻게 다른가?
단계 4 에서 ChatGPT 한 번만 두드렸는데, GPT-4 / Claude / Gemini 가 같은 프롬프트에 어떤 default 를 내는지 비교해보면 모델별 "안전한 기본값" 이 잡힐 거예요.

## Round 3 에 시도하고 싶은 것: Chat Memory 와 어떻게 연결할까

이번 라운드의 시나리오 5종 중에 의도적으로 빠진 게 있어요.

> 고객: "2024-1234 지금 어디예요?"
> 봇: "역삼역 사거리 부근..."
> 고객: "아 그거 취소해주세요"

두 번째 발화에서 "그거" 가 무엇인지 알려면 직전 대화 컨텍스트가 필요해요.
지금 우리 `AssistantController` 는 매 요청을 독립으로 처리하니까, 두 번째 발화에서 LLM 이 주문번호를 모르고 `cancelOrder(orderId="???", reason="...")` 를 부르거나 사용자에게 다시 물어봐야 합니다.

3주차 ChatMemory 가 풀어야 할 영역 이 사실 이 한 시나리오에 다 들어있어요.
- 직전 발화의 컨텍스트를 유지해 "그거" 같은 지시 대명사를 해결
- conversationId 로 고객별 세션을 분리
- 토큰 한도 안에서 메모리를 어떻게 자를지 (슬라이딩 윈도우 vs 요약)

이번 라운드 작업과 연결하면, 메모리 안에 "최근 언급된 orderId" 를 명시적으로 저장하는 게 가능한지 가 궁금해요.
LLM 이 자기 컨텍스트로 자동 추론하게 둘 수도 있고, 메모리 구조에 `currentOrderId` 같은 슬롯을 명시적으로 박을 수도 있어요. 후자가 더 안전하지만 (LLM 이 잘못 추론할 여지가 줄어듦) 메모리 구조가 복잡해집니다.

이게 3주차 들어가서 두드릴 영역인데, 사실 지금 시점에서 한 가지 답을 갖고 있긴 해요, LLM 자동 컨텍스트 추론에만 맡기지 말고, 핵심 슬롯은 명시적으로 박는다.
단계 3 에서 description 의 키워드 매칭이 추론보다 강했던 것과 같은 결의 발견인데, 메모리도 LLM 의 알아서 추론에 모든 걸 맡기면 비용도 늘고 정확성도 흔들립니다. 강한 신호 (orderId, customerId 같은 식별자) 는 별도 슬롯으로 잡아두는 게 안전하다, 이게 단계 1~4 에서 손에 잡힌 패턴의 자연스러운 연장이에요.

## 묶어보면

2주차의 한 줄 요약은 "LLM 의 자유를 줄이는 게 곧 정확성을 늘리는 일이다" 같아요.

description 으로 호출 라우팅을 잠그고, outcome enum 으로 응답 가능 영역을 잠그고, View DTO 로 노출 데이터를 잠그고, 멱등성 분기로 사이드이펙트 가능 횟수를 잠근다.
각 잠금이 LLM 의 자유도를 줄이는 가드레일인 동시에, 사용자에게 가는 응답의 정확성을 높이는 장치예요.

1주차에 "System Prompt 도 가드레일이다" 는 결을 두드렸고, 2주차에 "Tool 의 경계도 같은 결의 가드레일이다" 가 손에 잡혔습니다.
3주차에 ChatMemory 가 들어오면 또 한 겹의 가드레일이 추가되는 셈이고, 이 가드레일이 어떻게 쌓이는지가 6주차 마무리의 큰 그림 같아요.
