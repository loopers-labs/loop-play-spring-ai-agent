# 2주차 - 도메인과 Tool 뼈대 (단계 1)

> Mock 도메인 만들고 `@Tool` 세 개 붙이는 일이, 막상 해보니 만드는 것보다 "어디까지 노출할지" 가 더 어려웠어요.

## Mock 도메인을 record 가 아니라 가변 class 로 둔 이유

처음엔 `Order` 도 1주차의 `SupportResponse` 처럼 record 로 짜려고 했어요.
근데 단계 2 에 `cancelOrder` 가 들어오는 걸 미리 보고 멈췄습니다.

record 는 immutable 이라 `cancel()` 호출 시 `withStatus(CANCELED)` 처럼 새 인스턴스를 만들고 Map 에 다시 put 해야 합니다.
그러면 1주차 record 패턴과는 동작 모델 자체가 달라지고, 회고할 때 "왜 1주차는 record / 2주차는 class 인가" 를 한 줄 더 설명해야 해요.
또 `ConcurrentHashMap.computeIfPresent` 같은 분기를 매번 끼워야 하는데, 교육용 Mock 에 그 정도 동시성 코드를 넣을 이유가 별로 없었습니다.

그래서 `Order` 는 평범한 class 로 두고, `status / canceledReason / canceledAt` 세 필드만 mutable, 나머지는 final.
`OrderItem` 은 변하지 않으니 record 로 가져갔어요.
record/class 를 한 도메인 안에서 같이 쓰는 게 좀 어색해 보일 수도 있는데, "바뀌는 것 vs 안 바뀌는 것" 으로 자르는 게 read/write 의도를 시그니처에서 바로 읽게 만드는 쪽 같았습니다.

## 시드 6건의 분포를 의도적으로 잡은 거

`OrderMockService.seed()` 에 6건을 박았는데, 분포가 의도된 거예요.

| 주문번호 | 상태 | 이 데이터로 무엇을 테스트할 수 있나 |
|---|---|---|
| 2024-1234 | DELIVERING | `getDeliveryStatus` riderLocation 채워지는 정상 경로 |
| 2024-1235 | CREATED | `cancelOrder` 정상 취소 경로 |
| 2024-1236 | DELIVERED | `cancelOrder` `NOT_CANCELABLE` 분기 |
| 2024-1237 | COOKING | `cancelOrder` `NOT_CANCELABLE` 분기 (DELIVERED 와 다른 메시지로 자동 취소 불가가 뜨는지) |
| 2024-1238 | CANCELED (사전 취소) | `cancelOrder` `ALREADY_CANCELED` 분기, `canceledReason` 까지 채워둠 |
| 2024-1239 | ACCEPTED | 정상 취소 + 멱등 재호출 시나리오 |

이 분포가 단계 2에서 `Outcome` 4분기를 다 두드리려고 미리 깔아둔 거예요.
숙제 가이드에는 4건만 요구했는데, `2024-1235` 까지 합쳐서 6건으로 두면 단계 2의 멱등성 실험에서 시드 데이터를 "다 써먹는" 그림이 됩니다.

## 내부 `Order` 와 외부 `OrderDetailView` 를 분리한 이유

1주차 `SupportResponse` 는 도메인 = 응답이었어서 따로 가르지 않았어요.
2주차에선 둘을 갈라야 한다는 게 강의 자료에 강조돼 있었는데, 직접 짜보니 두 이유가 모두 손에 잡혔습니다.

(1) 민감 정보 노출
`Order` 에는 `deliveryAddress` ("서울시 강남구 역삼동 123-4") 가 있어요.
이걸 그대로 Tool 응답에 넣으면 LLM 입력 토큰에도 박히고, LLM 응답에도 새어 나올 수 있습니다.
회고 시점에 `OrderDetailView` 에서 의도적으로 뺀 건 다음 세 개예요.

- `deliveryAddress`, 사용자가 묻지 않은 한 노출할 이유 없음. 단계 2 에서 `cancelOrder` 가 ALREADY_CANCELED 메시지에 `canceledReason` 만 인용하는 것도 같은 이유.
- `riderLocation`, `getOrderDetail` 의 책임이 아님. 라이더 위치는 `getDeliveryStatus` 의 경계로 분리.
- `canceledReason / canceledAt`, 취소된 주문의 사유를 영수증 조회에서 한 줄 더 보여주는 건 다음 단계 PR 영역으로 미뤘어요.

`DeliveryStatusView` 도 같은 이유로 `riderLocation` 을 DELIVERING 상태에서만 채우게 강제했습니다.
주문이 COOKING 인데 라이더 위치가 채워져 있으면 LLM 이 "라이더가 지금 어디 있어요" 에 거짓말할 단서를 줘버려요.

(2) 입력 토큰 폭증
이건 단계 4에서 정량으로 보겠지만, 단계 1 만 두드려도 `promptTokens=2887` 같은 숫자가 보였습니다.
1주차 `SupportController` 가 1149~1159 사이였던 걸 생각하면 입력 토큰이 2.5배 가까이 늘어났고, 이 증가분의 대부분이 (a) Tool description 자체 + (b) 두 번째 라운드의 Tool 결과 JSON 이에요.
Tool 응답에 `deliveryAddress`, `riderLocation`, `canceledReason` 까지 다 박았으면 promptTokens 가 더 늘었을 거고, 그게 호출당 비용에 그대로 박힙니다.

## description 을 한국어로 쓴 이유

영어 한 줄 ("Get order detail by orderId") 로 적을지 한국어로 적을지 한참 망설였어요.
오픈소스 코드의 description 은 거의 다 영어라 그게 더 표준에 가까워 보이고, 영어가 모델의 학습 분포에 더 짙다는 가설도 있습니다.

그런데 실제 사용자 발화는 100% 한국어예요.
"지금 어디쯤에 있어요" 와 "이 Tool 은 라이더 위치를 조회한다" 사이의 의미 거리는, 영어 description ("Get rider location") 보다 한국어 description 이 분명히 짧을 거라고 봤습니다.
모델 입장에선 "한국어 발화 ↔ 한국어 설명" 매칭이 "한국어 발화 ↔ 영어 설명" 매칭보다 쉽다는 게 직관적으로 맞다 싶었어요.

이건 정량 비교 없이는 단정이라, 단계 3에서 description 변형 실험을 할 때 영어 버전도 한 차례 더 두드려볼 생각입니다.

## description 4요소를 미리 박은 거

강의 자료에 "무엇/언제/입력/실패" 4요소가 들어가야 한다고 명시돼 있어서 처음부터 4요소를 다 박았습니다.
`getDeliveryStatus` description 을 예로 들면:

- 무엇, "주어진 주문번호의 현재 배달 상태와 라이더의 대략적인 위치를 조회한다."
- 언제, `사용자가 "지금 어디쯤이에요", "라이더가 어디 있어요", "언제 도착해요" 처럼 배달 진행 상황을 물을 때 호출한다.`
- 입력, `@ToolParam(description = "배달 상태를 조회할 주문번호. 예: 2024-1234")`
- 실패, `존재하지 않는 주문번호면 null을 반환한다.`

`cancelOrder` 는 여기에 한 줄 더 추가했어요, 언제 호출하지 말아야 하는가 가 들어갈 자리가 따로 없어서 description 본문 안에 분기 조건을 다 적었습니다. (취소 가능 조건 / 자동 취소 불가 / 이미 취소된 경우 / 존재하지 않는 경우)

근데 이게 효과가 있었는지는 단계 1 라이브 두드림에서 절반만 확인됐어요. (다음 절)

## 라이브 호출에서 잡힌 큰 발견

`bootRun` 띄우고 시나리오 5종을 두드렸는데, 4종은 의도대로 동작했고 한 종이 무너졌습니다.

| 시나리오 | 발화 | 예상 Tool | 실제 동작 |
|---|---|---|---|
| 1 | 2024-1234 배달 어디쯤? | `getDeliveryStatus` | 호출됨, "역삼역 사거리 부근" 그대로 응답 |
| 2 | 2024-1234 어떤 메뉴? | `getOrderDetail` | 호출됨, 허니콤보/콜라 응답 |
| 3 | 2024-1235 취소해주세요 | `cancelOrder` | 호출 안 됨, LLM 이 자연어로 흉내만 냄 |
| 4 | 2024-1236 취소해주세요 (DELIVERED) | `cancelOrder`, NOT_CANCELABLE | 호출 안 됨, "취소되었습니다" 거짓말 |
| 5 | 2099-9999 어디예요? | `getDeliveryStatus`, null | 호출됨, "찾지 못했다" 응답 |

시나리오 3, 4 가 무너졌다는 게 단계 1 의 가장 큰 데이터예요.
`[Tool] cancelOrder` 로그가 한 번도 안 찍혔습니다.
시나리오 3 응답 본문에는 `)((((cancelOrder {"orderId": "2024-1235", "reason": "고객 요청"}))))` 라는 raw tool-call 흉내가 자연어로 새어 나왔는데, 이게 실제 Tool 호출이 아니라 LLM 이 "이런 호출을 해야 한다" 를 prose 로 출력해버린 거예요.
시나리오 4 는 더 심각합니다. Tool 호출도 없고 분기 검증도 없는데 "취소 처리하였습니다" 라고 답했어요. 데이터는 그대로 DELIVERED 인데 사용자 입장에선 취소된 줄 알게 됩니다.

다른 phrasing 두 가지도 더 시도했어요, `"2024-1235 주문 취소"`, `"주문번호 2024-1235 취소 처리해주세요"`.
두 경우 모두 `[Tool] cancelOrder` 로그가 안 찍혔고, promptTokens 가 1339~1349 사이에 머물러 있었습니다.
Tool 이 호출됐다면 2차 round (promptTokens ~2800) 가 잡혔을 텐데 그 흔적이 없어요.

## 왜 cancelOrder 만 무너졌는가, 가설

세 가지 가설이 있는데 어느 게 진짜인지는 단계 3 정량 실험 후에야 확정될 것 같아요.

가설 A, qwen2.5 (7B) 의 한계
7B급 instruction-tuned 모델은 read 계열 (`getOrderDetail`, `getDeliveryStatus`) tool call 은 학습 분포에 많이 들어있지만, 변경/사이드이펙트 계열 tool call (cancel, delete, transfer) 은 분포가 옅을 수 있어요.
이게 사실이면 description 을 아무리 잘 적어도 한계가 있고, 모델을 키우거나 (qwen2.5:14b, llama3.1:70b) 다른 모델로 가야 합니다.

가설 B, description 의 동사 강도가 약했다
`cancelOrder` description 첫 줄이 "주어진 주문번호의 주문을 취소한다" 인데, 강의 자료의 예시도 그렇게 적혀 있어서 그대로 갔어요.
근데 read 계열은 "조회한다" 가 사용자 발화 ("알려주세요", "어디예요") 와 잘 매칭되는 반면, "취소한다" 와 "취소해주세요" 사이엔 한 단계 더 추론이 필요할 수도 있겠다 싶었습니다.
이게 사실이면 description 첫 줄에 "고객의 취소 요청을 받아 주문을 취소 처리한다" 같이 사용자 의도 어휘를 직접 박는 게 도움이 될 수 있어요. 단계 3 에서 description 실험할 때 같이 두드려볼 예정입니다.

가설 C, Spring AI 의 Ollama tool-calling 통합 자체의 한계
Spring AI 1.0.0 + Ollama 조합이 OpenAI 와 비교했을 때 tool call 라우팅에 있어 일관성이 떨어진다는 얘기를 본 적이 있어요.
이걸 확인하려면 같은 description 으로 OpenAI 호출을 한 번 비교해봐야 하는데, 그건 비용/세팅 부담이 있어 회고 범위에선 못 했습니다.

세 가설 중 어느 게 우세한지는 단계 3 description 변형 실험 후에 가설 B 가 부분적으로라도 풀리는지를 보고 결정할 생각이에요.

## 안 풀린 채로 두는 것들

`cancelOrder` 의 LLM routing 신뢰도가 가장 큰 미해결입니다.
단계 2 멱등성 실습을 LLM 경로로만 했다간 데이터가 아예 안 만들어질 위험이 있어요.
그래서 단계 2 에서는 Tool 메서드 자체를 단위 테스트로 직접 호출해서 멱등성 4분기를 검증하고, 별도로 LLM 경로에서 한 번이라도 호출되도록 System Prompt 의 `[Tool 사용 규칙]` 을 강화해보려 합니다.

description 의 한국어/영어 효과 정량 비교도 미해결이에요.
단계 3 의 description A/B/C 실험에 영어 버전을 4번째 변형으로 추가할지는 시간이 되면 보겠습니다.

## 실측해보고 적어두는 부록

`./gradlew bootRun` 으로 띄운 직후 시나리오 5종을 두드린 raw 응답과 콘솔 로그는 `실측-raw/단계1-시나리오5종.md`, `실측-raw/단계1-콘솔로그.md` 에 그대로 남겨뒀어요.

특별히 짚어두고 싶은 토큰 수치는 다음 다섯 줄입니다.

```text
[시나리오 1] [Tool] getDeliveryStatus(orderId=2024-1234)
             LLM call elapsedMs=10420 promptTokens=2801 completionTokens=79  totalTokens=2880
[시나리오 2] [Tool] getOrderDetail(orderId=2024-1234)
             LLM call elapsedMs=3103  promptTokens=2887 completionTokens=102 totalTokens=2989
[시나리오 3] (Tool 호출 없음)
             LLM call elapsedMs=1086  promptTokens=1349 completionTokens=41  totalTokens=1390
[시나리오 4] (Tool 호출 없음)
             LLM call elapsedMs=1808  promptTokens=1343 completionTokens=72  totalTokens=1415
[시나리오 5] [Tool] getDeliveryStatus(orderId=2099-9999)
             LLM call elapsedMs=1468  promptTokens=2737 completionTokens=51  totalTokens=2788
```

Tool 이 실제로 호출된 시나리오 (1, 2, 5) 는 promptTokens 가 2737~2887 로 몰려 있고, Tool 이 호출되지 않은 시나리오 (3, 4) 는 1343~1349 에 몰려 있어요.
이 1400 토큰 차이가 곧 "Tool 결과를 다시 LLM 에 넣는 2차 round" 의 비용이라는 게 손에 잡혔습니다.
시나리오 1 의 첫 호출만 elapsedMs=10420 으로 튀는데, 이건 1주차 첫 호출과 같은 모델 로딩 워밍업으로 보여요.

토큰 그래프로 본 또 하나의 확신은, 시나리오 3, 4 가 Tool 호출 흉내만 낸 거지 실제론 안 부른 게 맞다는 거예요.
LLM 이 진짜로 cancelOrder 를 호출했다면 promptTokens 가 시나리오 1~2 와 비슷한 ~2800 대에 떨어졌을 텐데, ~1340 으로 1차 호출 흔적만 남아 있습니다.
LLM 응답 본문만 봤을 땐 "취소되었습니다" 라고 거짓말한 거 같은데, 로그를 같이 보면 그게 거짓말이라는 게 토큰 수치 하나로 잡힙니다.
1주차에 Advisor 패턴을 깔아둔 보람이 여기서 한 번 더 손에 잡혔어요.
