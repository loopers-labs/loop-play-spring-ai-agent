# 2주차 - 멱등성 설계 (단계 2)

> "취소해주세요. 진짜 취소된 거 맞나요? 한 번 더 확인 부탁드려요.", 이 한 문장이 LLM 에이전트의 멱등성 문제를 다 담고 있어요.

## 왜 멱등성을 cancelOrder 에 박았는가

`getOrderDetail`, `getDeliveryStatus` 는 read 라서 부작용이 없습니다. 백 번 호출해도 데이터는 그대로예요.
근데 `cancelOrder` 는 다릅니다. 두 번 부르면 두 번 취소가 일어나거나, 두 번째 호출이 데이터를 덮어씌우거나, 에러를 던지거나 셋 중 하나입니다.

처음엔 "에러 던지면 되지" 라고 생각했어요.
status 가 이미 CANCELED 면 `IllegalStateException` 한 줄로 끝낸다, Java 개발자라면 자연스럽게 떠올리는 패턴입니다.

근데 그게 LLM 에이전트에서는 가장 안 좋은 선택이 됩니다.
LLM 은 에러를 받으면 두 가지 중 하나를 합니다.
- 그대로 사용자에게 전달, "취소 실패" 가 고객에게 가버립니다. 정작 데이터는 취소된 상태인데요.
- 자기가 알아서 paraphrase, "음... 시스템 오류가 발생한 것 같습니다" 같은 모호한 답변이 나갑니다.

둘 다 정확하지 않아요. 진실은 "이미 취소된 상태" 인데 그걸 LLM 에게 직접 알려주려면 에러가 아니라 상태 코드 가 필요했습니다.

## Outcome enum 을 4개로 잡은 이유

`CancelOrderResult` 안에 `Outcome { CANCELED, ALREADY_CANCELED, NOT_CANCELABLE, NOT_FOUND }` 를 박았어요.

처음엔 `boolean success` 로 가려고 했습니다. 자바 라이브러리 시그니처가 그쪽이라 가장 익숙해요.
근데 `false` 만 봐서는 LLM 이 무엇을 안내할지 모르겠더라고요.
- 주문이 없어서 false?, "주문번호를 다시 확인해주세요"
- 이미 취소돼서 false?, "이미 취소된 상태입니다"
- 조리가 시작돼서 false?, "상담원 연결이 필요합니다"

세 가지가 같은 boolean 으로 묶이면, LLM 이 사용자에게 무엇을 안내할지 추론으로 갈라야 하는데 그게 자주 틀립니다.
4분기로 갈라두면 LLM 은 outcome 값 그대로를 받아 적절한 자연어 응답으로 매핑하면 됩니다.

값 이름도 의도적으로 자연어처럼 읽히게 잡았어요. `STATUS_1`, `CODE_42` 가 아니라 `ALREADY_CANCELED` 라고 적은 건 LLM 이 그 값을 보고 의미를 추론할 수 있게 하기 위한 거예요.
실제로 회고 시점에 단계 1 시나리오 5번 (`2099-9999`) 에서 LLM 이 "해당 주문번호를 찾지 못했습니다. 다시 확인해보실 수 있나요?" 라고 응답한 게 `null` 만 받고도 그렇게 매핑된 결과예요. enum 이 명확하면 모델이 따로 학습 안 해도 매핑이 쉽습니다.

왜 4개인가, UNKNOWN/FAILED 는 왜 없는가
이게 가장 신경 쓴 부분이에요.
`UNKNOWN` 을 넣으면 LLM 이 그 값을 받았을 때 무엇을 안내할지가 정의되지 않습니다. LLM 입장에서는 "뭐 어쩌라는 거지" 가 되고, 거의 항상 hallucinate 으로 풀어버립니다.
`FAILED` 도 마찬가지예요. "실패" 라는 단어가 들어가는 순간 LLM 이 사용자에게 "취소 실패" 라고 잘못 전달할 위험이 있어요. 실패의 종류를 구분해서 각각 다른 자연어 응답이 나가야 하는데, FAILED 하나로 묶으면 그게 무너집니다.

그래서 분기가 늘어나는 게 분기를 통합하는 것보다 안전 합니다. 이게 enum 설계의 일반 원칙과는 좀 반대인데, LLM 인터페이스에선 그게 맞다고 봐요.

앞으로 추가될 법한 Outcome 두 가지
운영 가정을 해보면 두 가지가 분명히 필요할 것 같아요.

- `REQUIRES_AGENT`, 자동 취소는 불가능하지만 상담사 권한으로 가능한 상태. 현재 `NOT_CANCELABLE` 메시지에 "상담원 연결" 이 텍스트로 들어가 있는데, LLM 이 그걸 항상 안정적으로 안내할 거란 보장이 없어요. 별도 enum 으로 갈라서 LLM 의 매핑 책임을 줄이는 게 맞을 것 같습니다.
- `COOLING_OFF`, 결제 후 일정 시간 이내(예: 5분) 에는 무조건 즉시 취소, 그 이후엔 사장님 합의 필요한 경계. 이건 한국 배달 운영에 실제로 있는 정책이라, `CANCELED` 와 분리해두면 환불 정책 안내까지 같이 칠 수 있어요.

이 둘이 들어오는 시점은 정책 팀이 구체화한 다음일 거고, 그 전까진 4분기로 충분하다고 봅니다.

## 멱등성의 세 가지 수준, 그리고 다른 상황에서의 선택

강의 자료가 세 가지를 비교해줬어요.

| 수준 | 동작 | cancelOrder 에서의 적합성 |
|---|---|---|
| 에러 | 두 번째 호출에서 예외 | LLM 이 사용자에게 "취소 실패" 전달 위험 |
| 무시 | 두 번째 호출을 조용히 무시 | LLM 이 상태를 모름, 자연어 응답 불가 |
| 같은 응답 + 상태 | 두 번째도 성공 처리, 상태 코드 명시 | "이미 취소된 상태입니다" 정확히 안내 가능 |

cancelOrder 에는 세 번째 (같은 응답 + 상태) 가 정답이에요.
근데 항상 그렇진 않습니다.

`getRiderPhoneNumber()` 같은 가상의 Tool 을 생각해보면, 라이더 전화번호 조회를 호출자가 다섯 번 시도하면 그건 데이터 유출 시도일 수 있어요. 다섯 번째 호출에서는 에러가 정답입니다.

또 `submitPayment(amount=10000)` 같은 결제 Tool, 두 번째 호출에서 "같은 응답 + 상태 (ALREADY_PAID)" 를 돌려주는 건 좋지만, 액수가 다르면 ("amount=20000") 명시적 에러로 차단해야 합니다.

결국 멱등성의 수준은 사이드이펙트의 종류 에 따라 갈리는 것 같아요. cancelOrder 가 "같은 응답 + 상태" 인 이유는, 취소라는 액션 자체가 한 번 이상 일어나도 외부에서 보이는 결과가 같기 때문입니다. 결제는 다르고, 데이터 조회의 반복 시도는 또 다른 분기입니다.

## 분기를 제거하면 무엇이 깨지는가, 실측

`OrderToolsIdempotencyObservationTest` 로 두 케이스를 측정했어요. raw 출력은 `실측-raw/단계2-멱등성실험.md` 에 그대로 박았습니다.

케이스 A, `if (status == CANCELED)` 분기만 제거

```text
[before] status=CANCELED canceledReason=주소가 잘못 입력되었어요
[cancel re-request] outcome=NOT_CANCELABLE
                    message=조리가 이미 시작되어(CANCELED) 자동 취소가 불가합니다. 상담원 연결이 필요합니다.
[after]  status=CANCELED canceledReason=주소가 잘못 입력되었어요
```

데이터 무결성은 OK (canceledReason 보존) 인데 메시지 의미가 완전히 깨졌어요.
LLM 이 이 메시지를 받으면 사용자에게 "조리가 시작되어 자동 취소가 불가합니다, 상담원 연결이 필요합니다" 라고 안내할 거예요.
실제로는 이미 취소돼 있어서 상담원 연결도 필요 없는데, 잘못된 안내가 나갑니다.
"분기 하나 빠지면 사용자가 받는 안내 문구의 정확성이 무너진다", 이게 케이스 A 의 결론이에요.

케이스 B, 두 분기 모두 제거

```text
[1st]     outcome=CANCELED message=주문이 취소되었습니다. ...
[between] status=CANCELED canceledReason=집 앞에 사람이 없어요
[2nd]     outcome=CANCELED message=주문이 취소되었습니다. ...
[after]   status=CANCELED canceledReason=한 번 더 확인 부탁드려요
```

여기선 데이터 자체가 깨져요. `canceledReason` 이 첫 번째 호출 reason ("집 앞에 사람이 없어요") 에서 두 번째 호출 reason ("한 번 더 확인 부탁드려요") 으로 덮어씌워졌습니다.
`canceledAt` 도 같이 갱신되니까, "이 주문이 언제 취소됐는가" 라는 timestamp 가 흔들립니다.
그리고 LLM 은 두 호출 모두 `Outcome=CANCELED` 와 "주문이 취소되었습니다" 메시지를 받았으니까, 사용자에게는 같은 안내가 두 번 나가게 됩니다. 사용자 입장에선 "두 번 다 정상 처리됐다" 로 받아들여요.

두 케이스를 같이 놓고 보니까 멱등성 분기는 단일 가드레일이 아니라 여러 겹의 가드레일 이라는 게 손에 잡혔어요.
한 분기만 빠져도 사용자 안내가 흔들리고 (케이스 A), 두 분기가 다 빠지면 데이터가 흔들립니다 (케이스 B).
그러니까 두 분기가 같이 박혀 있는 게 우연이 아니에요. 한 분기가 "메시지 의미" 를 지키고, 다른 분기가 "데이터 무결성" 을 지키는 거예요.

## 고객에게 어떤 오해를 줄 수 있는가, 케이스 B 기준

1. 이중 취소된 줄 알게 됨, "취소되었습니다" 가 두 번 나가니까 사용자 입장에선 두 번 다 새로운 취소가 일어난 줄 압니다. 카드 명세서를 보면 한 건만 환불되어 있을 텐데, "왜 두 번 취소했는데 환불은 한 번이지?" 같은 추가 문의로 이어집니다.
2. 첫 취소의 사유가 사라짐, 첫 번째 reason ("집 앞에 사람이 없어요") 이 사라지고 두 번째 ("한 번 더 확인 부탁드려요") 로 덮어씌워졌으니, 나중에 사장님이나 운영팀이 "왜 취소된 건이지" 라고 봤을 때 의미 없는 reason 만 남게 됩니다. 운영 관점의 데이터가 망가져요.
3. timestamp 가 흔들려서 환불 SLA 가 깨짐, `canceledAt` 이 두 번째 호출 시각으로 갱신되니까, "취소 후 N영업일 내 환불" 같은 SLA 계산이 늦은 시각으로 시작됩니다. 그만큼 환불도 지연되고요.

## 이 로직이 없었다면 프로덕션에서 어떤 장애가 생겼겠는가

1. 결제 이중 취소 시도, 우리 시스템에선 `order.cancel()` 만 호출했지만, 실제 운영에선 PG 사 환불 API 가 그 뒤에 붙습니다. 멱등성 분기가 없으면 PG 사 API 가 두 번 호출되고, PG 사가 멱등성을 지키지 않는 경우 환불이 두 번 일어나거나 (사용자에게 +N원 입금됨) 두 번째 호출이 PG 사 입장에서 에러로 떨어집니다. 어느 쪽이든 운영 사고예요.
2. 포인트/쿠폰 이중 환급, 주문 시 포인트 적립이 일어났다면, `cancel()` 시 그 적립이 회수되는 로직이 있을 거예요. 두 번 호출되면 포인트가 사용자 보유분보다 더 많이 빠지면서 음수가 됩니다. 회계 정합성 깨짐.
3. 사장님에게 알림 이중 발송, 매장 사장님에게 "주문이 취소되었습니다" 푸시가 두 번 가요. 사장님은 "어? 무슨 주문이 취소된 거지?" 하면서 매장 시스템을 들여다보게 되고, 이게 누적되면 사장님 입장에서 우리 플랫폼 신뢰도가 떨어집니다.

이 세 가지 중 가장 무서운 건 1번이에요. 1번은 돈이 직접 움직이는 사고고, 2~3번은 운영 부담이 늘어나는 정도지만 1번은 즉시 클레임으로 갑니다.

## 가이드 명시 시나리오: 2024-1239 LLM 경로 첫 취소 + 재취소

가이드의 필수 관찰 시나리오 B 입니다.
raw 는 `실측-raw/단계2-1239-LLM경로.md` + `단계2-1239-LLM경로-logs.txt` 에 그대로 있어요.

1차 발화: `"주문번호 2024-1239 주문 취소해주세요. 집 앞에 사람이 없어요"`
LLM 응답: `"주문이 취소되었습니다. 결제 취소는 카드사에 따라 최대 7영업일이 소요될 수 있습니다."`

2차 발화: `"주문번호 2024-1239 진짜 취소된 거 맞나요? 한 번 더 취소해주세요"`
LLM 응답: `"이미 해당 주문은 취소된 상태입니다. 고객님께서 지정하신 취소 사유는 '집 앞에 사람이 없어요'였습니다."`

advisor 로그:

```text
[Tool] cancelOrder(orderId=2024-1239, reasonLength=12)
LLM call elapsedMs=2545 promptTokens=2810 completionTokens=85
[Tool] cancelOrder(orderId=2024-1239, reasonLength=12)
LLM call elapsedMs=3250 promptTokens=2807 completionTokens=114
```

이게 단계 1, 2 에서 못 본 데이터예요. 두 호출 모두 `[Tool] cancelOrder` 가 정확히 찍혔고, 1차에서 `Outcome.CANCELED`, 2차에서 `Outcome.ALREADY_CANCELED` 가 떨어진 뒤 LLM 이 그걸 자연어로 정확히 풀었습니다. 특히 2차 응답에 첫 호출의 reason 인 "집 앞에 사람이 없어요" 가 그대로 인용되었어요. `CancelOrderResult.message` 가 outcome 별로 다르게 구성된 게 LLM 응답으로 그대로 흐른 거예요.

단계 1 의 단순 발화 ("2024-1235 취소해주세요") 에서는 한 번도 호출 못 했는데, 같은 cancelOrder 가 여기선 두 번 다 호출됐다는 게 의외였어요.
차이는 발화 길이와 컨텍스트의 풍부함이라고 봅니다. "집 앞에 사람이 없어요" 같은 사유 단서와 "진짜 취소된 거 맞나요? 한 번 더" 같은 의도 강화 표현이 함께 들어가면 qwen2.5 의 tool routing 이 더 안정적으로 떨어지는 패턴 같아요. 이건 단계 3 의 description 키워드 매칭 가설과 같은 결의 발견이에요. 사용자 발화 쪽에 라우팅을 유도하는 키워드/컨텍스트가 풍부하면 description 의 빈약함을 일부 보완할 수 있다는 거.

reasonLength 로그가 이번 라운드의 추가 변화 한 가지인데, CodeRabbit 피드백을 받고 `cancelOrder` 의 INFO 로그에서 reason 원문을 길이로 마스킹했어요. 두 호출 모두 reasonLength=12 로 찍힌 게 의외인데, 1차의 "집 앞에 사람이 없어요" 가 12자라 LLM 이 2차에서도 직전 발화의 사유를 그대로 가져다 쓴 것으로 추정. system prompt 에 "사유가 없으면 '고객 요청' 으로 채우라" 고 명시했는데도 LLM 이 직전 컨텍스트의 사유를 우선했어요.

## LLM 경로로 직접 4 outcome 두드려본 결과

가이드의 요구가 LLM 자연어 응답을 4 outcome 다 캡처하는 거였어서, 단위 테스트로 우회한 다음에라도 LLM 경로를 한 번 더 두드렸어요.
raw 는 `실측-raw/단계2-LLM경로-4outcome.md`, advisor 로그는 `실측-raw/단계2-LLM경로-logs.txt`.

| 의도한 outcome | 발화 | 실제 Tool 호출 | LLM 응답 |
|---|---|---|---|
| CANCELED | "주문번호 2024-1239 주문 취소해주세요" | Tool 미호출 | "취소하겠습니다. 잠시만 기다려 주세요" (거짓) |
| ALREADY_CANCELED | "주문번호 2024-1238 어떻게 처리됐나요? 취소해주세요" | `cancelOrder(2024-1238, reason="고객 요청")` | "이미 취소된 상태입니다. (취소 사유: 주소가 잘못 입력되었어요)" |
| NOT_CANCELABLE | "주문번호 2024-1236 취소해주세요" | Tool 미호출 | "취소하겠습니다. 잠시만 기다려 주세요" (거짓) |
| NOT_FOUND | "주문번호 9999-0000 취소해주세요" | Tool 미호출 | "주문을 취소하겠습니다. 취소가 완료되면 다시 알려드립니다" (거짓) |

4 중 1만 Tool 이 실제로 호출됐어요.
호출이 된 ALREADY_CANCELED 케이스의 응답은 정확합니다 ("이미 취소된 상태입니다. (취소 사유: ...)"), outcome enum 의 message 가 그대로 자연어로 매핑된 게 손에 잡혔어요.
나머지 셋은 Tool 호출 없이 LLM 이 "취소하겠습니다" 라고 거짓말을 했고, 실제 데이터는 그대로입니다.

호출된 케이스와 안 된 케이스의 발화 차이를 보면 한 가지가 눈에 띕니다.
- 호출된 케이스 (ALREADY_CANCELED), "어떻게 처리됐나요? 취소해주세요", read 의도 + cancel 의도가 같이 들어가 있어요.
- 안 된 케이스 셋, "주문번호 ... 취소해주세요", cancel 의도만.

가설은, qwen2.5 가 "취소해주세요" 단독 발화에는 cancelOrder Tool 을 잘 못 라우팅하는데, "조회 + 취소" 처럼 read intent 가 같이 섞이면 라우팅이 한 번 더 시도된다, 이거예요.
이게 진짜인지는 더 큰 표본 (각 발화 패턴 10회 이상) 으로 확인해야 합니다.
어쨌든 LLM 경로의 cancelOrder 호출률이 운영에 가져갈 수 있는 수준이 아니다 는 게 단계 2 의 추가 데이터예요.
단위 테스트로 4 outcome 분기를 직접 검증한 게 단순히 "편한 길로 갔다" 가 아니라, LLM 경로의 한계를 한 번 더 raw 로 확인한 후의 우회였다는 게 정직한 기록이에요.

운영에 들어가려면, LLM 경로의 cancelOrder 안정성을 description 으로 끌어올리거나, 모델을 키우거나, 아니면 cancel 같은 변경 계열은 LLM 이 자연어 confirm 을 한 단계 더 거친 후에 명시적 UI 확인 ("정말 취소할까요? [예] [아니요]") 를 거치는 식의 가드레일이 필요할 것 같아요.

## 단위 테스트로 검증한 거, 못한 거

`OrderToolsCancelTest` 7 케이스로 다음을 보장했어요.

- CREATED, CANCELED, ACCEPTED, CANCELED (정상 경로)
- COOKING, NOT_CANCELABLE, DELIVERED, NOT_CANCELABLE (자동 취소 불가)
- 사전 취소 (2024-1238) 재취소 시 ALREADY_CANCELED, canceledReason 보존
- 정상 주문 연속 취소 시 첫 번째 CANCELED, 두 번째 ALREADY_CANCELED, 첫 reason 보존
- 존재하지 않는 주문번호 NOT_FOUND

`OrderToolsIdempotencyObservationTest` 2 케이스로는 케이스 A/B 실험의 raw 값을 캡처했고요.

못한 검증
- 동시 두 번 호출, 두 스레드가 같은 주문에 동시에 `cancelOrder` 를 호출하면 어떻게 되는가. ConcurrentHashMap 은 `put` 단위로는 안전하지만, `findById` 후 `order.cancel(...)` 사이에서 race 가 가능합니다. 단계 2 범위에선 단일 스레드 검증으로 멈추고, 동시성은 4주차 (Retry / CircuitBreaker / 분산 환경) 와 함께 다루는 게 맞을 것 같아요.
- LLM 경로의 멱등성, `cancelOrder` 가 LLM 경로로 호출 자체가 잘 안 되는 게 단계 1 의 큰 발견이라, LLM 이 두 번 부르는 시나리오를 만들기조차 어려워요. 단계 3 description 실험 후에 한 번 더 시도해봅니다.

## 안 풀린 채로 두는 것들

`Idempotency Key` 헤더 기반 멱등성은 이번 회고 범위 밖이에요.
실제 PG 사 / 결제 API 들은 "같은 idempotency key 로 5분 내 재시도하면 캐시된 응답을 돌려준다" 식의 패턴을 표준으로 갖고 있는데, 이걸 Tool 레이어에 박는 건 4주차 외부 시스템 연동 영역에서 다루는 게 맞다고 봤습니다.

낙관적 락 (Optimistic Lock / `@Version`) 도 보류.
지금은 Mock 인 ConcurrentHashMap 이라 락 자체가 무의미하고, 실 DB 가 들어오는 시점에서야 의미가 있어요.

`canceledAt` 을 LLM 응답에 직접 노출할지도 미해결.
현재 `CancelOrderResult.message` 안에 시간을 넣지 않았는데, "취소 시각" 을 LLM 이 사용자에게 안내하면 더 친절할 수 있어요. 다만 시간을 정확히 안내하기 위해 timezone 처리가 들어가야 하고, 이건 4주차 운영 영역에 같이 묶어두려고 합니다.
