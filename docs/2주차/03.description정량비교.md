# 2주차 - description 정량 비교 (단계 3)

> "description 한 줄 바꾸면 LLM 동작이 그대로 흔들린다" 는 강의 멘트를 단계 1에서 절반은 확인했어요. 이번 단계는 그 흔들림을 숫자로 잡아보는 자리예요.

## 실험 세팅

`OrderTools.getDeliveryStatus` 의 description 만 3 버전으로 바꿔가며, 같은 발화 `"주문번호 2024-1234 배달 어디쯤이에요?"` 를 5회씩 호출했습니다.

매 버전마다 (1) description 만 변경, (2) `./gradlew compileJava + bootRun` 재기동, (3) warmup 한 번 ("안녕하세요") 으로 모델 워밍업, (4) 본 측정 5회, (5) `[Tool] getDeliveryStatus` 로그 + `LLM call elapsedMs promptTokens=...` advisor 로그 캡처.
세 버전 모두 같은 한 시간대에 같은 ollama 인스턴스로 측정했고, ChatClient 빌더와 시스템 프롬프트는 동일.

```text
버전 A (기준): 기존 description (6줄, 4요소 포함, "지금 어디쯤이에요" 같은 발화 예시까지 박혀 있음)
버전 B (빈약): "배달 정보 조회" 한 줄
버전 C (오해): "주문번호 조회용. 메뉴와 결제 금액만 반환한다."
```

C 는 일부러 실제 동작과 어긋나는 설명입니다. 메뉴/결제는 `getOrderDetail` 책임이고, `getDeliveryStatus` 는 라이더 위치/배달 상태를 반환해요.

## 정량 비교

| 버전 | description | Tool 호출 횟수 (5회 중) | "역삼역 사거리" 포함 횟수 | 2차 round promptTokens |
|---|---|---|---|---|
| A | 기준 (6줄, 4요소) | 3 | 3 | ~2801 |
| B | "배달 정보 조회" (1줄) | 2 | 2 | ~2540 |
| C | "주문번호 조회용. 메뉴와 결제 금액만 반환한다." | 4 | 4 | ~2570 |

raw 응답과 advisor 로그는 `실측-raw/단계3-{A,B,C}.txt` / `단계3-{A,B,C}-logs.txt` 에 그대로 박아뒀어요.
같은 raw 를 분석용 단일 스키마 (`{call_index, tool_called, source_format, prompt_tokens, ...}`) 로 정규화한 파일은 `실측-raw/단계3-정규화분석.md` 에 따로 정리했습니다. raw 의 비정형 토큰 (`ロン`, `ONGLUGE...`, `.nlm` 등) 이 자동 집계 파이프라인에서 파싱 실패를 유발하지 않도록 분리한 자리예요.

`[Tool] getDeliveryStatus` 로그가 한 번도 안 찍힌 호출은 LLM 이 자연어 응답으로 tool call XML 자체를 새어 내보낸 경우입니다. 본문에 `{"name": "getDeliveryStatus", "arguments": {"orderId": "2024-1234"}}` 같은 패턴이 그대로 박혔어요.

## 가장 의외였던 게 C 가 A 보다 호출률이 높았던 거예요

처음 표를 봤을 때 잠깐 멈췄어요.
"description 이 거짓말인 C 가 A 보다 호출률이 더 높다" 는 게 직관과 어긋났습니다.
강의 자료의 예측은 "C 에서 LLM 이 엉뚱한 Tool 을 호출하거나 hallucinate 한다" 였는데, 실제로는 그 반대 방향으로 흔들렸어요.

가만히 보고 있다가 두 가지 가설이 떠올랐습니다.

가설 1, description 의 키워드 매칭이 결정적이다
C 의 description 안에 "주문번호" 라는 단어가 들어 있어요.
사용자 발화 "주문번호 2024-1234 배달 어디쯤이에요?" 의 강한 토큰이 "주문번호" 인데, 이게 description 의 "주문번호 조회용" 과 직접 매칭됩니다.
A 의 description 안에는 "주문번호" 라는 단어가 들어 있긴 한데 6 줄 본문 중 한 군데에 있어서 매칭 강도가 약했을 수 있어요.
B 는 "주문번호" 라는 단어가 description 본문에 아예 없습니다 (`@ToolParam` 에는 있지만 그게 호출 라우팅에 어떻게 쓰이는지는 모델 구현에 따라 달라요).

가설 2, description 후반의 거짓 단서를 LLM 이 깊게 보지 않았다
C 의 description 후반 ("메뉴와 결제 금액만 반환한다") 이 사실이 아닌데도, 5회 중 4회는 호출이 됐어요.
LLM 입장에선 "이 Tool 을 호출할까 말까" 를 결정할 때 description 전체를 깊게 추론하기보다 앞부분 키워드에서 결정해버리는 경향이 있어 보입니다.
이 가설이 사실이라면, description 의 앞 한 줄 이 호출 결정의 큰 비중을 차지한다는 얘기가 됩니다.

이 두 가설 중 어느 게 우세한지는 더 큰 표본 (각 버전 20회 이상) 없이는 단정할 수 없어요.
다만 단계 1 의 `cancelOrder` 가 한 번도 호출되지 않았던 것과 같이 보면, "사용자 발화의 핵심 키워드 ↔ description 의 첫 한두 줄의 키워드" 매칭이 호출 결정에 굉장히 큰 비중을 차지한다는 건 다시 확인됐다고 봐요.

## 응답 본문이 C 에서도 거의 정상이었던 게 두 번째 의외

처음엔 C 가 호출되더라도 응답이 description 의 거짓 단서대로 "메뉴와 결제 금액" 만 안내할 거라고 예상했어요.
실제로는 라이더 위치, 예상 도착 시각이 다 들어간 정상 응답이 나왔습니다.
한 케이스 (C 의 call 4) 만 "현재 배달 상태는 조리 중이며, 라이더는 역삼역 사거리 부근에서 운행 중입니다" 처럼 약한 혼선이 보였는데, 라이더 위치 자체는 정확했어요.

여기서 드는 추측은, description 은 호출 라우팅에는 영향을 주지만, 응답 생성 단계에서는 실제 Tool 결과 JSON 이 우위 라는 거예요.
2 차 LLM 호출 시점에 LLM 은 Tool 결과 JSON (`{"orderId":"2024-1234","status":"DELIVERING","riderLocation":"역삼역 사거리 부근",...}`) 을 보고 응답을 생성하는데, 그 시점엔 description 의 거짓 단서보다 실제 데이터가 더 강한 신호로 작용하는 것 같습니다.

이게 사실이면, "description 거짓말 ↔ 데이터 거짓말" 둘 중 데이터 거짓말이 훨씬 더 위험 합니다.
description 은 호출 안 하게 막을 수는 있어도 응답을 거짓말로 만들지는 못해요. 그런데 Tool 이 잘못된 데이터를 돌려주면 LLM 이 그걸 그대로 자연어로 풀어버립니다.
이건 단계 4 의 Observability 로그를 볼 때도 다시 짚어둘 포인트예요.

## tool_call XML 누설은 별도 현상이에요

호출 안 된 케이스 (A 2회, B 3회, C 1회) 의 응답 본문에 `{"name": "getDeliveryStatus", "arguments": {"orderId": "2024-1234"}}` 같은 raw tool-call 패턴이 그대로 새어 나왔어요.
한 응답에는 `<tool_call>` 태그까지 보입니다.

이건 description 품질 문제라기보다, qwen2.5 + Spring AI 1.0.0 + ollama 통합의 한계 로 보입니다.
LLM 은 "tool 을 호출해야 한다" 는 의도까지는 잡았는데, 그걸 ollama API 의 tool_calls 필드로 emit 하지 못하고 일반 텍스트로 풀어버렸어요. Spring AI 입장에선 그게 텍스트로 보이니까 actual tool call 로 라우팅 못 하고 그대로 사용자에게 전달.

이 문제는 description 으로는 해결이 안 될 것 같고, 다음 둘 중 하나여야 합니다.
- 더 큰 모델 (qwen2.5:14b, llama3.1:70b), instruction-following + tool routing 안정성 ↑
- 다른 모델 (gpt-4o, claude-3-5-sonnet), function calling 이 학습 분포에 더 짙음

운영 비용 얘기라 회고 범위에선 못 풀고 다음 라운드로 미뤘어요.

## description 4요소를 본인 언어로 다시 적어두기

강의 자료가 제시한 "무엇 / 언제 / 입력 / 실패" 4요소를 단계 1, 3 두 번 두드려본 입장에서 중요도 순으로 재배열 해봅니다.

1. 언제 (호출 조건), 사용자 발화의 어떤 키워드와 어떤 의도일 때 호출되는가. C 실험에서 보였듯 LLM 은 description 의 키워드 매칭으로 호출 결정을 거의 끝냅니다. "주문번호" 같은 발화 토큰을 description 앞부분에 넣지 않으면 호출이 흔들립니다.

2. 무엇 (Tool 동작), 이 Tool 이 무엇을 반환하는가. 이건 응답 생성 단계에서 중요해요. description 의 "무엇" 이 모호하면 LLM 이 Tool 결과를 자연어로 풀 때 어디에 강조점을 둘지 잘못 잡습니다. C 케이스 4 의 "조리 중이며, 라이더는 역삼역 사거리..." 같은 약한 혼선이 그 흔적이에요.

3. 실패 (반환 변형), null, 빈 값, 에러 outcome 의 의미. 단계 1 시나리오 5 (`2099-9999`) 에서 LLM 이 "찾지 못했다" 라고 정확히 안내한 게 description 의 "존재하지 않으면 null 반환" 한 줄 덕분이었어요. 이게 빠지면 LLM 이 "확인했는데 없습니다" 같은 거짓 응답을 내거나 hallucinate.

4. 입력 (파라미터 형식), `@ToolParam(description=...)` 영역. 호출 결정 자체에는 영향이 작아 보였습니다. 단계 1 에서 LLM 은 발화의 주문번호 "2024-1234" 를 정확히 인자에 채웠어요. description 이 빈약했던 B 에서도 입력은 흔들리지 않았습니다. 이건 모델이 OpenAPI 스타일 schema 파라미터를 학습 분포에서 자주 본 결과 같아요.

순서가 강의 자료와 좀 달라졌는데, 이건 두 번의 실측 후 손에 잡힌 우선순위예요.

## description 이 "오래된 주석" 처럼 되는 걸 어떻게 막을까

회사 코드를 오래 보다 보면 가장 자주 보는 게 코드와 어긋난 주석이에요.
description 도 시간이 지나면 똑같은 운명을 맞을 것 같아서, 미리 막을 방법을 적어둡니다.

Contract Test 한 줄로 묶기
`OrderToolsCancelTest` 가 outcome 4분기를 단위 테스트로 박은 것처럼, description 안의 약속도 테스트로 박을 수 있어요.

```java
@Test
void getDeliveryStatus_returnsNullForUnknownOrder() {
    DeliveryStatusView v = tools.getDeliveryStatus("9999-9999");
    assertNull(v); // ← description "존재하지 않으면 null 반환" 와 동기화
}
```

description 의 "약속" 이 테스트로 박혀 있으면, 누군가 Tool 구현을 바꿔서 약속을 깨면 테스트가 fail 합니다. description 본문 자체는 자동 검증이 안 되지만, description 의 검증 가능한 약속들 은 테스트로 묶을 수 있어요.

PR 리뷰 체크리스트에 명시
"Tool 본문을 수정한 경우 description 의 4요소를 한 번씩 확인했는가" 를 PR 템플릿에 한 줄 박는 식. 사람 기억력에 기대는 거라 완벽하진 않지만, 없는 것보단 낫습니다.

description 끝에 ChangeLog 한 줄
`(updated: 2026-05-23, added DELIVERING-only riderLocation guard)` 같은 한 줄을 description 끝에 둘 수 있어요. 이건 코드 수정 시 자동으로 같이 손이 가는 영역이라, description 의 stale 여부를 시각적으로 짐작하게 만들 수 있습니다. 다만 description 안의 모든 글자가 LLM 입력에 들어가니까, 운영 토큰 비용에 약간 영향을 줘요.

세 가지 중 가장 효과적인 건 첫 번째 (Contract Test) 라고 봅니다.

## 안 풀린 채로 두는 것들

표본 5회는 통계적으로 너무 작아요.
A 가 3/5, B 가 2/5, C 가 4/5 인데, 운에 따라 ±1 정도는 흔들릴 수 있는 표본이에요.
각 버전 20회씩으로 늘리면 "C 가 A 보다 호출률이 높다" 가 진짜인지 운인지 갈릴 텐데, 그건 시간 부담이 있어 회고 범위에선 못 했습니다.
다음 라운드 PromptLab 류 batch 호출 인프라를 같이 두드릴 때 description 변형도 한 묶음으로 돌려볼 생각이에요.

영어 description 비교는 안 했어요.
영어로 description 을 적었을 때 한국어 발화에 대한 호출률이 어떻게 바뀌는지를 비교하면 단계 1 의 "한국어 vs 영어" 가설을 검증할 수 있어요. 다만 회고 분량 통제 상 이번엔 미뤘습니다.

큰 모델로 같은 실험을 못 했어요.
qwen2.5 (7B) 에서 보인 동작이 14B / 70B / OpenAI 에서도 같은 방향인지가 진짜 일반적 결론을 위한 검증이에요.
이건 운영 환경 차원의 얘기라 6 주차 마무리 시점에서 한 번 더 두드려볼지 결정하려고 합니다.

## 실측해보고 적어두는 부록

세 버전의 advisor 로그 핵심만 추려서 한 곳에 놓습니다.

```text
[A 기준 description]
[Tool] getDeliveryStatus(orderId=2024-1234)  (3회)
1차 round promptTokens=1347 (호출 안 된 케이스 평균)
2차 round promptTokens=2801

[B "배달 정보 조회"]
[Tool] getDeliveryStatus(orderId=2024-1234)  (2회)
1차 round promptTokens=1223
2차 round promptTokens=~2540

[C "주문번호 조회용. 메뉴와 결제 금액만 반환한다."]
[Tool] getDeliveryStatus(orderId=2024-1234)  (4회)
1차 round promptTokens=1237
2차 round promptTokens=~2570
```

1차 round 의 promptTokens 가 B (1223) < C (1237) < A (1347) 순으로 갈렸어요.
이게 곧 description 본문 + tool schema 가 시스템 프롬프트에 차지하는 토큰 양입니다. A 가 B 보다 124 토큰 많은데, 이건 description 6 줄 + 발화 예시 ("지금 어디쯤이에요" 등) 가 차지하는 분량이에요.
운영 관점에선 "description 124 토큰 더 박아서 호출률 1/5 더 잡았다" 가 비용 효율이 좋은지를 따져야 하는데, 그 답은 트래픽 / 모델 / 사용자 발화 분포에 따라 갈립니다.
회고 본문에서 "description 의 비용은 호출당 + 트래픽 곱" 이라는 한 줄을 머리에 박아둔 게 다음 라운드의 캐싱 / 축약 결정으로 이어질 것 같아요.

호출 안 된 케이스의 응답 본문 사례 하나만 마지막에 박아둡니다 (raw 는 `실측-raw/단계3-{B,C}.txt` 에 다 있어요).

```text
[B call 1]
배달의 진행 상황을 확인하겠습니다.

ONGLUGE {"name": "getDeliveryStatus", "arguments": {"orderId": "2024-1234"}}
```

`ONGLUGE` 같은 토큰이 응답 앞부분에 새어나온 게 인상적이에요. `<tool_call>` 시작 토큰이 학습 분포에서 다른 토큰으로 매핑된 흔적으로 보이는데, 이게 사용자한테 그대로 나간다는 게 그 자체로 문제입니다.
"description 잘 적으면 안 일어난다" 는 가설을 단계 3 전엔 갖고 있었는데, 이번 실험으로 그게 일부만 맞다는 게 확인됐어요. description 으로 호출 결정은 조금 더 안정화할 수 있지만, 모델 자체의 tool-call emit 안정성 은 description 으로 못 메웁니다.
이 한계는 단계 4 에서 토큰 비용을 같이 보면서 다시 짚어볼 거예요.
