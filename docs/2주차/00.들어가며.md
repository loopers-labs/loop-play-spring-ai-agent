# 2주차 - 들어가며

> 1주차에 만든 "잘 답하는 챗봇" 위에 실제 주문 데이터를 만질 수 있는 능력을 얹습니다.
> 강의에서는 "이 순간부터 챗봇이 아니라 에이전트다" 라고 하던데, 솔직히 한 줄이 그렇게 와닿진 않았어요.

## "판단은 LLM, 실행은 Spring Bean" 이 한 줄을 두고 잠깐 멈췄던 이유

강의 슬라이드에 큰 글자로 적힌 그 한 줄이 처음엔 너무 당연하게 들렸어요.
LLM에게 DB 접근 권한을 줄 사람은 어차피 없으니까, 어디까지가 LLM 일이고 어디서부터가 우리 코드 일인지는 그냥 자명하다고 생각했습니다.

그런데 한 단락 더 읽다 보니까 그게 그렇게 자명한 경계는 아닐 수 있겠다 싶었어요.
LLM이 호출할 "Tool 목록" 자체를 결정하는 게 우리 코드인 건 맞는데, 그 Tool을 부를지 말지의 결정권은 어쨌든 LLM에 있다는 점이 좀 묘했습니다.
1주차에서 System Prompt가 곧 LLM의 가드레일이었던 것처럼, 2주차에서는 `@Tool` description이 또 하나의 가드레일이 된다는 건데, 가드레일이 항상 의도대로 작동하지는 않더라고요. (이건 본문에서 더 적게 됩니다)

이 부분에서 살짝 바뀐 생각: "판단/실행을 가르면 된다", "둘을 가르는 글자(description, system prompt)가 LLM에게 어떻게 읽히는지를 다시 설계해야 한다".

---

## 1주차 코드를 어디까지 두고, 어디부터 새로 짤지

처음엔 `SupportController` 옆에 그냥 `@Tool` 메서드 몇 개 추가하면 될 거라고 생각했어요.
근데 막상 손대보니까 1주차 `SupportController` 는 트리아지 (분류 + JSON 응답) 용 시스템 프롬프트로 잠겨 있고, 2주차 `AssistantController` 는 자연어 대화 + Tool 호출 + 자연어 응답으로 결이 완전히 달랐습니다.
같은 ChatClient를 공유하면 두 가지 페르소나가 한 빌더에 섞여 들어가는 셈이라, 컨트롤러도 시스템 프롬프트도 따로 두는 게 깔끔하다 싶었어요.

그래서 `com.baedal.assistant.*` 라는 새 패키지를 열고 거기에 도메인/서비스/Tool/컨트롤러를 다 넣었어요.
`@SpringBootApplication` 의 base package 가 `com.baedal.support` 라서 component scan 이 새 패키지를 못 잡는 문제가 있었는데, `scanBasePackages = "com.baedal"` 한 줄로 풀었습니다.
처음엔 `com.baedal.support.assistant` 같은 하위 패키지로 갈까도 고민했는데, 2주차 분량이 컨트롤러 한 개로 끝날 게 아니라서 (멱등성 / 실험용 description 변형 / Tool 추가) 이름 공간을 처음부터 분리하는 쪽이 다음 주차에도 덜 어색할 것 같았어요.

이 결정에서 생각했던 트레이드오프: `com.baedal.support` 한 곳에 다 넣었다면 1주차 코드 ↔ 2주차 코드 사이를 점프할 일이 없었겠지만, `SupportController` (트리아지 봇) 와 `AssistantController` (Tool 봇) 이 같은 패키지에 있으면 의도가 헷갈리는 게 더 큰 비용이라고 봤습니다. 그래서 패키지 분리 + 메인 한 줄 수정.

## 강의에서 가장 인상 깊었던 한 줄

여러 문장 중에 마음에 남은 게 두 줄이에요.

> Tool을 만드는 것보다 Tool의 경계(boundary) 를 설계하는 훈련이 핵심입니다.

처음 봤을 땐 "경계가 뭐 별 거 있나, 메서드 시그니처지" 했어요.
근데 `cancelOrder` 를 직접 짜보니까 그게 시그니처 얘기만은 아니더라고요.
- 어디까지가 자동 취소이고 어디부터 상담사 연결인가 (`isCancelable()` 의 경계)
- 같은 요청이 두 번 들어왔을 때 에러를 던질지 / 무시할지 / 같은 응답을 또 돌려줄지 (멱등성의 경계)
- 내부 도메인 모델 `Order` 의 어떤 필드까지를 LLM에게 노출할지 (DTO 경계)
- description 안에 어디까지 적어야 LLM이 호출하고, 무엇까지 적으면 over-trigger 가 나는지 (의도의 경계)

이게 다 "Tool 하나 만들 때 정해야 하는 경계" 인데, 메서드 시그니처는 그 중 가장 얇은 한 줄에 불과했어요.

> description은 LLM에게 보여주는 유일한 API 문서다.

이 문장이 회고에 가장 자주 다시 등장할 거 같아요.
description 한 줄 바꾸면 모델 동작이 그대로 흔들리는 걸 단계 3에서 직접 두드려볼 예정인데, 단계 1만 두드려도 이미 절반은 확인됐습니다.
qwen2.5 가 `getDeliveryStatus`, `getOrderDetail` 은 또박또박 호출했는데 `cancelOrder` 는 자연어로 흉내만 내고 실제론 한 번도 안 부르더라고요.
description 끝에 적어둔 "결과는 항상 CancelOrderResult 로 돌아오며..." 같은 문장이 충분히 강한 신호가 아니었던 것 같은데, 이건 단계 1 본문에 더 적었습니다.

## 2주차에 풀고 싶은 것 / 못 풀 것 같은 것

풀어보려고 한 것
- `@Tool` / `@ToolParam` 으로 주문 조회/배달 추적/주문 취소 메서드를 LLM 호출 가능한 Tool로 등록
- `cancelOrder` 의 멱등성 4분기 (`CANCELED / ALREADY_CANCELED / NOT_CANCELABLE / NOT_FOUND`)
- description 3 버전 (기준 / 빈약 / 오해 유발) 으로 LLM 호출 결정을 정량 비교
- Tool 왕복 시 LLM ↔ 서버가 몇 번 오가는지 로그로 직접 관찰

못 풀고 다음 주차로 미룬 것
- "그거 취소해주세요" 같은 지시 대명사 (Memory 필요, 3주차 영역)
- Tool이 외부 결제 PG를 호출하는 케이스 (Outbox/SAGA, 4주차 영역)
- Tool 호출 실패 시 LLM 이 한 번 더 retry 할지, 다른 Tool 로 fallback 할지 결정하는 로직 (4~5주차 Retry/CircuitBreaker)
- qwen2.5 가 cancelOrder 같은 변경 계열 Tool을 안정적으로 호출하지 못하는 문제, 모델을 키우는 건 운영 비용 얘기라 일단 7B 한계로 안고 갑니다

2주차 마치고 나면 답을 얻고 싶은 질문: "description 만 잘 적으면 7B 모델로도 Tool routing 이 안정적인가?", 단계 3 정량 실험 후에 답이 나오기를 기대하고 있어요.
