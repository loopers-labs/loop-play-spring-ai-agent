# Round 3 · 2단계 — Memory 크기 실험 (MAX_MESSAGES)

> 동일한 10턴 시퀀스를 `MAX_MESSAGES` = **2 / 8 / 40** 으로 바꿔가며 실행.
> (10턴 = 20메시지이므로 quest의 "20 vs MAX"는 이 시퀀스에선 동일 → 대비가 드러나는 2/8/40 선택.)
> 입력 토큰은 `PerformanceLoggingAdvisor`의 `promptTokens`. 전체 응답: `docs/round-3/step2-seq-max{2,8,40}.txt`.

## 10턴 시퀀스
```
1) 2024-1234 배달 상황   2) 그거 몇 분 남았어요?   3) 2024-1235 메뉴 뭐였죠?
4) 아 그 버거 세트       5) 2024-1234 취소 가능?   6) 그럼 1235는 취소되죠?
7) 그거 취소해주세요(=1235)  8) 아까 1234 언제 도착?  9) 그 주문 라이더 위치
10) 요약해 주세요
```

## 정량 비교

| MAX_MESSAGES | promptTokens 추이 | 지시 대명사 해결 | 요약(turn10) |
|:---:|---|---|---|
| **2** | 평탄 ~1,800 (tool턴만 ~3,900 스파이크) | ❌ turn7 "그거" → **빈 응답**, turn6 1235 "찾을 수 없음" | ❌ 마지막 2턴만 회수 |
| **8** | 1,741 → ~2,096 상승 후 캡 | ✅ turn7 "그거"=**1235**, turn9 "그 주문"=1234 | △ 최근 4턴(1235취소·1234위치)만 |
| **40** | 1,848 → 2,678 **선형 증가**(캡 없음) | ⚠️ turn7 "그거"=**1234**(1235 기대), turn8/9 1234 ETA·위치 정확 회수 | △ 1234 thread 정확, 1235 thread 누락 |

## 실패 관찰 — MAX_MESSAGES=2의 파괴적 결과

`turn 7 "그거 취소해주세요"` → **빈 응답** (LLM이 아무것도 못 만듦):
```
── turn 7: 그거 취소해주세요
(빈 줄)
```
`turn 6 "그럼 1235는 취소되죠?"` → 윈도우=2라 turn3의 "1235" 언급이 이미 밀려나, 1235를 못 찾음:
```
해당 주문번호를 찾을 수 없습니다. 다시 한번 주문번호를 확인해주시겠어요?
```
`turn 10 요약` → 직전 1~2턴만 기억:
```
1. 그 주문의 라이더 위치를 다시 확인해달라고 요청
2. 주문 번호 2024-1235의 상세 정보를 확인
```
(turn 1~7의 "1234 배달/취소", "버거세트" 문맥 전부 소실.)

**왜 2는 부족한가**: `MessageWindowChatMemory(maxMessages=2)`는 USER/ASSISTANT **단 한 쌍**만 유지한다. 매 턴 직전 응답 하나만 남으므로, 2턴 이상 떨어진 주문번호를 가리키는 "그거"/"아까 그"는 참조 대상이 윈도우 밖이라 해결 불가. 멀티턴 상담의 핵심(누적 맥락)이 무너진다.

## 반직관적 발견 — "더 큰 윈도우 = 더 나은 해결"은 아니다

`turn 7 "그거 취소해주세요"`에서 quest 기대값은 **1235**(직전 turn 6 언급):
- **MAX=8** → "그거"=**1235** ✅ (의도대로)
- **MAX=40** → "그거"=**1234** ⚠️ (전체 이력에 1234가 더 자주/먼저 등장해 "가장 최근" 신호를 희석)

→ 맥락이 많을수록 *최신성 신호*가 묻힐 수 있다. 윈도우 크기는 "클수록 좋다"가 아니라 **"해당 도메인의 대화 길이에 맞춘 적정값"** 이 핵심. (단 MAX=40은 turn 8의 ETA, turn 9의 라이더 위치처럼 *오래된 사실 회수*는 가장 정확했다 — 트레이드오프.)

## 응답 시간 / 토큰
- MAX=2: 입력 토큰 평탄(윈도우가 안 늘어남) → 토큰 비용 최저, 그러나 기능 붕괴.
- MAX=40: 입력 토큰이 매 턴 선형 증가(캡 없음) → 긴 세션일수록 비용·지연 누적.
- MAX=8/20: 적정 구간 — 윈도우 채워질 때까지 증가 후 안정.

## 설계 결정 문서 (2단계) — *초안, 제출 전 검토*

**Q. 슬라이딩 윈도우 vs 대화 요약(summarization) — 언제 어느 것?**

| 전략 | 적합 상황 | 장점 | 단점 |
|------|-----------|------|------|
| 슬라이딩 윈도우(현재) | 짧은 거래형 상담(배달: 보통 한 세션 내 해결) | 구현 단순, 지연 낮음, 결정적 | 윈도우 밖 정보 완전 소실 |
| 대화 요약 | 길고 누적되는 상담(반복 문의, 장기 케이스) | 오래된 맥락도 압축 보존, 토큰 상한 | 요약용 LLM 호출 추가(비용/지연), 요약 손실/오류 위험 |

배달 상담은 대개 단일 세션에서 끝나는 거래형이라 **슬라이딩 윈도우가 기본**으로 충분. 요약은 "어제 환불 건 재문의"처럼 세션을 넘는 장기 맥락이 필요할 때.

**Q. "지시 대명사 해결 성공률"이 10턴 중 몇 회 미만이면 프로덕션 금지?**
지시 대명사가 결제/취소 같은 **상태 변경 액션의 대상**을 결정한다면, 오해석은 곧 잘못된 주문 취소다. 기준: 안전이 걸린 액션(cancel)에 대해 **해결 성공률 100% 미만이면 자동 실행 금지** — "그거 취소"는 반드시 "2024-1235 맞으세요?" 재확인을 거치게 한다(human-in-the-loop). 조회성(어디쯤?)은 95% 이상이면 허용.

**Q. 배달 도메인에서 "오래된 대화"가 의미 있는 경우?**
- 3시간 전 주문 건을 "아까 그거 아직도 안 왔어요" 재문의 → 같은 세션이라면 윈도우 밖일 수 있음.
- 어제 환불 신청 건 "그거 처리됐어요?" 재문의 → 세션 수명을 넘는 영속 메모리 필요(→ 3단계 JDBC).

**Q. Memory를 세션이 아닌 고객 단위로 영속한다면?**
- 가능해지는 것: 재방문 고객 맥락 유지("지난번처럼 매운맛 빼고"), 반복 불만 패턴 감지, 개인화 추천.
- 리스크: 개인정보 장기 보관(전화번호/주소가 대화에 평문 축적) → 보존기간·마스킹·삭제권 필요. 잘못된 과거 맥락이 새 주문을 오염(stale context). 저장 비용·프라이버시 컴플라이언스 부담.
