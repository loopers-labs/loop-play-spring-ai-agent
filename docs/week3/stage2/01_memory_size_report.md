# Round 3 — 2단계: Memory 크기 실험 + 실패 관찰

`MAX_MESSAGES`를 3가지 값(2, 20, MAX)으로 바꾸고 동일한 10턴 시나리오를 실행해 입력 토큰, 응답 시간, 지시 대명사 해결 성공률을 정량 비교한다.

> **결과 요약**
> - **인접 지시 대명사(T2/T4/T7/T9)는 세 조건 모두 3/4** — 메모리 크기로 갈리지 않았다.
> - **이유:** ① 모든 대명사 선행사가 *직전 턴*에 있어 window=2도 주문번호를 푼다. ② T4는 상류 T3의 메뉴 환각 탓에 세 조건 공통으로 실패(메모리 아닌 도구 문제).
> - **차이가 드러난 곳:** **(a) 전역 회상(T10)**, **(b) 입력 토큰 비용**.

## 5. 실험 B (MAX=2) — 실패 관찰

### 왜 MAX=2는 부족한가

`MessageWindowChatMemory(maxMessages=2)`는 최근 메시지 2건(USER 1 + ASSISTANT 1)만 유지한다.

```
T1 처리 후 store: [T1-USER, T1-ASSISTANT]   ← 2건 full
T2 처리 후 store: [T2-USER, T2-ASSISTANT]   ← T1 쌍 축출
T3 처리 후 store: [T3-USER, T3-ASSISTANT]   ← T2 쌍 축출
…
T10 처리 후 store: [T10-USER, T10-ASSISTANT]
```

**결과: 매 턴 직전 한 쌍 외 모든 발화는 프롬프트에 포함되지 않는다.** 스냅샷 건수가 10턴 내내 **2 고정**.

### 인접 지시 대명사 — 3/4 (A와 동률)

| 턴 | 응답(요지) | tool | 판정 |
|----|-----------|------|------|
| T2 | "2024-1234 도착 예정 5시 10분경, 약 10분" | — | ✅ 1234 |
| T4 | "2024-1235 불고기 버거 세트와 치즈 햄버거 세트" | — | ❌ 메뉴 환각 |
| T7 | "2024-1235 성공적으로 취소" | `cancelOrder(1235)` | ✅ 1235 |
| T9 | "2024-1234 역삼역 사거리, 5시 10분경" | — | ✅ 1234 |

- **3/4 — A와 같다.** 
- 대명사 선행사가 전부 *직전 턴*에 있어 window=2도 주문번호를 푼다 : T7 "그거"=1235는 직전 T6의 1235 언급으로 해결돼 실제 `cancelOrder(1235)` 호출. 

### 진짜 B-고유 실패 — T10 전역 회상 붕괴

대명사가 아니라 "**지금까지 전부 요약**"처럼 2턴 이상 전 맥락을 요구하는 순간 무너진다.

- **요청** : `요약해 주세요 지금까지 제가 뭘 물어봤는지`
- **주입 history** = 직전 T9 한 쌍뿐(1234 라이더 위치) — **1235 발화(T3·T4·T6·T7) 전부 축출.**
- **응답** — 1234 한 줄, 1235 통째 누락 (기대식 `2024-1234 && 2024-1235` ❌):
  ```
  현재까지 고객님이 요청하신 내용을 요약하면, 최근에 "2024-1234" 주문의 배달원 위치를 다시 확인하셨습니다. …
  ```

#### **B vs A·C 대조 — 같은 T10:**

| 실험 | T10 주입 history | 1235 발화 포함? | 요약 주문 | 판정 |
|------|------------------|----------------|-----------|------|
| **B(2)** | 직전 T9 한 쌍(2건) | ❌ 전부 축출 | 1234만 | ❌ |
| A(20) | T1~T9 18건 전부 | ✅ | 1234 **+ 1235** | ✅ |
| C(MAX) | T1~T9 18건 전부 | ✅ | 1234 **+ 1235** | ✅ |

> 주입 messages 총건수 = history + system + 현재 USER → **B 4건 / A·C 20건**(server.log `[Ollama 요청]`로 확정).

### 입력 토큰 — 평탄

```
T1: 2521  ← 시스템 + 툴 정의 + T1-USER
T2: 2639  ← + 직전 T1 쌍
T3: 2639  ← 직전 T2 쌍 (T1 축출)
…
T10: 2620 ← 직전 T9 쌍
```
T2부터 ~2,600에 **고정**된다. 대화가 길어져도 입력이 안 느는 것 자체가 **맥락 손실의 증거**다.

## 6. 실험 C (MAX=∞) — 입력 토큰 선형 증가 관찰

### 입력 토큰 선형 증가

```
T1: 2521   (기저: 시스템 + 툴 + T1-USER)
T2: 2636   T3: 2748 (+112)   T4: 2834 (+86)   T5: 2910 (+76)
T6: 3009 (+99)  T7: 3074 (+65)  T8: 3251 (+177)  T9: 3342 (+91)  T10: 3440 (+98)
```
- **선형 증가 확인** — T3→T10: 2748 → 3440 = **+692 토큰**, 7턴 평균 **+99/턴**.
- **A≈C (변곡점 미관측)** — 윈도우 20이 미포화(T10에 딱 20건)라 A도 축출이 없어 A·C가 동일 이력을 주입한다. 21턴 이상으로 길어져 A가 축출을 시작하면 두 곡선이 분기(A는 상한에서 평탄, C는 계속 증가). **후속 과제**: 15~20턴+ 또는 tool-heavy 시나리오.

### 인접 지시 대명사 결과 (3/4 — A·B와 동률)

| 턴 | 응답(요지) | tool | 판정 |
|----|-----------|------|------|
| T2 | "2024-1234 도착 예정 5시 12분, 약 12분" | — | ✅ 1234 |
| T4 | "2024-1235 **치킨 버거 세트** (콜라 중)" | — | ❌ 메뉴 환각 |
| T7 | "2024-1235 정상 취소" (+ 중국어 토큰 누출) | `cancelOrder(1235)` | ✅ 1235 |
| T9 | "2024-1234 역삼역 사거리, 5시 12분" | — | ✅ 1234 |

- **판정 3/4** — T7은 `cancelOrder(2024-1235)`를 정확히 호출.
- **T7 토큰 누출(관찰)** — 응답에 한국어/중국어 혼용이 보였으나 **취소 자체는 정상 실행**되고 `response_match("취소")`는 통과. 무제한 맥락이 응답 *형식*을 흔든 사례지 "대명사 오해"는 아니다(qwen2.5 알려진 누출 패턴).

```
… 결제 취소는 카드사에 따라 최대 7영업日内，您应该发送的回复是： json {"outcome":"…"} … 订单号2024-1235已成功取消。…
```

## 7. 설계 결정 문서

### Q1. 슬라이딩 윈도우 vs 요약(Summarization) 전략

| 기준 | 슬라이딩 윈도우 (`MessageWindowChatMemory`) | 요약 전략 |
|------|------------------------------------------|---------|
| 작동 방식 | 최근 N개 메시지만 유지, 오래된 것 삭제 | 오래된 대화를 LLM이 요약해 압축 보존 |
| 토큰 비용 | N에 비례, 예측 가능 | 요약 호출 비용 추가 (1~2 LLM 왕복) |
| 정확도 | 오래된 맥락 완전 손실(B의 T10) | 오래된 맥락이 요약 형태로 보존 |
| 구현 복잡도 | 낮음 | 높음 (요약 시점·품질·프롬프트 관리) |
| 적합 시나리오 | 짧은 세션 (배달 상담 1회 = 5~10턴) | 장기 세션 (법률 상담, 고객 이력 등) |

**배달 상담에 슬라이딩 윈도우가 맞는 이유:** 평균 5~10턴으로 짧고 주문번호가 명시되는 경우가 많아 장거리 참조 필요성이 낮다. 단, 전역 요약 요청(T10)처럼 전체 회상이 필요한 턴이 있으면 윈도우는 충분히 커야 한다(MAX=2 부족, MAX=20은 10턴 전체 보존).

### Q2. "지시 대명사 해결 성공률" 프로덕션 기준

**기준: 10회 중 9회 이상(90%).** 근거: "그거 취소해주세요"가 틀린 번호로 풀리면 실제 취소 사고로 직결된다.

**이 run의 실측 한계(정직하게):**
- 인접 대명사(`/4`)는 A·B·C 모두 3/4(75%)로 메모리 크기로 안 갈렸다(T4 공통 실패) → **단일 회차 `/4`는 변별력이 약함**, 신뢰성 있는 비교엔 조건별 N회 반복이 필요.
- 변별이 생긴 곳: 전역 회상(T10) A·C ✅ / **B ❌**, 그리고 토큰 비용(B 평탄 / A 상한 / C 무제한).
- T4(메뉴) 실패는 세 조건 공통이며 원인이 *도구 미호출*

**결론 — MAX=20 권장** (너무 작은 2와 너무 큰 ∞의 가운데 균형점):

- **이유 ① 토큰에 "상한"이 있다.** 윈도우가 20이면 프롬프트에 함께 실리는 과거 대화가 **최대 20건에서 멈춘다(=상한).** 21번째 메시지가 생기면 가장 오래된 것을 버리므로, 대화가 아무리 길어져도 입력 토큰이 그 이상으로는 늘지 않는다 → 비용·응답시간이 예측 가능하다. (반대로 MAX=∞는 상한이 없어 대화가 길어질수록 토큰이 끝없이 증가한다.)
- **이유 ② 짧은 세션 전체를 담는다.** 배달 상담은 보통 5~10턴인데 10턴이면 20건이라, **한 상담 전체가 윈도우 안에 다 들어온다.** 그래서 T10 "지금까지 전부 요약"(전역 회상)도 성공했다.
- **MAX=2가 부적합한 이유** — 직전 1턴(2건)만 남아 2턴 이상 전 맥락을 잃는다 → T10 전역 회상 붕괴(1235를 통째로 잊음, §5).
- **MAX=∞가 부적합한 이유** — 토큰 상한이 없어 길어질수록 비용·지연이 무한 증가하고, 맥락이 과해지면 응답 형식까지 흔들린다(C의 T7 한·중 혼용, §6).

### Q3. 배달 상담에서 "오래된 대화"가 의미 있는 경우

| 케이스 | 설명 | Memory 요구사항 |
|--------|------|-----------------|
| 3시간 전 주문 재문의 | "아까 1234 시킨 거 아직도 안 왔어요" | 세션 수명 연장 (InMemory 불가 → JDBC) |
| 어제 환불 건 재문의 | "어제 환불 신청했는데 처리됐나요?" | 세션 간 영속성 (고객 단위 DB) |
| 재주문 패턴 참조 | "저번에 주문한 것과 같이 해주세요" | 고객 단위 장기 Memory |

**메모리 범위는 아래처럼 3단계로 넓어진다(① 세션 → ② 세션 영속 → ③ 고객 단위).** 위 케이스들은 한 상담 세션이 아니라 고객의 과거 이력을 끌어와야 하므로 **모두 가장 넓은 ③(고객 단위)을 요구** — 그래서 현재 구현(①)으로는 불가하다.

- **① 현재 = InMemory + 세션 단위 → 불가.** `InMemoryChatMemoryRepository`는 대화를 프로세스 메모리(맵)에만 보관해 **서버 재시작 시 소실**되고, `conversationId`(`X-Session-Id`)별로만 묶여 **다른 세션·다른 시점의 대화엔 접근할 수 없다.** → "어제 환불 건", "3시간 전 주문"을 애초에 못 불러온다.
- **② 3단계 JDBC 전환 → 세션 간 "영속성"까지.** 저장소를 DB로 바꾸면 대화가 디스크에 남아 재시작해도 보존되고 **같은 sessionId로 나중에 다시 꺼내 올 수 있다.** 단 이건 **세션 ID 단위** 영속성이다.
- **③ 고객 단위 장기 Memory → 별도 설계 필요.** "이 고객의 모든 이력"을 부르려면 sessionId가 아니라 **`customerId`(고객 단위)로 묶어 조회**해야 하고, 고객 식별·이력 조회 방식·**보존 기간/개인정보 정책**(Q4)을 새로 설계해야 한다. JDBC로 저장만 한다고 자동으로 되지 않는다.

### Q4. Memory를 세션이 아닌 고객 단위로 영속 유지한다면

**먼저 — "세션 단위 영속" vs "고객 단위 영속".** 영속 = 저장소(DB)에 보관해 재시작·시간 경과 후에도 남기는 것. 둘의 차이는 **대화를 묶는 키**다.

| 구분 | 세션 단위 영속(②) | 고객 단위 영속(③)                                                   |
|---|---|---------------------------------------------------------------|
| 묶는 키 | `sessionId`(=conversationId) | `customerId`(고객 ID)                                           |
| 보관 범위 | 한 번의 상담(대화) | 그 고객의 **모든 상담·이력**(여러 세션)                                     |
| 다시 왔을 때 | 같은 sessionId라야 복원, 새 세션이면 단절 | 고객만 식별되면 과거 전체 회상<br>(단골 패턴 인식, 과거 환불·취소 이력 참조, "저번과 같이" 재주문) |
| 예시 | "이 상담 중 아까 말한 1234" | "어제 환불한 거", "저번과 같이"                                          |
| 구현 | JDBC 저장소 + 키는 sessionId 그대로(3단계 숙제) | **별도 설계 필요**(아래 리스크)                                          |

####  고객 단위 영속 리스크
- 고객 단위는 단순히 `conversationId`에 `customerId`를 넣어 한 키에 다 쌓는다고 되지 않는다. 
- 그러면 **무한 누적·세션 간 오염·개인정보 영구보관** 문제가 따라오므로, 아래 기능과 리스크를 함께 설계해야 한다.
- "고객 식별 + 어떤 이력을 얼마나·어떻게 불러올지 + 보존 정책"을 따로 설계해야 한다.

| 새로운 리스크 | 설명                                     |
|--------|----------------------------------------|
| 개인정보 무제한 누적 | 주문 이력·주소·민감 패턴 영구 저장 → 개인정보보호법/GDPR 위험 |
| 세션 간 오염 | 과거 맥락이 현재 주문에 혼입 → 틀린 주문번호 참조(세션간 오염)  |
| 저장소 비용 | 고객 수 × 대화 수 × 메시지 크기                   |
| 보존 기간 정책 | 법적 보존 의무 + 파기 설계 필요                    |
