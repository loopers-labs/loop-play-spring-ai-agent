# Chat Memory 저장소 설계 결정 — InMemory vs JDBC 의사결정 트리

**목적** : stage3의 두 실측 리포트(`01`·`02`)를 **운영 판단 기준**으로 환원한다. "언제 InMemory로 충분하고, 언제 JDBC가 필요하며, 실제 운영이면 어떤 DB를 고르고 무엇을 함께 준비해야 하는가"를 조건별로 정리해 향후 저장소 선택(특히 Round 4의 PgVector 도입을 앞둔 DB 종류 선택)을 근거 있게 내릴 수 있게 한다.

> 핵심 전제 : **JDBC ≠ 영속**. 영속을 결정하는 건 JDBC 사용 여부가 아니라 **DB의 저장 모드(mem vs file)** 다. JDBC를 써도 `h2:mem`이면 InMemory와 똑같이 재시작 시 사라진다. — `02_restart_persistence_report.md`

---

## 1. 의사결정 트리

| 운영 조건 | Yes/No | 선택                            |
|---|---|-------------------------------|
| 서비스가 로드밸런서 뒤 멀티 인스턴스로 뜨는가? | Yes | **JDBC (외부 DB)**              |
| 서버 재시작 후에도 고객 대화가 이어져야 하는가? | Yes | **JDBC (file 모드 H2 / 외부 DB)** |
| 법적/감사 이유로 상담 이력을 N년 보관해야 하는가? | Yes | **JDBC (외부 DB) + 백업·보관정책**    |
| 단일 인스턴스 + 세션이 분 단위로 짧은가? | Yes | **InMemory로 충분**              |

**왜 그렇게 갈리는가**

- **멀티 인스턴스** : InMemory는 인스턴스별 프로세스 힙(Map)이다. 같은 세션 요청이 다른 인스턴스로 라우팅되면 그 인스턴스 힙엔 이력이 없어 맥락이 끊긴다. 모든 인스턴스가 같은 외부 DB를 바라봐야 세션이 공유된다.
- **재시작 유지** : `02` 리포트 실측상 **InMemory와 `h2:mem` 둘 다 재시작 시 소멸**(JVM 종료와 함께 힙/인메모리 DB가 사라짐). file 모드 H2(`./data/baedal.mv.db`)나 외부 DB만 재기동 후 복원된다.
- **N년 보관** : 휘발성 힙엔 보관 자체가 불가능하다. 외부 DB에 적재하고 백업·보관정책을 둬야 감사 대응이 된다.
- **단일·단명 세션** : 위 세 조건이 모두 No라면 운영 부담이 없는 InMemory가 가장 단순하고 빠르다.

## 2. InMemory로 충분한가, JDBC로 넘어가야 하는가

판단의 핵심 질문은 "세션이 짧은가"가 아니라 **"서버가 대화 상태의 source of truth(진실의 원본)인가"** 다. 서버가 원본이 아니면 대화가 길게 이어져도 InMemory로 충분하다. 세 축으로 본다.

- **① 대화 상태의 주인** — 클라이언트·상위 레이어·별도 저장소가 들고 있는가, 아니면 이 서버만 갖고 있는가
- **② (멀티 인스턴스라면) 세션 어피니티** — 같은 세션이 항상 같은 인스턴스로 라우팅되는가
- **③ 영속·보관 요구** — 재시작/배포 후 유지, 감사 장기보관, 서버측 이력 조회가 요구인가

### InMemory가 운영에서도 정당한 경우

프로덕션에서도 아래 중 하나에 해당하면 InMemory(또는 무저장)가 옳은 선택이다 — "PoC(개념 증명)라서"가 아니다.

1. **클라이언트/호출자가 이력 보유 (stateless 서버)** — LLM API 자체가 stateless라 매 호출에 `messages[]`를 통째로 보낸다. 클라이언트나 상위 게이트웨이가 대화를 **계속 덧붙여 재전송**하면 서버의 ChatMemory는 요청당 작업 버퍼일 뿐 — 재시작해도 잃을 게 없다.
2. **수명이 짧은 단일-run 에이전트** — 에이전트가 떠서 한 작업을 멀티턴으로 처리하고 끝난다. 메모리는 process가 아니라 **run 수명**만 넘기면 되므로 재시작 영속이 무의미하다.
3. **Sticky session(세션 어피니티)** — 멀티 인스턴스라도 LB가 세션을 한 인스턴스에 고정하면 그 대화 동안 InMemory가 그대로 동작한다. 즉 **"멀티 인스턴스 = 무조건 JDBC"가 아니다.**
4. **진실의 원본이 다른 레이어에 있음** — 이미 자체 `conversations` 테이블·이벤트 로그·분석 파이프라인에 대화를 적재 중이라면, ChatMemory는 거기서 재구성하는 **LLM 주입용 캐시**일 뿐이라 durable일 필요가 없다.
   - 대화 기록의 진짜 원본이 ChatMemory가 아니라 **다른 곳에 따로 저장된 경우**다. 화면 표시용 `conversations` 테이블, 감사·디버깅용 이벤트 로그, 상담 분석 파이프라인처럼 **다른 목적으로 이미 대화를 쌓고 있으면** 그게 source of truth가 된다.
   - 이때 ChatMemory의 역할은 "LLM 프롬프트에 넣어줄 최근 대화 토막"을 들고 있는 것뿐이다. 원본이 안전하게 따로 있으니, 서버 재시작으로 InMemory가 날아가도 **원본에서 다시 읽어 복원**하면 된다 → ChatMemory 자체는 영속일 필요가 없다.

5. **의도적 비영속(프라이버시·규제)** — "대화를 저장하지 않습니다"가 요구사항인 도메인. 휘발성이 버그가 아니라 **기능**이다.
   - **금융·법률 익명 상담** — 신원 노출 없이 채무·세금·법률을 묻는 서비스. 기록이 남으면 익명성이 깨지므로, 안 남기는 것이 신뢰의 핵심이다.
   - **프라이버시를 내세운 제품** — "당신의 대화를 저장하지 않습니다"를 차별화 기능·계약 조건으로 내거는 서비스(프라이버시 중심 AI, 기업용 "학습/보관 안 함" 보장).
   - **키오스크·공용 단말** — 매장 키오스크·공항 안내처럼 여러 사람이 번갈아 쓰는 단말. 앞 사람 대화가 남으면 안 되므로 세션 종료 시 즉시 폐기해야 한다.
6. **운영 단순성·지연** — 턴마다 DB 왕복이 없고 스키마·백업·마이그레이션 부담이 없다. 대량·저위험 어시스턴트엔 실질 이득.

> **한계** : "전부 덧붙이기" 방식은 대화가 길어질수록 **컨텍스트 윈도우 천장**에 부딪힌다(입력 토큰 무한 증가). 위 1·2가 "오래 끌지 않는" 도메인에서만 통하는 이유이고, 이 프로젝트가 `MessageWindowChatMemory(maxMessages=20)`로 윈도우를 자르는 이유다.

### JDBC로 넘어가는 신호

위 어느 것으로도 InMemory를 정당화하지 못하고, 아래 중 하나라도 참이면 JDBC(+영속 백엔드)로 전환한다.

- **서버가 유일한 원본인데 재시작·배포 후에도 대화가 이어져야 함** — 어피니티가 있어도 그 인스턴스가 죽으면 잃는다. → file 모드 H2 / 외부 DB (`h2:mem`은 안 됨 — `02` 리포트)
- **멀티 인스턴스 + 어피니티 없음** — 세션을 인스턴스 간 공유해야 함 → 공유 외부 DB
- **감사·규제 장기보관 또는 서버측 이력 조회·분석 필요** — `GET /session/{id}/messages`, `GET /session/ids` 등 → 외부 DB + 백업·보관정책

> 현재 dev 기본 프로필(`InMemoryChatMemoryRepository`, `MAX_MESSAGES=20`)은 위 신호가 모두 없는 구간이다.

## 3. 실제 운영이라면 어떤 DB? — **PostgreSQL**

후보(PostgreSQL / MySQL / Redis / DynamoDB) 중 **PostgreSQL**을 선택한다.

**근거**

- **① Round 4 PgVector와의 단일화 (핵심)** — Round 4에서 RAG를 위해 **PgVector**(PostgreSQL 벡터 확장)를 띄운다. Chat Memory와 Vector Store를 **같은 Postgres 인스턴스**가 담당하면 운영 DB 종류가 하나로 통일된다 → 백업·모니터링·접근통제·운영 노하우를 일원화할 수 있다. 굳이 종류가 다른 DB를 둘 운영할 이유가 없다.
- **② 스키마가 명확해 마이그레이션이 쉬움** — Spring AI `JdbcChatMemoryRepository`가 기대하는 `SPRING_AI_CHAT_MEMORY` 스키마(`schema-postgresql.sql`)가 정해져 있고, `01` 리포트에서 H2를 `MODE=PostgreSQL` + `platform: postgresql`로 띄워 검증한 것과 같다. 단, **운영에선 `initialize-schema`로 자동 생성하지 않는다** — `never`로 끄고 **Flyway/Liquibase 버전 마이그레이션**으로 관리한다(런타임 DB 계정엔 DDL 권한 미부여, 인덱스·파티셔닝은 직접 소유). 즉 번들 스크립트는 *자동 적용용*이 아니라 **마이그레이션 baseline 참고용**이다. ※ `MODE=PostgreSQL`은 흉내일 뿐 동시성·성능까지 보장하지 않으므로, 전환 전 **실 Postgres 통합 테스트(예: Testcontainers)** 가 필요하다.

**탈락 근거 (비교)**

| 후보 | 판정 | 이유 |
|---|---|---|
| PostgreSQL | ✅ 선택 | PgVector로 Chat Memory + RAG 단일 DB, Spring AI 기본 스키마 일치 |
| MySQL | ❌ | 관계형은 충분하나 벡터 확장이 약해 Round 4 RAG와 시너지가 없음 |
| Redis | ❌ | TTL·고속 접근엔 강하나 휘발 캐시 성격 — N년 보관·감사·복잡 쿼리에 부적합 |
| DynamoDB | ❌ | 관리형 KV/문서. 자체 호스팅 PgVector·관계형 쿼리와 결이 안 맞고 RAG 통합 이점 없음 |

## 4. JDBC 도입 시 동시에 고려할 비기능 요구사항 — 3가지

1. **백업·복구** — 영속의 실질 전제다. file H2(`./data/baedal.mv.db`)든 외부 DB든 **정기 백업 + 시점 복구(PITR)** 가 없으면 "파일에 남는다"는 사실만으로는 장애에 무력하다. `02` 리포트가 말한 "진짜 영속"은 백업까지 포함해야 성립한다.
2. **인덱스 + 보관정책(TTL/파티셔닝)** — `SPRING_AI_CHAT_MEMORY` 테이블은 **행이 무한 증가**한다(`01` 리포트: *"저장소 보존량 ≠ 컨텍스트 주입량"* — 테이블엔 계속 쌓이지만 `MessageWindowChatMemory(maxMessages=20)`는 최근 20개만 주입). 따라서 `conversation_id` + `timestamp` 조회용 **복합 인덱스**로 조회 성능을 지키고, **TTL 또는 파티셔닝**으로 테이블 비대화를 막아야 한다. 감사 보관기간과 충돌하면 오래된 파티션을 아카이브로 분리한다.
3. **저장 암호화·접근통제** — 대화엔 **개인정보(주문번호·배달 위치)** 가 평문으로 적재된다(부록 H2 콘솔 덤프 참고 — `01`/`02`). 저장 시 암호화(at-rest) + 관리 엔드포인트(`GET /session/ids`, `DELETE /session/{id}`) 인가가 필요하다. 이는 stage1 설계 결정 리포트의 IDOR·세션 식별 보안 분석과 직접 연결된다.

> **스키마 마이그레이션(Flyway/Liquibase)** — 운영에선 Spring AI의 `initialize-schema` 자동 DDL을 끄고(`never`) 버전 마이그레이션으로 스키마를 관리한다. 번들 `schema-postgresql.sql`은 첫 마이그레이션의 baseline으로 가져오고, 이후 인덱스·파티셔닝 변경도 모두 마이그레이션으로 추적한다(런타임 계정엔 DDL 권한 미부여).

## 5. 종합

- 지금의 **학습/개발 단계는 InMemory로 충분**하다(단일 인스턴스·유실 허용·보관 불요).
- 그러나 **멀티 인스턴스 · 재시작 후 대화 유지 · 감사 보관** 중 하나라도 들어오는 순간 JDBC가 필요하고, 그때 **file 모드/외부 DB라야 실제로 영속**된다.
- Round 4의 RAG(PgVector)까지 내다보면 **종착지는 외부 PostgreSQL** 이다 — Chat Memory와 Vector Store를 한 DB로 묶고, 백업·인덱스/보관정책·암호화를 함께 갖춘다.
