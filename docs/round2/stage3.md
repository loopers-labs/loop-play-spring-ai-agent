# 3단계: Tool description 실험 — LLM이 Tool을 안 부르게 만들기

**목표**: `description`이 LLM에게 보여주는 유일한 API 문서임을 정량적으로 체감한다.

## 실험 설계

`OrderTools.getDeliveryStatus`의 `description`을 3가지 버전으로 바꿔가며, 같은 질문을 5회씩 호출한다.

질문: `"주문번호 2024-1234 배달 어디쯤이에요?"`

| 버전 | description |
|---|---|
| A (기준) | 현재 코드 — 4줄 |
| B (빈약) | `"배달 정보 조회"` 한 줄만 |
| C (오해 유발) | `"주문번호 조회용. 메뉴와 결제 금액만 반환한다."` |

```bash
curl -s -X POST http://localhost:8080/api/v1/assistant \
  -H "Content-Type: application/json" \
  -d '{"message":"주문번호 2024-1234 배달 어디쯤이에요?"}'
```

## 설계 결정 문서

### 버전 C에서 LLM이 어떤 행동을 했는가?

예상과 달리 `getDeliveryStatus`를 5/5 모두 호출했다. `getOrderDetail`로 전환되지도 않았고 hallucination도 없었다. "역삼역 사거리"가 5번 모두 응답에 포함됐다.

description이 "메뉴와 결제 금액만 반환한다"고 써있음에도 Tool이 정상 실행된 이유는, 모델이 함수명 `getDeliveryStatus`에서 의미를 읽었기 때문으로 보인다. "배달 어디쯤이에요?"라는 질문과 `getDeliveryStatus`라는 이름이 충분히 매칭됐다. description보다 함수명이 Tool 선택에 더 강한 신호를 준 것이다.

다만 응답 1번에서 "8시 28분 46총체간에 있습니다"라는 깨진 출력이 나왔다. 잘못된 description이 Tool 선택에는 영향을 못 미쳤지만, 응답 생성 품질에는 영향을 준 것으로 보인다.

---

### description 작성 시 반드시 포함해야 할 항목 4가지 (중요도 순)

실험 결과를 보면 qwen2.5는 함수명이 명확할 때 description 없이도 Tool을 고른다. description이 빛을 발하는 건 "어떤 Tool을 골라야 할지 판단이 필요할 때"다. 그 관점에서 중요도 순으로,

1. **언제 호출하는가 (호출 조건)** — 비슷한 기능의 Tool이 여러 개일 때 어떤 걸 골라야 하는지 구분하는 기준. 이게 없으면 모델이 함수명에 의존한다. 함수명이 불명확할수록 이 항목이 결정적이다.

2. **실패 시 어떤 값을 반환하는가** — null인지, 에러 메시지인지, ALREADY_CANCELED 같은 enum인지. LLM이 Tool 결과를 받았을 때 어떻게 해석해야 할지 알 수 없으면 hallucination이 생긴다.

3. **무엇을 하는가** — 기본 중의 기본이지만 함수명으로 이미 어느 정도 전달되는 경우가 많다. 함수명이 동사+명사 구조로 명확하면 이 항목의 비중이 줄어든다.

4. **입력 파라미터 형식** — `@ToolParam`의 description이 이미 담당하지만, 특수한 형식(예: YYYY-XXXX)이나 제약이 있으면 `@Tool` description에도 명시하는 게 좋다. 잘못된 형식으로 Tool이 호출되면 null 반환 → LLM hallucination으로 이어진다.

---

### description이 실제 Tool 동작과 어긋나게 되는 상황을 프로덕션에서 막는 방법

description은 코드와 같은 파일에 있지만 컴파일러가 일치 여부를 검증하지 않는다. 그래서 코드는 바뀌는데 description은 그대로 남는 일이 생긴다.

방법은 세 층으로 생각해볼 수 있다.

**테스트 층**: LLM을 포함한 E2E 테스트를 돌린다. "주문번호 2024-1236 취소해주세요" → `cancelOrder` 호출 확인 같은 시나리오를 자동화한다. description이 잘못되면 Tool이 잘못 선택되거나 안 불리니까 테스트가 깨진다.

**리뷰 층**: PR에서 Tool 메서드 시그니처나 반환 타입이 바뀌면 description도 같이 업데이트됐는지 확인한다. "코드 변경 = description 변경 검토" 규칙을 팀 컨벤션으로 만든다.

**계약 층**: Consumer-Driven Contract Test처럼 LLM이 기대하는 Tool 동작을 명세로 관리한다. description이 그 명세와 다르면 CI에서 잡힌다. 아직 이 분야는 표준이 없어서 직접 만들어야 하지만, Tool이 많아지면 투자할 만하다.

## 회고

---

### 회고 1 — 실험이 예상대로 안 됐다

버전 C에서 "메뉴와 결제 금액만 반환한다"고 description을 써도 `getDeliveryStatus`가 5/5 호출됐다. 예상은 `getOrderDetail`으로 전환되거나 hallucination이 생기는 것이었다.

이게 의미하는 건 qwen2.5가 이 상황에서 description보다 함수명에 더 강하게 반응한다는 것이다. "배달 어디쯤이에요?"라는 질문과 `getDeliveryStatus`라는 이름이 충분히 매칭됐다. description이 일치 여부를 무력화했다.

실험이 예상대로 안 됐다고 해서 실험이 무의미한 게 아니다. description이 결정적이지 않은 조건이 어떤 건지 알게 됐다. 함수명이 명확하고 질문이 직접적일 때 description의 영향이 작다는 게 이번 실험의 결론이다.

---

### 회고 2 — 깨진 응답이 하나 나왔다

버전 C 응답 1번: "8시 28분 46총체간에 있습니다".

Tool은 정상 실행됐고 데이터도 정상이다. 그런데 LLM이 응답을 만들 때 글자가 깨졌다. description이 "메뉴와 결제 금액만 반환한다"고 하는데 실제 Tool이 배달 상태를 돌려주니, 모델이 예상한 context와 실제 결과가 달라서 생긴 혼란으로 보인다.

Tool 선택은 함수명이 감당했는데, 응답 생성은 description의 영향을 받았다. 잘못된 description이 영향을 안 준다고 말할 수 없다는 걸 이 하나의 깨진 응답이 보여줬다.

---

### 회고 3 — description이 중요한 건 Tool이 여러 개일 때다

이번 실험에서 Tool이 3개(`getOrderDetail`, `getDeliveryStatus`, `cancelOrder`)였다. 질문이 "배달 어디쯤"으로 명확했고, 그걸 담당할 Tool도 이름에서 명확했다.

만약 함수명이 `executeQuery1`, `executeQuery2`처럼 추상적이었다면 description이 유일한 단서가 됐을 것이다. 또는 "주문 현황이 어떻게 돼요?"처럼 `getOrderDetail`과 `getDeliveryStatus` 중 어느 쪽인지 애매한 질문이었다면 description의 "언제 호출하는가" 항목이 결정적인 역할을 했을 것이다.

description은 항상 중요하지만, 그게 결정적으로 드러나는 건 함수명이 모호하거나 유사한 Tool이 여러 개 있을 때인 것 같다.

## 추가 실험: 모호한 질문에서 description의 역할

### 실험 설계

질문: `"주문 2024-1234 상황이 어떻게 됐어요?"`

"상황"은 `getOrderDetail`(주문 상태)과 `getDeliveryStatus`(배달 현황) 둘 다에 연결될 수 있다. 이 모호한 질문으로 description의 "언제 호출하는가" 항목이 실제로 Tool 선택을 가르는지 확인했다.

| 버전 | `getOrderDetail` description | `getDeliveryStatus` description |
|---|---|---|
| A (기준) | `"고객이 주문 메뉴, 금액, 현재 상태를 물을 때 호출합니다."` 포함 4줄 | `"고객이 배달 진행 상황이나 라이더 위치를 물을 때 호출합니다."` 포함 4줄 |
| B (최소) | `"주문 정보 조회"` 한 줄 | `"배달 정보 조회"` 한 줄 |

### 추가 실험 결론

**description의 "언제 호출하는가" 항목이 모호한 질문에서 Tool 선택을 가른다.**

버전 A: `getOrderDetail` description "주문 메뉴, 금액, 현재 상태를 물을 때"가 "상황이 어떻게 됐어요?"와 매칭 → 5/5 일관.

버전 B: 두 Tool 모두 한 줄 description. "상황"이 어느 함수명과 가까운지 단서가 부족 → 4:1로 분기.

버전 C: `getDeliveryStatus` description이 "메뉴와 결제 금액만 반환한다"(오해 유발), `getOrderDetail` description은 그대로 → `getOrderDetail` 5/5. 모델은 두 description을 읽고 "상황이 어떻게 됐어요?"와 비교한다. `getDeliveryStatus`는 "메뉴와 결제 금액" 얘기뿐이라 질문과 맞지 않는다. `getOrderDetail`은 "현재 상태를 물을 때 호출한다"고 써있어 "상황"과 맞는다. `getOrderDetail`이 선택됐다.

**버전 C에서 응답이 깨지지 않았다.** 원본 실험(직접 질문) Version C에서 "8시 28분 46총체간에 있습니다" 같은 깨진 응답이 나왔던 것과 대조된다. 원본에서는 실제 호출된 Tool(`getDeliveryStatus`)의 description이 결과와 달라서 모델이 혼란했다. 이번에는 실제 호출된 Tool(`getOrderDetail`)의 description이 정확했다.

**원본 실험 버전 C와의 대조**: 직접 질문("배달 어디쯤")에서는 함수명 `getDeliveryStatus`가 description을 눌렀다. 모호한 질문에서는 잘못된 description이 함수명을 눌렀다. 질문의 명확성이 어느 신호가 우선하는지를 결정했다.

### 회고 4 — description이 결정적인 조건

회고 1에서 "description이 결정적이지 않은 조건이 어떤 건지 알게 됐다"고 썼다. 이번 실험에서 그 반대편을 봤다.

질문이 모호할 때 ("상황이 어떻게 됐어요?"처럼 여러 Tool이 답할 수 있을 때) description의 "언제 호출하는가" 항목이 일관된 Tool 선택을 만들었다. 없으면 흔들렸다(버전 B 4:1). 잘못 쓰면 그 Tool을 선택지에서 제거하는 방향으로 작동했다.

프로덕션에서 사용자는 "배달 어디쯤이에요?"처럼 명확하게 묻지 않는다. "지금 어떻게 돼요?", "상황 알려줘", "확인해줘"처럼 모호하게 묻는다. 그 질문들이 오는 상황에서 "언제 호출하는가"가 없으면 Tool 선택이 비결정적이 되고, 잘못 쓰면 엉뚱한 Tool을 막아버린다.
