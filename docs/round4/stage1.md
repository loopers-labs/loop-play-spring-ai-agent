**요청**

## 설계 결정 문서

### 왜 청크 크기 800 / min 350인가?

배달 정책 문서는 조항 단위로 이미 짧게 쪼개져 있다. 실제로 7개 문서 모두 청크가 1개씩 나왔다. 각 문서가 하나의 정책 주제(취소 정책, 쿠폰 FAQ 등)만 다루기 때문에 800토큰이면 문서 전체가 하나의 청크에 들어간다.

청크 크기를 더 작게(예를 들면 200) 잡으면 정책 조항 하나가 두 청크로 쪼개져 "예상 시간 +" 같이 수치가 잘리는 문제가 생긴다(2단계에서 실험). 더 크게(예: 2000) 잡으면 이미 짧은 문서에서 의미 있는 차이가 없고, 다른 주제 문서를 다룰 때 여러 주제가 한 청크에 묶여 유사도가 뭉툭해진다.

**다른 도메인이라면**: 블로그 글이나 장문 PDF처럼 하나의 문서가 여러 주제를 다루는 경우, 청크를 더 작게(200~400) 잡아 주제 단위로 분리해야 검색 정확도가 올라간다. 사용자 리뷰처럼 한 문장이 독립된 의견인 경우, 문장 단위 분할이 더 효과적이다.

### 왜 Top-K = 4인가?

정책 문서가 총 7건인 상황에서:

#### 실험 결과

질문: `"비 오는 날 배달이 늦으면 보상 받을 수 있나요?"` (weather-delay + delay-compensation 두 정책이 모두 필요한 복합 질문)

| Top-K | 입력 토큰 | weather-delay 포함 | delay-compensation 포함 | 답변 품질 |
|---|---|---|---|---|
| 1 | 1903 | ✅ (기상 특보 언급) | ❌ (보상 수치 없음) | 애매 |
| 4 | 2336 | ✅ (기상 특보 + 앱 안내 언급) | △ (구체 수치 미포함) | 애매 |
| 10 | 2336 | ✅ (기상 특보 + 앱 안내 언급) | △ (구체 수치 미포함) | 애매 |

**TOP_K=1 전체 응답**

```
비 오는 날 자체만으로 배달이 늦어도 보상 대상이 되지 않을 수 있습니다. 기상 특보 여부를 확인해야 합니다. 현재 주문의 예상 배송 시간과 실제 도착 시간을 알려주시면, 그에 따른 보상을 안내해 드리겠습니다.

주문번호를 알려주시겠어요?
```

로그: `입력 토큰: 1903 | 출력 토큰: 79`

> `weather-delay`와 `delay-compensation` 중 하나만 Top-1에 올라왔다. "기상 특보 여부"는 언급됐지만 "예상 시간 + 30분", 쿠폰 지급 같은 보상 수치는 없다. 복합 정책 질문에서 Top-K=1은 반쪽짜리 답변만 생성한다.

---

**TOP_K=4 전체 응답**

```
비 오는 날 자체만으로 배달이 늦어졌다고 보상 받을 수 있는 것은 아닙니다. 기상 특보가 발효되었는지 여부를 확인해야 합니다.

주문 시점에 기상 특보가 있으면 앱에서 안내 메시지가 노출되며, 이를 확인하고 주문한 경우 지연을 감안한 것으로 간주됩니다.

어떤 주문과 관련하여 보상을 문의하시는 건가요? 주문번호를 알려주시겠어요?
```

로그: `입력 토큰: 2336 | 출력 토큰: 115`

> TOP_K=1(1903) 대비 입력 토큰 +433. `weather-delay` + `delay-compensation` 두 문서가 모두 주입됐다. "앱에서 안내 메시지 노출", "지연을 감안한 것으로 간주" 같은 세부 조건이 추가됐지만 "예상 시간 + 30분" 같은 구체적 보상 수치는 응답에 없다. Context에는 수치가 있었지만 LLM이 요약 응답에서 생략했다. [정책 인용 규칙]에 "수치는 원문 그대로 인용"이 명시되지 않아서 생긴 결과다.

#### 분석

| Top-K | 결과 |
|---|---|
| 1 | 복합 질문("기상 지연 + 보상")에서 하나의 정책만 들어와 보상 수치를 놓침. 입력 토큰 1903 |
| **4** | 2336 토큰. threshold=0.5를 통과하는 문서를 모두 커버. 커버리지와 토큰 비용의 균형점 |
| 10 | 2336 토큰. 4와 동일. 문서가 7건뿐이라 threshold=0.5를 통과하는 문서 수가 TOP_K=10보다 적어 상한이 먼저 걸림 |

TOP_K=4와 TOP_K=10의 입력 토큰이 2336으로 동일하다. 전체 문서 7건 중 threshold=0.5를 통과하는 문서 수가 10보다 적기 때문에 TOP_K를 높여도 실제 주입되는 Context는 늘지 않았다. 소규모 도메인에서 실질적인 상한은 TOP_K가 아니라 `similarityThreshold`가 결정한다. 문서가 수천 건으로 늘어나면 그때부터 TOP_K 조정이 의미를 갖는다. 지금 설정에서는 threshold=0.5가 사실상 TOP_K 역할을 겸한다.

**TOP_K=10 전체 응답**

```
비 오는 날 자체만으로는 보상 대상이 되지 않습니다. 기상 특보가 발효되었는지 여부와 실제 배달 시간을 확인해야 합니다. 주문 시점에 기상 특보가 있는 경우 앱에서 안내 메시지가 노출됩니다.

어떤 주문의 배송 상태를 확인하시겠어요?
```

로그: `입력 토큰: 2336 | 출력 토큰: 80`

### 왜 `QuestionAnswerAdvisor.order(20)`인가?

Advisor 실행 순서: `memoryAdvisor(10) → ragAdvisor(20) → performanceAdvisor(100)`

시나리오 5가 이 순서의 근거를 직접 보여준다.

2턴에서 사용자가 "아까 그 주문 환불 돼요?"라고 물었다. 이 시점의 원문 질문에는 주문번호가 없다.

- **Memory(10)가 먼저 실행**: 이전 대화 이력을 프롬프트에 주입 → 프롬프트 안에 "주문번호 2024-1234"가 복원됨
- **RAG(20)가 그 다음 실행**: 복원된 질문("2024-1234, 환불")을 임베딩해 `refund-basic`, `refund-after-delivered` 문서를 검색 → 정확한 환불 정책이 Context에 주입됨

순서가 뒤바뀌면(`ragAdvisor(5) → memoryAdvisor(10)`):
- RAG가 먼저 "아까 그 주문 환불 돼요?"를 원문 그대로 임베딩 → "그 주문"이 무엇인지 알 수 없어 관련 없는 정책이 검색됨
- Memory가 나중에 붙여봤자 RAG Context는 이미 잘못된 문서로 채워져 있음

### `similarityThreshold = 0.5`의 근거

`qwen3-embedding:0.6b` 기준 코사인 유사도 0.5는 대략 "같은 주제 도메인에 속하는 정도"를 의미한다.

#### 실험 결과

질문 A (도메인 내): `"결제 후 바로 취소하면 환불되나요?"`
질문 B (도메인 밖): `"오늘 점심 뭐 먹을까요?"`

| threshold | 질문 A 입력 토큰 | 질문 A 응답 품질 | 질문 B 입력 토큰 | 질문 B Fallback 출력 |
|---|---|---|---|---|
| 0.3 | 3181 | 만족 (CREATED/ACCEPTED 조건 원문 포함) | 1455 | ✅ |
| 0.5 | 1886 | 만족 (조리 시작 전 조건 포함) | 1455 | ✅ |
| 0.8 | 1457 | 불만족 (Fallback만 출력) | 1455 | ✅ |

---

**threshold = 0.3 — 전체 응답**

질문 A:
```
결제 후 바로 취소하면 전액 환불이 가능하지만, 주문 상태가 조리 시작 전인 CREATED 또는 ACCEPTED여야 합니다. "그거"의 주문상태를 알려주시겠어요?

주문 상태와 함께 주문번호를 말씀해주시면 정확한 답변을 드릴 수 있습니다.
```

질문 B:
```
배달 서비스 관련 문의만 도와드릴 수 있습니다. 다른 도움이 필요하신가요?
```

로그: 질문 A `입력 토큰: 3181 | 출력 토큰: 75` / 질문 B `입력 토큰: 1455 | 출력 토큰: 24`

**threshold = 0.5 — 전체 응답**

주문을 결제 후 즉시 취소하면 전액 환불이 가능합니다. 하지만 주문 상태가 이미 조리 시작 이후라면 단순 변심으로 인한 환불은 어려울 수 있습니다.

어떤 주문을 말씀하시는 건가요? 그 주문의 현재 상태를 알려주시겠어요?

주문번호를 알려주시면 정확한 상황을 확인할 수 있을 것 같습니다.
```

```

질문 B:
```
배달 서비스 관련 문의만 도와드릴 수 있습니다. 다른 도움이 필요하신가요?
```

로그: 질문 A `입력 토큰: 1457 | 출력 토큰: 54` / 질문 B `입력 토큰: 1455 | 출력 토큰: 24`

#### 분석

| threshold | 문제 |
|---|---|
| 너무 낮음(0.3) | 도메인 내 입력 토큰 3181로 폭증. 낮은 유사도 문서까지 Context에 포함되어 토큰 낭비. `[정책 인용 규칙]`이 없었다면 그 문서를 근거로 환각 생성 위험 |
| **0.5** | 도메인 내 1886 토큰으로 효율적. 정책 원문 조건(조리 시작 전/후) 정확히 반영. 도메인 밖은 Context 최소화 + Fallback |
| 너무 높음(0.8) | 도메인 내 질문에서도 `cancel-policy` 문서가 임계값을 넘지 못해 Context가 비었다. 입력 토큰 1457로 도메인 밖(1455)과 거의 같아졌고, `[정책 인용 규칙]`의 Fallback 문구("고객센터(1588-0000)")가 출력됐다. 정책을 알고 있는데도 못 쓰는 상태 |

**도메인 밖 질문의 입력 토큰(1455)이 세 실험 모두 동일한 이유**: "오늘 점심 뭐 먹을까요?"의 임베딩은 어떤 임계값에서도 정책 문서와 유사도 차이가 없었다. threshold가 0.3으로 내려가도 음식 추천 질문의 코사인 유사도는 배달 정책 문서와 본질적으로 멀기 때문에 Context가 주입되지 않았다.

**threshold=0.8이 도메인 내 질문에서 실패하는 구체적 이유**: `qwen3-embedding:0.6b`의 코사인 유사도 0.8은 "거의 동일한 문장" 수준을 요구한다. "결제 후 바로 취소하면 환불되나요?"라는 질문과 `cancel-policy` 문서 임베딩의 유사도가 0.5~0.7 구간에 있어 0.8 임계값에서 걸린다. 정책 내용을 알고 있는 문서가 Context에서 통째로 배제돼 Fallback 문구가 나오는 상황이 생긴다. 임계값이 너무 높으면 정보를 쓸 수 없는 모순이 발생한다.

threshold 하나로 환각을 막을 수 없다. 0.3에서 도메인 밖 질문에도 Context가 주입됐지만 `[정책 인용 규칙]`이 2중 방어했다. 0.8에서 `[정책 인용 규칙]`이 없었다면 LLM이 학습 지식으로 틀린 환불 정보를 지어냈을 것이다. threshold와 `[정책 인용 규칙]` 두 장치가 모두 필요하다.
