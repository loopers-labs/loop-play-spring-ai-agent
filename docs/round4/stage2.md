# 2단계: 청킹 전략 실험 + 실패 관찰

## 실험 설정

각 실험 전 PgVector를 초기화한다.

```bash
docker exec -it baedal-pgvector psql -U baedal -d baedal -c "TRUNCATE TABLE vector_store;"
```

앱 재기동 후 `KnowledgeLoader`가 새 설정으로 재적재.

| 실험 | chunkSize | minChunkSizeChars | 목적 |
|---|---|---|---|
| A | 800 (기준) | 350 | 정상 케이스 |
| B | 100 (극단적으로 작게) | 40 | 문맥 조각남 관찰 |
| C | 2000 (크게) | 800 | 유사도 뭉툭 + 토큰 낭비 관찰 |

동일 질문 5종:
1. "비 오는 날 배달이 늦으면 보상 받을 수 있나요?"
2. "결제 후 바로 취소하면 환불되나요?"
3. "쿠폰 중복 사용되나요?"
4. "배달 완료 후에도 환불 받을 수 있나요?"
5. "오늘 점심 뭐 먹을까요?" (도메인 밖 — Fallback 기대)

| 질문 | 입력 토큰 | 출력 토큰 | 답변 품질 |

| **평균** | **1972** | | |

질문 1:
```
비 오는 날 자체만으로 배달이 늦어졌다고 보상 받을 수 있는 것은 아닙니다. 기상 특보가 발효되었는지 여부를 확인해야 합니다. 현재 배달 지연 보상 정책은 예상 시간과 실제 배달 시간의 차이, 그리고 기상 특보 여부에 따라 달라집니다.

```

질문 2:
```
주문 상태와 배달 상황에 따라 환불이 달라질 수 있습니다. 결제 후 바로 취소할 경우, 조리가 시작되지 않은 상태라면 전액 환불 가능하지만, 이미 음식을 준비하고 있다면 불가능합니다. 어떤 주문을 말씀하시는 건가요?
```

질문 3:
```
쿠폰 중복 사용은 일반적으로 불가능합니다. 예를 들어, 두 개의 할인 쿠폰을 같은 주문에 동시에 적용할 수 없습니다. 하지만 프로모션 쿠폰과 일반 쿠폰의 경우 쿠폰마다 다르게 적용될 수 있으므로, 해당 쿠폰 상세를 확인해주세요.
```

```
배달 완료 후에도 특정 사유에 따라 환불이 가능합니다. 주문한 메뉴 중 일부가 누락되었거나 품질 문제가 있는 경우에는 환불을 신청할 수 있습니다.

어떤 사유로 환불을 원하시는지 알려주시겠어요? 예를 들어, 메뉴 누락이나 품질 불량 등이 있으면 말씀해 주세요.
```

질문 5:
```
배달 서비스 관련 문의만 도와드릴 수 있습니다. 다른 도움이 필요하신가요?
```

## 실험 B (chunkSize=100) 상세

**기동 로그**: `신규 7건 / 스킵 0건` — 7개 문서가 49개 청크로 분할

```
privacy: 6개 / cancel-policy: 7개 / coupon-faq: 6개 / delay-compensation: 7개
weather-delay: 8개 / refund-after-delivered: 7개 / refund-basic: 8개 = 총 49개
```

> SELECT count(\*) = 6은 적재 진행 중 스냅샷(privacy 6개만 커밋된 시점). 최종 row 수 49는 KnowledgeLoader 로그의 문서별 청크 수를 합산한 값이다(6+7+6+7+8+7+8=49). "신규 7건 / 스킵 0건"이 찍혔으므로 모든 청크가 적재됐다.

| 질문 | 입력 토큰 | 출력 토큰 | 답변 품질 |
|---|---|---|---|
| 1. 비 오는 날 배달 지연 보상 | 1660 | 67 | 애매 |
| 2. 결제 후 취소 환불 | 1666 | 60 | 만족 |
| 3. 쿠폰 중복 | 1712 | 66 | 만족 |
| 4. 배달 완료 후 환불 | 1685 | 73 | 만족 |
| 5. 오늘 점심 (도메인 밖) | 1455 | 24 | ✅ Fallback |
| **평균** | **1636** | | |

**전체 응답**

질문 1:
```
비 오는 날 배달이 늦어졌을 때 보상은 기상 특보 여부와 실제 지연 시간을 기준으로 결정됩니다. 정확한 지연 시간을 확인해주시면 더 자세히 안내드릴 수 있습니다.

주문번호를 알려주시겠어요?
```

질문 2:
```
주문 상태가 CREATED 또는 ACCEPTED인 경우 결제 후 즉시 취소해도 전액 환불이 가능합니다. 현재 어떤 주문을 말씀하시는 건가요? 그 주문의 상태를 확인한 뒤, 다음 단계를 제안하겠습니다.
```

질문 3:
```
쿠폰 중복 사용은 제한이 있습니다. 할인 쿠폰과 배달비 쿠폰을 함께 사용할 수 있지만, 할인 쿠폰만 여러 장을 사용하는 것은 불가능합니다.

다른 질문이 있으시면 알려주세요!
```

질문 4:
```
배달이 완료된 상태에서도 단순 맛 불만족은 환불 대상이 아니지만, 음식 누락이나 오배송 등 특정 사유로는 환불을 요청할 수 있습니다.

어떤 사유로 환불을 원하시는지 말씀해 주실 수 있나요?
```

질문 5:
```
배달 서비스 관련 문의만 도와드릴 수 있습니다. 다른 도움이 필요하신가요?
```

질문 1의 입력 토큰이 1660으로 실험 A(2336)보다 676 낮다. `weather-delay` 문서가 chunkSize=100으로 8개 청크로 분할됐고, "기상 특보 조건"을 담은 청크는 유사도 상위권에 올라왔지만 "예상 시간 + 30분", 쿠폰 지급 조건이 담긴 청크는 유사도 순위에서 밀려 Top-K=4 안에 들지 못했다. 조각난 청크들은 개별 임베딩 품질은 유지하지만 어떤 4개를 가져오는지가 유사도 순위에 달려 있어, 정책 전체를 담보할 수 없다. 응답이 "기상 특보 여부와 실제 지연 시간을 기준으로 결정됩니다"로 뭉개진 표현에 그친 직접 원인이다.

## 실험 C (chunkSize=2000) 상세

**기동 로그**: `신규 7건 / 스킵 0건` — 7개 문서 각각 청크 **1개** (실험 A와 동일)

> chunkSize=2000이어도 배달 정책 문서들이 모두 2000 토큰 미만이라 분할이 일어나지 않았다. row 수 7 = 실험 A와 동일.

| 질문 | 입력 토큰 | 출력 토큰 | 답변 품질 |
|---|---|---|---|
| 1. 비 오는 날 배달 지연 보상 | 2336 | 126 | 만족 (중국어 혼입) |
| 2. 결제 후 취소 환불 | 1886 | 78 | 만족 |
| 3. 쿠폰 중복 | 1875 | 83 | 만족 |
| 4. 배달 완료 후 환불 | 2310 | 90 | 만족 |
| 5. 오늘 점심 (도메인 밖) | 1455 | 24 | ✅ Fallback |
| **평균** | **1972** | | |

**전체 응답**

질문 1 (중국어 혼입):
```
비 오는 날 배달이 늦어졌을 때 보상 받을 수 있는지에 대해 답변 드리겠습니다.

1. 비가 오더라도 기상 특보 여부와 실제 지연 시간을 확인해야 합니다.
2. 예상 시간보다 60분 이상 지연된 경우 전액 환불 검토 대상이 됩니다.

具体的来说，如果订单延迟超过预计时间60分钟以上，可以考虑全额退款。但需要确认是否有气象预警以及实际延迟时间，请提供订单号以便进一步查询。

주문번호를 알려주시겠어요?
```

질문 2:
```
주문 상태가 CREATED 또는 ACCEPTED인 경우 결제 후 바로 취소해도 전액 환불이 가능합니다. 하지만 주문 상태가 이미 조리 시작 이후라면 단순 변심으로는 환불이 어려울 수 있습니다.

어떤 주문을 말씀하시는 건가요? 그 주문의 현재 상태를 알려주시겠어요?
```

질문 3:
```
쿠폰 중복 사용은 프로모션 쿠폰과 일반 쿠폰의 경우 가능하지 않습니다. 하지만 할인 쿠폰과 배달비 쿠폰을 함께 사용할 수 있습니다.

어떤 쿠폰이 중복 사용 가능한지 확인하시려면 주문 상세 정보를 알려주시겠어요?
```

질문 4:
```
배달 완료 후에도 특정 사유에 따라 환불이 가능합니다. 주문한 메뉴가 누락되었거나 품질 문제가 있는 경우 환불을 신청할 수 있습니다.

어떤 사유로 환불을 요청하시려나요? 예를 들어, 메뉴가 누락되었거나 품질 문제로 인해 불만이 있으시다면 알려주세요.
```

질문 5:
```
배달 서비스 관련 문의만 도와드릴 수 있습니다. 다른 도움이 필요하신가요?
```

질문 1 응답에 중국어 문단이 섞였다. qwen2.5는 중국어 사전학습 비중이 높은 모델이다. 장문의 한국어 Context를 처리하다가 언어 생성이 중국어로 전환됐다. 내용은 맞지만("60분 이상 지연 시 전액 환불 검토") 언어가 틀렸다. chunkSize=2000이 혼입의 직접 원인은 아니지만, Context 텍스트 양이 많아질수록 이 모델에서 언어 혼입 트리거 가능성이 높아진다. 프로덕션에서는 언어 고정 지시를 시스템 프롬프트에 명시해야 한다.

입력 토큰이 실험 A와 완전히 동일(1972). 배달 정책 문서들이 모두 2000 토큰 미만이라 chunkSize=2000을 설정해도 청크 수와 Context 내용이 바뀌지 않았다. "유사도 뭉툭" 효과는 하나의 문서 안에 여러 주제가 섞여 실제로 분할이 일어날 때만 관찰된다. 데이터 특성 파악 없이 청크 크기를 올리는 것은 무의미하다.

## 실패 관찰 — 청크가 너무 작을 때 (실험 B, chunkSize=100)

> Spring AI 1.0의 `QuestionAnswerAdvisor`는 주입한 Context 원문을 DEBUG 로그에 별도로 출력하지 않는다. Context 블록은 토큰 차이(실험 A 2336 vs 실험 B 1660, -676)와 응답 내용 비교로 간접 확인한다.

**질문**: "비 오는 날 배달이 늦으면 보상 받을 수 있나요?"

**실험 B 응답**:
```
비 오는 날 배달이 늦어졌을 때 보상은 기상 특보 여부와 실제 지연 시간을 기준으로 결정됩니다. 정확한 지연 시간을 확인해주시면 더 자세히 안내드릴 수 있습니다.

주문번호를 알려주시겠어요?
```

**실험 A 응답 (비교)**:
```
비 오는 날 자체만으로 배달이 늦어졌다고 보상 받을 수 있는 것은 아닙니다. 기상 특보가 발효되었는지 여부를 확인해야 합니다. 현재 배달 지연 보상 정책은 예상 시간과 실제 배달 시간의 차이, 그리고 기상 특보 여부에 따라 달라집니다.

어떤 주문을 말씀하시는 건가요? 주문번호를 알려주시겠어요?
```

| | 실험 A (800) | 실험 B (100) |
|---|---|---|
| 입력 토큰 | 2336 | 1660 |
| "기상 특보" 조건 언급 | ✅ | ✅ |
| "예상 시간 차이" 보상 기준 언급 | ✅ | ❌ |
| "지연 시간 확인" 뭉개진 표현 | ❌ | ✅ |

`weather-delay` 문서가 chunkSize=100으로 8개 청크로 분할됐다. Top-K=4로 그 중 4개만 검색되어 "기상 특보" 조건 청크는 올라왔지만 "예상 시간 대비 지연 기준" 수치를 담은 청크는 유사도 순위에서 밀려 빠졌다. 입력 토큰 2336→1660(-676)이 Context 양이 줄어든 직접 증거다. 더 많은 청크를 보고 싶으면 Top-K를 8 이상으로 올려야 하지만, 그러면 다른 문서의 관련 없는 청크들도 함께 올라와 Context가 오염된다. chunkSize=100은 Top-K 설정 어디로도 해결이 안 되는 구조적 문제다.

## 실패 관찰 — 청크가 너무 클 때 (실험 C, chunkSize=2000)

**결과**: 실험 C에서는 "유사도 뭉툭" 효과를 관찰할 수 없었다.

배달 정책 문서들이 모두 2000 토큰 미만이라, chunkSize=2000을 설정해도 각 문서가 1개 청크로 유지됐다. row 수 7, 입력 토큰, 답변 품질 모두 실험 A(chunkSize=800)와 동일했다.

**유사도 뭉툭 현상이 발생하는 조건**: 하나의 문서에 여러 주제가 섞여 있을 때 chunkSize를 크게 잡으면 발생한다. 예를 들어 하나의 큰 정책 PDF에 "취소 정책 + 환불 정책 + 쿠폰 정책"이 모두 들어있는 경우, chunkSize=2000으로 잡으면 세 주제가 한 청크에 섞인다. "쿠폰 중복 사용"이라는 질문 임베딩과 이 청크 임베딩의 유사도는 쿠폰 내용만 있는 청크보다 낮아진다(여러 주제가 벡터를 분산시키기 때문). 그 결과 관련 문서가 임계값 아래로 떨어지거나 순위가 낮아진다.

**실험 C에서 관찰된 다른 실패**: 질문 1 응답에 중국어 문단이 혼입됐다. 내용은 정확하나("60분 이상 지연 시 환불 검토") 고객 서비스용으로는 사용 불가한 출력이다. 청크가 크면 Context 텍스트 양이 많아지고, qwen2.5 모델이 장문의 한국어 Context를 처리할 때 중국어로 언어를 전환하는 경향이 나타났다.

## 실패 관찰 — Fallback 없는 환각

### 1차 실험 (질문 2개)

**방법**: `BaedalPrompt.java`의 `[정책 인용 규칙]` 섹션 5개 항목을 제거 후 앱 재시작.

**질문 1 — 도메인 밖** (`"오늘 점심 뭐 먹을까요?"`)

규칙 제거 후:
```
배달 서비스 관련 문의만 도와드릴 수 있습니다. 다른 도움이 필요하신가요?
```
로그: `입력 토큰: 1478 | 출력 토큰: 24`

규칙 복원 후 (비교):
```
배달 서비스 관련 문의만 도와드릴 수 있습니다. 다른 도움이 필요하신가요?
```
로그: `입력 토큰: 1455 | 출력 토큰: 24`

**질문 2 — 도메인 내** (`"결제 후 바로 취소하면 환불되나요?"`)

규칙 제거 후:
```
주문 상태가 CREATED 또는 ACCEPTED인 경우 결제 후 바로 취소하면 전액 환불이 가능합니다. 그러나 주문 상태가 이미 조리 시작 이후라면 단순 변심으로 인한 환불은 어려울 수 있습니다.

어떤 주문을 말씀하시는 건가요? 그 주문의 현재 상태를 알려주시겠어요?
```
로그: `입력 토큰: 1909 | 출력 토큰: 78`

### 2차 실험 — 도메인 밖 10개 + 도메인 내 10개 (확장 재실험)

**방법**: `SYSTEM_PROMPT_NO_CITATION_RULES` 상수 추가(`[정책 인용 규칙]` 5항목 전부 제거) 후 `AssistantController`에 적용, 앱 재시작.

**결과 요약**

| 구분 | 질문 수 | 환각 | 올바른 응답 | 패턴 |
|---|---|---|---|---|
| 도메인 밖 | 10 | 0 | 0 | 전부 "어떤 주문을 말씀하시는 건가요?" |
| 도메인 내 | 10 | 0 | 0 | 전부 "어떤 주문을 말씀하시는 건가요?" |

**전체 응답 (대표 샘플)**

도메인 밖 — 오늘 점심 뭐 먹을까요?:
```
죄송하지만 이해하지 못했습니다. 어떤 주문을 말씀하시는 건가요? 다시 한번 알려주시겠어요?
```

도메인 밖 — 비빔밥 레시피 알려주세요:
```
죄송합니다만 맥락이 불명확해요. 어떤 주문을 말씀하시는 건가요? 주문번호를 알려주시면 도와드릴 수 있을 것 같습니다.
```

도메인 내 — 비 오는 날 배달이 늦으면 보상 받을 수 있나요?:
```
죄송합니다만, 입력된 내용이 불명확해 정확한 답변을 드릴 수 없습니다. 어떤 주문에 대해 문의하시는 건가요? 주문번호를 알려주시면 도와드리겠습니다.
```

도메인 내 — 기상 특보 발효 시 배달 지연 보상 기준이 어떻게 되나요?:
```
죄송합니다만 맥락이 불명확해요. 어떤 주문을 말씀하시는 건가요? 주문번호를 알려주시면 도와드릴 수 있을 것 같습니다.
```

**원인 분석**

기대한 실패(환각 = 없는 정보를 지어내기)가 발생하지 않았다. 대신 다른 실패 모드가 나타났다.

`[정책 인용 규칙]`이 제거되자 모델이 어떤 지시를 따를지 재선택했다. 선택된 것은 `[대화 맥락 사용 규칙]`의 마지막 항목이다:

> "맥락이 모호하면 추측하지 말고 '어떤 주문을 말씀하시는 건가요?'라고 다시 확인합니다."

"날씨 어때요?"도 "환불 기준이 어떻게 되나요?"도 모두 "모호한 맥락"으로 분류되어 전부 동일한 주문번호 요청으로 수렴했다. FAQ 질문 10개가 하나도 답변되지 않는다.

`[정책 인용 규칙]`이 없으면 두 가지 경로가 모두 막힌다:
- 도메인 밖 → 올바른 Fallback 문구 없음 (주문번호 요청으로 전락)
- 도메인 내 → 정책 원문 인용 없음 (주문번호 요청으로 전락)

환각이 0/20인 것은 "안전"이 아니라 "기능 마비"다. 규칙이 없어도 모델은 절대로 아무 말이나 지어내지 않았지만, 대신 아무것도 답하지 않는 쪽을 택했다.

**1차(2개) vs 2차(20개) 결과 차이**

1차 실험에서 도메인 내 질문에 정책 내용 응답이 나온 것은 세션 맥락 차이 때문이다. 1차 실험에서는 직전 턴에 도메인 밖 질문이 있었고 모델이 배달 서비스 맥락을 유지한 상태였다. 2차 실험의 각 질문은 독립 세션으로 맥락이 전혀 없어 `[대화 맥락 사용 규칙]`이 더 강하게 작동했다.

**결론**

`[정책 인용 규칙]`의 역할은 세 가지다:
1. 도메인 밖 질문 → 명확한 Fallback 문구로 유도
2. 도메인 내 FAQ 질문 → Context 인용 강제 (주문번호 없이도 답변 가능하게)
3. 미세 환각 방어 → 정책 수치를 임의로 바꾸거나 없는 조항을 지어내는 것 차단

이 규칙 없이는 모델이 `[대화 맥락 사용 규칙]`으로 fallback하여 모든 질문을 "모호한 주문 문의"로 처리한다. 규칙은 제거할 수 없다.

## 설계 결정 문서

### 배달 정책 도메인에서 가장 적합한 청크 크기는?

실험 결과를 근거로 **800**이 최적이다.

| 실험 | row 수 | 평균 입력 토큰 | 특이사항 |
|---|---|---|---|
| A (800) | 7 | 1972 | 안정적 품질, 정책 조건 원문 포함 |
| B (100) | 49 | 1636 | 복합 질문에서 맥락 조각남, 토큰은 낮지만 정보 누락 |
| C (2000) | 7 | 1972 | A와 동일 (문서가 짧아 효과 없음), 중국어 혼입 발생 |

B(100)는 입력 토큰이 낮지만 정책 조항이 여러 청크로 쪼개져 Top-K=4 안에서 전체 맥락을 담보하지 못한다. C(2000)는 이 도메인에서 A와 차이가 없다. 배달 정책 문서는 이미 조항 단위로 짧아서 800이면 하나의 정책 주제가 하나의 청크에 들어간다. 800을 선택하는 근거다.

### 청크 오버랩을 0으로 바꾸면 어떤 문제가 생기는가?

`TokenTextSplitter`의 기본 오버랩은 문장 경계를 기준으로 앞 청크의 끝부분을 다음 청크에 포함시킨다. 오버랩이 0이면 두 청크의 경계에 걸쳐 있는 정책 조항이 완전히 잘린다.

예: "조리 시작 전 취소 가능 / **[경계]** 조리 시작 후 취소 불가" 라는 정책이 있을 때, 오버랩 없이 경계에서 자르면 뒤 청크는 "조리 시작 후 취소 불가"만 갖고 전후 맥락이 없다. 검색 시 이 청크만 올라오면 "언제부터 취소 불가인지"를 알 수 없다. 오버랩은 이 경계 맥락을 보존하기 위해 필요하다.

### 문서가 "사용자 리뷰 10만 건"이라면?

| 관점 | 배달 정책 (현재) | 사용자 리뷰 10만 건 |
|---|---|---|
| 청크 크기 | 800 (조항 단위) | 50~100 (리뷰 1건 = 1~3 문장) |
| 중복 방지 | faqId 기반 (7건) | 리뷰 ID 기반 (10만 건 → DB 인덱스 필수) |
| 재인덱싱 주기 | 정책 변경 시 (저빈도) | 리뷰 추가될 때마다 (고빈도 → 증분 인덱싱) |

리뷰는 한 건이 독립된 의견이므로 짧은 청크가 적합하다. 10만 건이면 재기동 시 전체 재적재 대신 새 리뷰만 추가하는 증분 인덱싱과 오래된 리뷰 TTL 정책이 필요하다.

### similarityThreshold만으로 환각을 막을 수 있는가?

막을 수 없다. threshold 실험이 이를 직접 보여준다.

threshold=0.3에서 도메인 밖 "오늘 점심 뭐 먹을까요?"에도 Context가 주입됐지만 `[정책 인용 규칙]`이 Fallback을 강제했다. threshold=0.8에서 도메인 내 질문인데도 Context가 비어 `cancel-policy` 내용을 쓸 수 없게 됐고, 프롬프트의 Fallback 문구("고객센터 1588-0000")가 출력됐다.

threshold는 "관련 없는 문서를 걸러내는" 역할만 한다. Context가 비었을 때 LLM이 학습 지식으로 답을 지어내는 것은 막지 못한다. `[정책 인용 규칙]`의 Fallback 문구가 2중 방어선으로 반드시 있어야 한다.
