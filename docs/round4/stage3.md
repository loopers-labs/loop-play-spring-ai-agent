## 실험 2 — 순서 뒤바꾸기 `rag(5) → memory(10)` 고장 관찰

`RagConfig.java`의 `.order(20)` → `.order(5)` 변경 후 동일 2턴 실행.

**1턴**: "주문번호 2024-1234 배달 어디?"

```
현재 라이더는 역삼역 사거리 부근에서 배달 중이라고 합니다. 예상 도착 시간은 22시 36분경입니다.

다른 정보가 필요하시면 알려주세요!
```

로그: `[Tool] getDeliveryStatus(orderId=2024-1234)` / `입력 토큰: 3039 | 출력 토큰: 101`

> 1턴은 주문번호가 명시돼 있어 순서와 무관하게 정상 동작.

---

**2턴**: "아까 그 주문 환불 돼요?"

```
아까 그 주문의 상태를 확인해보겠습니다.

주문번호 2024-1234의 상세 정보를 조회한 결과, 현재 상태는 배달 완료로 표시되고 있습니다. 따라서 환불은 가능하지만, 정책에 따라 처리가 다릅니다.

더 자세한 안내가 필요하시면 고객센터(1588-0000)로 연락해 주세요.
```

로그: `입력 토큰: 2031 | 출력 토큰: 99` (Tool 호출 없음)

> RAG가 먼저 "아까 그 주문 환불 돼요?" 원문을 임베딩해 검색했다. Memory가 아직 붙지 않은 상태라 주문번호를 모르고, "환불" 키워드만 보고 `refund-after-delivered`(배달 완료 후 환불) 문서를 가져왔다.    
> 문제 1 — RAG Context에 "배달 완료 후 환불" 정책이 주입되자 LLM이 현재 주문 상태를 "배달 완료"로 잘못 추론했다. 실제 주문 상태는 1턴에서 확인한 "배달 중"이다. LLM이 Tool을 재호출하거나 Memory를 기준으로 판단하지 않고 RAG Context를 현실로 받아들인 결과다.    
> 문제 2 — "정책에 따라 처리가 다릅니다"로 얼버무렸다. 정상 순서에서는 Memory가 먼저 "배달 중" 상태를 복원하고 RAG가 그에 맞는 `refund-basic` 정책을 검색해 "조리 시작 전/후" 구분이 명확하게 나왔다.

## 관찰 기록 표

| 관찰 포인트 | `memory(10) → rag(20)` 정상 | `rag(5) → memory(10)` 고장 |
|---|---|---|
| 2턴 Context에 들어간 정책 카테고리 | refund-basic (현재 배달 중 기준) | refund-after-delivered (배달 완료 기준) |
| Context 정책이 현재 주문 상황과 맞는가 | ✅ (배달 중 → 환불 조건 정확) | ❌ (배달 완료 정책이 주입 → 상태 오판) |
| LLM 응답의 정확도 | ✅ "조리 시작 전/후" 원문 조건 포함 | ❌ "정책에 따라 다릅니다" 뭉툭한 답 |
| 주문번호 복원 | ✅ Memory가 먼저 복원 후 RAG 검색 | △ Memory가 나중에 복원 (RAG는 원문으로 검색) |
| 입력 토큰 (2턴) | 1981 | 2031 |

입력 토큰이 고장 케이스(2031)에서 오히려 50 높다. `refund-after-delivered` 문서가 `refund-basic`보다 텍스트가 길기 때문이다. 더 비싼 토큰을 썼는데 더 틀린 답이 나왔다. Advisor 순서 오류의 비용이 정확도와 토큰 두 방향 모두에서 손실로 나타났다.

## 설계 결정 문서

### 왜 Memory Advisor가 RAG보다 먼저 실행되어야 하는가?

RAG는 임베딩 검색이다. 검색 품질은 쿼리 품질에 달려 있다. "아까 그 주문 환불 돼요?"라는 원문 쿼리에는 주문번호가 없다. 이 쿼리로 임베딩하면 "환불"이라는 단어만 유효한 시그널이 되고, "배달 완료 후 환불" 문서가 가장 높은 유사도로 올라온다.

Memory(order=10)가 먼저 실행되면 이전 대화 이력이 프롬프트에 주입된다. 그 결과 프롬프트 안에 "주문번호 2024-1234, 배달 중" 정보가 복원된다. RAG(order=20)가 그 다음 실행될 때 임베딩 대상은 "2024-1234 환불"이 포함된 질문이 되고, 배달 중 상태에 맞는 `refund-basic` 정책이 검색된다.

Memory는 RAG의 쿼리를 완성한다. RAG 검색이 먼저 일어나면 쿼리가 항상 원문 상태이고, Memory는 이미 잘못 채워진 Context를 고칠 수 없다.

순서가 뒤바뀌면 일어나는 일:
1. RAG가 "아까 그 주문 환불 돼요?" 원문을 임베딩 → "환불" 키워드로 `refund-after-delivered` 검색
2. Memory가 나중에 붙어 주문번호를 복원했지만 RAG Context는 이미 "배달 완료 후 환불" 정책으로 채워진 상태
3. LLM이 Context를 읽고 주문 상태를 "배달 완료"로 잘못 추론 → 실제 상태("배달 중")와 충돌하는 응답 생성

---

### 반대 순서가 더 나은 상황이 존재하는가?

Memory에 개인 정보(주민번호, 카드번호 등)가 들어있는 경우가 예외다.

Memory가 먼저 실행되면 그 개인 정보가 임베딩 쿼리에 포함된다. 이 쿼리가 외부 임베딩 서버로 나가면 개인 정보가 외부로 유출된다. RAG를 Memory보다 먼저 실행하면 임베딩 대상에 Memory 내용이 들어가지 않아 유출을 막을 수 있다. 대신 쿼리 품질 손실을 감수해야 한다.
