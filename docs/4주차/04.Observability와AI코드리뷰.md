# 4단계 — RAG가 토큰을 얼마나 먹는지 재 보고, AI가 짠 RAG 코드를 뜯어본다

4단계는 두 가지였습니다.
하나는 RAG를 붙였을 때 입력 토큰이 실제로 얼마나 늘어나는지 `PerformanceLoggingAdvisor`로 재 보는 것, 다른 하나는 AI가 만들어 주는 전형적인 RAG 코드에서 프로덕션에 올리면 안 되는 결함을 찾아보는 것이었어요.

## RAG는 토큰을 얼마나 더 먹나

같은 질문 "배달 완료 후에도 환불 받을 수 있나요?"를 advisor 조합만 바꿔 가며 던졌습니다.
조합을 바꾸려고 `AssistantController`의 `defaultAdvisors`를 임시로 세 가지로 수정하고 매번 재기동했어요(측정 후 (c)로 복원).

| 조건 | Advisor 체인 | promptTokens | 응답 |
| --- | --- | --- | --- |
| (a) Memory·RAG 없음 | performance | 1688 | Fallback |
| (b) Memory만 | memory, performance | 1688 | Fallback |
| (c) Memory + RAG | memory, rag, performance | 2590 | Fallback |

(c)가 (a)보다 입력 토큰이 902 더 컸습니다.
이 902가 RAG가 프롬프트에 끼워 넣은 정책 원문(Context)의 무게입니다.
(a)와 (b)가 1688로 똑같았던 건, 첫 턴이라 메모리가 비어 있어서 Memory advisor가 실제로 더할 게 없었기 때문이에요.
그러니까 Memory는 "대화가 쌓이면" 토큰을 먹기 시작하고, RAG는 "첫 질문부터" 검색 결과만큼 바로 먹습니다.

그런데 곱씹게 된 건 셋 다 응답이 Fallback이었다는 점입니다.
(a)(b)는 RAG가 없어 정책을 못 찾으니 Fallback이 당연한데, (c)는 902 토큰짜리 환불 정책을 분명히 프롬프트에 실었는데도 "확인이 필요합니다"로 빠졌어요.
"정확도를 토큰(돈)으로 산다"는 말은 절반만 맞았습니다.
토큰은 확실히 더 냈는데, 이 질문에서는 그 대가만큼의 정확도를 못 건졌으니까요.
2단계에서 본 임계값 경계의 출렁임과 같은 결인데, Context를 넣는 것과 모델이 그 Context를 실제로 답에 쓰는 것은 별개라는 걸 토큰 숫자로 다시 확인했습니다.

## RAG가 끼워 넣는 Context는 실제로 어떻게 생겼나

기본 로깅으로는 최종 프롬프트가 안 찍혀서, 3단계에서 order를 5로 뒤집었을 때 ChatMemory에 그대로 저장돼 버린 증강 프롬프트로 Context 전문을 확보했습니다.
RAG는 사용자 질문 뒤에 이런 블록을 붙여요.

```
Context information is below, surrounded by ---------------------
---------------------
# 환불 기본 정책
- 조리 시작 전 취소: CREATED/ACCEPTED인 경우 전액 즉시 취소/환불
- 음식 누락/오배송: 배달 완료 후에도 증빙 조건으로 전액/부분 환불
- 배달 지연 과도(60분 이상): 배달비 환불 또는 쿠폰 보상
...
# 주문 취소 정책
- CREATED / ACCEPTED: 자동 취소 가능, 전액 환불
- COOKING / DELIVERING / DELIVERED: 자동 취소 불가 ...
---------------------
Given the context and provided history information and not prior knowledge,
reply to the user comment. If the answer is not in the context, inform
the user that you can't answer the question.
```

이 블록이 통째로 입력 토큰에 더해지니, Top-K를 키우거나 청크를 크게 잡을수록 902가 더 부풀어 오릅니다.
1단계에서 Top-K를 4로 묶고 청크를 800에 둔 게 결국 이 토큰 무게를 통제하려는 선택이었다는 게 여기서 이어졌어요.

## AI가 짜 주는 RAG 코드를 뜯어보면

"Spring AI 1.0으로 PgVector + 임베딩을 쓰는 RAG FAQ 챗봇을 만들어 줘"라고 하면 보통 이런 코드가 나옵니다(전형적인 생성 패턴을 재현한 것입니다).

```java
@Configuration
class RagConfig {
    @Bean
    QuestionAnswerAdvisor qaAdvisor(VectorStore vectorStore) {
        return new QuestionAnswerAdvisor(vectorStore);   // SearchRequest 없이 기본값
    }
}

@Service
class FaqIndexer {
    private final VectorStore vectorStore;

    @PostConstruct
    void index() {
        String faq = Files.readString(Path.of("faq.md"));
        vectorStore.add(List.of(new Document(faq)));     // 통 문서, 재기동마다 add
    }
}
```

```yaml
spring:
  ai:
    openai:
      embedding:
        options:
          model: text-embedding-3-small   # 1536차원
    vectorstore:
      pgvector:
        # dimensions 설정 없음
```

겉보기엔 돌아가는데, 프로덕션에 올리면 안 되는 구멍이 최소 세 개 보였습니다.

**하나, 검색 파라미터를 기본값으로 둔 것.**
`new QuestionAnswerAdvisor(vectorStore)`는 `topK`도 `similarityThreshold`도 기본값이라, 관련 없는 문서까지 Top-K에 끌려 들어오고 프롬프트가 부풉니다.
2단계에서 본 것처럼 임계값이 없으면 도메인 밖 질문에도 무관 정책이 붙어 환각으로 이어져요.
저는 `SearchRequest.builder().topK(4).similarityThreshold(0.5)`로 묶어서 검색 단계에서 한 번 걸러지게 했습니다.

**둘, 청크도 안 나누고 중복 방지도 없는 것.**
`new Document(faq)` 하나를 통째로 add하면 문서 전체가 벡터 하나로 뭉개져 유사도가 둔해지고, `@PostConstruct`라 재기동할 때마다 같은 문서가 또 쌓입니다.
저는 `TokenTextSplitter`로 쪼갠 뒤 add하고, `alreadyLoaded(faqId)`로 이미 있으면 건너뛰게 했어요.
1단계에서 재기동 시 "스킵 7건"이 찍힌 게 이 차이입니다.

**셋, Fallback이 없는 것.**
이 코드에는 "Context에서 못 찾으면 이렇게 답하라"는 규칙이 시스템 프롬프트 어디에도 없습니다.
2단계에서 규칙을 떼고 "오늘 점심"을 물었더니 모델이 메뉴를 추천하며 상담 범위를 넘어간 그 장면이 바로 이 상태예요.
저는 `[정책 인용 규칙]`에 "Context에 없으면 상담원 연결로 안내"를 박아 검색이 비어도 모델이 지어내지 않게 했습니다.

여기에 하나 더, 임베딩 모델 차원이 위험합니다.
`text-embedding-3-small`은 1536차원인데 `application.yml`에 `dimensions`가 없어 PgVector 기본값(보통 1536이 아닐 수 있음)과 어긋나면 조용히 쓰레기 결과가 나옵니다.
인덱싱과 검색에 서로 다른 임베딩 모델을 섞어 쓰면 벡터 공간 자체가 안 맞아 더 위험하고요.
저는 인덱싱·검색을 `qwen3-embedding:0.6b`로 통일하고 `dimensions: 1024`를 모델 차원과 맞췄습니다.

📌 포기한 것 — Context 전문은 `SimpleLoggerAdvisor`를 정식으로 붙여 캡처하는 게 깔끔한데, 이번엔 3단계 order 뒤집기에서 메모리에 새어 나온 걸 재활용했습니다. AI 코드리뷰의 결함 코드도 실제 한 번 돌려 본 게 아니라 전형적 생성 패턴을 재현해 짚은 것이라, "이 코드가 실제로 이렇게 실패한다"까지 실측으로 보이진 않았습니다.
