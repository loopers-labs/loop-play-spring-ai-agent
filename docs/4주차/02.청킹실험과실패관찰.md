# 2단계 — 청크 크기를 바꿔 가며 무엇이 망가지는지 본다

2단계 목표는 청크 크기를 800에서 100, 2000으로 흔들어 보면서 검색 품질과 입력 토큰이 어떻게 달라지는지 직접 재 보는 것이었습니다.
세 조건 모두 같은 5개 질문을 던졌고, 매 조건 전에 `vector_store`를 비우고 새 splitter로 재적재했습니다.

질문은 이렇게 고정했어요.

```
1) 비 오는 날 배달이 늦으면 보상 받을 수 있나요?
2) 결제 후 바로 취소하면 환불되나요?
3) 쿠폰 중복 사용되나요?
4) 배달 완료 후에도 환불 받을 수 있나요?
5) 오늘 점심 뭐 먹을까요?        (도메인 밖 — Fallback 기대)
```

## 정량 비교

| 실험 | chunkSize / min | vector_store row | 평균 입력 토큰(4턴) | 답변 |
| --- | --- | --- | --- | --- |
| A | 800 / 350 | 7 | 약 2381 | Q3 인용 / Q1·Q2·Q4 Fallback / Q5 거절 |
| B | 100 / 40 | 49 | 약 1977 | Q2 인용 / Q1 수치 누락 / Q3 모호 / Q4 Fallback / Q5 거절 |
| C | 2000 / 800 | 7 | 약 2381 | A와 사실상 동일 |

평균 입력 토큰은 `PerformanceLoggingAdvisor`의 `promptTokens`를 4턴 기준으로 냈습니다(동시 실행 로그에서 한 턴이 누락돼 5턴 전부는 못 모았어요).
답변 품질은 "정책 수치를 원문대로 인용하면 만족 / 정책을 모호하게만 언급하거나 수치가 빠지면 애매 / 정답 문서가 있는데 Fallback이면 불만족"으로 제 나름의 기준을 정해 분류했습니다.

## 청크를 작게(100) 했더니 — 조각났고, 토큰은 줄었다

가장 또렷하게 갈린 건 B였습니다.
`weather-delay` 문서 하나가 8청크, `refund-basic`이 8청크처럼 7건이 전부 6~8조각으로 흩어져 `vector_store` row가 7에서 49로 뛰었어요.

품질에서 기대했던 "문맥 조각남"이 Q1에서 그대로 나왔습니다.

규칙 있는 정상 답(1단계 S1)에서는 "60분 이상 지연", "기상 특보" 같은 원문 수치가 나왔는데, B(100)에서는 이렇게 뭉개졌습니다.

```
비 오는 날 배달이 늦어졌을 때 보상 여부는 기상 특보 발효 여부와 실제 지연 시간을 확인해야 합니다.
```

"기상 특보"라는 키워드는 살아남았지만 "예상 시간 + 30분", "60분 이상" 같은 숫자가 사라졌어요.
청크를 100 토큰으로 자르니 숫자가 박힌 문장과 그 숫자의 조건을 설명하는 문장이 다른 청크로 흩어졌고, Top-K 4건이 그중 숫자 없는 조각들로 채워진 걸로 보입니다.

그런데 B가 전부 나빴던 건 아니라는 게 재밌었습니다.
Q2 "결제 후 바로 취소"는 A에서는 Fallback이었는데 B에서는 오히려 정확히 인용됐어요.

```
주문 상태가 CREATED 또는 ACCEPTED인 경우 결제 후 바로 취소해도 전액 환불이 가능합니다.
그러나 조리가 시작된 COOKING 상태에서는 자동 취소가 불가능하며 ...
```

작게 쪼갠 덕에 "결제 후 바로"라는 질문이 `cancel-policy`의 "CREATED/ACCEPTED 전액 환불" 조각과 더 가깝게 매칭된 것으로 보입니다.
그래서 "작은 청크 = 무조건 나쁨"이 아니라, 숫자가 흩어지는 질문엔 불리하고 짧은 조항에 정확히 꽂히는 질문엔 유리하다는, 질문에 따라 갈리는 트레이드오프로 읽었습니다.
입력 토큰은 평균 1977로 A(2381)보다 낮았는데, Top-K 4건이 100짜리 작은 조각이라 프롬프트에 실리는 총량이 적었기 때문입니다.

📌 포기한 것 — B에서 Q2가 잘 된 게 "작은 청크의 일반적 장점"인지 이 질문에서 우연히 맞은 건지는 한 번의 실측으로 단정하지 않았습니다. 같은 질문을 여러 번 돌려 분산을 봐야 합니다.

## 청크를 크게(2000) 했더니 — 우리 문서엔 아무 일도 안 일어났다

C는 솔직히 예상과 달랐습니다.
교재는 큰 청크에서 row가 줄고 유사도가 뭉툭해진다고 했는데, 우리 정책 문서는 전부 2000 토큰 미만이라 800일 때도 2000일 때도 똑같이 "1청크"로 들어갔어요.
그래서 row도 7로 A와 같고, 입력 토큰도 2615/2166/2154/2590으로 A와 사실상 동일했습니다.

이건 "큰 청크가 안전하다"는 결론이 아니라, **이 도메인 문서가 애초에 작아서 청크 크기를 키우는 실험 자체가 의미를 갖지 못한다**는 뜻으로 받아들였습니다.
조각남을 보려면 문서가 충분히 길어야 하는데, 조항 단위로 짧게 끊긴 배달 정책에서는 800 위로 올리는 건 변화를 못 만들고, 800 아래로 내리는 것(B)만 변화를 만들었어요.

## 같은 A 조건인데 1단계와 답이 달랐다

A(800)는 1단계와 같은 설정인데, 1단계에서 원문을 인용했던 Q1(비 오는 날)이 2단계 재실행에서는 Fallback으로 빠졌습니다.
Q4(배달 완료 환불)도 정답 문서가 있는데 Fallback이었어요.
설정을 안 바꿨는데 답이 달라진 건, qwen2.5의 temperature 0.3 비결정성과 유사도가 0.5 임계값 근처에서 출렁이는 게 겹친 결과로 보입니다.
이건 청크 실험과 별개로, "RAG가 붙었다고 같은 질문에 항상 같은 근거를 무는 건 아니다"라는 걸 보여준 셈이라 그대로 남겼습니다.

## 임계값만으로 환각을 막을 수 있을까 — 규칙을 떼어 봤다

마지막으로 `AssistantPrompt`의 `[정책 인용 규칙]`을 통째로 빼고 도메인 밖 질문을 던졌습니다.

규칙이 있을 때 "오늘 점심 뭐 먹을까요?"는 세 조건 모두 이렇게 막았어요.

```
저는 주문·배달·환불 관련 상담을 도와드리고 있습니다. 메뉴 추천은 해당 범위를 넘어서므로 ...
```

규칙을 빼니 바로 범위를 넘어갔습니다.

```
안녕하세요. 오늘 점심 메뉴를 추천해 드리겠습니다. 하지만 먼저 주문하신 음식을 확인해야 합니다 ...
```

"점심 메뉴를 추천해 드리겠습니다"가 그대로 나온 겁니다.
`similarityThreshold=0.5`는 무관한 정책이 Top-K에 끼는 걸 줄여 주긴 하지만, 그것만으로는 "상담 범위 밖 질문에 답하지 말라"를 강제하지 못했어요.
검색에서 관련 문서가 0건이어도 모델은 자기 일반 지식으로 친절하게 답해 버리니까, 임계값(검색 단계)과 시스템 프롬프트의 모름 규칙(생성 단계)이 같이 있어야 환각이 실질적으로 막힌다는 걸 눈으로 확인했습니다.

## 설계 결정으로 정리하면

배달 정책 도메인에서 가장 적합한 청크 크기는, 이번 실측 기준으로는 **800(기본값) 근처**라고 봤습니다.
100은 숫자가 흩어져 핵심 수치를 놓치는 손해가 컸고, 2000은 문서가 작아 800과 차이가 없었으니, 굳이 더 잘게 썰 이유가 없었어요.

오버랩을 0으로 두면 어떻게 되냐는 질문에는, B에서 본 조각남이 더 심해질 거라고 봅니다.
청크 경계에서 "예상 시간 +"와 "30분"이 갈렸을 때 두 청크가 일부를 겹쳐 들고 있으면 한쪽 청크만 Top-K에 와도 숫자가 살아남는데, 오버랩이 0이면 그 안전장치가 사라지니까요.

만약 문서가 "사용자 리뷰 10만 건"이라면 전략이 완전히 달라져야 한다고 정리했습니다.
리뷰는 한 건이 짧으니 한 리뷰를 한 청크로 두되, 중복 방지를 `faqId` 같은 고정 id가 아니라 리뷰 id + 내용 해시로 잡아야 하고, 새 리뷰가 계속 쌓이니 기동 시 1회 적재가 아니라 주기적 증분 인덱싱으로 바꿔야 합니다.
지금 우리 `alreadyLoaded`는 "id가 있으면 스킵"이라 내용이 바뀌면 못 잡는데, 리뷰 규모에서는 이게 바로 약점이 됩니다.

📌 포기한 것 — 평균 입력 토큰을 5턴 전부가 아니라 4턴으로 냈고(동시 실행 로그 한 턴 누락), 답변 품질 분류도 한 번의 실행에 기댔습니다. 분산까지 보려면 같은 조건을 반복해야 하는데 거기까지는 안 갔습니다.
