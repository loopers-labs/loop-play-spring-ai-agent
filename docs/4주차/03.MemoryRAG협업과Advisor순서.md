# 3단계 — Advisor 순서를 뒤집었더니 메모리가 오염됐다

3단계는 Memory와 RAG가 같은 체인에서 각각 무슨 일을 하는지 보고, 순서를 일부러 뒤집어 무엇이 깨지는지 관찰하는 단계였습니다.
같은 2턴 대화를 정상 순서(`memory(10) → rag(20)`)와 뒤집은 순서(`rag(5) → memory(10)`)로 각각 돌렸어요.

```
1턴: 주문번호 2024-1234 배달 어디?
2턴: 아까 그 주문 환불 돼요?
```

## 정상 순서에서 본 것

정상 순서에서는 1턴이 Tool로 "역삼역 사거리 부근, 배달 중"을 잘 답했고, 세션 메모리에는 사용자 발화가 깨끗하게 저장됐습니다.

```json
{"type":"user","text":"주문번호 2024-1234 배달 어디?"}
{"type":"assistant","text":"현재 배달 상태는 배송 중이며, 라이더의 위치는 역삼역 사거리 부근입니다..."}
{"type":"user","text":"아까 그 주문 환불 돼요?"}
```

2턴은 1단계와 마찬가지로 "해당 주문번호를 찾지 못했습니다"로 빠졌는데, 메모리 자체는 오염 없이 사용자가 실제로 친 문장만 들고 있었어요.

## 순서를 뒤집었더니 — 메모리에 Context가 통째로 박혔다

진짜 차이는 응답이 아니라 **메모리에 무엇이 저장됐는가**에서 났습니다.
`rag(5)`로 RAG를 Memory보다 먼저 돌렸더니, 세션 메모리의 USER 메시지가 이렇게 변했어요.

```
"아까 그 주문 환불 돼요?

Context information is below, surrounded by ---------------------
---------------------
# 환불 기본 정책
...조리 시작 전 취소 / 음식 누락 / 배달 지연 60분 이상...
# 주문 취소 정책
...CREATED / ACCEPTED / COOKING / DELIVERING...
---------------------
Given the context and provided history information and not prior knowledge,
reply to the user comment. ..."
```

RAG가 Memory보다 먼저 실행되니까, 사용자 질문에 검색된 정책 원문을 덧붙인 "증강된 프롬프트"를 만들고, 그 증강된 덩어리가 그대로 ChatMemory에 사용자 발화로 저장된 겁니다.
1턴도 마찬가지로 빈 Context 틀("Context information is below ... ---------------------")이 사용자 메시지에 끼어 저장됐어요.

이게 왜 문제냐면, 메모리는 다음 턴에 다시 프롬프트로 주입되니까 한 번 오염되면 대화가 길어질수록 같은 Context 틀이 눈덩이처럼 쌓입니다.
원래 RAG의 Context 주입은 "이번 호출에만 쓰고 버리는" 일회성이어야 하는데, 순서가 뒤집히면 그게 영구 기록으로 굳어 버려요.

## 관찰 정리

| 관찰 포인트 | `memory(10) → rag(20)` 정상 | `rag(5) → memory(10)` 뒤집음 |
| --- | --- | --- |
| 2턴 메모리의 USER 메시지 | 사용자가 친 문장 그대로 | 문장 + 환불/취소 정책 원문 Context가 통째로 박힘 |
| Context가 향한 곳 | 이번 호출 프롬프트에만(일회성) | ChatMemory에 영구 저장(오염) |
| 2턴 응답 | "주문번호를 찾지 못했습니다" | "주문번호 2024-1234를 찾지 못했습니다" (응답 자체는 유사) |

흥미로운 건 2턴 응답 문장은 둘 다 비슷하게 "주문 못 찾음"으로 빠졌다는 점입니다.
그러니 순서를 뒤집은 손해는 "이번 답이 틀린다"보다 "메모리가 오염돼 다음 턴부터 점점 망가진다"는 누적형 문제로 읽었어요.

## 왜 Memory가 먼저여야 하는가

프롬프트 조립 순서로 보면, Memory가 먼저 돌아야 이전 턴의 맥락(여기서는 1턴의 `2024-1234`)이 프롬프트에 복원되고, 그 다음 RAG가 "복원된 질문"을 임베딩해 정책을 검색하는 게 자연스럽습니다.
반대로 RAG가 먼저면 "아까 그 주문"이 무슨 주문인지 모르는 상태로 그 문장 자체를 검색하게 되고, 게다가 이번 실측처럼 그 증강 프롬프트가 메모리에 저장되는 부작용까지 생겨요.

다만 반대 순서가 항상 틀린 건 아니라고 봅니다.
예를 들어 메모리에 개인정보(주소, 연락처)가 섞여 있다면, 그걸 그대로 임베딩해서 벡터 검색에 흘리는 게 오히려 위험할 수 있어요.
그런 경우엔 "메모리를 임베딩 쿼리에서 빼고 싶다"는 요구가 생기는데, 이건 다음 라운드 Guardrail에서 입력 필터로 다룰 주제로 메모만 남겨 둡니다.

📌 포기한 것 — 정상 순서의 2턴 Context는 기본 로깅에 안 잡혀 직접 못 봤습니다. 뒤집은 순서에서 메모리 오염 덕에 Context 원문을 우연히 확보했을 뿐이라, "정상 순서에서 RAG가 정확히 무엇을 주입했는지"는 4단계에서 따로 캡처합니다. 그리고 order를 5로 둔 실험 코드는 20으로 복원했습니다.
