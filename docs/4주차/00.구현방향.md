# 4주차 구현 방향 — 정책 문서를 검색해서 답하게 만들기

4주차 PDF를 읽고 먼저 정리한 건, RAG를 "붙이는" 일과 RAG를 "쓸 만하게 만드는" 일이 다른 문제라는 점이었습니다.
검색해서 프롬프트에 끼우는 건 `QuestionAnswerAdvisor` 한 줄이면 끝납니다.
정작 손이 가는 건 문서를 얼마나 잘게 쪼갤지, 몇 건을 가져올지, 유사도 얼마 위를 믿을지, 그리고 못 찾았을 때 어떻게 입을 다물지를 정하는 쪽이었어요.
그래서 이번 구현은 RAG를 켜는 데서 멈추지 않고, 그 경계값들을 실측으로 만져 보는 걸 목표로 잡았습니다.

## 스타터 코드와 내 레포가 갈라져 있었다

이번엔 시작부터 결정할 게 하나 있었습니다.
강의 스타터 코드(`round4` 브랜치)는 모든 클래스가 `com.baedal.support` 한 트리에 모여 있고 `rag` 패키지에 TODO만 비워 둔 형태인데, 제 레포는 3주차까지 오면서 Tool 도메인을 `com.baedal.assistant`로, 메모리·인프라를 `com.baedal.support`로 갈라 둔 상태였습니다.
스타터의 `RagConfig`/`KnowledgeLoader`를 그대로 복붙하면 패키지 경로와 import가 어긋나니까, 자산은 가져오되 제 구조에 맞춰 이식하기로 했어요.
RAG는 두 컨트롤러가 같이 쓰는 횡단 인프라라서, 인프라성 코드가 모여 있는 `com.baedal.support.rag`에 두면 스타터와 패키지명도 맞아떨어져 import 손질이 가장 적었습니다.

한 가지 더 갈린 건 정책 인용 규칙을 어느 프롬프트에 넣느냐였습니다.
스타터 TODO는 `BaedalPrompt`에 넣으라고 하는데, 1단계 검증 시나리오는 전부 `/api/v1/assistant`를 두드립니다.
그 엔드포인트가 쓰는 건 `AssistantPrompt`라서, 규칙은 `AssistantPrompt`에 먼저 넣고 트리아지용 `BaedalPrompt`에도 같은 취지로 한 벌 더 넣었습니다.

## 3주차에서 이어받은 전제

- `AssistantController`(`com.baedal.assistant`)는 2주차 Tool Calling의 중심이고 `String`을 그대로 돌려줍니다. 4주차 시나리오가 두드리는 곳도 여기입니다.
- `SupportController`는 1차 트리아지 JSON을 만듭니다. 같은 체인을 쓰니 RAG를 동일하게 끼웠습니다.
- `ChatMemoryConfig`는 기본 프로파일에서 InMemory, `jdbc` 프로파일에서 H2를 씁니다. 이게 4주차에서 작은 사고를 냈습니다(아래).
- `PerformanceLoggingAdvisor`는 호출 시간과 토큰을 남깁니다. RAG가 키운 입력 토큰을 보는 기준은 4주차에도 이 advisor입니다.

## 이번 1단계에서 일부러 좁힌 범위

3주차 때처럼, 첫 커밋은 "RAG가 실제 정책 원문을 검색해 답한다"까지만 확인하고 멈추는 단위로 잘랐습니다.
청크 크기 실험과 임계값 튜닝까지 한꺼번에 섞으면, 검색이 안 되는 게 청킹 문제인지 임계값 문제인지 프롬프트 문제인지 분리가 안 됩니다.
그래서 1단계는 다음 세 가지가 서면 끝으로 봤어요.
하나, `RagConfig`/`KnowledgeLoader`가 Spring AI 1.0 실제 API로 컴파일되고 기동 시 7건이 적재된다.
둘, 시나리오 5종에서 정책 원문 수치가 응답에 그대로 나오거나, 못 찾을 땐 Fallback으로 빠진다.
셋, 재기동해도 같은 문서가 두 배로 쌓이지 않는다.

## datasource를 더했더니 메모리 빈이 충돌했다

이식에서 제일 먼저 터진 건 RAG가 아니라 메모리 쪽이었습니다.
PgVector는 PostgreSQL이라 기본 프로파일에 datasource를 새로 넣었는데, 그 순간 `spring-ai-starter-model-chat-memory-repository-jdbc`의 자동 구성이 깨어나 `jdbcChatMemoryRepository`를 만들었습니다.
제가 `ChatMemoryConfig`에서 등록한 InMemory 저장소와 합쳐 `ChatMemoryRepository` 빈이 둘이 되니까, `chatMemory(...)`가 어느 걸 받을지 몰라 기동이 통째로 멈췄어요.

```
No qualifying bean of type 'ChatMemoryRepository' available: expected single matching bean but found 2:
  chatMemoryRepository, jdbcChatMemoryRepository
```

해결은 프로파일로 갈랐습니다.
기본 프로파일에서는 InMemory 메모리만 쓰니까 `application.yml`에서 JDBC ChatMemory 자동 구성을 `spring.autoconfigure.exclude`로 끄고, 3주차 실험용인 `jdbc` 프로파일에서는 `exclude`를 비워 다시 켜지도록 했습니다.
PDF가 "Round 3 JDBC Chat Memory도 PgVector와 같은 인스턴스로 합칠 수 있다"고 가볍게 언급한 부분이, 막상 한 datasource를 둘이 나눠 쓰려니 자동 구성끼리 부딪히는 현실적인 마찰로 돌아온 셈이었어요.
지금은 둘을 합치지 않고 프로파일로 떼어 놓는 선택을 했고, 한 PostgreSQL에 메모리와 벡터를 같이 얹는 건 다음 과제로 남겨 뒀습니다.

## 실측에 쓴 기본 흐름

```bash
docker compose up -d                # baedal-pgvector (pg16)
ollama pull qwen3-embedding:0.6b    # 1024차원 임베딩
./gradlew bootRun                   # 기동 시 KnowledgeLoader가 7건 적재
```

```bash
curl -s -X POST http://localhost:8080/api/v1/assistant \
  -H "Content-Type: application/json" -H "X-Session-Id: rag-1" \
  -d '{"message":"비 오는 날 배달이 늦으면 보상 받을 수 있나요?"}'
```

raw는 `docs/4주차/실측-raw/` 아래에 남겼습니다.
여기서 봐야 할 건 답이 매끄러운지가 아니라, 응답 안에 정책 원문의 수치("60분", "24시간")가 그대로 박혀 들어왔는지였습니다.
단계별 상세는 `01.RAG기본구현과시나리오5종.md`에 적었습니다.
