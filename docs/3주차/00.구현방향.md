# 3주차 구현 방향 전수조사

3주차 PDF를 읽고 나서 먼저 든 생각은, 이번 라운드는 기능을 하나 켜는 문제가 아니라 세션 경계를 어디에 둘지 정하는 문제라는 점이었다. 2주차까지의 코드는 주문번호가 한 턴 안에 들어온 경우에는 Tool Calling을 할 수 있지만, "그거", "아까 그 주문" 같은 표현을 처리할 근거가 없다. 그래서 이번 구현은 LLM 답변 품질을 바로 단정하기보다, Spring AI의 Memory가 프롬프트 조립에 실제로 끼어들 수 있는 구조를 먼저 만든다.

## 현재 코드에서 이어받은 전제

- `AssistantController`는 2주차 Tool Calling의 중심이다. `OrderTools` 3개가 이미 붙어 있고, 주문 조회/배달 상태/취소를 처리한다.
- `SupportController`는 1차 트리아지 JSON 응답을 만든다. 상담 맥락을 이어받아야 하므로 3주차 Memory 연결 대상에 포함한다.
- `PerformanceLoggingAdvisor`는 LLM 호출 시간과 토큰 메타데이터를 남긴다. 3주차의 입력 토큰 증가 관찰은 이 advisor 로그를 기준으로 잡는다.
- `application.yml`은 `org.springframework.ai: DEBUG`를 켜고 있다. Memory가 프롬프트 앞에 붙는지 확인할 수 있는 최소 조건은 이미 있다.

## 이번 구현에서 일부러 좁힌 범위

첫 커밋 범위는 1단계 구조를 잡는 데 뒀다. JDBC 저장소와 10턴 정량 실험까지 한 번에 섞으면, 컴파일 문제인지 세션 설계 문제인지 LLM 응답 편차인지 분리하기 어렵다. 그래서 지금은 다음 세 가지가 통과하면 멈추는 작은 단위로 잘랐다.

1. Memory 3레이어 Bean이 Spring AI 1.0 실제 API로 컴파일된다.
2. 컨트롤러가 `X-Session-Id`를 요청별 `ChatMemory.CONVERSATION_ID`로 넘긴다.
3. 세션 목록, 메시지 조회, 삭제가 Memory 저장소 기준으로 동작한다.

현재 검증 근거는 두 층이다. 첫째, `./gradlew test --rerun-tasks`로 Memory wiring, 세션 조회/삭제, 헤더 누락 400, window size 설정을 고정했다. 이 테스트는 LLM을 호출하지 않으므로 "지시 대명사가 잘 풀린다"까지 증명하지 않는다. 둘째, `docs/3주차/실측-raw/`에 curl 응답, 세션 JSON, advisor token, Tool 로그를 남겼다. 이 raw는 LLM 응답 품질이 아니라 이번 조건에서 관측된 동작을 보여준다.

## 실측에 사용한 기본 흐름

서버를 띄우고 PDF의 시나리오를 두드렸다. raw는 `docs/3주차/실측-raw/` 아래에 남겼다.

```bash
./gradlew bootRun
```

```bash
curl -s -X POST http://localhost:8080/api/v1/assistant \
  -H "Content-Type: application/json" \
  -H "X-Session-Id: cust-A" \
  -d '{"message":"2024-1234 어디쯤 있어요?"}'

curl -s -X POST http://localhost:8080/api/v1/assistant \
  -H "Content-Type: application/json" \
  -H "X-Session-Id: cust-A" \
  -d '{"message":"그거 언제 도착해요?"}'

curl -s http://localhost:8080/api/v1/session/cust-A/messages | jq
```

이 결과에서 봐야 할 것은 답변이 그럴듯한지가 아니라, 2회차 요청이 이전 `2024-1234` 맥락을 들고 들어갔는지다. 그 증거는 세션 JSON, DEBUG 로그, `[Tool] getDeliveryStatus(orderId=2024-***)` 로그를 같이 봤다.

남은 불확실성은 세 가지다. 첫째, 이번 raw에는 Memory advisor가 최종 모델 입력에 삽입한 프롬프트 전문이 없다. 둘째, Spring AI의 기본 Memory advisor가 Tool 메시지를 저장하지 않는다면, 다음 턴의 추론은 1회차 assistant 자연어 응답에 남은 주문번호에 기대게 된다. 셋째, Qwen2.5가 "그거"를 어떤 주문으로 해석하는지는 프롬프트와 직전 응답 문장에 흔들릴 수 있다. 그래서 문서에서는 성공 사례뿐 아니라 실패 턴도 raw로 남겼고, 모델 일반화는 하지 않았다.
