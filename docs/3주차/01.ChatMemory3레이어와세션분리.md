# 3주차 - ChatMemory 3레이어와 세션 분리 (단계 1)

> 이번 단계에서 먼저 확인하고 싶었던 건 "그거"를 잘 알아듣는지가 아니었다. 그 전에, 이전 턴을 세션별로 저장하고 다음 호출에 다시 끼워 넣을 통로가 실제로 열렸는지부터 봐야 했다.

## 시작점

2주차까지의 `/api/v1/assistant`는 주문번호가 한 문장 안에 들어오면 Tool을 부를 수 있었다. 하지만 다음 문장처럼 주문번호가 빠지는 순간 서버 쪽에는 이어받을 맥락이 없었다.

```text
고객: 2024-1234 어디쯤 있어요?
고객: 그거 언제 도착해요?
```

LLM이 두 번째 문장의 "그거"를 `2024-1234`로 해석하려면, 첫 번째 USER/ASSISTANT 메시지가 같은 세션 안에 남아 있어야 한다. 그래서 1단계는 답변 품질보다 Memory wiring을 먼저 고정했다.

## 구현한 경계

`ChatMemoryConfig`에 Spring AI Memory 3레이어를 명시적으로 조립했다.

- `ChatMemoryRepository`: 기본 profile에서는 `InMemoryChatMemoryRepository`
- `ChatMemory`: `MessageWindowChatMemory`, `MAX_MESSAGES = 20`
- `MessageChatMemoryAdvisor`: `order(10)`으로 `PerformanceLoggingAdvisor(order=100)`보다 앞에 둠

`AssistantController`와 `SupportController`는 둘 다 `X-Session-Id`를 받는다. 처음에는 헤더가 없으면 Spring AI 기본값인 `default`로 떨어지게 했지만, 세션 오염 위험이 더 크다고 보고 최종 구현에서는 헤더 누락을 400으로 막았다. 구버전 클라이언트가 헤더를 못 보내거나, 악의적인 사용자가 일부러 헤더를 빼도 여러 사용자가 같은 default 세션을 공유하지 않게 하려는 선택이다.

```java
.advisors(a -> a.param(ChatMemory.CONVERSATION_ID, sessionId))
```

이 한 줄이 이번 단계의 핵심이다. ChatClient를 요청마다 다시 build하지 않고, 요청별 advisor parameter만 바꿔서 같은 ChatClient에 다른 conversationId를 넘긴다.

## 세션을 눈으로 보기 위한 API

실험용으로 세션 API를 열었다.

- `GET /api/v1/session/{id}/messages`
- `DELETE /api/v1/session/{id}`
- `GET /api/v1/session/ids`

운영 API라기보다 관찰 도구다. 이번 라운드에서는 LLM 응답만 보고 판단하지 않고, Memory에 실제로 무엇이 쌓였는지를 같이 봐야 한다.

## 단위 테스트로 잠근 것

`ChatMemoryConfigTest`는 `MAX_MESSAGES`가 실제로 최근 메시지만 남기는지 확인한다. 지금 값 20은 USER/ASSISTANT 합산 최근 20개라, 대략 10턴 정도의 대화를 남기는 출발점이다.

`SessionControllerTest`는 세션 A/B가 서로 섞이지 않는지, `DELETE`가 지정 세션만 지우는지 확인한다.

컨트롤러 테스트는 `MessageChatMemoryAdvisor`가 `PerformanceLoggingAdvisor`보다 먼저 등록되고, 요청별로 `advisors(...)`가 호출되는지까지 맞췄다.

## 첫 smoke에서 본 것

raw는 `실측-raw/단계1-smoke.md`에 남겼다.

첫 턴:

```text
2024-1234 어디쯤 있어요?
```

로그:

```text
Executing tool call: getDeliveryStatus
[Tool] getDeliveryStatus(orderId=2024-***)
LLM call elapsedMs=9856 promptTokens=2980 completionTokens=93 totalTokens=3073
```

두 번째 턴:

```text
그거 언제 도착해요?
```

응답은 첫 턴의 예상 도착 시간을 이어서 말했다. `/api/v1/session/smoke-r3/messages`에는 USER/ASSISTANT 2쌍이 저장됐다.

다만 2턴에서 `[Tool] getDeliveryStatus` 로그가 다시 찍히지는 않았다. 이건 중요하다. 이번 smoke는 "Memory가 저장되고 다음 턴에서 사용될 통로가 있다"는 근거이지, "지시 대명사를 매번 Tool 파라미터로 정확히 복원한다"는 근거가 아니다. LLM이 첫 assistant 응답 안의 도착 시간을 재사용했을 가능성이 더 크다.

## 5종 시나리오를 돌려본 결과

raw는 `실측-raw/단계1-시나리오5종.md`에 따로 남겼다.

| 시나리오 | 기대 | 관찰 |
| --- | --- | --- |
| 1. 같은 세션에서 "그거 언제 도착" | 이전 1234 맥락 사용 | 도착 시간을 이어 말했지만 Tool 재호출 로그는 없음 |
| 2. 취소 대상 전환 | 1235로 취소 대상 전환 | 1턴 1234 취소는 Tool 없이 흉내, 2턴 1235는 `cancelOrder` 호출 |
| 3. 이전 주문 참조 | "아까 물어본 주문"을 1234로 해석 | 맥락은 일부 이어졌지만 응답에 중국어/터키어 문장 섞임 |
| 4. 세션 오염 테스트 | B 세션은 A의 주문번호를 모름 | B는 주문번호를 되물었고 A의 1234를 참조하지 않음 |
| 5. Memory 삭제 후 "그거" | 삭제 후 맥락 소실 | 삭제 직후 messages는 `[]`, 이후 "그거"는 되물음 |

가장 확실한 성공은 세션 분리와 삭제다. 세션 B가 A의 주문번호를 가져오지 않았고, `DELETE` 이후 같은 세션에서 "그거"를 던졌을 때 이전 주문번호를 이어받지 못했다.

반대로 LLM 응답 품질은 아직 불안정하다. 특히 취소 시나리오의 1턴은 Tool 호출 없이 "취소 처리하겠다"는 식으로 말했고, 이전 주문 참조 시나리오에서는 다른 언어 문장이 응답에 섞였다. 이건 Memory wiring 문제가 아니라 모델 응답 품질과 Tool routing 안정성 문제로 따로 봐야 한다.

## 다음 단계로 넘기는 질문

이제 봐야 할 것은 `MAX_MESSAGES` 크기를 줄이거나 늘렸을 때 이 통로가 어떻게 망가지는지다. 특히 `MAX_MESSAGES = 2`에서는 직전 USER/ASSISTANT 한 쌍만 남기 때문에, "아까 1234" 같은 표현이 깨질 가능성이 높다. 그 실패를 단순히 "안 됐다"가 아니라 요청, 응답, Memory JSON, Tool 로그로 잡아야 한다.
