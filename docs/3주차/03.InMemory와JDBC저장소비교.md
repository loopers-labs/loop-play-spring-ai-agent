# 3주차 - InMemory와 JDBC 저장소 비교 (단계 3)

> 여기서 보고 싶은 건 "JDBC로 바꿀 수 있다"가 아니라, 어떤 운영 조건에서 InMemory가 더 이상 답이 아닌지를 재시작과 세션 유지 실험으로 확인하는 것이다.

## 구현한 것

기본 profile은 `InMemoryChatMemoryRepository`를 쓴다.

```java
@Profile("!jdbc")
ChatMemoryRepository chatMemoryRepository() {
    return new InMemoryChatMemoryRepository();
}
```

`jdbc` profile에서는 Spring AI 자동 구성이 `JdbcChatMemoryRepository`를 만든다. 이때 같은 `MessageWindowChatMemory` 정책 레이어가 저장소 위에 얹힌다.

추가한 의존성:

```groovy
implementation 'org.springframework.ai:spring-ai-starter-model-chat-memory-repository-jdbc'
runtimeOnly 'com.h2database:h2'
```

## 첫 실패에서 배운 것

raw는 `실측-raw/단계3-jdbc-memory.md`에 남겼다.

처음에는 H2니까 `initialize-schema: embedded`만 두면 될 거라고 봤다. 그런데 Spring AI 1.0.0 jar에는 `schema-h2.sql`이 없었다.

```text
No schema scripts found at location
'classpath:org/springframework/ai/chat/memory/repository/jdbc/schema-h2.sql'
```

jar 내부에는 `schema-postgresql.sql`, `schema-sqlserver.sql`, `schema-hsqldb.sql`, `schema-mariadb.sql`만 있었다. 그래서 H2를 PostgreSQL mode로 띄우고, JDBC memory repository platform도 `postgresql`로 지정했다.

```yaml
spring:
  datasource:
    url: jdbc:h2:mem:baedal;MODE=PostgreSQL;DB_CLOSE_DELAY=-1;DB_CLOSE_ON_EXIT=FALSE
  ai:
    chat:
      memory:
        repository:
          jdbc:
            initialize-schema: always
            platform: postgresql
```

`initialize-schema: always`로 둔 이유는 file 기반 H2도 스키마를 만들어야 하기 때문이다. Spring AI의 postgresql schema는 `CREATE TABLE IF NOT EXISTS`라 재기동 시 중복 생성 에러는 나지 않았다.

## 비교할 조건

| 저장소 설정 | 재시작 후 Memory 유지? | 확인 방법 | 비고 |
| --- | --- | --- | --- |
| InMemory | 아니오 | JVM 종료 시 저장소 자체 소실 | 기본 profile |
| `jdbc:h2:mem:...` | 아니오 | 재시작 뒤 `/api/v1/session/r3-jdbc-mem/messages`가 `[]` | JDBC여도 DB가 메모리 |
| `jdbc:h2:file:...` | 예 | 재시작 뒤 같은 세션 메시지 유지 | 파일 기반 영속 |

file 기반 H2는 앱 재시작 뒤에도 다음 행이 남았다.

```text
CONVERSATION_ID | TYPE      | CONTENT
r3-jdbc-file    | USER      | 2024-1234 어디쯤 있어요?
r3-jdbc-file    | ASSISTANT | 현재 배달원은 역삼역 사거리 부근에서 작업 중이며, 예상 도착 시간은 2026년 6월 1일 오후 8시 17분입니다. 추가로 궁금한 점이 있으시면 알려주세요.
```

## 봐야 할 운영 판단

InMemory로 충분한 조건은 꽤 좁다.

- 단일 인스턴스다.
- 세션이 짧고, 서버 재시작 후 이어질 필요가 없다.
- 상담 이력을 감사나 CS 조회용으로 보관하지 않는다.

JDBC가 필요한 조건은 반대다.

- 로드밸런서 뒤 멀티 인스턴스다.
- 앱을 껐다 켜도 대화가 이어져야 한다.
- 상담 이력을 일정 기간 보관해야 한다.

## 실제 운영이면 무엇을 고를까

배달 상담 운영이라면 H2가 아니라 PostgreSQL 쪽으로 간다. 이유는 세 가지다.

- Round 4에서 PgVector를 쓸 예정이라 같은 운영 DB 계열 안에서 정책/RAG/Memory를 같이 설계하기 쉽다.
- 상담 이력은 조회, 백업, 접근 제어, TTL 정책이 필요하다.
- 멀티 인스턴스 배포에서 로컬 JVM 메모리나 로컬 파일 DB는 세션 분리를 보장하지 못한다.

다만 JDBC로 바꾸는 순간 Memory 테이블은 개인정보 저장소가 된다. 그래서 동시에 봐야 할 것은 백업, TTL, 인덱스, 암호화, 상담원 조회 권한이다.

## 남은 한계
