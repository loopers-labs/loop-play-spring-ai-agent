# 3주차 - Observability와 AI 코드 리뷰 (단계 4)

> 2주차에서 Tool Calling은 응답 본문만 보면 속기 쉽다는 걸 봤다. 3주차도 마찬가지다. "그거"를 잘 답한 것처럼 보여도 실제로는 Tool을 다시 부른 게 아니라 이전 assistant 문장을 복사했을 수 있다.

## 이번 단계에서 보고 싶은 것

이번 단계의 질문은 두 가지였다.

- Memory가 붙은 뒤 입력 토큰과 응답이 어떻게 흔들리는가.
- AI가 만든 "세션별 Memory 예시 코드"는 이번 프로젝트의 구현 방향과 어디서 어긋나는가.

raw는 두 파일로 나눴다.

- `실측-raw/단계4-observability-token-growth.md`
- `실측-raw/단계4-AI코드리뷰-codex원본.md`

프롬프트 전문 캡처는 이번 단계에서 확보하지 못했다. 그래서 "Memory가 어떤 문자열로 프롬프트에 삽입됐다"가 아니라, 세션 메시지 API / advisor token / Tool 로그를 나눠서 관찰한 수준으로만 적는다.

이 단계의 관찰은 `qwen2.5` 한 모델에서의 결과다. 언어 혼입, Tool 재호출 여부, "가능해요?"를 실행 의도로 해석하는 문제는 Spring AI Memory의 구조적 특성이라기보다 모델의 지시 준수와 Tool Calling 성향이 섞인 결과일 수 있다. 그래서 여기서는 모델 일반화 대신, 같은 코드와 같은 시나리오에서 다시 확인할 수 있는 raw를 남기는 데 집중했다.

## 10턴 토큰 증가 표

`MAX_MESSAGES = 20` 기준 단계 2의 10턴 실행을 이 단계의 observability raw로 재사용했다. 조건이 같고, 단계 2 raw에 advisor 로그와 최종 Memory가 이미 남아 있었기 때문이다.

| 턴 | 입력 토큰 | 출력 토큰 | 응답 시간(ms) | 관찰 |
| ---: | ---: | ---: | ---: | --- |
| 1 | 2982 | 90 | 7011 | `2024-1234` 배달 상황 |
| 2 | 1532 | 27 | 4751 | "그거 몇 분"을 이전 답변에서 이어 말함 |
| 3 | 3340 | 120 | 3440 | `2024-1235` 메뉴 |
| 4 | 1671 | 71 | 1975 | "버거 세트"로 잘못 바뀜 |
| 5 | 1766 | 72 | 1839 | `2024-1234` 취소 가능 |
| 6 | 1860 | 59 | 1525 | `1235` 취소 가능 |
| 7 | 1934 | 41 | 1115 | "그거 취소"를 `2024-1235`로 해석 |
| 8 | 1998 | 73 | 2012 | `2024-1234` 도착 시간 |
| 9 | 2090 | 47 | 1266 | "그 주문"을 `2024-1234`로 해석 |
| 10 | 2162 | 85 | 2180 | 질문 요약 |

숫자만 보면 3턴이 3340으로 가장 크고, 이후 4턴부터는 1600~2100대에서 움직인다. 단순히 "턴이 늘수록 계속 선형 증가한다"고 쓰면 틀린 해석이다. 같은 10턴 안에서도 Tool 호출 여부, Tool 결과 JSON, 직전 대화 길이가 같이 섞인다.

이번 표에서 말할 수 있는 건 더 좁다.

- Memory window가 20개 메시지라 10턴 대화 전체가 남았다.
- 지시 대명사 입력에서 이전 assistant 답변을 재사용하는 장면이 있었다.
- advisor token만으로는 Tool 재호출 여부를 알 수 없고, Tool 로그를 따로 봐야 한다.

단계 1 smoke가 이 한계를 잘 보여준다. 2턴 `"그거 언제 도착해요?"`는 도착 시간을 답했지만, 새 `getDeliveryStatus` Tool 로그는 없었다. 이 경우 관측은 "Tool을 다시 불렀다"가 아니라 "직전 assistant 답변에 남은 도착 시간을 이어 썼다"에 가깝다.

## AI 코드 리뷰에서 볼 결함

이번 작업에서 AI가 만들 법한 짧은 예시 코드를 하나 작성하고, 그 코드를 현재 구현과 비교했다. 원문은 `실측-raw/단계4-AI코드리뷰-codex원본.md`에 남겼다.

```text
Spring AI 1.0으로 배달 챗봇에 대화 메모리 기능을 붙여줘. 세션별로 대화가 유지되어야 해.
```

이번 코드 리뷰 raw는 여러 모델 비교가 아니다. Codex가 만든 짧은 예시를 현재 구현과 비교한 것이다. 받은 코드는 짧게는 그럴듯했다. `MessageChatMemoryAdvisor`를 붙이고, 요청별 `sessionId`를 `ChatMemory.CONVERSATION_ID`로 넘긴다. 하지만 이번 프로젝트 구현과 비교하면 바로 걸리는 지점이 있다.

### 결함 1: 요청마다 ChatClient를 다시 build

생성 코드는 컨트롤러 메서드 안에서 매번 다음 흐름을 탄다.

```java
ChatClient chatClient = builder
        .defaultAdvisors(new MessageChatMemoryAdvisor(chatMemory))
        .build();
```

이번 프로젝트에서는 이 패턴을 피했다. `AssistantController`와 `SupportController`는 생성자에서 `defaultTools(...)`, `defaultAdvisors(...)`를 한 번만 등록하고, 요청마다 바꾸는 값은 conversation id만 `.advisors(...)`로 넘긴다.

```java
.advisors(a -> a.param(ChatMemory.CONVERSATION_ID, sessionId))
```

요청마다 build하면 지금처럼 테스트로 "매 요청마다 tools/advisors를 재등록하지 않는다"는 경계를 잡기 어렵고, Builder 상태를 공유하는 코드에서 의도하지 않은 중복 등록을 만들 수 있다.

### 결함 2: Spring AI 1.0 Memory 레이어가 흐릿하다

생성 코드는 `InMemoryChatMemory`라는 Bean을 둔다. 하지만 이번 구현에서 실제로 다룬 구조는 세 겹이다.

- `ChatMemoryRepository`: 저장소. 기본은 InMemory, `jdbc` profile은 JDBC
- `MessageWindowChatMemory`: 최근 N개 메시지만 프롬프트에 넣는 정책
- `MessageChatMemoryAdvisor`: ChatClient 호출에 Memory를 끼워 넣는 어댑터

이 세 겹을 나눠야 2단계와 3단계가 가능했다. Memory 크기는 `baedal.chat-memory.max-messages`로 조정했고, 저장소는 profile로 JDBC까지 바꿨다. AI 예시처럼 한 Bean으로 뭉개면 "크기 정책"과 "저장소 영속성"을 따로 실험하기 어렵다.

### 결함 3: Memory window와 보관 정책이 없다

AI 예시에는 몇 개 메시지를 기억할지, 언제 버릴지, 어떤 저장소를 쓸지 기준이 없다. 단계 2에서 `MAX_MESSAGES=2`는 지시 대명사 복원이 크게 흔들렸고, `MAX_MESSAGES=20`과 `100000`은 10턴에서는 비슷했다. 이 관측만으로 운영값을 정할 수는 없지만, 적어도 window가 실험 대상이라는 점은 분명했다.

상담 Memory는 단순 편의 기능이 아니라 사용자 발화와 주문 맥락을 저장한다. 그래서 저장 기간, 세션 삭제, 재시작 후 유지 여부, 멀티 인스턴스에서 같은 세션을 누가 읽는지까지 같이 봐야 한다.

### 결함 4: 세션 ID 정책이 너무 낙관적이다

AI 예시는 request body의 `sessionId`를 그대로 믿는다. 이번 구현도 아직 운영 인증까지 붙인 것은 아니지만, 적어도 API 표면에서는 `X-Session-Id` 헤더로 분리하고, 세션 조회/삭제 API를 따로 만들었다.

운영이라면 여기서 더 나가야 한다. 세션 ID가 비어 있을 때 default로 모을지, 로그인 사용자별로 묶을지, 브라우저 탭 단위로 나눌지, 상담 종료 시 삭제할지를 정해야 한다. 이 정책 없이 Memory만 붙이면 "이전 대화가 이어진다"는 장점이 곧 다른 사용자의 맥락이 섞일 수 있는 위험으로 바뀐다.

## 이번 단계에서 확정한 것과 아닌 것

확정한 것:

- 4단계 문서는 단계 2의 10턴 advisor 로그를 근거로 token 관찰을 정리했다.
- 응답 본문만으로 Tool 재호출을 판단하지 않고, Tool 로그와 분리해서 본다.
- AI 생성 예시 코드는 이번 프로젝트의 3레이어 Memory 구조, window 설정, JDBC 전환 기준을 충분히 담지 못했다.

아직 아닌 것:

- Memory advisor가 모델에게 넘긴 최종 프롬프트 전문은 캡처하지 못했다.
- 10턴보다 긴 대화에서 `MAX_MESSAGES=20`과 `100000`이 어느 지점부터 갈라지는지는 보지 못했다.
- AI 코드 리뷰는 한 번 만든 예시를 현재 구현과 비교한 것이지, 모델별 생성 코드 품질 비교는 아니다.
