# Round 4 · 3단계 — Advisor 순서 (Memory ↔ RAG)

> Advisor 체인은 `order` 오름차순 실행: memory(10) → rag(20) → performance(100).
> `QuestionAnswerAdvisor`의 order를 20 → 5로 뒤집어(rag가 memory보다 먼저) 멀티턴 품질이 깨지는지 관찰.

## 실험 — 동일 2턴 대화 비교

turn1: `"2024-1234 주문 받았는데 음식이 상해서 왔어요"` (메모리에 orderId 축적)
turn2: `"아까 그거 환불돼요?"` (memory로 "그거"=1234 복원 + RAG 환불정책 필요)

| 순서 | turn2 결과 |
|------|-----------|
| **정상 (memory 10 → rag 20)** | "그거"를 **2024-1234로 복원**, 환불 정책 안내 ✅ |
| **뒤집음 (rag 5 → memory 10)** | "그거"를 **못 풀고** "어떤 주문이요? 주문번호를 알려주세요" 되물음 ❌ (게다가 중국어로 누출 — qwen 불안정) |

뒤집힌 순서 turn2 실제 응답:
```
그거指的是您之前提到的那笔订单。请问您是希望为哪一笔订单申请退货呢?
请您提供一下具体的订单号...
```

## 무엇이 깨졌나
rag가 memory보다 먼저 실행되면, "그거"가 1234로 복원되기도 **전에** RAG가 막연한 원문 질문으로 검색·응답 조립을 시작한다. 그 결과 대화 맥락이 제때 결합되지 못해 모델이 "주문번호를 다시 알려달라"로 후퇴 — 멀티턴 상담의 핵심(이전 턴 참조)이 무너진다.

## 설계 결정 (3단계) — *초안, 제출 전 검토*
- **순서를 뒤바꾸면?** → 위 관찰대로 지시 대명사("그거/아까 그") 기반 후속 질문이 깨진다. Memory가 먼저 대명사를 구체 orderId로 복원해야 RAG가 "그 주문의 정책"을 의미 있게 검색할 수 있다. order는 단순 숫자지만 **데이터 의존성(memory 출력 → rag 입력)** 을 표현한다.
- **반대 순서가 더 나은 경우는?** → 대화 맥락과 무관하게 "정책 자체"만 묻는 단발성 FAQ("환불 정책 알려줘")라면 memory 복원이 불필요하므로 순서 영향이 적다. 또한 5주차 Guardrail 관점에서, 검색된 정책으로 **먼저** 입력을 필터링/차단해야 하는 보안 시나리오라면 RAG성 검사를 앞단에 두는 설계가 정당화될 수 있다(맥락 주입과는 다른 목적).
- **similarityThreshold만으로 환각을 100% 막을 수 있나?** → 아니다. 임계값은 "관련 없는 문서 제거"만 한다. 검색이 비어도 LLM은 없는 얘기를 지어낼 수 있으므로, 프롬프트의 [정책 인용 규칙](Context 없으면 상담원 연결 Fallback)이 함께 있어야 환각을 막는다. 임계값(검색 레벨) + Fallback 규칙(생성 레벨)의 **이중 방어**.
