# Round 4 · 4단계 — Observability(토큰 비용) + AI 코드 리뷰

## RAG의 입력 토큰 비용 — PerformanceLoggingAdvisor

| 호출 | promptTokens | completionTokens | 비고 |
|------|:---:|:---:|------|
| 정책 질문 "배달 지연 보상 정책?" (RAG 검색 발동) | **2,924** | 405 | 검색된 정책 청크가 Context로 주입됨 |
| 인사 "ㅎㅇ" (검색 결과 임계값 미달 → Context 비움) | **2,044** | 87 | 정책 없음, 베이스(시스템+[정책 인용 규칙]+tool 스키마+memory)만 |
| 인사 "안녕하세요 반가워요" | 2,049 | 36 | 위와 동급 |

→ **RAG가 실제로 정책을 회수해 주입하면 입력 토큰이 ~880(약 43%) 증가**. 검색이 안 걸리는 질문은 베이스만 소비.
- 베이스(~2,044)에는 RAG를 안 써도 `QuestionAnswerAdvisor`의 프롬프트 템플릿 + [정책 인용 규칙] 섹션 + (R2의) tool 스키마가 이미 상주.
- **비용 = TOP_K × 청크 크기**에 비례. TOP_K=10·chunkSize=2000이면 정책 원문 10개가 매 요청 프롬프트에 들어가 토큰이 폭증한다. "정확도 ↑ ↔ 토큰·지연 ↑" 트레이드오프를 TOP_K/threshold/chunkSize로 조율하는 것이 RAG 튜닝의 본질.

## AI 코드 리뷰 — 프로덕션 결함 3개

> RAG 코드(`KnowledgeLoader`, `RagConfig`)를 프로덕션 기준으로 비판적 리뷰.

### 결함 1 — `alreadyLoaded()`가 "내용 변경"을 감지 못 함
중복 적재 방지를 **faqId 존재 여부**로만 한다. 그래서 정책 문서의 *내용이 바뀌어도*(예: 환불 가능 기간 30분→60분) faqId가 이미 있으니 **스킵** → 벡터스토어엔 **옛 정책이 영원히 남고**, 고객에게 낡은 수치를 인용한다. (코드 주석도 이 한계를 명시.)
→ **수정**: 문서 내용의 **해시(checksum)** 를 metadata에 저장하고, 적재 시 해시가 다르면 기존 청크 삭제 후 재임베딩(upsert). 또는 버전 필드.

### 결함 2 — 임베딩 차원 불일치의 "조용한 실패"
`application.yml`의 `pgvector.dimensions=1024`와 임베딩 모델 차원이 어긋나면(예: nomic-embed-text=768로 교체) 명확한 에러 없이 검색이 **조용히 망가진다**(빈 결과/엉뚱한 결과). 기동 시 검증이 없다.
→ **수정**: 기동 시 `embeddingModel.dimensions()` 와 설정 dimensions를 비교해 불일치면 **fail-fast**(명시적 예외). 환경 의존 실수를 배포 즉시 드러나게.

### 결함 3 — `filterExpression` 문자열 결합
`alreadyLoaded()`가 `"faqId == '" + faqId + "'"` 로 필터를 **문자열 연결**한다. faqId에 작은따옴표/특수문자가 들어오면 표현식이 깨지거나 주입성 위험. 지금은 faqId가 깨끗한 파일명이라 우연히 안전할 뿐.
→ **수정**: 파라미터 바인딩 가능한 필터 API 사용, 또는 faqId를 화이트리스트 정규식으로 검증 후 결합.

> 추가 후보: 임베딩 호출 실패 시 `KnowledgeLoader.run()` 예외 → 기동 실패(재시도/부분복구 없음); 범위 밖 질문도 매번 벡터 검색(임베딩 1회 비용) — 명백한 비정책 질문 short-circuit 여지.
