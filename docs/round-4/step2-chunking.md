# Round 4 · 2단계 — 청킹(chunkSize) 실험

> `TokenTextSplitter`의 chunkSize를 200 / 800 / 2000으로 바꿔가며 조각 수 + 검색 품질 비교.
> **각 실험 전 `TRUNCATE vector_store` 필수** (안 하면 옛 청크 + 새 청크가 섞여 측정 오염). 매번 재기동 → KnowledgeLoader 재시드.

## 정량 결과

| chunkSize | vector_store 조각 수 | 검색 품질(동일 질문 3종) |
|:---:|:---:|---|
| **200** | 21 (문서당 3) | 정상. TOP_K=4가 같은 문서 조각들을 함께 회수 → 지연보상에서 **오히려 더 상세**(10분/11–29분/30–59분/60분+ 전 구간 + 제외사유) |
| **800** | 7 (문서당 1) | 깔끔. 1정책 = 1조각 = 1검색단위 |
| **2000** | 7 | 800과 **동일** (문서가 2000토큰 미만이라 통째로 1청크) |

## 핵심 관찰 — 교과서 vs 우리 코퍼스

교과서: "작게 자르면 문맥 조각남 → 환각". 그러나 우리 코퍼스(정책 7건, 각 ~600자, 1문서 1주제)에서는 **200으로 쪼개도 품질 저하가 없었다.**
- 이유: 한 정책이 3조각으로 나뉘어도, TOP_K=4가 그 3조각을 한꺼번에 회수해 정책이 사실상 재조립됨.
- 즉 "조각남 → 환각" 실패는 **"큰 다주제 문서" + "작은 TOP_K"** 조합에서 발생한다. (예: 한 문서에 환불+취소+배송이 섞여 있고 TOP_K=1이면, 환불 조각만 와서 취소 질문에 환각)
- → 청크 크기는 "무조건 작게/크게"가 아니라 **문서당 주제 수 × TOP_K** 에 맞춰 정하는 변수다. (R3의 "큰 메모리 윈도우 ≠ 더 나은 해결"과 같은 결의 정직한 발견.)

## 별개 관찰 — 임계값/임베딩 취약성 (청킹과 무관)
"환불은 언제까지 신청할 수 있고 조건이 어떻게 되나요?" 질문은 chunkSize 200·800 **둘 다** Fallback("상담원 연결")으로 빠졌다. → 작은 임베딩 모델(0.6b)이 이 표현의 유사도를 임계값 0.5 밑으로 매긴 것. 청크 크기 문제가 아니라 **임베딩 모델 정밀도 + 임계값**의 문제. 통제 질문("음식 상해서 환불")은 800에서 정상 검색됨.

## 설계 결정 (2단계) — *초안, 제출 전 검토*
- **이상적 청크 크기?** → 우리 정책 문서는 1개 = 1조항이라 **800**이 적절(문서당 정확히 1청크 = 검색 단위가 "정책 한 건"과 일치). 200은 조각 3배(임베딩/저장 비용 3배)인데 이득 없음. 2000은 지금 800과 동일하나 문서가 길어지면 여러 주제를 한 청크에 뭉쳐 정밀도 저하. → **800 = 현재도 깔끔 + 확장 여유.**
- **문서가 "사용자 리뷰 10만 건"이라면?** → 리뷰는 짧은 독립 단위라 **리뷰 1건 = 1청크**처럼 더 작게. 다만 진짜 과제는 청크 크기보다 **양(volume)** 으로 이동: 인덱싱 전략(HNSW 파라미터), metadata 필터(기간/별점), 임베딩 비용·재색인 주기. 청킹은 "단위가 자명"해 오히려 단순해지고, 스케일·운영이 병목이 된다.
