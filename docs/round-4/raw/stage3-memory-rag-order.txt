============= PART F. Advisor order 증거 (2단계, 검색 레벨) ===========

###################################################################
# Round4 — 왜 memory(10) → rag(20) → performance(100) 인가?
#   order는 '검색을 바꾸는 파라미터'가 아니라 '각 advisor가 무엇을 보는가'의 순서.
#   따라서 증거도 (검색 불변성) + (재작성 역효과) + (가시성 메커니즘) 으로 잡는다.
#   vectorstore=800(7문서), embedding=qwen3-embedding:0.6b, threshold0.5
###################################################################

[F-1] 현재 구현: RAG는 '현재 턴 user text'만 임베딩 → memory↔rag 순서는 검색 결과 불변
  - QuestionAnswerAdvisor.before()는 현재 UserMessage 텍스트로 similaritySearch 한다(이력 미포함).
  - 증거(기존 데이터 대조):
      · 시나리오5-Q2 (memory 보유, PART A) 가 주입한 문서 = "환불 기본 정책" + "주문 취소 정책"
      · 동일 질의 standalone (PART E) Top-2          = refund-basic 0.5408 + cancel-policy 0.5083
      → 둘이 동일. 즉 memory 주입 유무와 무관하게 검색 결과가 같다.
  - 결론: memory(10)와 rag(20)의 order를 바꿔도 '현재 구현'의 검색 문서 집합은 불변.

[F-2] 그러면 memory로 질의를 재작성하면 검색이 좋아지나? → 이 도메인에선 오히려 악화
  질의 변형                                    Top-1                Top-2               0.5통과
  ----------------------------------------------------------------------------------------------
  "아까 그 주문 환불 돼요?" (현재 원문)          refund-basic 0.5408   cancel-policy 0.5083   2건
  "주문번호 2024-1234 환불 돼요?" (orderId 주입) refund-basic 0.4997   cancel-policy 0.4532   0건  ← 둘 다 탈락
  "2024-1234" (orderId 단독)                  privacy      0.3220   weather       0.2494   0건
  "아까 그거 어떻게 돼요?" (순수 대명사)          privacy      0.1725   delay         0.1689   0건
  "환불 돼요?" (정책키워드만)                    refund-basic 0.4184   refund-after  0.3786   0건
  ----------------------------------------------------------------------------------------------
  - orderId "2024-1234"는 정책 문서의 검색 신호가 아니다(정책=상태·규칙 기술, 주문번호 아님).
  - memory가 orderId를 앞에 붙이면 "환불" 의미가 희석 → 0.5408 → 0.4997 로 하락, threshold 탈락.
  - 즉 naive memory 기반 재작성은 정책 RAG를 '개선'이 아니라 '악화'시킨다.
    (정책 검색 신호는 현재 턴의 정책 키워드 '환불/취소/쿠폰'에서 나오며, 이는 이미 현재 턴에 있다.)

[F-3] 그럼 order는 왜 중요한가 — '검색'이 아니라 '가시성·측정'
  - 직접 실측 증거: SimpleLoggerAdvisor order(20)→(30) 사건.
      · order==rag(20) 일 때: request 로그에 RAG가 붙인 [정책 문서] Context 블록이 누락(주입 전만 보임).
      · order>rag(30)  일 때: Context 블록 + qa_retrieved_documents 가 로그에 출현.
      → "advisor는 자기보다 낮은 order의 산출물만 본다"는 체인 원리의 직접 증거(=PART A 로그).
  - 같은 원리로 memory(10) < rag(20) < performance(100):
      · performance(100)는 항상 가장 바깥 → 최종 LLM 호출의 토큰/시간을 '온전히' 측정한다.
        (perf가 rag보다 안쪽이면 RAG 주입 전 프롬프트 기준으로 측정돼 토큰 집계가 틀어진다.)

[결론]
  - 현재 구현에서 memory↔rag order는 검색 결과를 바꾸지 않는다(F-1).
  - naive memory 재작성(orderId 주입)은 정책 검색을 오히려 악화시킨다(F-2).
  - order의 실질 가치는 (a) 체인 가시성/결합 정확성, (b) performance가 전체 호출을 측정하도록 보장(F-3).
  - memory→rag 기본 순서는 여전히 옳다(이력→컨텍스트→측정의 자연스러운 결합)지만,
    그 근거는 "검색 개선"이 아니라 "정확한 결합·측정"이다. order의 검색상 이득은 이 도메인에선 ~0이며,
    발현되려면 다른 설계(주문번호로 키된 '주문별 문서' RAG, 또는 정책 의도까지 추론하는 질의 재작성)가 필요하다.

[결론]
  - order를 20→5로 바꿔도 '아무것도 깨지지 않았다'. Memory 주입·RAG Context·LLM 응답 모두 동일.
  - 이유: Spring AI QuestionAnswerAdvisor는 advisor 순서와 무관하게 '현재 턴 user text'
    ("아까 그 주문 환불 돼요?")를 임베딩하고, MessageChatMemoryAdvisor는 순서와 무관하게 이력을
    별도 메시지로 주입한다. 두 advisor는 서로 다른 부분을 건드려 '교환 가능(commute)' → 최종 프롬프트 동일.
  - 숙제가 기대한 '고장'(order 바꾸면 검색이 엉뚱해짐)은 'memory가 질의를 재작성하는 설계'에서만
    발생한다. 이 구현엔 그 재작성이 없으므로(현재 턴 텍스트로만 검색) 정상/스왑 차이가 없다.
    힌트의 "그 주문이 1234로 복원되기 전이라 자체로 검색"은 맞지만, 그건 '정상 order에서도' 동일하다.
  - (PART F의 검색-레벨 결론을 실제 order(5) 스왑으로 end-to-end 재확인.)

# 목적: stock QuestionAnswerAdvisor는 '현재 턴 텍스트'만 임베딩해 advisor 순서가 검색에 무관(PART F·M).

# 구현(@Profile("raa")): RagAdvancedConfig

#     queryTransformers: CompressionQueryTransformer(chatClientBuilder)  ← 이력+후속질문 → standalone 질의로 압축
#     documentRetriever: VectorStoreDocumentRetriever(threshold 0.45, topK 4)
#     queryAugmenter:    ContextualQueryAugmenter(allowEmptyContext=…)
#   AssistantChatClientConfig: raa 프로파일이면 RAA가 QuestionAnswerAdvisor를 대체(memory(10) → RAA(20) → perf(100)).
#   의존성 추가: build.gradle 'org.springframework.ai:spring-ai-rag'
# 질문: T1 "주문번호 2024-1234 배달 어디?"  T2 "아까 그 주문 환불 돼요?"  (env: ollama 반복 wedge로 모델 상주 후 측정)
