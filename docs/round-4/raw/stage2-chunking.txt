# Spring AI TokenTextSplitter엔 오버랩이 없다(항상 0). 커스텀 OverlappingTokenTextSplitter +
# rag.chunk-overlap 프로퍼티(기본 0=투명)로, chunk=100에서 overlap 0 vs 30 을 검색 레벨 비교.
# 대상: coupon-faq의 '## 쿠폰 중복 사용' 섹션이 chunk=100에서 경계로 쪼개지는 지점(= PART N의 B-③ 자기모순 뿌리).

[overlap=0 — 섹션이 경계에서 분리됨] coupon 청크:
   [5] ## 쿠폰 중복 사용  - 할인 쿠폰 + 배달비 쿠폰 → 가능 - 할인 쿠폰 + 할인 쿠폰 → 불가
   [6] - 프로모션 쿠폰과 일반 쿠폰의 중복 여부는 쿠폰마다 다르며 ...        ← 헤더·앞 규칙 없이 중간에서 시작
   → '중복 사용' 3조항(할인+배달비 / 할인+할인 / 프로모션)이 [5]·[6] 두 청크로 갈림.

[overlap=30 — 앞 청크 꼬리 30자 prepend로 경계 회복] coupon 청크:
   [6] 비 쿠폰 → 가능 - 할인 쿠폰 + 할인 쿠폰 → 불가 - 프로모션 쿠폰과 일반 쿠폰의 중복 여부는 ...

  row 수                                     49                 49 (오버랩은 청크 '개수'가 아니라 '내용'만 늘림)

[해석]
  - 오버랩의 가치는 'cosine↑'가 아니다(0.7705→0.7749, 거의 동일). 핵심은 검색된 top-1 청크의 '자기완결성':
    overlap=0의 top-1은 불완전 조각(프로모션만)이라 그 한 청크로는 "할인끼리 중복?"에 답 못 함
    → PART N의 B-③ 자기모순/조각남의 뿌리. overlap=30의 top-1은 경계 내용을 품어 한 청크로 답 가능.
  - 단, 기본값 chunk=800에서는 정책 문서<800토큰이라 문서당 1청크 → 경계 자체가 없어 오버랩 무의미
    (0이든 30이든 결과 동일). 오버랩은 '문서가 chunkSize보다 길어 쪼개질 때'(chunk=100, 장문 PDF 등)에만 효과.
  - 결론: 짧은 정책 + chunk 800(1문서=1청크) 조합엔 overlap=0이 정답. 긴 문서로 가면 chunk를 줄이고
    overlap(>0)을 둬 경계 손실을 막아야 한다 — 본 실험이 그 효과를 정량 확인(완전성 0→1).
