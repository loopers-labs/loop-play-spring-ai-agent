# `Outcome` enum 설계 결정

`CancelOrderResult`의 `Outcome` enum은 4개 값을 가진다. boolean이 아닌 enum으로 분기한 이유, 4개로 한정한 기준, 멱등성 정책의 근거를 정리한다.


## TL:DR;

- `Outcome` 4개는 안내 톤·다음 액션·분석 카테고리가 모두 달라 분기되어야 하는 최소 집합이다.
- `FAILED`·`UNKNOWN`은 결정을 미루는 신호라 배제했다. 
- cancelOrder가 "같은 응답 재전달"을 택한 것은 호출자가 LLM이기 때문이며, **에러는 추상화를 깨고 무시는 정보를 잃는다.** 작업 성격에 따라 멱등성 정책은 달라야 한다.


---
## 1. enum 분리 기준 
- **다음 액션** : enum 값은 비즈니스가 다음에 무엇을 할지 결정짓는 분기점이어야 한다.
- **운영 분석 카테고리** : 각 outcome은 운영팀이 다른 지표로 모니터링·분석해야 하는 다른 유형의 이벤트다.
- **고객 안내 톤** : 각 outcome은 고객에게 다른 톤과 메시지로 안내해야 한다.

```java
public enum Outcome {
    CANCELED,            // 이번 호출에서 취소됨  - 환불 절차 시작
    ALREADY_CANCELED,    // 이미 취소되어 있었음 (멱등 — 에러 아님) - 추가 액션 없음 (사용자 재확인용)
    NOT_CANCELABLE,      // 조리 시작 이후 등 취소 불가 - CS 연결  
    NOT_FOUND            // 주문번호 없음 - 주문번호 재확인
}
```

---

## 2. `FAILED`·`UNKNOWN`을 넣지 않은 이유

**원칙: enum 값은 비즈니스가 다음에 무엇을 할지 결정짓는 분기점이어야 한다.**

- `FAILED`는 사유를 알 수 없어 고객이 즉시 "왜요?"라고 되묻는다. 분류되지 않은 잔여 케이스가 모두 흘러와 분석 가치가 사라진다.
- `UNKNOWN`은 "결정을 못 했다"는 신호이며, 도메인 로직이 명확한 한 정상 경로에 나오면 버그다. enum 값이 아니라 **로깅·알람의 대상**이어야 한다.

---

## 3. 추가될 수 있는 Outcome

- `REQUIRES_AGENT` — PG 장애 등 시스템 사유로 자동 취소 불가, 상담사 수동 처리. (`NOT_CANCELABLE`은 비즈니스 규칙, 이건 외부 의존성 문제)
- `COOLING_OFF` — 단시간 반복 취소 어뷰징 방지 잠금. (주문 상태가 아닌 고객 행동 문제)

---

## 4. 멱등성의 세 가지 정책

같은 호출이 반복됐을 때의 선택지:

1. **에러 (Strict)** — 두 번째 호출 거부. 중복을 강제 차단하지만 무해한 재시도·더블클릭까지 예외로 격상.
2. **무시 (Lenient)** — 응답 없이 그냥 통과. 호출자가 "이미 취소됐는지, 방금 취소됐는지" 구분 불가.
3. **같은 응답 재전달 (Idempotent)** — 두 번째 호출에도 의미 있는 응답. 현재 상태와 추가 정보를 명확히 전달, 대신 outcome 값이 늘어난다.

---

## 5. `cancelOrder`가 "같은 응답 재전달"을 택한 이유

호출자가 **LLM**이고, LLM은 자연어로 고객에게 응답을 생성해야 하기 때문이다.

- **재전달의 이점** — outcome과 message를 함께 줘서 상황별로 다른 자연어 응답을 생성하게 하고, `ALREADY_CANCELED` 빈도로 사용자 재확인 패턴을 정량화할 수 있다.

- **에러는 추상화를 깬다** — 자연어 흐름이 끊기고, "이미 취소된 정상 상황"과 "진짜 시스템 오류"를 구분하기 어렵다. 재취소 요청은 에러가 아니라 정상 흐름의 하나다.
- **무시는 정보를 잃는다** — 응답이 빈약하면 LLM이 혼란스러운 안내나 거짓("취소되었습니다") 안내를 할 수 있다.


---

## 6. 반대 사례 — `chargePayment`는 에러가 적절

결제 같은 **자원 생성** 작업은 멱등성을 다르게 다룬다. 중복 결제는 에러로 격상해야 한다.

- **금전적 위험** — 중복 결제 시도가 "정상 흐름"으로 흡수되면 모니터링에서 누락된다.
- **감사 추적** — 모든 결제 시도가 기록되어야 하므로 예외로 던져 로그·알람에 잡혀야 한다.
- **호출자가 시스템 코드** — cancelOrder의 호출자는 LLM이라 자연어 응답이면 충분하지만, chargePayment는 결제 모듈이 호출자라 명시적 신호(예외)가 더 안전하다.

### 작업 성격별 권장 정책

| 작업 성격 | 권장 정책 | 이유 |
|---|---|---|
| 상태 변경 (취소·완료) | 같은 응답 재전달 | 호출자에게 현재 상태 안내 |
| 자원 생성 (주문·결제) | 에러 | 의도하지 않은 중복 생성 방지 |
| 외부 알림 (이메일·푸시) | 무시 또는 재전달 | 빈도 제한·로깅으로 보강 |
| 읽기 조회 | 멱등성 무관 | 부작용 없음 |
