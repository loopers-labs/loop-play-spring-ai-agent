## TL;DR

1. **시스템 프롬프트가 description보다 우선한다.** 규칙 절이 있으면 description 품질과 무관하게 호출이 강제된다.
2. **모델마다 사용자 메시지와 잘 매칭되는 description 표현 형태가 다르다.** qwen2.5에서는 `"배달 정보 조회"` 단독(5/5)이 가장 강했고, 단어 한 개 차이("현황", 1/5)나 조건 명세 문장 부가(0/5)로 매칭이 무너졌다. 단, `[라벨] 값` 구조화는 회복 효과를 보였다(4/5, 조건부).
3. **KV 캐시가 도구 호출 여부를 뒤집는다.** 동일 description이 캐시 비활성 4/5, 활성 1/5로 갈렸다.

## 1. 배경 및 동기

**가설** — tool description은 LLM이 보는 유일한 API 문서다. LLM은 함수 구현이나 시그니처를 보지 못하고 description과 파라미터 스키마만으로 도구 호출 여부를 판단한다. 그렇다면 description을 바꾸면 동작도 바뀌어야 한다.

**초기 실험** — 같은 도구에 description만 다르게 한 세 버전으로 동일 질문을 5회씩 테스트했다.

- A — 조건·형식을 상세히 명시한 정상 버전
- B — `"배달 정보 조회"`처럼 빈약한 한 줄
- C — 오해를 유발하도록 설계한 버전

**결과** — 세 버전 모두 도구 호출 5/5. description 품질 차이가 동작에 전혀 반영되지 않았다.

**원인 가설** — 시스템 프롬프트의 `# Tool 사용 규칙` 절(도구를 반드시 호출하라는 강제 지시)이 description 품질과 무관하게 호출을 강제하고 있다.

**후속 조치** — 이 절만 제거한 `assistant_system_prompt_without_tool_rule.md`로 교체해, 강제 지시가 없는 상태에서 description 변형만으로 동작이 갈리는지 다시 관찰했다.

## 2. 핵심 발견

상세 가설 검증([4절](#4-상세-가설-검증-흐름))을 한 단계 위에서 요약한 세 가지 발견이다.

> **표기 규칙**: 
> - `x/5`의 x는 5회 중 Tool을 호출한 trial 수 
> - `✓`는 올바른 Tool , `✗`는 잘못된 Tool, 기호 없음은 미호출 의미
> - 미호출 trial도 분모(5)에 포함된다. 
> - (전체 판정 기준은 [3절](#3-실험-환경-및-판정-기준) 참조)

### 발견 1 — 시스템 프롬프트 > description

**시스템 프롬프트와 description이 충돌하면 시스템 프롬프트가 이긴다.** 규칙 절이 호출을 강제하면 description 품질은 무력화되고, 규칙 절을 제거해야 비로소 description이 결정권을 갖는다.

| 버전 | description | `Tool 사용 규칙` 있음 | 규칙 절 제거                |
|---|---|-----------------|------------------------|
| A | 정상 5줄 멀티라인 | 5/5             | **0/5**                |
| B | `"배달 정보 조회"` 단독 | 5/5             | **5/5 ✓**              |
| C | 오해 유발 단독 | 5/5             | **5/5 ✗(잘못된 Tool 호출)** |

규칙 절이 있을 땐 description 품질과 무관하게 전부 5/5(강제 호출). 제거하자 A는 0/5로 붕괴하고 B는 5/5를 유지하며 갈렸다.

### 발견 2 — 모델별로 매칭되는 description 표현 형태가 있다

qwen2.5에서 사용자 질문("배달 어디쯤")과 매칭되는 정도는 description 표현 형태에 따라 크게 달랐다. (모두 시스템 프롬프트 규칙 절 제거 조건)

| description 형태 | 예시 | 결과 |
|---|---|---|
| 단순 키워드 | `"배달 정보 조회"` | 5/5 ✓ |
| 1단어 변형 | `"배달 현황 조회"` | 1/5 ✓ |
| 조건 명세 평문 | A (5줄 멀티라인) | 0/5 |
| `[라벨] 값` 구조화 | G (4줄, KV 비활성) | 4/5 ✓ |

#### 차이는 정보의 *양*이 아니라 *구조*로 추정된다 
- 정보량이 많은 A(0/5)와 G(4/5)가 정반대 결과를 냈다.
- 평문 조건 문장은 모델이 "복잡한 출력 계약"으로 읽어 호출을 주저하게 만든다.
- 반면, `[라벨]` 형식은 같은 정보를 파싱하기 쉬운 형태로 제시해 매칭을 회복시킨 것으로 보인다.

> **주의**: qwen2.5 한정 특성이며 일반 법칙이 아니다. "정보 vs 현황"의 우열, "짧을수록 낫다", "라벨링이 낫다"가 다른 모델에서 재현된다는 보장은 없다. 또한 G의 4/5는 KV 캐시 비활성 조건에 묶여 있다(발견 3 참조).

### 발견 3 — KV 캐시라는 교란 변수

**동일한 description이 KV 캐시 설정만으로 결과가 뒤집혔다.** KV 캐시란 LLM이 토큰 생성 시 이전 토큰들의 Key/Value 연산 결과를 재사용해 추론을 가속하는 메커니즘으로, 실험에서는 `numKeep` 값으로 활성/비활성을 제어했다.

| 버전 | KV 캐시 | 호출 | 관찰                                             |
|---|---|---|------------------------------------------------|
| G | 비활성 | 4/5 ✓ | Tool 정상 호출                                     |
| G | 활성 | 1/5 ✓ | Trial 3~5 Tool 미호출, 동일 대기 메시지 반복 (응답 0.9~1.0s) |

**함의** — KV 캐시는 의도한 변수가 아니었으나 결과를 뒤집을 만큼 강력했다. 따라서 모든 결과 비교 시 KV 캐시 상태를 반드시 함께 기록해야 한다.

**원인은 미상이다.** 
- 측정된 사실은 "Trial 3~5 응답 시간이 급락하며 동일한 대기 메시지가 반복됐다"는 것뿐이다. 
- 추정 경로는 하나 — 도구를 호출하지 않은 이전 응답이 캐시에 저장되고, 이후 요청이 그 prefix를 재사용하면서 호출 
단계를 건너뛴다. 
- 다만 Ollama의 KV 캐시 내부 동작을 외부에서 검증할 수단이 없어 확인되지 않은 추정이다.

## 3. 실험 환경 및 판정 기준

### 공통 조건 (재현 정보)

| 항목 | 값 |
|---|---|
| 모델 | qwen2.5:latest (7.6B, Q4_K_M) |
| temperature | 0.3 ([`application.yml`](../../../src/main/resources/application.yml)) |
| 시스템 프롬프트 | [`assistant_system_prompt_without_tool_rule.md`](../../../src/main/resources/prompts/assistant_system_prompt_without_tool_rule.md) — `# Tool 사용 규칙` 절 제거 |
| 테스트 질문 | `"주문번호 2024-1234 배달 어디쯤이에요?"` |
| 반복 횟수 | 버전당 5회 |
| trial 간 대기 | 2초 (`sleep 2`) |
| KV 캐시 | 버전별 활성/비활성 명시 (`numKeep`으로 제어) |

### 성공 판정 기준

- **호출 성공** — 올바른 도구(`getDeliveryStatus`)를 호출하고 응답에 올바른 배달 위치("역삼역 사거리")가 포함됨.
- **잘못된 호출** — 도구는 호출했으나 의도와 다른 도구 선택(예: C가 `getOrderDetail` 호출). 호출 횟수에는 포함되나 성공은 아님.
- **미호출** — 도구를 호출하지 않고 텍스트로 응답하거나 tool call을 텍스트로 누출.

**표기 규칙** — `x/5`의 x는 5회 중 도구를 호출한 trial 수. `✓`는 올바른 도구, `✗`는 잘못된 도구, 기호 없음은 미호출. 미호출 trial은 분모(5)에만 포함된다.

- `5/5 ✓` — 5회 모두 올바른 도구 호출 + 역삼역 사거리 반환
- `5/5 ✗` — 5회 모두 잘못된 도구 호출
- `0/5` — 5회 모두 미호출
- `1/5 ✗` — 1회 잘못된 도구 호출, 나머지 4회 미호출 (D)
- `1/5 ✓` — 1회 올바른 도구 호출, 나머지 4회 미호출 (E)

## 4. 상세 가설 검증 흐름

발견들의 근거가 된 검증 과정이다. 가설을 하나씩 좁혀나가는 직렬 구조다.


### 시스템 프롬프트 영향 격리

**가설** — `# Tool 사용 규칙` 제거 시 description 품질에 따라 동작이 달라지는가?

| 버전 | description | 호출 | 결과 |
|---|---|---|---|
| A | 정상 5줄 멀티라인 (조건·형식·null 명시) | 0/5 | 미호출, 텍스트 형식 tool call 누출 |
| B | `"배달 정보 조회"` 단독 | 5/5 ✓ | 정상 호출 |
| C | `"주문번호 조회용. 메뉴와 결제 금액만 반환한다."` 단독 | 5/5 ✗ | `getOrderDetail` 잘못 호출 |

**판정** — 가설 확인. 규칙 절 없이 description이 호출을 직접 결정한다. 예상과 달리 A(정상)가 0/5, B(빈약)가 5/5로 짧고 단순한 쪽이 유리했다.

### 포맷 vs 키워드 격리

**가설** — A 실패 원인이 멀티라인 포맷 때문인가, B의 특정 키워드 때문인가?

| 버전 | description | 호출 | 판정 |
|---|---|---|---|
| D | A 내용을 단일 줄로 압축 | 1/5 ✗ | 기각 (포맷이 원인 아님) |
| E | `"배달 현황 조회"` 단독 | 1/5 ✓ | 부분 확인 (키워드 영향, 단 약함) |

**D 회차별 호출 내역**

| 회차 | 호출한 도구 | 판정 |
|---|---|---|
| 1 | `getOrderDetail` | ✗ 잘못된 도구 |
| 2~5 | 미호출 | — |

**판정** — A 실패 원인은 포맷이 아닌 내용 자체(조건 명세 문장)다. "정보" vs "현황" 한 단어 차이로 5/5 vs 1/5 격차가 발생했다.

### 키워드 접두어 효과 격리

**가설** — A 앞에 B의 키워드(`"배달 정보 조회."`)를 붙이면 호출이 회복되는가?

| 버전 | description | 호출 | 판정 |
|---|---|---|---|
| F | `"배달 정보 조회."` + A 전체 내용 | 0/5 | 기각 (키워드 추가로 회복 안 됨) |

**판정** — 키워드를 타이틀로 추가해도 A의 조건 문장이 있으면 실패한다. B의 성공 원인은 키워드가 아니라 "그 외 내용이 없다는 단순함" 자체다.

### 구조화 헤더 + KV 캐시 변수

**가설** — `[라벨] 값` 형식으로 4항목을 명시하면 호출이 회복되는가? KV 캐시 활성/비활성 두 조건으로 분리.

| 버전 | description | KV 캐시 | 호출 | 판정 |
|---|---|---|---|---|
| G | `[무엇을 하는가]` 등 4줄 구조화 헤더 | 비활성 | 4/5 ✓ | 부분 확인 (회복 효과 있음) |
| G (KV 활성) | 동일 | 활성 | 1/5 ✓ | 사실상 기각 (캐시 활성 시 붕괴) |

**부가 현상**

- `[라벨]` 형식이 qwen2.5의 중국어 처리 경로를 활성화 → 응답에 중국어 혼입.
- G (KV 활성) Trial 3~5 응답 0.9~1.0s — 캐시 재사용으로 호출 없이 대기 메시지 반복.

**판정** — `[라벨]` 구조화는 KV 캐시 없는 조건에서 부분 유효하나 불안정하다. B는 동일 조건에서 5/5 안정 → 단순함이 가장 견고한 전략.

## 6. 한계 및 다음 단계

### 한계

- **단일 모델** — 모든 결론은 qwen2.5 기준이다. "단순할수록 낫다", "라벨링이 회복 효과를 낸다" 등은 모델 의존적이므로 다른 모델에 그대로 적용하면 안 된다.
- **단일 질문·5회 반복** — 질문 하나, 반복 5회로 표본이 작아 통계적 신뢰도가 제한적이다.
- **KV 캐시 교란** — 동일 description이 캐시 설정만으로 4/5↔1/5로 갈렸다. 캐시 상태를 통제하지 않은 비교는 무효다.
- **모델 특이 현상** — `[라벨]` 형식이 중국어 경로를 유발하는 등 qwen2.5 고유의 부작용이 관찰됐다.

### 다음 단계 (제안)

- 다른 모델(Llama, GPT 계열 등)에서 동일 description 세트를 재현해 일반화 가능성 확인.
- 질문 다양화(주문 상태, 환불 등)와 반복 횟수 증대로 표본 확대.
- KV 캐시 활성 조건을 고정한 상태에서 description 변형만 비교하는 통제 실험.
- 매칭에 영향을 주는 표현 형태 특성(키워드 중복, 구조화 정도, 정보량)을 독립 변수로 분리해 정량화.

## 부록 B: G vs G_kvcache 코드 차이

두 버전의 description은 동일하다. 유일한 차이는 `AssistantController.java`의 `defaultOptions` 설정이다.

**G — numKeep=0 추가 (KV 캐시 비활성)**

```java
import org.springframework.ai.ollama.api.OllamaOptions;

// KV 캐시 비활성화 — 매 요청마다 새 컨텍스트로 처리하도록 numKeep=0 설정
this.chatClient = builder
        .defaultSystem(BaedalPrompt.ASSISTANT_SYSTEM_PROMPT)
        .defaultOptions(OllamaOptions.builder().numKeep(0).build())
        .defaultAdvisors(performanceAdvisor, new SimpleLoggerAdvisor())
        .defaultTools(orderTools)
        .build();
```

**G_kvcache — defaultOptions 없음 (KV 캐시 활성)**

```java
this.chatClient = builder
        .defaultSystem(BaedalPrompt.ASSISTANT_SYSTEM_PROMPT)
        .defaultAdvisors(performanceAdvisor, new SimpleLoggerAdvisor())
        .defaultTools(orderTools)
        .build();
```
