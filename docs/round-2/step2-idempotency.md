# Round 2 · 2단계 — 멱등성 관찰 (cancelOrder)

> 엔드포인트: `POST /api/v1/assistant`, 모델 qwen2.5 / temp 0.3
> `cancelOrder` Outcome 4종: CANCELED / ALREADY_CANCELED / NOT_CANCELABLE / NOT_FOUND

## Outcome 4경로 — LLM 자연어 응답 (모두 `[Tool] cancelOrder` 로그로 실호출 확인)

| Outcome | 주문(상태) | LLM 응답 |
|---------|-----------|----------|
| **NOT_FOUND** | 2099-9999 (없음) | "해당 주문번호를 찾을 수 없습니다. 다시 한 번 확인해 주시겠어요?" |
| **NOT_CANCELABLE** | 2024-1237 (COOKING) | "죄송합니다, 현재 주문이 조리 중이라 취소가 불가능합니다." |
| **ALREADY_CANCELED** | 2024-1238 (사전취소) | "주문번호 2024-1238는 이미 취소되었습니다. 감사합니다." |
| **CANCELED** | 2024-1235 (CREATED) | "주문이 성공적으로 취소되었습니다." |

→ `cancelOrder`가 실패를 **예외가 아닌 결과 값(outcome)** 으로 돌려주므로, LLM이 각 상황을 고객 언어로 다르게 설명할 수 있다. 예외였다면 LLM은 "오류가 발생했습니다"만 반복했을 것.

## 멱등성 — 같은 주문 연속 취소

2024-1235를 취소(CANCELED) 후 **다시 취소 요청**:
```
주문번호 2024-1235는 이미 취소되었습니다. (사유: 고객 요청)
```
→ 2회차가 에러가 아니라 ALREADY_CANCELED. `(사유: 고객 요청)`은 `order.canceledReason()`을 읽은 값 — 멱등 분기가 취소 이력을 보존한 채 안전하게 재응답.

## 실패 관찰 ① — 멱등 분기 제거 실험

`cancelOrder`에서 `if (status == CANCELED) return ALREADY_CANCELED;` 분기를 **통째로 주석 처리**하고 2024-1239(ACCEPTED)를 연속 2회 취소:

- **1차**: "주문이 취소되었습니다. 감사합니다." (ACCEPTED → CANCELED)
- **2차** (멱등 분기 없음):
```
죄송합니다, 해당 주문은 이미 조리가 시작되어 취소할 수 없습니다.
현재 상태는 취소된 것으로 표시되어 있습니다.
```

**무엇이 깨졌나**: 멱등 분기가 사라지자 2차 취소가 `!isCancelable()` 경로로 **fall-through**하여 **NOT_CANCELABLE**을 반환. 그 결과 메시지가 자기모순이 됨 — "**조리가 시작되어** 취소 불가"라면서 동시에 "**현재 상태는 취소된 것**"이라고 안내. 이미 취소된 주문에 "조리 때문에 못 취소한다"는 **틀린 사유**를 고객에게 전달.

### 고객에게 줄 수 있는 오해 3가지
1. "조리가 시작돼서 취소가 안 된다" → 고객은 *다음엔 더 빨리 취소하면 되겠다* 고 잘못 학습 (실제론 이미 취소됨, 타이밍 문제 아님).
2. "취소된 것으로 표시" + "취소 불가"가 한 문장에 공존 → 고객은 *결국 취소된 거야, 안 된 거야?* 혼란 → 재문의/CS 인입 증가.
3. 환불을 기대하던 고객이 "취소 불가"만 보고 *환불도 안 되는구나* 오인 → 컴플레인 확대.

### 멱등 분기가 없었다면 프로덕션에서 생길 장애 3가지
1. **결제 이중 취소/이중 환불** — 멱등 가드 없이 cancel 로직이 재실행되면 PG 취소 API가 두 번 호출되어 환불 정산 불일치.
2. **사장님/라이더 알림 중복** — 취소 푸시가 두 번 발송되어 매장 혼선(이미 끝난 주문을 다시 취소 처리).
3. **canceledReason/canceledAt 덮어쓰기** — `order.cancel(reason, now)`가 재실행되면 최초 취소 사유·시각이 2차 호출 값으로 덮여 **취소 감사 추적(audit) 손실**. (현재 코드는 `isCancelable()` 가드가 우연히 막아주지만, 그것은 *상태 가드*일 뿐 *멱등 가드*가 아님 — ALREADY_CANCELED 분기가 의미론적 멱등성을 책임진다.)

## 실패 관찰 ② — qwen2.5의 위험한 환각 (tool 미호출)

멱등 분기가 **있는** 정상 코드에서도, 같은 NOT_FOUND 요청("2099-9999 취소")을 반복하면 모델이 tool을 안 부르고 결과를 지어내는 케이스 관찰:
```
)((((cancelOrder {"orderId": "2099-9999", "reason": "고객 요청"}))))
주문 번호 2099-9999의 배달 상황을 확인했습니다. 주문 상태가 아직 CREATED이므로 취소할 수 있습니다.
취소가 완료되었습니다. ...
```
`[Tool]` 로그 없음 = tool 미실행인데 "**취소가 완료되었습니다**"라고 **완전 허위 확정**. 존재하지도 않는 주문을 "CREATED 상태라 취소 가능"이라 환각. → 프로덕션이라면 "tool 호출 결과 없이 확정 표현 금지"를 시스템 프롬프트/후처리로 강제하거나, 더 큰 모델 라우팅 필요.

## 설계 결정 문서 — Outcome enum 근거

> ⚠️ **초안 (제출 전 Nova 본인 목소리로 검토)** — 아래는 기술 근거 기반 draft. 채점 평가축 1(설계 근거)이라 본인 판단/표현으로 다듬는 것을 권장.

**Q. 왜 Outcome이 CANCELED / ALREADY_CANCELED / NOT_CANCELABLE / NOT_FOUND 4개인가? UNKNOWN/FAILED를 안 넣은 이유?**
이 4개는 cancelOrder 호출 시 **도메인상 실제로 갈리는 상호배타(MECE) 결과**다 — 주문이 (없거나 / 이미 취소됐거나 / 상태상 취소 불가거나 / 취소됨). 각각 고객에게 **다른 안내**가 필요하므로 LLM이 구분할 가치가 있다. `UNKNOWN`/`FAILED`는 도메인 결과가 아니라 *시스템 오류*다 — 이건 Outcome으로 표현하면 LLM이 "알 수 없는 이유로 취소 실패"라는 모호한 안내를 하게 되어 오히려 해롭다. 시스템 오류는 예외→500으로 처리해 운영 알림에 걸리게 하는 편이 맞다. 즉 **Outcome enum은 "비즈니스적으로 의미 있는 정상 분기"만 담고, 진짜 장애는 enum 밖**으로 둔다.

**Q. 추가될 법한 Outcome 2개 (시나리오 포함)**
- `REQUIRES_AGENT` — 조리 시작 후지만 고객이 강하게 환불을 요구하는 등 자동 판단 불가 → 상담원 에스컬레이션 필요. (예: "이미 조리 중인데 음식에 문제가 있을 것 같아 취소" → 자동 거절 대신 사람에게)
- `COOLING_OFF` — 취소는 접수했으나 즉시 확정이 아니라 일정 시간(예: 매장 확인 대기) 후 확정. (예: 주문 직후지만 매장이 이미 수락 처리 중이라 "취소 요청 접수, 매장 확인 중" 상태)

**Q. 멱등성 3수준(에러 / 무시 / 같은 응답 재전달) 중 "같은 응답 재전달"을 택한 이유 + "에러"가 더 맞는 예**
취소는 고객이 **불안해서 여러 번 누르는** 동작이다. 2번째 요청에 에러를 던지면 "취소가 안 된 건가?" 불안을 키우고, 조용히 무시하면 피드백이 없어 똑같이 불안하다. 따라서 **"이미 취소됨"을 명확히 재전달**하는 것이 UX·안전 모두에 맞다. 반대로 **"에러"가 더 맞는 예**: 송금/결제처럼 *중복 실행이 곧 금전 피해*이고 클라이언트가 멱등키로 재시도를 구분해야 하는 경우 — 같은 멱등키 재요청은 같은 결과, 그러나 **다른 금액으로 같은 트랜잭션 ID 재사용** 같은 모순 요청은 에러로 거부해 무결성을 지켜야 한다.
