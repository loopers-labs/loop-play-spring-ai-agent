# Round 2 · 3단계 — Tool description 실험

> getDeliveryStatus의 `@Tool(description=...)`만 4버전으로 바꿔가며 동일 질문 5회씩.
> 질문: `"주문번호 2024-1234 배달 어디쯤이에요?"` / 모델 qwen2.5 temp 0.3
> 호출 여부는 `[Tool] getDeliveryStatus(orderId=2024-1234)` 로그 카운트로 측정.

## 정량 비교

| 버전 | description | getDeliveryStatus 호출 | getOrderDetail 호출 | 관찰 |
|------|-------------|:---:|:---:|------|
| **A** 명확(4요소) | 무엇/언제/입력/실패 모두 포함 (full) | **4/5** | 0/5 | 1회 tool-call 텍스트 누출(`</tool_call>`) |
| **B** 모호 | `"배달 상태를 조회한다."` 한 줄 | **5/5** | 0/5 | 가장 안정적. 1회 중국어 토큰 누출(`左右/请稍后`)되었으나 tool은 발동 |
| **C** 오도 | `"결제 영수증 재발송 … 배달과 무관"` | **5/5** | 0/5 | 거짓 설명 **무시** — 메서드 이름으로 호출 |
| **C-strong** 명시적 금지 | `"[내부 디버깅 전용] 고객 응대 호출 금지"` | **0/5** | 2/5 | 호출 억제됨, 대신 **불안정 degrade** |

## 버전별 관찰

### A (명확) — 4/5
3건 정상 응답. 1건은 `berra\n\nONGL\n{"name":"getDeliveryStatus",...}\n</tool_call>` 처럼 tool-call 마크업을 본문으로 누출(미실행).

### B (모호) — 5/5 (의외)
한 줄 설명이 **오히려 더 안정적**. 질문("배달 어디?")이 설명("배달 상태를 조회한다")과 거의 1:1로 매칭돼 모델이 헤맬 여지가 없음. 장황한 A가 토큰·노이즈를 늘려 작은 모델에는 불리할 수 있음을 시사.

### C (오도, 틀린 용도) — 5/5
"이 도구는 영수증 재발송이고 배달과 무관"이라 거짓 설명했는데도 **5/5 호출**. 모델이 **메서드 이름 `getDeliveryStatus`** 를 description보다 강한 신호로 사용. → "description이 LLM이 보는 유일한 API 문서"는 **부분적으로만 참**. 함수 이름도 강력한 신호이며, 작은 모델일수록 이름 의존이 큼.

### C-strong (명시적 사용 금지) — 0/5, 대신 붕괴
"고객 응대에 절대 호출 금지"라고 직접 명령하자 getDeliveryStatus 호출이 0이 됨. 대신:
- **getOrderDetail로 대체(2/5)** — 라이더 위치 데이터가 없으니 매장명을 위치처럼 둘러댐: *"교촌치킨 강남점에서 배달 중"* (riderLocation "역삼역 사거리"가 사라짐 → 정보 열화).
- **tool-call 마크업 누출**: `.GetOrdinalDetail {"orderId":"2024-1234"}`, `ordinal\n{"name":"getOrderDetail",...}\n</tool_call>`.
- **환각**: call 5에서 존재하는 주문 2024-1234를 *"해당 주문번호를 찾을 수 없습니다"* 라고 거짓 응답.

## 설계 결정 문서 (README)

> ⚠️ **초안 (제출 전 Nova 본인 목소리로 검토)** — 평가축 1.

**Q. 버전 C에서 LLM이 어떤 행동을 했는가?**
오도 description(C)은 **무시**하고 메서드 이름으로 정상 호출(5/5). 명시적 금지(C-strong)에서야 호출을 멈췄고, 그때는 (a) 형제 tool(getOrderDetail) 대체 호출 → 라이더 위치 누락, (b) tool-call 마크업 본문 누출, (c) 존재하는 주문을 "없음"으로 환각 — 세 가지 붕괴가 동시에 관찰됨.

**Q. description 필수 항목 4가지 (실험으로 체감한 중요도 순 재배열)**
강의 자료의 4요소(무엇/언제/입력/실패) 중, 이번 실험 기준 중요도 순서:
1. **언제 호출하는가 (트리거 조건)** — 모델이 tool 선택을 가르는 1차 신호. B(트리거가 이름과 일치)가 5/5인 이유.
2. **무엇을 하는가** — 1과 묶여 의미 경계를 정함. 단, 메서드 이름이 이미 이걸 절반 전달하므로 이름과 모순되면 이름이 이김(C).
3. **실패 시 반환값(null 의미)** — 호출률엔 영향 적지만, 호출 *후* 응답 품질(없는 주문 안내)을 좌우.
4. **입력 형식** — 작은 모델에선 가장 영향 적었음(orderId 형식을 안 적어도 "2024-XXXX"를 잘 추출). 그래도 파라미터 검증·문서화 측면에서 유지.
→ 핵심 교훈: **이름과 description은 한 방향을 가리켜야 한다.** 모순되면 작은 모델은 이름을 따른다.

**Q. description이 "오래된 주석"처럼 실제 동작과 어긋나는 것을 프로덕션에서 어떻게 막나?**
- **Contract Test**: tool 호출 시 description에 명시한 트리거/입력/실패 동작을 케이스로 고정. description 수정 시 테스트가 깨지게.
- **PR 리뷰 체크리스트**: tool 시그니처/로직 변경 PR은 description 동시 갱신을 필수 항목으로.
- **단일 출처(Single Source of Truth)**: description에 박는 입력 형식("YYYY-XXXX")을 상수/검증 로직과 공유해 한쪽만 바뀌지 않게.
- **회귀 평가셋**: 대표 질문 N개에 대한 tool 호출률을 CI에서 측정, description 변경이 호출률을 떨어뜨리면 경보(이번 A/B/C 실험을 자동화한 형태).
