# RAG 설계 결정

> `RagConfig`의 핵심 파라미터 4개를 **왜 그 값으로 정했는지** 근거 정리.
> 실측 데이터는 검증 리포트 [`01_rag_5scenario_report.md`](01_rag_5scenario_report.md)에서 가져왔다.
> 일부 값(Top-K·threshold·chunkSize)은 3단계에서 정량 실험으로 재검증한다.

---

## 1. 청크 크기 — `TokenTextSplitter(800, 350, ...)`

**결정**: `chunkSize=800` 토큰, `minChunkSizeChars=350`.

### 근거 — 배달 정책 문서는 이미 "조항 단위"로 짧다

- 시드 문서 7개 크기: **573~723자** (`coupon-faq` 573 ~ `cancel-policy` 723). 한국어 700자 ≈ `cl100k` 기준 400~600토큰.
- 즉 **문서 한 개가 이미 800토큰 한 창에 통째로 들어간다** → 분할이 안 일어나고 **문서 1개 = 청크 1개**.
- 실측: `vector_store` row **7개 = 문서 7개**(리포트 검증 대상 요약)로 1:1 확인됨.
- 문서가 이미 "취소 정책", "환불 기본 정책"처럼 **주제 단위로 쪼개져 있어** 추가 분할의 실익이 적다. 800은 "이 정도면 한 조항이 안 잘린다"는 안전 상한.
- `minChunkSizeChars=350`: 분할이 일어나더라도 350자 미만 조각은 앞 청크에 병합 → **의미 없이 잘린 토막 청크 방지**.

### 다른 도메인이라면 — 블로그 글 / 장문 PDF

- **장문 PDF·블로그**: 한 문서가 수천~수만 토큰이라 800은 너무 커서 한 청크에 여러 주제가 섞인다 → 검색 정밀도 하락. **chunkSize를 200~400으로 낮춰** 문단/섹션 단위로 쪼개야 "질문과 관련된 부분만" 검색된다.
- 트레이드오프: 작게 쪼갤수록 검색은 정밀해지지만 **하나의 의미 단위가 청크 경계에서 잘린다.** 예를 들어 표가 쪼개지면 **헤더 행(열 이름)은 앞 청크, 데이터 행은 뒤 청크**로 갈라져 — 데이터만 든 청크가 검색됐을 때 "그 숫자가 어느 열 값인지" 알 수 없다. → 청크 간 **overlap**(겹침: 다음 청크가 앞 청크 끝부분을 일부 복제)으로 헤더가 데이터에 따라붙게 해 보완.
- 즉 청크 크기는 "**문서가 이미 얼마나 잘게 나뉘어 있나**"에 맞춘다. 우리 정책 문서는 이미 잘게 나뉘어 있어 800(=분할 안 함), 장문이면 작게 + overlap.
- 2단계 과제에서 `chunkSize`를 200 / 800 / 2000으로 바꿔 분할 수·검색 품질 변화를 관찰한다.

> **[참고] `cl100k`란?** `cl100k_base`는 OpenAI GPT-3.5/4가 쓰는 BPE 토크나이저(`tiktoken`)다. Spring AI `TokenTextSplitter`가 **토큰 수를 셀 때 이걸 사용**하므로, `chunkSize=800`은 "글자 800"이 아니라 "**cl100k 토큰 800**"이다. 그래서 "문서가 한 청크에 들어가나?"는 글자 수를 cl100k 토큰으로 환산해 본다.
> - 글자 ≠ 토큰: 한국어는 cl100k에서 비효율적이라 한 글자가 1~2토큰씩 먹는다(영어보다 토큰이 더 붙음). "700자 ≈ 400~600토큰"은 **정확히 센 값이 아니라 어림치**이고, 한국어는 변동이 크다. 문서가 청크 1개로 들어갔다는 **진짜 근거는 이 추정 토큰 수가 아니라, 실측한 `vector_store` 7 rows(= 1문서 1청크)**다.
> - 세는 토크나이저 ≠ 임베딩 토크나이저: 청킹은 cl100k로 길이를 재지만, 실제 임베딩은 `qwen3-embedding`이 **자기 토크나이저**로 처리한다(둘은 무관).

> **[판단 기준] "문서가 이미 얼마나 잘게 나뉘어 있나"**
>
> - **뜻**: 임베딩 전 단계에서 **각 소스 파일이 이미 '한 주제' 단위로 분리돼 있는 정도**.
> - **우리 문서**: 7개 파일이 각각 한 주제(`cancel-policy` = 취소 정책 하나) → **이미 잘게 나뉨** → splitter가 더 쪼갤 게 없어 chunkSize 크게(분할 X).
> - **반대 사례(장문 PDF·블로그)**: 한 파일에 여러 주제가 뭉쳐 있음 → 작게 쪼개야 함.
>
> **확인 방법** — "검색 단위(청크 1개) = 답변 단위(질문 하나에 필요한 만큼)"인가:
> - **파일 열어보기(가장 직접적)**: 한 파일이 한 주제냐 여러 주제냐. (`coupon__coupon-faq.md`는 처음부터 끝까지 쿠폰 FAQ 하나.)
> - **헤더 독립성**: 문서 안 `##` 섹션들이 **서로 독립된 주제**고 개수가 많으면 → 한 파일에 여러 단위가 든 것 → 쪼개야. (우리 파일의 `##`은 한 주제의 하위 항목이라 독립 문서급은 아님.)
> - **길이(간접 신호)**: 짧으면(수백 자) 보통 단일 주제, 길면(수천+ 자) 여러 주제 섞임 가능성↑. 우리는 573~723자.
> - **"한 질문 = 한 파일로 답되나"(실전)**: "쿠폰 중복?" → `coupon-faq` **하나**로 답됨(검증 시나리오 3) = 이미 잘 나뉨. 검색했더니 질문과 무관한 내용이 잔뜩 딸려오면 = 덜 나뉨 → chunkSize를 낮춰 쪼갠다.

## 2. Top-K — `topK=4`

**결정**: `topK=4` (1 / 4 / 10 중 4).

### topK이란 — "유사도 상위 K개까지"의 상한

- `topK=4` = "질문과 가장 비슷한 문서를 **유사도 순으로 최대 4개까지** 반환하라"는 검색 파라미터다. **4개를 무조건 채우는 게 아니라 개수 상한**이다. 
- 동작: 전체 문서(7개) 각각과 질문의 유사도 계산 → 내림차순 정렬 → 상위 K개 반환.
- **threshold와 함께**: 실제 반환 = `min(K, threshold(0.5) 넘는 수)`. "비 오는 날" 질문은 유사도가 `0.592 / 0.525 / 0.409 / …`라, topK=4여도 threshold 0.5가 넘는 **2개만** 반환됐다.
- 비유: 점수로 줄 세워 "상위 4등까지 합격, 단 60점 미만은 4등 안이어도 탈락" — **topK = 등수 컷, threshold = 과락 점수**.

### 근거 — 문서 7건 / threshold가 실제로 1~2개만 통과시킴

- 정책 문서가 **7건**뿐이라 Top-K는 "그중 상위 몇 개를 컨텍스트에 넣을까"의 문제.
- **실측(리포트)**: threshold 0.5 때문에 실제 반환은 질문당 **1~2개**였다 — 기상 질문 2개(delivery-delay), 환불 1개, 쿠폰 1개, 시나리오5 2개. **topK=4는 상한일 뿐 대부분 다 안 채워진다.**
- **왜 1이 아닌가**: 복합 질문("환불 + 지연"처럼 두 정책이 걸리는 경우)에서 1개만 뽑으면 한쪽 정책을 놓친다. 실제로 시나리오 5 T2는 **refund-basic + cancel-policy 2개**가 같이 필요했다 — topK=1이면 둘 중 하나만 와 답이 불완전해질 수 있다.
- **왜 10이 아닌가**: 문서가 7개라 10이면 사실상 threshold 통과분 전부를 넣는 셈. 무관 문서까지 컨텍스트에 들어와 **입력 토큰이 늘고**(문서는 user 메시지에 붙음 — 토큰 비용 직결), LLM이 무관 정책을 근거로 오해할 위험이 커진다.
- **4 = 복합 질문 여유 + 토큰 절제의 균형**. 7건 도메인에서 "관련된 건 거의 다 담되, 무관한 건 안 담는" 적정선.
- 3단계에서 1 / 4 / 10으로 검색 품질·토큰 비용을 비교한다.

> **[참고] "LLM이 무관 정책을 근거로 오해"란?** RAG는 검색 문서를 user 메시지에 `[참고 정책]`으로 붙이고 모델에 "이걸 근거로 답하라"고 지시한다 → 모델은 **컨텍스트에 든 문서 = 신뢰할 근거**로 취급한다. 그래서 질문과 무관한 문서가 섞이면 그걸 답에 끌어쓴다.
> - **예**: "쿠폰 중복?" 질문에 환불·취소 정책까지 주입되면, 모델이 환불의 "카드사 7영업일"·취소의 "조리 시작 전" 같은 걸 쿠폰 답변에 섞어 **혼선된 답**을 낸다.
> - **단, 정확히는**: `threshold=0.5`가 고정이라 topK를 10으로 올려도 0.5 미달 문서는 안 들어온다(우리 질문은 1~2개만 통과). 이 노이즈 오해의 **진짜 주범은 topK보다 threshold가 낮을 때**다(→ 4장). topK=10의 실제 비용은 "무관 문서 대량 유입"보다 **경계(0.5~0.6) 문서 몇 개 + 입력 토큰 증가**에 가깝다.

### 규모가 커지면 어떻게 달라지나 — 이 근거의 적용 한계

> 위 "4가 적정"은 **7문서 · 단일주제 · threshold 0.5**라는 전제 위에서만 성립한다. 전제(코퍼스 크기·청크 단위·질문 복잡도)가 바뀌면 K도 다시 정해야 한다. **원리(트레이드오프·threshold 결합)는 통용**, **수치 결론(4 / 1~2개 / 10이면 전부)은 우리 한정**이다.

| | 우리 (소규모 큐레이션, 7건) | 대규모 코퍼스 (수만~수백만) |
|---|---|---|
| 주 레버 | **threshold** (K는 거의 안 참) | **K** + 검색 정밀도 |
| 보통 K | 4 (여유) | 더 크게(20~100) 뽑고 **rerank로 상위 3~5개 압축** |
| 노이즈 원천 | 거의 없음(문서 적음) | 커서 별도 단계로 걸러야 |

- **K가 주 레버가 된다**: 큰 코퍼스는 threshold(예: 0.5)를 넘는 문서가 **수백 개**라, threshold만으론 못 줄인다. 결국 "상위 몇 개를 넣을까"의 **K가 1차 컷**이 된다(우리는 반대로 threshold가 컷).
- **높은 K + 재정렬(rerank)**: 임베딩 유사도 1차 검색은 **recall 위주로 넓게**(K=20~100) 뽑고, 그다음 **cross-encoder reranker**로 질문-문서를 정밀 채점해 상위 3~5개로 압축한다. 임베딩 코사인만으론 대규모에서 정밀도가 떨어지기 때문(우리는 7건이라 rerank 불필요).
- **무작정 K↑는 오히려 독**: 문서를 많이 넣을수록 ① 입력 토큰·비용·지연 증가, ② 컨텍스트 윈도우 압박, ③ **lost-in-the-middle**(모델이 중간에 낀 문서를 무시·무관 문서에 휘둘림)으로 **품질이 되레 하락**. 그래서 "많이 뽑되 적게 넣는다"(retrieve wide → rerank narrow).
- **메타데이터 선필터**: 대규모에선 카테고리·날짜·권한 등으로 후보를 먼저 좁힌 뒤 K를 적용한다(`metadata` 필터). 우리 `category` 필드가 그 씨앗 — 지금은 문서가 적어 안 쓰지만, 정책이 수천 건이 되면 "환불 카테고리 안에서만 topK" 식으로 확장한다.
- **우리 프로젝트에 적용**: 정책 문서가 7 → 수백~수천 건으로 늘면, 지금의 "threshold가 알아서 1~2개로 줄여줌"이 깨진다. 그때는 **카테고리 선필터 + K 상향 + rerank** 구조로 가고, K=4는 "rerank 후 최종 주입 수"로 역할이 바뀐다.

## 3. Advisor 순서 — `QuestionAnswerAdvisor.order(20)`

**결정**: `memoryAdvisor(10) → ragAdvisor(20) → performanceAdvisor(100)`.

### order = 실행 순서 (낮을수록 먼저). 무엇이 좌우되나

- advisor는 **order가 낮을수록 요청을 먼저** 처리한다(Memory 10 → RAG 20 → Performance 100).
- ⚠️ **RAG 검색 결과는 이 순서와 무관하다.** 기본 `QuestionAnswerAdvisor`는 현재 질문 텍스트를 그대로 임베딩해 검색하고, Memory는 질문을 고치지 않고 직전 대화만 덧붙인다 → Memory가 
  앞이든 뒤든 검색 질의는 같다. (시나리오 5에서도 RAG는 "환불" 단어로 검색했고, "그 주문"=2024-1234 해소는 RAG가 아니라 **tool 레벨**(`getOrderDetail`)에서 일어났다. 맥락으로 
  RAG 검색을 바꾸려면 `RewriteQueryTransformer` 같은 질의 재작성 단계가 따로 필요 — 현재 구현엔 없음.)
- 그럼 order는 무엇을 위해 정하나 → 아래 ①②.

### ① Performance(100)는 반드시 마지막 — 전체 측정

- order가 가장 높아 **체인 전체(Memory 주입 + RAG 검색 + tool 왕복)를 감싸** 총 호출 시간을 잰다. 앞에 두면 RAG·tool 시간이 측정에서 빠진다.

### ② Memory(10)는 RAG(20)보다 먼저 — 메모리 위생 (소스 확인)

Memory–RAG 상대 순서가 실제로 중요한 이유. **두 advisor 모두 `before()`에서 같은 user 메시지를 다룬다**:

- **RAG**는 user 메시지를 "질문 + 검색 문서"로 **교체**한다:
  ```java
  // QuestionAnswerAdvisor.before() - (spring-ai-advisors-vector-store)
  return chatClientRequest.mutate()
      .prompt(chatClientRequest.prompt().augmentUserMessage(augmentedUserText));  // user 메시지 교체
  ```
- **Memory**는 **그 시점의** user 메시지를 읽어 그대로 저장한다:
  ```java
  // MessageChatMemoryAdvisor.before() - (spring-ai-client-chat)
  UserMessage userMessage = processedChatClientRequest.prompt().getUserMessage();  // 현재 user 메시지 읽고
  this.chatMemory.add(conversationId, userMessage);                                // 그대로 메모리에 저장
  ```
- → 둘 다 `before()`에서 일어나므로, Memory의 `getUserMessage()`가 읽는 게 **RAG 교체 전이냐 후냐**가 order로 갈린다.

| 순서 | Memory가 저장하는 user 메시지 |
|---|---|
| **현재 (Memory 10 → RAG 20)** | RAG 교체 **전** → `"아까 그 주문 환불 돼요?"` (깨끗) |
| 반대 (RAG 10 → Memory 20) | RAG 교체 **후** → `"...질문 + [refund-basic 전문 + cancel-policy 전문]"` (검색 문서 포함) |

- **멀티턴 누적이 진짜 문제**: 반대 순서면 2턴에서 저장된 검색 문서가 **3턴 history에 그대로 딸려 들어온다** → 턴이 갈수록 입력 토큰 폭증 + 옛 문서가 끼어들어 혼선. 현재 순서는 이력에 **깨끗한 대화만** 남겨 이를 막는다.
- (어시스턴트 응답은 `after()`에서 저장되며 모델의 자연어 답이라 검색 문서 원문이 아니다 — 응답 쪽 누수는 없다.)

## 4. 유사도 임계값 — `similarityThreshold=0.5`

**결정**: `0.5` (COSINE, "주제가 같은 정도").

### 근거 — 우리 도메인/임베딩에서 0.5가 관련성 경계에 걸린다

이번 검증에서 측정한 실제 유사도가 0.5를 **관련/무관의 경계**로 잘 가른다:

| 질문 | Top 문서 | 유사도 | 0.5 컷 |
|---|---|---|---|
| 쿠폰 중복 | coupon-faq | 0.638 | 통과(확실) |
| 비 오는 날 보상 | delivery-delay 2개 | 0.592 / 0.525 | 통과(경계 근처) |
| 사장님 전화번호 | privacy | **0.482** | **탈락(경계 바로 아래)** |

- **너무 낮으면(예: 0.3)**: 도메인 밖 질문("오늘 점심 뭐?")에도 무관 정책이 Top-K에 끌려와, LLM이 그걸 근거라고 오해해 **환각**을 만든다. 위 표의 차순위들(0.2~0.3대)까지 통과시키면 노이즈가 컨텍스트에 섞인다.
- **너무 높으면(예: 0.8)**: 정답 문서도 걸러져 **Context가 비고 Fallback만** 나온다. 실제로 0.525인 weather-delay는 0.55만 돼도 탈락했을 것이다.
- **0.5의 위치**: privacy(0.482)는 막고 delivery-delay(0.525)는 통과 — 우리 임베딩(`qwen3-embedding:0.6b`)·도메인에서 **"느슨하게 관련"을 가르는 선**에 0.5가 놓인다.
- 단, 0.5는 **경계가 빡빡하다** — privacy 0.482처럼 의미상 관련 있는 문서도 살짝 아래로 떨어진다(시나리오 4). 그래서 threshold만으로 환각을 100% 막진 못하고, **시스템 프롬프트 Fallback/guardrail과 함께** 동작해야 한다.
- 3단계에서 0.3 / 0.5 / 0.7로 "환각 vs 빈 Context" 트레이드오프를 정량 관찰한다.

### 다른 모델/도메인이면 — 0.5는 재보정 대상

> **0.5라는 숫자는 범용이 아니다.** 우리 `qwen3-embedding:0.6b` + COSINE + 배달정책(한국어)에서 관련/무관을 가르는 선일 뿐이다. **원리(관련 컷)와 보정 방법은 통용, 값은 재보정 대상**이다.

- **왜 모델마다 다른가** — 임베딩 모델이 바뀌면 같은 질문·문서라도 유사도 숫자가 달라진다:

| 모델 성향 | 유사도 분포 | 0.5의 의미 |
|---|---|---|
| 우리 `qwen3-embedding:0.6b` | 관련 0.5~0.64 / 무관 0.2~0.48 | 경계선에 맞음 |
| 전부 높게 깔리는 모델 | 관련·무관 모두 0.7~0.95 | 0.5면 **다 통과**(필터 무의미) |
| 전부 낮게 깔리는 모델 | 관련도 0.3~0.5 | 0.5면 **정답도 다 탈락** |

- **값을 바꾸는 변수**: ① 임베딩 모델(가장 큼) ② 거리 척도(COSINE / dot-product / L2(유클리드)면 스케일·방향이 다름) ③ 도메인·언어 ④ 질문 스타일(키워드 vs 문장).
- **보정 방법(통용)**: 대표 질문 몇 개로 **관련 문서와 무관 문서의 유사도를 실측해 둘을 가르는 선**을 고른다 — 위 4장 표가 바로 그 작업이다. 모델/도메인을 바꾸면 이 측정을 다시 해 임계값을 다시 잡아야 한다.
- 즉 **"0.5 = 주제가 같은 정도"는 우리 모델에서의 경험칙**이지, 다른 임베딩에 그대로 옮기면 안 된다.

> **[참고] 거리 척도가 바뀌면 임계값이 통째로 달라진다.** "거리 척도"는 두 벡터가 얼마나 가까운지 재는 공식인데, 척도마다 ① 숫자 범위(스케일)와 ② "큰 값이 가까운 거냐"(방향)가 달라 같은 `0.5`가 전혀 다른 뜻이 된다.
>
> | 척도 | 재는 것 | 범위 | 방향 |
> |---|---|---|---|
> | **COSINE** (우리 설정) | 두 벡터의 **각도**(길이 무시) | 0 ~ 1 | **클수록 = 비슷함** |
> | **Dot product(내적)** | 각도 × **벡터 길이** | 제한 없음(0~수백) | 클수록 = 비슷함 |
> | **L2/유클리드** | 두 점의 **직선 거리** | 0 ~ ∞ | **작을수록 = 비슷함(반대)** |
>
> - **스케일**: COSINE `0.5`="절반쯤 비슷", L2 `0.5`="아주 가까움(거의 붙음)", Dot `0.5`=벡터 길이에 따라 "거의 무관"일 수도. → 같은 0.5가 의미가 제각각.
> - **방향(부등호)**: COSINE·Dot은 `유사도 >= 0.5`(위로 컷), L2는 `거리 <= X`(아래로 컷) → 척도 바꾸면 **부등호까지 뒤집어야** 한다.
> - 우리는 `application.yml`의 `distance-type: COSINE_DISTANCE` → `similarityThreshold=0.5`는 **코사인 유사도 0.5(클수록 비슷, 이상 통과)**다. L2 쓰는 시스템의 임계값을 그대로 옮기면 스케일·방향이 안 맞아 깨진다.
