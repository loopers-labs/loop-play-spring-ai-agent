# Streaming을 모든 엔드포인트에 적용해야 하는가

`/api/v1/support`(Structured Output)에 `.stream()`을 쓰면 어떤 문제가 생기는가에 대한 검토

---

## 1. 배경: 스트리밍은 무엇이고 왜 등장했는가

### 1.1 토큰 생성 메커니즘

LLM은 본질적으로 **다음 토큰을 예측하는 모델**이다. 한 번의 forward pass에서 "다음에 올 가장 그럴듯한 토큰 하나"를 계산하고, 그 토큰을 입력에 다시 붙여 또 다음 토큰을 계산하는 자기회귀(autoregressive) 방식으로 응답을 생성한다. 즉 100토큰짜리 응답은 100번의 순차적 계산을 거쳐 만들어진다.

이 특성 때문에 응답 생성에는 **시간이 비례적으로 든다**. 짧은 응답은 빠르고, 긴 응답은 느리다. 그리고 토큰은 어차피 하나씩 생성되므로, **이미 만들어진 토큰을 굳이 끝까지 모아두지 않고 즉시 클라이언트로 흘려보낼 수 있다**. 이것이 스트리밍의 기술적 근거다.

### 1.2 TTFT와 체감 지연

LLM 응답 성능의 핵심 지표는 두 가지로 나뉜다.

- **TTFT (Time To First Token)**: 첫 토큰이 도착할 때까지의 시간
- **TTLT (Time To Last Token)**: 마지막 토큰까지의 전체 완료 시간

비스트리밍 응답은 사용자가 TTLT만큼 빈 화면을 본다. 스트리밍 응답은 TTFT 직후부터 글자가 흘러나오기 시작한다. **TTLT는 줄지 않지만 체감 지연은 극적으로 줄어든다**. ChatGPT, Claude 등 챗 UI에서 글자가 좌르륵 흘러나오는 동작이 이걸 활용한 것이다.

### 1.3 스트리밍이 해결하는 문제

정리하면 스트리밍은 **사람이 글을 읽기 시작할 수 있는 시점을 앞당기는 UX 최적화**다. 응답을 더 빨리 만드는 게 아니라, 사용자가 더 빨리 무언가를 볼 수 있게 하는 기법이다. 따라서 이 가치는 **응답을 사람이 순차적으로 읽을 때만 발생**한다.

## 2. Structured Output은 무엇이고 왜 검증이 필요한가

### 2.1 정의

Structured Output은 LLM의 응답을 **정해진 스키마(JSON, enum, 객체 구조)에 맞춰 받는 방식**이다. 자연어 응답이 아니라 코드가 직접 소비할 수 있는 데이터 구조를 받는 것을 목표로 한다.

예시 — `/api/v1/support`의 응답 스키마:

```json
{
  "category": "PAYMENT",
  "priority": "HIGH",
  "summary": "환불 요청 건",
  "requires_human": true
}
```

### 2.2 검증이 필요한 이유

LLM은 확률적 시스템이라 스키마를 지시받아도 100%의 확률로 따르지는 않는다. 따라서 코드 레벨에서 **응답 검증**이 필수다.

- **타입 검증**: `priority`가 enum 값인지(`HIGH | MEDIUM | LOW`)
- **필수 필드 검증**: `category`가 누락되지 않았는지
- **JSON 자체의 유효성**: 괄호와 따옴표가 맞는지

검증이 실패하면 후속 비즈니스 로직(라우팅, DB 저장, 알림 발송)이 깨지므로, **부분적으로 유효한 응답은 무의미하다**. 전체가 유효하거나, 전체가 무효하거나 둘 중 하나다(all-or-nothing).

### 2.3 검증 시점

검증은 본질적으로 **응답이 완성된 시점**에 한 번 수행된다. JSON은 마지막 닫는 괄호가 도착하기 전까지는 파싱 자체가 불가능하기 때문이다.

## 3. 둘이 만났을 때 — 본질적 충돌

스트리밍과 Structured Output을 동시에 쓰려고 하면 세 가지 충돌이 발생한다.

### 3.1 부분 JSON은 의미가 없다

스트리밍 중간 시점의 응답은 거의 항상 **깨진 JSON 상태**다.

```
시점 1:  {"categ
시점 2:  {"category": "PAY
시점 3:  {"category": "PAYMENT", "priori
시점 4:  {"category": "PAYMENT", "priority": "HIGH", "summary": "환불 요청
시점 N:  {"category": "PAYMENT", "priority": "HIGH", "summary": "환불 요청 건", "requires_human": true}
```

스트리밍이 주는 이점은 "사용자가 부분 결과를 일찍 볼 수 있다"는 것인데, **부분 JSON은 사람에게도 기계에게도 의미가 없다**. 사람은 `{"categ`를 읽고 싶어하지 않고, 코드는 그걸 파싱할 수 없다.

자연어 응답이라면 `"안녕하세요 고객님, 환불"`까지만 받아도 사용자가 읽기 시작할 수 있지만, JSON은 그 속성이 없다.

### 3.2 검증 시점이 어그러진다

Structured Output의 검증은 응답 완성 시점에 한 번 일어난다. 스트리밍은 응답을 토막내서 흘려보낸다. **결국 다음 둘 중 하나가 된다.**

- **(A) 전체를 모아서 한 번에 검증**: 그러면 스트리밍 의미가 사라진다. 이미 TTLT까지 기다린 셈이다.
- **(B) 점진적 검증을 시도**: partial JSON parser(`json-stream`, `jsonparser`, OpenAI의 `parse_partial_json` 등)를 동원해야 한다. 그런데 검증 실패 시 어떻게 복구할 것인가? 절반쯤 흘려보낸 토큰을 클라이언트에서 되돌릴 방법은 없다.

### 3.3 에러 처리 복잡도가 폭증한다

비스트리밍 응답의 에러 처리는 단순하다.

```
요청 → 응답 받음 → 검증 → 성공이면 처리, 실패면 재시도/에러
```

스트리밍 응답은 다음 시나리오를 모두 다뤄야 한다.

- 첫 토큰이 안 옴 (TTFT 타임아웃)
- 중간에 끊김 (커넥션 드롭)
- 스트림은 완료됐는데 JSON이 깨짐 (검증 실패)
- 스트림이 완료됐고 JSON은 유효한데 enum 값이 범위 밖 (도메인 검증 실패)
- 클라이언트가 느려서 backpressure 발생

게다가 **HTTP status code의 의미도 흔들린다**. 스트리밍은 `200 OK`로 시작하는데 그 후에 실패해도 status code는 이미 보냈다. 클라이언트는 본문을 끝까지 파싱해야 진짜 성공인지 알 수 있다. 일반 REST의 계약과 다르다.

## 4. `/api/v1/support`에 적용해보면

### 4.1 이 엔드포인트의 성격

- **응답 소비자**: 사람이 아니라 **다음 단계의 코드**. 분류 결과를 받아 라우팅, 우선순위 큐 적재, 담당자 배정, DB 기록 등의 로직이 이어진다.
- **응답 형태**: Structured Output (JSON 스키마)
- **응답 크기**: 일반적으로 작음 (수십~수백 토큰 수준의 분류·요약)
- **사용 맥락**: 동기 REST 호출, 일반적인 요청-응답 패러다임

### 4.2 스트리밍의 이점

- TTFT 개선의 가치: **0**. 코드는 부분 JSON으로 할 일이 없다.
- 체감 지연 개선: **0**. 읽는 주체가 사람이 아니다.
- UX 개선: **0**. 직접적인 UI 노출이 없다.

### 4.3 스트리밍의 비용

- 에러 처리 경로가 4~5배 늘어남
- partial JSON 처리 로직 또는 "결국 전부 모아서 검증" 코드 필요
- 커넥션을 더 오래 잡음 (동시 처리량 영향)
- 리버스 프록시(Nginx 등)의 버퍼링 설정 등 인프라 가정이 깨질 위험
- 로깅·트레이싱이 어려워짐 (응답 전체를 한 번에 기록하기 까다로움)
- API 계약이 일반 REST 컨벤션에서 벗어남 → 클라이언트 측 SDK·테스트도 복잡해짐

### 4.4 결론

**`/api/v1/support`에서 스트리밍은 이점이 0에 가깝고 비용은 실재한다.** 적용해서는 안 된다.

## 5. 일반화된 의사결정 기준

> **스트리밍은 응답 소비자가 사람이고, 부분 결과에 의미가 있을 때만 유용하다.**

이 기준을 두 축으로 풀면 다음과 같다.

| 응답 소비자 | 응답 형태 | 스트리밍 가치 |
|---|---|---|
| 사람 | 자연어 (긴 글, 챗) | **높음** — TTFT 단축이 체감 지연을 크게 줄임 |
| 사람 | Structured (표/카드 UI) | 보통 — 부분 렌더링 가능하면 의미 있음, 아니면 0 |
| 코드 | 자연어 | 낮음 — 코드는 보통 전체를 기다려야 후처리 가능 |
| 코드 | Structured | **0에 가까움** — 부분 JSON은 무의미, 검증 시점 어긋남 |

`/api/v1/support`는 표의 마지막 행에 해당한다.

### 5.1 추가 고려: 하이브리드 패턴

내부적으로는 LLM 클라이언트에서 스트리밍으로 받되, **사용자에게 노출되는 API에서는 완성된 응답만 반환**하는 패턴도 가능하다. 이 경우 스트리밍은 서버 내부의 구현 디테일이고, API 계약은 동기 REST를 유지한다. 단, `/api/v1/support`에서는 이 패턴조차 이점이 거의 없다(분류 응답은 보통 짧아서 내부 스트리밍의 효용도 작다).

## 6. 실험 설계 (검증)

위 주장을 데이터로 뒷받침하려면 다음 실험을 수행할 수 있다.

### 6.1 설정

- 동일한 프롬프트와 동일한 모델로 N회(예: 100회) 호출
- 한 그룹은 `.stream()` 사용, 다른 그룹은 일반 호출
- `/api/v1/support`와 동일한 응답 스키마 사용

### 6.2 측정 지표

1. **첫 유효 JSON 시점**: 응답을 누적해가며 파싱이 성공하는 가장 빠른 시점 (스트리밍 그룹)
   - 비스트리밍 그룹과 비교했을 때, 스트리밍이 실제로 더 빠른가?
2. **전체 완료 시점 (TTLT)**: 마지막 토큰 수신 시각
   - 스트리밍과 비스트리밍 간 의미 있는 차이가 있는가?
3. **검증 실패율**: 스키마 검증을 통과하지 못한 응답 비율
   - 스트리밍에서 partial parsing 도중 실패가 추가로 발생하는가?

### 6.3 가설

- 첫 유효 JSON 시점 ≈ 전체 완료 시점 (스트리밍의 점진적 이점이 거의 없음)
- TTLT는 두 그룹이 비슷함
- 검증 실패율은 비슷하거나 스트리밍 쪽이 약간 더 높음 (중간 끊김 등의 추가 실패 경로 때문에)

이 가설이 데이터로 확인되면 결론이 강화된다. "**스트리밍은 부분 결과가 의미 있을 때 가치가 있고, Structured Output에서는 그 조건이 성립하지 않는다.**"

## 7. 서버 운영 관점의 비용

스트리밍 도입의 운영 비용은 한 줄로 정리하면 **"커넥션을 오래 잡는다"**는 사실에서 거의 다 파생된다. 일반 REST 요청이 수십~수백 ms 안에 끝나는 데 비해, 스트리밍은 초~분 단위로 커넥션을 유지한다. 이 한 가지 변화에서 다음 운영 이슈들이 모두 따라온다.

### 7.1 동시 처리량(throughput)의 재계산

서버 사이징 가정이 깨진다. 평균 응답 시간이 100ms에서 10초로 늘어나면 동시에 잡고 있어야 할 커넥션 수가 100배가 된다. 스레드 풀 기반 서버(Tomcat 등)는 스레드 고갈에 빠르게 도달한다. 이것이 Spring WebFlux 같은 **리액티브/논블로킹 스택**이 LLM 백엔드에서 자주 선택되는 이유다. WebFlux의 `Flux<String>`은 정확히 이 목적에 맞춰진 추상화다.

OS 레벨의 한도들도 평소엔 안 보이다가 떠오른다.

- **ulimit (open file descriptors)**: 리눅스 기본값 1024는 스트리밍 워크로드에서 금방 한계에 부딪힌다. 수만 단위로 늘려야 한다.
- **ephemeral port range**: LLM 프로바이더로의 outbound 커넥션이 누적되면 포트 고갈 가능성이 있다.
- **TCP 상태**: ESTABLISHED 상태가 오래 유지되어 일반 REST와 다른 종류의 압박이 온다.

### 7.2 타임아웃 — 모든 레이어를 손봐야 한다

요청 경로의 어느 한 레이어라도 타임아웃이 짧으면 스트림이 끊긴다.

```
클라이언트 → CDN → 로드밸런서 → 리버스 프록시 → 애플리케이션 → LLM 프로바이더
```

각 레이어의 기본 타임아웃이 보통 30~60초이며, 긴 응답은 이를 쉽게 넘긴다. 점검해야 할 곳들:

- **로드밸런서 (ALB 등)**: idle timeout 기본 60초. 스트리밍 워크로드면 5분 수준까지 늘려야 한다.
- **Nginx**: `proxy_read_timeout`, `proxy_send_timeout`. 더 중요한 건 `proxy_buffering off`로 버퍼링 자체를 끄는 것.
- **CDN (CloudFlare 등)**: 자체 idle timeout이 있고, 플랜에 따라 변경이 제한된다.
- **애플리케이션 서버**: Spring의 `spring.mvc.async.request-timeout`, WebFlux의 응답 타임아웃 등.
- **LLM 프로바이더 SDK**: 클라이언트 측 기본 타임아웃이 짧을 수 있다.

**Idle timeout과 전체 timeout을 구분**해서 설정하는 것이 좋다. 토큰이 활발히 흘러나오는 동안은 idle이 아니며, 토큰 간 간격이 비정상적으로 길 때만 끊어야 한다.

### 7.3 버퍼링과 압축 — 스트리밍을 죽이는 침묵의 함정

코드는 다 맞는데 클라이언트에서 토큰이 한꺼번에 도착하는 현상은 거의 항상 **중간 어딘가의 버퍼링** 때문이다.

- **Nginx**: `proxy_buffering off` 또는 응답 헤더 `X-Accel-Buffering: no`
- **gzip/brotli 압축**: 압축 자체가 버퍼링을 동반할 수 있다. SSE는 압축을 끄거나 streaming-safe한 설정을 써야 한다.
- **CDN**: `Content-Type: text/event-stream`을 정확히 설정해야 통과한다.
- **애플리케이션 프레임워크**: 응답을 자동 버퍼링하는 미들웨어가 있는지 확인하고 명시적 flush 필요.

이 문제는 **로컬 개발에서는 안 보이다가 프로덕션에서 발견**되는 경우가 많다. staging 환경을 프로덕션과 동일한 인프라(프록시·CDN 포함)로 구성하는 것이 특히 중요하다.

### 7.4 로깅·모니터링·트레이싱이 어려워진다

응답 전체를 한 줄에 로깅하려면 스트림이 끝날 때까지 누적해야 한다. 클라이언트가 중간에 끊으면 부분 응답을 어떻게 로깅할지 결정해야 한다. 일반적으로 다음 패턴을 쓴다.

- **요청 시작 로그**와 **응답 완료 로그**를 분리해서 기록
- 본문은 누적 후 한 번에 기록, 너무 길면 truncate
- 토큰 수, TTFT, TTLT 같은 메트릭은 별도 수집

기존 RED 메트릭(Rate/Errors/Duration)에 더해 스트리밍 전용 지표가 필요하다.

- **TTFT (Time To First Token)**: 사용자 체감 지연의 핵심
- **TTLT (Time To Last Token)**: 전체 완료 시간
- **Tokens per second**: 생성 속도
- **Active streaming connections**: 동시에 잡혀있는 스트림 수
- **Stream completion rate**: 정상 종료 비율

OpenTelemetry 같은 분산 트레이싱도 span이 너무 길어져서 시각화가 깨진다. **하위 span으로 "첫 토큰까지", "마지막 토큰까지"를 분리**하거나 이벤트(annotation)로 마킹하는 방식이 좋다.

### 7.5 비용 관리와 어뷰징

사용자가 stop을 누르거나 페이지를 닫아도 **이미 생성된 토큰은 LLM 프로바이더가 과금**한다. 클라이언트 disconnect를 빠르게 감지해서 LLM 호출도 함께 끊어야 비용이 절약된다. WebFlux는 cancellation propagation으로 이를 자동 처리하지만, 일반 서블릿 스택에서는 disconnect 감지가 까다롭다.

Rate limiting도 일반 REST와 다르게 설계해야 한다.

- **요청 수 제한**: 기본
- **동시 스트림 수 제한**: 사용자당 동시에 열 수 있는 스트림 수
- **토큰 처리량 제한**: 분당 누적 토큰 수
- **비용 기반 제한**: 일정 금액 초과 시 차단

악의적 사용자가 "긴 응답을 유도한 뒤 즉시 끊기"를 반복하거나, 동시에 다수의 스트림을 열어 리소스를 점유하는 패턴도 감지·차단 대상이 된다.

### 7.6 배포와 그레이스풀 셧다운

스트리밍 워크로드는 배포 시점에 가장 까다롭다. 진행 중인 응답이 30초~수 분일 수 있어서, 일반 REST 기준의 grace period(예: 30초)로는 부족하다.

배포 절차:

1. 새 요청 받는 걸 멈춤 (readiness probe를 fail로 전환)
2. 진행 중인 스트림은 끝까지 처리
3. 모두 완료된 후 종료

Kubernetes의 `terminationGracePeriodSeconds`를 충분히 늘려야 한다. 그렇지 않으면 SIGKILL이 날아가 진행 중인 스트림이 끊긴다. 카나리·블루-그린 배포에서도 구버전 인스턴스를 너무 빨리 내리면 같은 문제가 발생한다.

### 7.7 보안 측면

- **인증 토큰 유효기간**: JWT 등 단기 토큰을 쓸 때, 토큰 만료 시점이 스트림 중간에 걸칠 수 있다. 갱신 정책이나 grace period가 필요하다.
- **CORS와 SSE**: SSE는 preflight·credentials 처리가 일반 fetch와 미묘하게 다르다. `Access-Control-Allow-Origin`을 정확히 설정해야 하며 와일드카드와 credentials를 함께 쓸 수 없는 등의 제약이 있다.
- **응답 본문 후처리**: PII 마스킹 같은 응답 필터링을 스트리밍에서는 실시간으로 적용하기 어렵다. 끝난 뒤 마스킹하면 이미 사용자에게 노출된 뒤다.

### 7.8 운영 점검 체크리스트

**인프라 레이어**
- [ ] 로드밸런서 idle timeout이 충분히 길게 설정되어 있는가
- [ ] 리버스 프록시의 응답 버퍼링이 꺼져 있는가
- [ ] CDN 경로에서 SSE가 통과되도록 설정되어 있는가
- [ ] gzip/brotli 압축이 SSE 응답에서 비활성화되어 있는가
- [ ] ulimit, ephemeral port range 등 OS 한도가 점검되어 있는가

**애플리케이션 레이어**
- [ ] 리액티브/논블로킹 스택을 쓰고 있는가, 또는 스레드 풀 크기가 충분한가
- [ ] 클라이언트 disconnect 시 LLM 호출이 자동 취소되는가
- [ ] 토큰 단위 rate limit이 구현되어 있는가
- [ ] 그레이스풀 셧다운이 진행 중인 스트림을 보호하는가

**관찰성**
- [ ] TTFT, TTLT, tokens/sec 등 스트리밍 메트릭이 수집되는가
- [ ] 응답 본문 로깅이 컴플라이언스 요구를 만족하는가
- [ ] 분산 트레이싱이 스트리밍 워크로드에 맞춰 구성되어 있는가

**배포·운영**
- [ ] `terminationGracePeriodSeconds`가 충분한가
- [ ] 카나리·블루-그린 배포 시 진행 중인 스트림이 보호되는가
- [ ] staging 환경이 프로덕션과 동일한 프록시·CDN 구성을 갖는가

### 7.9 `/api/v1/support`에 대한 함의

위 운영 비용 대부분은 **그 부담을 감당할 가치가 있는 워크로드에서만 정당화된다**. `/api/v1/support`는 짧은 분류 응답을 코드가 소비하는 엔드포인트이므로, 이 7장의 비용들 중 사실상 어느 것도 정당화되지 않는다. 4장의 결론("스트리밍의 이점이 0에 가깝고 비용은 실재한다")이 운영 관점에서 한 번 더 강화된다.

---

## 8. 요약

- 스트리밍은 토큰 단위 생성이라는 LLM의 본질을 활용한 **사람용 UX 최적화** 기법이다.
- Structured Output은 코드가 소비하는 응답이며, **all-or-nothing 검증**을 전제로 한다.
- 둘은 본질적으로 충돌한다 — 부분 JSON은 무의미하고, 검증 시점이 어긋나며, 에러 처리가 폭증한다.
- 운영 관점에서도 스트리밍은 **커넥션을 오래 잡는다**는 한 가지 변화에서 동시 처리량, 타임아웃, 버퍼링, 로깅, 비용, 배포까지 전반적인 재검토를 요구한다.
- `/api/v1/support`는 기계용 응답을 다루는 엔드포인트이므로 스트리밍의 이점이 거의 없고 비용은 실재한다.
- 일반화하면: **스트리밍은 응답 소비자가 사람이고 부분 결과에 의미가 있을 때만 적용한다.**
