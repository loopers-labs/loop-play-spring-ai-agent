# 프로덕션에서 Streaming 적용 시 프론트엔드의 변화

스트리밍 도입은 프론트 입장에서 단순한 API 호출 방식 변경이 아니라, **비동기 데이터 흐름을 다루는 아키텍처 변화**다. 영향 영역을 7가지로 정리한다.

## 1. 프로토콜 수신 방식

`fetch().then(res => res.json())` 패턴이 더 이상 통하지 않는다. 응답 본문을 `ReadableStream`으로 다뤄야 하며, **SSE(Server-Sent Events)**가 가장 흔한 선택지다. 직접 구현보다 Vercel AI SDK의 `useChat`, `microsoft/fetch-event-source` 같은 검증된 라이브러리 사용을 권장한다. 주의점 두 가지: **하나의 청크가 하나의 토큰이 아니다**(여러 토큰이 묶이거나 한 토큰이 청크 경계에 걸칠 수 있음), 그리고 `TextDecoder`는 한국어 등 멀티바이트 문자 깨짐 방지를 위해 `{ stream: true }` 옵션이 필수다.

## 2. 상태 관리 모델

단일 전이(`loading → success/error`)가 다단계 상태 머신으로 바뀐다: `idle → connecting → streaming → completed/error/cancelled`. 누적 텍스트를 별도 관리해야 하며, **토큰마다 setState를 호출하면 리렌더가 폭주**한다. `requestAnimationFrame`이나 16ms 간격 배치 업데이트로 묶어야 한다. **취소(`AbortController`)**도 필수다 — 사용자가 페이지를 떠나거나 stop을 눌렀을 때 스트림을 끊지 않으면 좀비 커넥션과 LLM 비용이 계속 발생한다.

## 3. 렌더링

**자동 스크롤**: "사용자가 위로 스크롤하지 않았으면 따라가고, 올렸으면 멈춘다" 패턴이 표준. `IntersectionObserver`로 바닥 도달을 감지한다. **마크다운 렌더링**: 미완성 마크다운(닫히지 않은 코드 블록, 미완성 테이블)을 어떻게 표시할지 결정해야 한다. 토큰마다 전체 재파싱하면 성능 문제가 생기므로 일정 간격으로만 재파싱한다. 코드 블록 syntax highlighting은 미완성 상태에서는 끄는 게 보통이다.

## 4. UX 변화

스트리밍 도입은 사용자에게 **다른 UX 약속**을 하는 것이다. 추가되어야 하는 UI 요소들이 있다.

- **stop 버튼**: 잘못된 응답이 끝까지 흐르는 걸 막기 위해 거의 필수
- **regenerate 버튼**: 응답이 마음에 안 들 때 재요청
- **스트리밍 인디케이터**: TTFT 동안 보여줄 placeholder(타이핑 점, 깜빡이는 커서 등). 없으면 사용자가 "고장났나?" 의심한다.
- **부분 응답 정책**: 중간에 끊긴 응답을 채팅 기록에 남길지, "중단됨" 표시를 할지

## 5. 에러 처리

에러 발생 지점이 늘어난다. 연결 실패, TTFT 타임아웃, 중간 끊김, 토큰 간 idle 타임아웃, 서버의 명시적 에러 이벤트. 특히 **HTTP status code의 의미가 흔들린다** — `200 OK`로 시작한 뒤 실패할 수 있으므로, 보통 서버가 `data: [DONE]` 같은 종료 마커를 보내는 컨벤션을 두고 그것이 없으면 비정상 종료로 간주한다. 재시도도 일반 REST처럼 단순히 다시 호출하면 되는 게 아니라, 받은 부분을 어떻게 할지(버릴지, 보존할지) 결정해야 한다.

## 6. 인프라적 함정

프론트 코드가 맞아도 환경에서 막히는 경우가 있다.

- **리버스 프록시 버퍼링**: Nginx, CloudFlare 등이 기본 설정으로 응답을 버퍼링하면 스트리밍이 무력화된다. `proxy_buffering off`, `X-Accel-Buffering: no` 필요.
- **gzip 압축**: 일부 압축 구현이 버퍼링을 동반한다. SSE는 압축을 끄거나 streaming-safe 설정 필요.
- **HTTP/1.1 커넥션 제한**: 같은 도메인 동시 6개 제한. 스트리밍이 오래 잡으면 다른 요청이 막힐 수 있다. HTTP/2 권장.
- **모바일 네트워크**: 백그라운드 전환, Wi-Fi↔LTE 전환 시 안정성 시나리오 필요.

## 7. 테스트

시간 축이 있는 모킹이 필요하다. MSW로 SSE 응답을 흉내내거나, `ReadableStream`을 직접 만들어 fetch를 모킹한다. E2E도 "특정 텍스트가 누적되었는가"를 검증하는 방식으로 바뀐다.

## 결론

영향 범위를 한눈에:

| 영역 | 변화 |
|---|---|
| 네트워크 | fetch + ReadableStream/SSE, AbortController |
| 상태 관리 | 누적 텍스트, 다단계 상태 머신, 배치 업데이트 |
| 렌더링 | 자동 스크롤, 점진적 마크다운, 성능 최적화 |
| UX | stop/regenerate, 인디케이터, 부분 응답 정책 |
| 에러 처리 | 여러 실패 지점, 종료 마커, 재시도 정책 |
| 인프라 | 프록시 버퍼링, 압축, HTTP 버전 |
| 테스트 | 시간 축 있는 모킹, E2E 검증 변화 |

백엔드에서 스트리밍을 도입할지 결정할 때는 **프론트가 이만큼의 변화를 감당할 가치가 있는 시나리오인가**를 함께 따져야 한다. 사람이 자연어를 길게 읽는 화면에서는 정당화되지만, 기계가 짧은 분류 결과를 받는 API에서는 정당화되지 않는다.
