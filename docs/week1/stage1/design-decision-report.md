## 2. SYSTEM_PROMPT [금지] 섹션 — 삭제·추가 검토 결과

**3가지 모두 필수**다. 경쟁사 언급은 브랜드 신뢰 문제, 개인정보 노출은 안전·법률 문제, 보상 약속은 기대-현실 괴리 문제로 각각 독립적인 이유가 있다.

2가지를 추가해 총 5가지로 확장했다:

| 추가 금지 | 이유 |
|-----------|------|
| 시점·결과 단정 | "3일 이내 환불"처럼 말했다가 실제로 다르면 거짓말로 받아들여진다. 보상 약속 금지의 시간적 확장판 |
| 일방적 책임 추궁 | 고객 주장만으로 점주·라이더 과실을 단정하면 사실 확인 전에 판결을 내린 것이고, 이후 사실이 달라지면 분쟁이 커진다 |

## 3. SupportResponse.Category — 6개 enum 값 선택 근거

스타터의 5개에서 `FOOD_QUALITY`를 추가해 총 6개로 확장했다.

| 값 | 대상 |
|----|------|
| ORDER | 주문 취소·변경·내역 확인 및 쿠폰 관련 |
| DELIVERY | 배달 지연·미수령·추적 |
| REFUND | 환불 요청·처리 현황 |
| PAYMENT | 결제 오류·중복 결제 (REFUND와 대응 경로가 다름) |
| FOOD_QUALITY | 이물질·음식 불량·오배달(다른 음식 수령) |
| ETC | 위 5개에 해당하지 않는 문의의 안전망 |

`FOOD_QUALITY`를 별도 카테고리로 추가한 이유는 처리 절차가 다른 카테고리와 다르기 때문이다.
- 증빙 사진 요청 필수
- 이물질은 `urgency=CRITICAL`이 될 수 있어 안전 우선 처리
- ORDER로 묶으면 이 차이를 표현할 수 없다

## 4. SupportResponse 추가 필드 — escalationRequired 선택 근거

1차 상담 응답(SupportResponse)에 추가한 필드: **`boolean escalationRequired`**

`urgency`와 `nextAction`만으로는 호출자가 "상담사로 넘겨야 하는가"를 코드에서 판단하려면 문자열 파싱이 필요하다. 예를 들어 `urgency=HIGH`라도 AI가 처리 가능한 케이스가 있고, `urgency=LOW`라도 권한 초과 요청이면 에스컬레이션이 필요하다.

`escalationRequired`를 boolean으로 명시하면 호출자가 별도 해석 없이 분기할 수 있다. triage의 최종 출력을 **단일 명확한 신호**로 만드는 것이 이 필드의 역할이다.
