# 5주차 1단계 — InputGuardrail 설계 결정

`InputGuardrailAdvisor` 구현에서 내린 네 가지 설계 결정의 근거. 대상 코드:
`src/main/java/com/baedal/support/guardrail/InputGuardrailAdvisor.java`,
`AssistantController.java`.

---

## Q1. 왜 `MAX_INPUT_CHARS = 2000`인가?

- **무엇**: 입력 글자 수가 2000자를 넘으면 `INPUT_TOO_LONG`으로 차단.
- **왜 이 값**:
  - 실제 고객 상담 입력은 보통 수십~수백 자다("환불 어떻게 해요?", "2024-1234 어디쯤?"). 2000자는
    복잡한 질문(주문 여러 건 + 배달 지연 + 쿠폰…)까지 충분히 담을 **넉넉한 상한**이다.
  - 동시에 정상 트래픽에서 거의 닿지 않으므로, 2000자를 넘는 입력은 **남용으로 간주**해도 오탐이 적다.
  - 글자 수 검사는 O(1)이고, 요청이 **Ollama 서버로 넘어가 토큰화·추론되기 전에** 도는
    **가장 싼 1차 필터**다.

| 값 설정 | 문제                                                                  |
|---|---------------------------------------------------------------------|
| 너무 낮음 (예: 200) | **FalsePositive↑** — 정상이지만 긴 질문이 잘림. 고객이 복합 이슈를 한 번에 설명 못 함 → UX 저하 |
| 너무 높음 (예: 100,000) | **DoS/비용↑** — 공격자가 입력을 부풀려 토큰·추론시간·컨텍스트 창을 폭증시킴. 길이 가드가 사실상 무력      |

- **결론**: 2000자는 "정상 트래픽은 통과 / 토큰 폭탄은 차단"의 균형점. 정밀한 값보다 **싸고 안전한 상한**이 목적.

## Q2. 왜 정규식 기반인가? (분류 LLM / Moderation API 대비)

- **왜 정규식**:
  - **비용 0** — 이번 과제의 핵심은 LLM 호출 없이 차단하는 것. 가드 자체가 LLM을 부르면 cost-0이 깨진다.
  - **지연 0** — 정규식 매칭은 마이크로초 단위. 모든 요청에 붙어도 체감 비용이 없다.
  - **결정적·테스트 가능** — 같은 입력은 늘 같은 판정 → 단위 테스트(`InputGuardrailAdvisorTest`)가 신뢰성 있게 보증.
  - **투명** — 무엇을 막는지 패턴만 읽으면 안다(`INJECTION_PATTERNS`).

| 방식 | 강점 | 약점 | 이 단계 선택? |
|---|---|---|---|
| 정규식 | 비용·지연 0, 결정적, 투명 | 우회·신종 공격에 약함 | **O** (교육 단계: 메커니즘·cost-0 증명이 깔끔) |
| 분류 LLM / Moderation API | 변형·난독화 공격 회수율↑ | 매 요청 추가 호출 = 비용·지연·실패모드 발생 (cost-0과 상충) | X (프로덕션에서 정규식 뒤에 계층화) |

- **한계 (FalsePositive/FalseNegative)**:
  - **FN(미탐)**: 패러프레이즈("앞의 안내는 잊고…"), 타 언어, base64/leetspeak, 분할 입력은 정규식이 놓침.
    → OutputGuardrail(2단계)이 한 번 더 거르는 **다층 방어**로 완화.
  - **FP(오탐)**: 트리거 단어를 담은 정상 질문("개발자 모드가 뭐예요?", "시스템 프롬프트가 뭔가요?")이 차단됨.
    → 패턴을 좁게 잡아 FP를 줄이면 FN이 늘어나는 **상충 관계**가 본질.

> **참고 — 우회 기법 용어**
> - **base64**: 텍스트를 인코딩해 원문 단어를 숨김(정규식은 못 잡지만 LLM은 디코딩해 이해).
> - **leetspeak**: 글자를 비슷한 숫자·기호로 치환(`ignore`→`1gn0r3`, 한글은 자모 분리 `무시`→`ㅁㅜㅅㅣ`).
> - **분할 입력**: 차단 단어를 토막 내거나(`i g n o r e`, `ig`+`nore`) 여러 메시지로 나눠 보내 패턴 매칭을 깸.

## Q3. 왜 `InputGuardrailAdvisor.order = 5`가 Memory(10)보다 앞인가?

- **order 의미**: 값이 낮을수록 체인 **최외곽**에서 **먼저** 실행. order=5는 Memory(10)·RAG(20)·LLM·
  OutputGuardrail(50)·Performance(100)보다 앞.
- **앞에 둬야 하는 이유**: 차단 대상이 **어떤 상태·유료 연산에도 닿기 전에** 걸러야 한다.
- **뒤에 두면(예: Memory·RAG 다음)**:
  - 공격 입력이 먼저 **대화 메모리에 기록**됨 → 이후 턴 프롬프트가 인젝션 문구로 오염.
  - RAG가 공격 질의를 **임베딩·검색**함 → 임베딩 호출 비용 발생 + 검색 결과 오염.
  - 그 뒤에야 차단 → cost-0·오염 방지 이점이 모두 사라짐.
- **결론**: 가장 이른 위치(order=5)가 옳다 — 상태를 바꾸거나 돈이 드는 연산 **이전**에 필터.

## Q4. Short-circuit 시 비용 0이 왜 중요한가? (DoS 관점)

- **LLM 호출의 비대칭 비용**: 요청 1건은 토큰(돈) + 추론 시간(수십 초, S5는 32.6초/4103토큰) +
  유한한 추론 슬롯(Ollama는 동시성 제한)을 소비한다. 반면 공격자가 요청을 **보내는 비용은 거의 0**이다.
- **가드 없으면**: 공격자가 악성·쓰레기 요청을 쏟아부으면 각 요청이 풀 추론을 유발 → 소수의 동시 공격만으로
  추론 큐가 포화 → **정상 고객이 타임아웃**. 전형적 비대칭 DoS(공격은 싸고 방어는 비쌈).
- **Short-circuit이 뒤집는 것**: 차단은 정규식+길이 검사로 **마이크로초·토큰 0·슬롯 0**에 끝난다.
  → 방어가 공격보다 **싸진다**. 서버가 폭주를 거의 0의 한계비용으로 흡수.
- **실측 근거**: 차단 4종(S1·S2·S4)은 2~57ms / 0토큰, 통과 1종(S5)만 32.6s / 4103토큰.
  → cost-0은 단순 과금 절감이 아니라 **가용성·DoS 내성** 속성이다.
    가드 비용이 막아주는 추론 비용보다 훨씬 쌀 때만 방어로서 의미가 있다.

> **참고 — 추론 슬롯**
> - LLM이 동시에 처리할 수 있는 요청 자리 수. Ollama는 GPU/메모리 한계로 병렬 추론 개수가 정해져 있다(기본 보통 1~몇 개).
> - 슬롯이 차면 이후 요청은 줄 서서 대기 → 긴 추론(S5 32.6초) 몇 건만 동시에 들어와도 정상 고객이 타임아웃.
> - 입력 단 차단은 슬롯을 아예 점유하지 않아("슬롯 0") 폭주 중에도 정상 고객용 자리가 남는다.
