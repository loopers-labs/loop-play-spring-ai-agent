# 5주차 2단계 — 가드레일 배치·계층 설계 결정

가드레일을 **어디에 두고**(order), **어떻게 가리고**(제거 vs 대체), **왜 입력·출력 양쪽**에 둬야 하는지
세 가지 설계 결정을 기록한다.

> Q1·Q2는 [`02_masking_design_decision.md`](02_masking_design_decision.md)에서 다룬 항목을 그대로 옮겨 왔다(요청에 따라 복붙). Q3은 본 문서에서 새로 작성한다.

---

## Q1. 왜 Output Guardrail이 Performance보다 안쪽(`order=50`)인가? 바깥으로 빼면 로그에 무슨 문제가 생기나?

`InputGuardrail(5) → Memory(10) → RAG(20) → (LLM) → OutputGuardrail(50) → Performance(100)`

- **Performance(100)보다 안쪽(작은 order)**: 응답 객체는 체인을 거슬러 올라오며 가공되므로, OutputGuardrail이 안쪽이어야 Performance 로깅·관측에 **이미 마스킹된** 최종 응답이 찍힌다. 바깥이면 원본(미마스킹) 응답이 로그·관측에 남아 또 다른 누출 경로가 된다.
- **Memory/RAG(10/20)보다 바깥**: 그들이 조립한 프롬프트가 LLM을 왕복한 **뒤** 최종 출력만 검사해야 한다. 더 안쪽이면 검사 시점에 LLM 응답이 아직 없다.

> **바깥(`order > 100`)으로 빼면**: Performance 로깅이 OutputGuardrail보다 먼저 응답을 가로채므로, `[PERF]`/관측 백엔드·로그 파일에 **마스킹 전 원본(전화·이메일·주소·내부 
> 섹션)이 평문으로 기록**된다. 사용자 응답은 가려져도 **로그가 새 PII(Personally Identifiable Information :개인식별정보) 유출 지점**이 되어, 로그 수집·APM·외부 관측 SaaS로 
> 민감정보가 그대로 흘러간다.

## Q2. 왜 마스킹은 "제거"가 아니라 "대체"인가?

민감 정보를 응답에서 **삭제**하지 않고 `010-****-5678` / `[주소 비공개]` 형태로 **치환**한다.

- **맥락 보존**: 상담 응답은 "등록된 연락처는 *로 확인됩니다"처럼 값의 **존재·종류**를 알려줘야 대화가 자연스럽다. 통째로 지우면 문장이 깨지고 사용자는 무엇이 가려졌는지 모른다.
- **마스킹은 가역성이 없다**: 뒷 4자리만 남겨 본인 확인 단서는 주되, 전체 식별은 불가능하게 한다(전화). 이메일은 첫 글자+도메인만 남긴다.
- **로깅·감사**: `[OutputGuardrail] 응답 치환 — reason=SENSITIVE_MASKED` 로그로 "무엇이 가려졌는가"를 남겨 사후 감사가 가능하다.

| 방식 | 장점 | 단점 | 선택 |
|---|---|---|---|
| 제거(삭제) | 노출 0 | 문장 파손·맥락 상실 | ✗ |
| 치환(마스킹) | 맥락 유지·부분 단서·감사 가능 | 패턴 의존(FP/FN) | ✅ |

## Q3. Input만으로는 왜 불충분하고, Output만으로는 왜 불충분한가?

입력 가드와 출력 가드는 **서로 다른 실패를 막는** 상보 관계다. 한쪽만 두면 다른 쪽이 막던 실패가 그대로 새어 나간다(다층 방어).

| 가드 | 검사 대상 | 막는 실패 | 못 막는 실패 |
|---|---|---|---|
| Input(order=5) | 사용자 **입력** | 비용·오염 선제 차단(인젝션·DoS·빈입력) | LLM이 출력에서 흘리는 것 |
| Output(order=50) | LLM **응답** | 확률적 누출(민감정보·내부 섹션) | 이미 치른 LLM 호출 비용 |

### Input만으로는 불충분 — 실패 예시: 출력단 PII 누출

- **입력**: `"배달 기사님께 전달할 연락처가 010-1234-5678인데 이 번호 그대로 한 번 확인차 다시 적어줘"`
- Input 가드는 이 입력을 **정상으로 통과**시킨다(인젝션 패턴이 아님). 그러나 LLM은 사용자 제공 번호를 **그대로 복창**한다:
  `"… 등록된 연락처는 010-1234-5678로 확인되었습니다 …"`
- Input 가드는 **출력을 보지 않으므로** 이 번호가 그대로 사용자에게 나간다. Output 가드(`SENSITIVE_MASKED`)가 있어야 `010-****-5678`로 가려진다.
- 실측: 2단계 [`03_masking_5scenario_report.md`](03_masking_5scenario_report.md) 프로브 P6 — Output 가드 발동으로 `010-****-5678` 치환 확인.

> 핵심: LLM은 시스템 프롬프트로 "노출 금지"를 줘도 **확률적으로** 흘린다. 입력만 검사하면 이 확률적 누출을 막을 길이 없다.

### Output만으로는 불충분 — 실패 예시: 초장문 입력 DoS(비용 폭탄)

- **입력**: `"배달 늦어요 " × 834 = 5838자` (>2000자 임계)
- Output 가드는 **LLM이 응답을 생성한 뒤** 검사하므로, 이 5838자를 LLM이 **전부 토큰화·추론한 다음**에야 개입한다 — 토큰·지연 비용은 이미 다 치렀다(추론 슬롯 점유 = DoS 노출).
- Input 가드(order=5)는 `INPUT_TOO_LONG`으로 **short-circuit** 해 `chain.nextCall()`을 호출하지 않으므로 **LLM 호출 0회(cost-0)**. 인젝션·빈입력도 마찬가지로 LLM 도달 전에 차단된다.
- 실측: 1단계 [`01_guardrail_5scenario_report.md`](../stage1/01_guardrail_5scenario_report.md) S4 — 5838자 입력이 advisor에서 차단되어 LLM 호출 0, 5ms로 응답.

> 핵심: 비용·오염은 **LLM에 닿기 전에** 막아야 의미가 있다. 출력단에서 잡으면 "이미 비용을 다 치른 뒤의 사후 처리"라 DoS·토큰 폭탄을 막지 못한다.

### 결론 — 다층 방어

- **Input = 비용·오염의 선제 차단**(cost-0, 메모리 오염 방지), **Output = 확률적 누출의 안전망**(PII·내부 섹션).
- 둘은 대체재가 아니라 보완재다. 어느 한쪽만으로는 위 두 실패 중 하나가 반드시 새어 나간다.

## Q4 정규식 가드의 본질과 한계 

- 정규식은 **알려진 형태**만 잡는다. 변형 표기(전화 `공일공`, 이메일 `len[at]woowahan`)나 신종 주소 표기는 놓친다.
- 근본 방어는 **모델 정렬(시스템 프롬프트로 노출 거부)**이고, 출력 가드는 그것이 실패했을 때의 **안전망**이다.
- 실무에서는 정규식 + 분류 모델/PII 탐지 API를 다층으로 두고, 패턴은 코퍼스로 FP/FN을 계속 보정한다. (아래 부록 참조)


## 참고 — 실무 PII 방어: 다층 구조와 코퍼스 기반 보정

본 프로젝트의 `SensitiveDataMasker`는 정규식 한 겹이다. 교육용으로는 충분하지만, 실서비스에서는
**탐지 방식을 여러 겹 쌓고, 그 정확도를 데이터로 계속 보정**한다. Q3에서 본 "Input + Output 상보"
논리를, 이번엔 **PII 탐지 내부**에 한 단계 더 적용하는 셈이다.

### 1. 왜 다층(layered)인가

- **정규식 한 겹의 한계**: 결정적·0비용이지만 **알려진 형태**만 잡는다. 변형 표기(`공일공`, `len[at]woowahan`),
  띄어쓰기 교란(`010 1234 5678`), 신종 주소(`종로3가`)는 놓친다(FN).
- **모델 한 겹의 한계**: 문맥·변형은 잘 잡지만 **요청마다 비용·지연**이 들고, 오탐(FP)·드리프트가 있다.
- 그래서 **싼 것으로 먼저 거르고, 모호한 것만 비싼 것으로 확정**한다. 어느 한 겹도 단독으론 비용·정확도를
  동시에 만족하지 못한다 — Q3의 "보완재" 논리와 같다.

### 2. 레이어 구성 (싼 것 먼저 → 비싼 것 나중)

| 레이어 | 방식 | 잘 잡는 것 | 비용/지연 | 한계 |
|---|---|---|---|---|
| **L1** | 정규식·사전(deny list) | 명백한 형태(전화·이메일·카드번호·주민번호) | 0 (마이크로초) | 변형·문맥 못 봄 |
| **L2** | NER·토큰 분류 모델 (MS Presidio, spaCy NER, HF 토큰분류) | 문맥·변형(`공일공`, 자연어 속 이름·주소) | 추론 비용(로컬) | 오탐·라벨 한계 |
| **L3** | 클라우드 PII/DLP API (GCP DLP, AWS Comprehend PII, Azure AI Language PII) | 광범위 엔티티·다국어·신뢰도 점수 | 요청당 과금·네트워크 지연 | 외부 전송 위험 |

- **전략**: L1으로 후보를 빠르게 추출 → **모호하거나 고위험인 것만** L2/L3로 확정. 전 트래픽을 L3에 태우면
  비용·지연이 폭발하므로, 본 프로젝트의 정규식은 그대로 **L1 자리**에 남고 그 위에 겹을 얹는 식으로 확장한다.
- **신뢰도 점수 활용**: L2/L3는 엔티티별 confidence를 주므로, 높으면 마스킹·낮으면 통과·중간만 사람 검토로
  3분기할 수 있다(4주차 RAG threshold를 점수 분포로 잡은 것과 동일한 발상).

### 3. 코퍼스로 FP/FN을 계속 보정하는 루프

- **코퍼스** = 실제 상담 응답을 모아 **어디에 PII가 있는지 정답을 라벨링**한 데이터셋.
- **측정**: 코퍼스에 탐지기를 돌려 두 오류율을 본다.
  - **FP율(과잉 마스킹)** — 정상 토큰을 PII로 오인. 예: 주문번호 `2024-1234`를 전화번호로 가림 → 상담 파손.
  - **FN율(미흡 마스킹)** — 실제 PII를 놓침. 예: `종로3가`·변형 전화번호가 그대로 노출.
- **조정은 감이 아니라 분포로**: 임계값·패턴을 바꿀 때 코퍼스의 점수 분포를 보고 정한다
  (4주차 [`02_design_decision`](../../week4/stage2/03_design_decision.md) threshold 접근과 동일).
- **보정 루프**: `누출/오탐 발견 → 코퍼스에 케이스 추가 → 재측정 → 패턴·모델 갱신 → 회귀 테스트로 고정`.
  - 본 프로젝트의 단위 테스트(`주문번호는_전화번호로_오탐하지_않는다`, `옛지번_가_접미어_주소는_패턴이_놓친다`)가
    바로 이 **회귀셋의 씨앗**이다 — FP 회피와 알려진 FN을 코드로 박아 두어, 패턴을 고쳐도 다시 깨지지 않게 한다.

### 4. 운영 함정 (실무 주의)

- **PII 탐지 API 자체가 새 유출 지점**: 원문을 외부 SaaS(L3)로 보내면 Q1의 "로그가 유출 지점" 문제와
  똑같아진다. 민감 도메인은 **온프레미스(Presidio 등)**·리전 고정·DPA(데이터 처리 계약)를 검토한다.
- **마스킹 후 로깅 순서**: 어떤 레이어를 쓰든 Q1의 원칙은 그대로 — **로깅·관측보다 안쪽에서 먼저 마스킹**해
  로그가 원본 PII를 담지 않게 한다.
- **드리프트·다국어**: 신조어·표기 변화·언어 추가로 FN이 서서히 증가한다. 코퍼스를 **주기적으로 갱신**하고
  탐지율을 모니터링해, 정확도가 떨어지면 패턴·모델을 다시 보정한다.

> 한 줄 요약: **싼 정규식(L1)으로 먼저 거르고, 비싼 모델/API(L2·L3)로 모호한 것만 확정하며, 그 정확도(FP/FN)는
> 라벨링된 코퍼스로 계속 측정·보정한다.** 본 프로젝트는 그 사다리의 첫 칸(L1 + 회귀 테스트 씨앗)을 놓은 것이다.
