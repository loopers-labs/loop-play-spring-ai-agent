### 프롬프트 변경 경위와 트레이드오프

1단계에서 세션 하이재킹 시나리오를 테스트하다가, Memory에 위치 정보가 없는 상태에서 "그거 지금 어디쯤이야?"를 물었을 때 LLM이 존재하지 않는 주소("서울특별시 영등포구 선유동 157-6, 2층")를 만들어냈다. 이를 막기 위해 ASSISTANT_PROMPT에 금지 조항을 추가했다.

```
도구 응답에 없는 정보는 절대 추측하거나 만들어내지 마세요.
타 배달 플랫폼을 추천하거나 비교하지 마세요.
사장님·라이더의 개인정보를 노출하지 마세요.
쿠폰·할인·보상 지급을 약속하지 마세요.
```

결과: 할루시네이션은 막혔지만 프롬프트가 1273 → 2728 토큰으로 늘면서 qwen2.5의 Tool calling 안정성이 깨졌다(portun 재발, Turn 1 중국어 응답). 안전 규칙을 프롬프트에 넣는 것과 모델 안정성 사이의 트레이드오프다.

2단계 실험은 MAX_MESSAGES 효과를 측정하는 것이 목적이므로 금지 조항을 제거하고 진행했다. 현재 ASSISTANT_PROMPT(금지 조항 없음)에서 할루시네이션이 다시 발생하는지 아래에서 확인한다.

## 실패 관찰: MAX_MESSAGES = 2의 파괴적 결과

> MAX_MESSAGES = 2 는 직전 USER 메시지 + 직전 ASSISTANT 메시지 **한 쌍**밖에 기억하지 못한다.
> 3턴 이상 넘어가면 처음 언급된 orderId는 이미 윈도우 밖으로 밀려난 상태다.

## 회고

### 회고 1 — T3은 명시적 번호가 있어도 실패했고, T4는 맥락만으로 맞혔다

A 실험 T3 "2024-1235 주문도 있는데 메뉴 뭐였죠?"에서 모델이 "어떤 주문인가요?"로 되물었다. 메시지에 "2024-1235"가 그대로 들어있는데도. T4 "아 그 버거 세트"에서야 `getOrderDetail(1235)`가 호출됐다.

이상한 점이 두 가지다. 먼저 명시적 번호가 있는데 왜 실패했냐. Memory에 1234 관련 대화가 쌓여 있으니 모델이 "이게 1234 메뉴를 묻는 건지, 1235 신규 조회인지"를 혼동한 것으로 보인다. 다음으로 "아 그 버거 세트"는 번호가 없는데 왜 맞혔냐. T3 실패 응답("어떤 주문인가요?")이 Memory에 들어가고, T4는 그 앞뒤 흐름에서 1235를 추론했다. 숫자를 명시하는 것보다 대화 흐름이 더 강한 신호로 작동한 셈이다.

C 실험(MAX_VALUE)에서도 T3이 실패했다. B 실험(MAX=2)에서는 T3이 맞혔다. Memory가 작아서 1234 맥락이 없으니 "2024-1235"만 보고 바로 호출한 것이다. 맥락이 많을수록 오히려 판단을 흐리게 할 수 있다.

---

### 회고 2 — B 실험에서 실패한 응답이 다음 턴의 단서가 됐다

T6 "그럼 1235는 취소되죠?"에서 "어떤 주문이요?"로 실패했다. 그런데 그 실패 응답 자체에 "1235"라는 숫자가 들어있었다. 그 T6 쌍이 Memory 윈도우에 남은 채로 T7 "그거 취소해주세요"를 받았더니 `cancelOrder(1235)`가 성공했다.

실패한 응답이 다음 턴의 맥락 단서가 된 것이다. T6이 조용히 실패해서 Memory에 1235 언급이 없었다면 T7도 실패했을 것이다. MAX=2 조건에서 벌어진 우연한 연쇄다.

---

### 회고 3 — Memory가 많을수록 입력 토큰이 줄어드는 역설

실험에서 가장 예상 밖이었던 건 C(MAX_VALUE)의 평균 입력 토큰(1157)이 A(1523)보다 낮다는 점이다. Memory가 무제한인데 왜 토큰이 더 적냐.

Memory가 많을수록 Tool 재호출이 줄기 때문이다. Memory에서 답을 꺼낼 수 있으면 Tool을 부르지 않는다. Tool 결과 JSON이 프롬프트에서 빠진다. 그 JSON이 텍스트 메시지 수십 개보다 토큰을 더 많이 잡아먹는다.

C에서 T5와 T6의 입력 토큰이 936, 1009인데 A에서는 같은 자리가 2094, 2193이다. A에서는 Tool을 불러서 높고, C에서는 Memory에서 꺼내서 낮다. Memory 크기와 입력 토큰의 관계는 단순하지 않다. "Memory 크기가 크면 토큰이 더 많다"는 건 Tool 미호출 턴에서만 성립하는 말이다.

---

### 회고 4 — T10 요약 실패: 모델이 모르는 걸 만들어내지 않았다

MAX=2에서 T10 "지금까지 뭘 물어봤는지 요약해줘"에 T9 내용 1개만 돌아왔다. 1234 배달 조회, 1235 메뉴 확인, 취소 요청 같은 9턴이 없는 것처럼 대답했다.

처음엔 모델이 없는 정보를 채워 넣을 거라고 예상했는데 그러지 않았다. Memory에 T9 한 쌍밖에 없으니 그게 전부라고 답했다. 환각이 아니라 알고 있는 것만 말한 것이다.

같은 실험에서 할루시네이션 유도 테스트(Memory에 위치 정보 없이 "지금 어디쯤이야?"를 물었을 때)에서는 "강남역 인근"을 만들어냈다. 요약 질문은 "모르면 모른다"고 할 수 있는 상황이었고, 위치 질문은 라이더 위치를 알아야 한다는 역할 기대가 있었다. 같은 모델인데 다른 반응이 나온 이유가 질문의 성격 차이였던 것 같다.

---

### 회고 5 — 금지 조항이 실험 자체를 망가뜨렸다

금지 조항을 추가했더니 Turn 1부터 중국어로 응답하거나 portun 오류가 재발했다. 그 데이터로는 MAX_MESSAGES 효과를 측정할 수 없어서 금지 조항을 빼고 다시 실행해야 했다.

안전을 강화하려다 기능이 망가진 것이다. 프롬프트 길이가 늘면서 qwen2.5의 Tool calling 안정성이 깨졌다. 규칙이 많을수록 모델이 더 잘 따를 거라는 기대가 이 모델에서는 통하지 않았다.

프로덕션이었다면 더 작은 모델을 별도로 써서 입력을 필터링하거나, 안전 규칙만 처리하는 레이어를 분리하는 방식을 검토했을 것이다. 하나의 모델에 역할을 많이 쌓는 것에는 한계가 있다.

### MessageWindowChatMemory(슬라이딩 윈도우) vs 대화 요약 전략 비교

| 항목 | 슬라이딩 윈도우 | 대화 요약 |
|---|---|---|
| 동작 방식 | 최근 N개 메시지만 유지, 오래된 것은 버림 | 오래된 대화를 LLM이 요약해 압축 저장 |
| 구현 복잡도 | 낮음 (Spring AI 기본 제공) | 높음 (요약 시점 판단, 추가 LLM 호출 필요) |
| 토큰 비용 | 고정 (maxMessages 설정값에 비례) | 요약 시 추가 비용 발생, 이후엔 절약 |
| 정확도 | 최근 발화만 정확, 오래된 맥락 소실 | 압축된 맥락 유지 가능, 단 요약 정확도에 의존 |
| 배달 상담 적합 시나리오 | 짧은 상담(5~10턴), 빠른 해결이 목적 | 길고 복잡한 상담, 이전 문의 이력 참조가 필요할 때 |

**요약 전략이 적합한 시나리오**: 고객이 30분에 걸쳐 10턴 이상 대화하거나, 어제 문의한 건을 다시 꺼내는 경우. 슬라이딩 윈도우는 오래된 맥락을 버리므로 "저번에 말씀드린 그 건" 같은 발화에서 실패한다.

### "지시 대명사 해결 성공률"의 프로덕션 기준

10턴 중 7회 미만 성공이면 프로덕션에 올리면 안 된다고 생각한다.

지시 대명사를 잘못 해석하면 다른 고객 주문을 취소하거나 잘못된 정보를 안내하게 된다. 배달 상담은 금전·서비스 피해로 직결되니 10번 중 3번 틀리는 건 그냥 넘어갈 수 없다.
7회는 "이 정도면 괜찮다"가 아니라, 7회를 못 넘으면 MAX_MESSAGES 자체가 너무 작다는 신호로 읽어야 할 것 같다.

---

### 배달 상담 도메인에서 "오래된 대화"가 의미 있는 경우

1. **3시간 전 주문 건 재문의**: "아까 시킨 거 아직 안 왔어요" — 1~2시간 전 주문 orderId가 필요하다. 슬라이딩 윈도우가 짧으면 이 orderId가 소실된다.

2. **어제 환불한 건 재문의**: "어제 환불 신청했는데 아직 처리 안 됐어요" — 어제 대화가 필요하다. InMemory + 슬라이딩 윈도우로는 불가능하고 영속 저장소가 필요하다.

3. **재주문 패턴**: "저번에 시킨 거랑 똑같이 주문하고 싶어요" — 이전 세션의 메뉴 이력 참조. 고객 단위 영속 Memory가 필요한 케이스다.

---

### Memory를 세션이 아닌 고객 단위로 영속 유지할 때

**가능한 새 기능**:
- "저번에 시킨 거랑 같은 메뉴" 재주문 지원
- 단골 고객의 선호 가게 / 주소 자동 인식
- 이전 불만 기록 참조 → 보상 정책 자동 안내

**리스크**:
- 개인정보 보호법상 상담 이력 보관 기간 제한 (예: 3년)
- 고객이 "내 대화 삭제해달라"고 요청할 때 완전 삭제(Right to be forgotten) 구현 필요
- 세션 간 교차 오염: 고객 단위로 묶으면 다른 기기에서 접속한 동일 고객의 대화가 섞일 수 있다
- 저장 데이터 암호화 및 접근 제어 필요 (배달지 주소, 결제 정보 포함 가능)
