# Round 3 — 학습 기록

## 내가 배운 것

---

### 1. 토큰 증가는 Memory 크기보다 Tool 호출 여부에 더 달려 있었다

2단계 실험에서 MAX_VALUE인데도 평균 입력 토큰이 maxMessages(20)보다 낮은 역설이 나왔다. Tool JSON 하나가 텍스트 메시지 수십 개보다 토큰을 더 먹기 때문이다. Memory 기여분만 정확히 보려면 Tool 미호출 턴만 따로 추려야 한다.

4단계 10턴 실험에서 재확인했다. Tool 없는 턴만 뽑으면 T3(917) → T10(1670)으로 선형 증가가 보인다. Tool이 끼면 그 턴이 튄다.

---

### 2. LLM은 Memory가 어디에 있는지 모른다

LLM이 받는 건 프롬프트뿐이다. 저장소가 HashMap이든 H2든 `MessageChatMemoryAdvisor`가 꺼내서 앞에 붙여주면 LLM 입장에서는 똑같다. 3단계 시나리오를 InMemory와 JDBC에서 각각 돌렸는데 응답이 동일했고 토큰 차이도 17개 이내였다. 저장소가 어디냐가 LLM 동작을 바꾸지 않는다는 걸 수치로 확인했다.

---

### 3. 프롬프트 지시 준수는 비결정적이다

1단계에서는 "이미 조회한 정보는 재사용하라"는 지시대로 2회차에 Tool을 재호출하지 않았다. 4단계 10턴 실험에서는 같은 프롬프트인데 T2에서 Tool을 다시 호출했다. 같은 모델, 같은 지시에서 반대 동작이 나왔다. qwen2.5에서 프롬프트 지시 준수는 보장이 없다.

---

### 4. Memory에 쌓인 오염 응답이 이후 대화 품질을 끌어내린다

4단계 T1에서 중국어가 섞인 응답이 Memory에 들어갔고, T10 요약이 전부 중국어로 나왔다. Memory는 좋은 맥락만 쌓이는 게 아니라 나쁜 응답도 그대로 축적한다. 초반 오염이 10턴 내내 프롬프트에 실려간다.

---

### 5. "취소 가능해요?"에 cancelOrder가 호출됐다

4단계 T5에서 확인했다. 가능 여부를 묻는 질문인데 모델이 `getDeliveryStatus`로 상태를 확인하고 곧바로 `cancelOrder`까지 호출했다. 해당 주문이 취소 불가 상태라 실제로 처리되지는 않았지만, 취소 가능한 주문이었다면 고객이 요청하지 않은 취소가 실행됐을 것이다.

Round 2에서 "Tool 결과는 값으로 표현해야 한다"를 배웠는데, Round 3에서는 "의도 파악과 실행을 LLM이 스스로 구분하지 않는다"는 걸 배웠다. 금전 피해가 가능한 Tool은 이 패턴을 반드시 사전에 검증해야 한다.

## 의문점

---

**Q1. T1 중국어 혼입이 T10 전체 중국어의 원인인가?**

T10 요약이 전부 중국어로 나온 이유로 T1 오염 응답이 Memory에 남아 있었을 가능성을 제기했지만, 확인하지 못했다. T1을 정상 응답으로 교체하고 T10을 다시 돌리면 달라지는가? 아니면 10턴이 길어지면서 모델이 언어를 전환한 것인가?

---

**Q2. Tool 결과가 Memory에 없을 때 정확도가 얼마나 떨어지는가?**

`SPRING_AI_CHAT_MEMORY`에 TOOL 타입 행이 없다는 것을 확인했다. Tool 결과는 ASSISTANT 응답 텍스트에 녹아든 채로만 Memory에 남는다. Tool 결과 JSON 원문이 직접 있을 때와 자연어로 변환된 것만 있을 때 다음 턴의 정확도 차이가 얼마나 되는가?

---

**Q3. 요약 전략을 구현한다면 언제 요약할지 어떻게 판단하는가?**

2단계에서 슬라이딩 윈도우와 요약 전략을 표로 비교했는데, 요약 시점을 어떻게 트리거할지는 다루지 않았다. 메시지 수로 할지, 주제 전환 감지로 할지, 토큰 수로 할지 기준이 불분명하다. qwen2.5에서 요약 품질이 충분히 보장되는가?

---

**Q4. 실패 응답이 다음 턴의 성공 단서가 된 패턴은 어떻게 다뤄야 하는가?**

2단계 MAX=2 실험에서 T6 실패 응답("어떤 주문이요?")이 Memory에 "1235"를 남겨 T7 `cancelOrder(1235)` 성공의 단서가 됐다. 의도하지 않은 성공이었다. 이 패턴을 설계에서 활용할 수 있는가, 아니면 방지해야 하는 부작용인가?

## Round 4에 시도하고 싶은 것

---

**Memory + RAG를 같은 체인에 연결하면 어떤 질문을 커버할 수 있는가**

Memory는 "그 주문 언제 와요?" 같은 세션 맥락을 추적하고, RAG는 "배달 지연 보상 정책이 어떻게 되나요?" 같은 도메인 지식을 검색한다. 두 Advisor가 체인에 같이 붙으면 "아까 1234가 지연됐는데 보상받을 수 있어요?"라는 질문에 Memory에서 1234 지연 맥락을 꺼내고, RAG에서 보상 정책 문서를 검색해 함께 답할 수 있을 것 같다.

---

**두 Advisor의 `order` 설정이 프롬프트 조립에 어떤 영향을 미치는가**

Memory Advisor와 RAG Advisor의 실행 순서가 달라지면 프롬프트에서 Memory 블록과 RAG 컨텍스트의 위치가 바뀐다. Memory가 앞에 오면 LLM이 세션 맥락을 먼저 읽고 RAG 결과를 참조하는 순서가 된다. 어느 쪽이 더 정확한 응답을 만드는지 확인해보고 싶다.

---

**3단계에서 선택한 PostgreSQL을 RAG까지 공유하면 운영이 단순해진다**

Chat Memory는 `SPRING_AI_CHAT_MEMORY` 테이블에, 벡터 인덱스는 PgVector 익스텐션에 같은 PostgreSQL 인스턴스로 넣으면 백업, 모니터링, 접근 제어를 한 곳에서 관리할 수 있다. 3단계 DB 선택 근거가 여기로 연결된다.
