# 3단계 — Tool description A/B/C 정량 비교 보고서

> Round 2 / 3단계 — `getDeliveryStatus` 의 `@Tool(description)` 을 3가지 버전으로 바꿔가며 같은 질문(`"주문번호 2024-1234 배달 어디쯤이에요?"`)을 5회씩 호출 → Tool 호출률·응답 정확도 정량 비교.
> 평가 핵심: *description 이 LLM 에게 보여주는 유일한 API 문서* 임을 정량적으로 체감.

## 실험 환경

| 항목 | 값 |
|---|---|
| 모델 | Ollama `qwen2.5`, temperature 0.3 |
| 엔드포인트 | `POST /api/v1/assistant` (Tool 등록된 자유 텍스트 채널) |
| 입력 (고정) | `"주문번호 2024-1234 배달 어디쯤이에요?"` |
| 정답 데이터 | 1234 DELIVERING, riderLocation = "배달 시작 · 현재 역삼역 사거리 부근" |
| 반복 | 각 버전 5회 |
| 측정 | (1) `getDeliveryStatus` Tool 호출 횟수 (2) 응답에 "역삼역 사거리" 포함 여부 (3) LLM 행동 패턴 |

## description 3 버전

### 버전 A (기준 — 한국어 + 상세, 우리 정상 description)

```
주문번호로 현재 배달 진행 상태와 라이더 위치, 예상 도착 시간을 조회합니다.
호출 시점: 고객이 '배달 어디쯤?'·'언제 도착?'·'라이더 위치' 등을 물을 때 사용합니다.
입력: orderId 는 'YYYY-XXXX' 형식의 문자열입니다. 예: '2024-1234'.
반환 정보: 현재 상태(예: 조리 중·배달 중·도착)와 사람이 읽기 쉬운 안내 메시지를 함께 반환합니다.
           라이더의 정확한 위치는 배달 중(DELIVERING) 상태에서만 유효한 값이 들어 있고,
           그 외 상태에서는 null 일 수 있습니다.
실패: 존재하지 않는 주문번호이면 null 을 반환합니다.
```

### 버전 B (빈약)
```
배달 정보 조회
```

### 버전 C (오해 유발 — 실제 기능과 불일치)
```
주문번호 조회용. 메뉴와 결제 금액만 반환한다.
```

## 버전 A — 5회 raw 응답 (요약)

| # | Tool 호출 | 응답 요지 |
|---|---|---|
| 1 | ✅ | "배달 중이며 라이더가 역삼역 사거리 부근. 예상 도착 11:16:35" |
| 2 | ✅ | "배달 중이며 라이der가 역삼역 사거리 부근에서 배송 중. 약 15분 후 도착" |
| 3 | ✅ | "배달 중이며 라이der가 역삼역 사거리 부근. 약 15분 내 도착 예정" |
| 4 | ✅ | (3 과 거의 동일) |
| 5 | ✅ | (3 과 거의 동일) + 이모지 📐⏳ |

→ **모든 호출이 Tool 발동 + 정확한 라이더 위치 안내**. 미세 결함: "라이더" → "라이der" 한·영 혼용 3건 + 이모지 1건 (qwen2.5 다국어 모델 한계).

## 버전 B — 5회 raw 응답 (요약)

| # | Tool 호출 | 응답 분석 |
|---|---|---|
| 1 | ❌ | *"라이더의 위치 정보와 함께 주문 상태를 알려드릴게요. 주문번호 2024-1234의 배달 진행 상황을 확인하겠습니다."* — **Tool 호출 약속만, 실제 호출 X** |

| 3 | ✅ | 정상 (역삼역 사거리) |
| 4 | ✅ | 정상 |
| 5 | ✅ | 정상 |

### 버전 B 의 결정적 발견 — 응답 2 *시스템이 고객에게 되묻기*

> *"라이더가 현재 어느 위치에서 진행 중인지 알려주시면 더 정확한 예상 도착 시간을 안내드릴 수 있습니다. 현재 배달 상태는 어떻게 되나요?"*

→ **빈약한 description 으로 LLM 이 *"이 Tool 이 뭘 하는 건지"* 모호** → 호출 회피 → *"고객이 알려달라"* 식 자기 정합성 무너진 응답. 운영 시 고객 신뢰 ↓↓.

### 버전 C 의 결정적 발견 — 거짓 description 이 Tool 호출 결정에 *오히려* 영향 적음

| 측정 | 결과 |
|---|---|
| Tool 호출률 | 4/5 (B 보다 높음) |
| description 의 거짓 정보 (*"메뉴와 결제 금액만 반환"*) 가 응답에 노출되는가? | ❌ **노출 안 됨** — 모든 정상 응답이 *실제 반환 값* (배달 상태·라이더 위치) 사용 |
| Hallucination 발생? | ❌ LLM 이 description 의 거짓 정보를 그대로 *"메뉴와 금액은..."* 라고 답하지 않음 |
| 다른 Tool (getOrderDetail) 로 흐름? | ❌ 0건 |

### 메타 발견 — *"description 의 두 역할"* 분리

| 역할 | A | B | C |
|---|:---:|:---:|:---:|
| **(1) Tool 호출 결정 자료** — *"이 Tool 을 부를 때인가?"* | ✅ 5/5 | △ 3/5 | ✅ 4/5 |
| **(2) Tool 결과 해석 자료** — *"반환 값을 어떻게 사용할까?"* | ✅ | ✅ (호출되면) | ✅ (호출되면, 거짓 description 무시) |

→ LLM 이 description 을 *호출 결정* 시점에서만 강하게 의존하고, *결과 해석* 시점에서는 **실제 반환 값 (구조와 필드) 을 우선** 사용. C 의 거짓 정보가 응답에 안 새어나간 이유.

이게 평가 가치 큰 미세 발견: **description 의 정확성 > description 의 풍부함**.

|---|---:|---|---|

| **C (오해 유발)** | **80%** | 호출되면 정확 (거짓 description 이 결과 해석에는 영향 X) | △ 조건부 — 호출률 자체는 양호, 다만 *"왜 이 description 으로 호출되는가"* 가 코드 리뷰에서 trap |

### description 작성 시 반드시 포함해야 할 4가지 (본인 언어 + 중요도 순)

quest 명세는 강의 자료의 *"무엇 / 언제 / 입력 / 실패"* 를 그대로 옮기지 말고 본인이 *체감* 한 중요도 순으로 재배열하라고 요구.

본 실험으로 체감한 중요도 순:

**(1) 언제 호출해야 하는가 (Trigger Words)** ⭐⭐⭐⭐⭐
- 본 실험 핵심 발견 — 버전 B 가 60% 로 떨어진 *진짜 이유* 가 *"호출 시점"* 키워드 부재
- 버전 C 가 거짓이라도 80% 인 이유 — *"주문번호 조회용"* 이라는 호출 시점 단서가 있음
- → **사용자 메시지에 어떤 표현이 들어있을 때 이 Tool 을 부르는지** 가 가장 중요한 자료

**(2) 무엇을 하는가 (Tool 의 정확한 책임 영역)** ⭐⭐⭐⭐
- 호출 시점과 매칭하면서 *"이 Tool 이 다른 Tool 과 무엇이 다른가"* 의 경계 알리기
- 본 실험에서는 `getDeliveryStatus` vs `getOrderDetail` 의 경계가 흐려질 때 다른 Tool 로 흐를 위험 (다만 본 실험에서는 발생 X — 두 Tool 의 의미 도메인이 충분히 분리)

**(3) 입력 형식 (Parameter Schema)** ⭐⭐⭐
- `orderId` 가 *"YYYY-XXXX"* 형식 명시 → LLM 이 사용자 메시지에서 정확히 추출
- 형식 모호 → 입력 추출 실패 → Tool 호출 자체 회피
- 본 실험에서는 모든 버전이 동일 입력 형식을 받았으므로 영향 측정 안 됨, 다만 1단계 실험에서 *주문번호 형식 명시* 가 추출 성공률에 영향

**(4) 실패 시 반환 값 (Fallback Path)** ⭐⭐
- null 반환 가능성 명시 → LLM 이 *"찾을 수 없습니다"* 자연어로 fallback
- 명시 안 하면 LLM 이 *Hallucinate* — Round 2 1단계 S5 의 자연 응답에서 직접 관찰 (서버 재시작 후 1235 등에서 hallucinate)

### "오래된 주석" 방지 대책

description 이 *코드 변경 따라가지 못해 거짓이 되는* 위험. 본 실험 버전 C 가 그 시뮬레이션.

**프로덕션 대응**:

1. **테스트로 description 의 *호출 시점* 검증** — *"주문번호 + 위치 질문"* 입력 시 `getDeliveryStatus` 가 호출되는지 자동 검증 (Spring AI Test 또는 단순 통합 테스트)
2. **PR 리뷰 체크리스트** — Tool 메서드 시그니처 (파라미터·반환 타입) 가 변경되면 *description 변경 검토 표시* 필수
3. **Contract Test 또는 IDE 분석** — description 안의 *키워드* (예: "메뉴", "결제 금액") 와 반환 타입의 필드 매칭 정합성 검사
4. **운영 모니터링** — Tool 호출률·응답 정확도 지표를 advisor 로 추적 → 갑작스러운 하락이 description 노후화 신호일 수 있음
5. **description 을 코드 주석으로도 동기화** — Tool 메서드 위 javadoc 과 `@Tool(description=)` 가 같은 톤·내용을 유지 → 코드 리뷰 때 둘 다 함께 보게 됨

본 실험의 메타 — *"description 이 LLM 에게 보여주는 유일한 API 문서"* 라는 명제는 강했고, *"부정확한 description 이 *호출률을 일부* 깎지만 *결과 해석은 망가뜨리지 않는다"* 는 새 발견.
