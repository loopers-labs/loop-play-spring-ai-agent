## ⚡ 멱등성 분기 제거 실험 — 평가 핵심

### 두 실험 진행 — quest 명세의 가정과 실제 코드의 미세 갭 발견

quest 명세 *"ALREADY_CANCELED 분기를 통째로 제거하라"* 의 가정:
> 두 번째 호출에서 canceledReason 이 덮어씌워짐

그런데 우리 `Order.isCancelable()` 은 CANCELED 를 제외 → 단순 분기 제거만으로는 `NOT_CANCELABLE` 로 흐름. **quest 가정대로 가려면 `isCancelable()` 체크도 함께 우회해야 함**.

→ **두 실험** 진행:

| 실험 | 변경 | 의미 |
|---|---|---|
| **실험 1** | `ALREADY_CANCELED` 분기만 제거 | quest 명세 literal — 실제 동작 관찰 |
| **실험 2** | 분기 + `isCancelable()` 체크 둘 다 제거 | quest 의도된 시나리오 재현 (cancel() 무조건 실행 → 덮어쓰임) |

### 실험 1 결과 — *"메시지가 거짓이 됨"*

코드 변경:


| 호출 | Outcome | message | 평가 |
|---|---|---|---|
| 1239 첫 (ACCEPTED) | CANCELED | "취소되었습니다. 사유: 마음 바뀜" | ✅ |

## 고객에게 줄 수 있는 오해 (실험 1+2 종합, 5개)

1. **"방금 취소된 것 같은데 또 취소되었다고?"** (실험 2 응답 1·2) — 이미 25분 전 취소된 주문에 *"방금 배달 중지"* 안내 → 중복 처리 인상
2. **"환불은 한 번 받는 거 아닌가? 또 들어온다고?"** (실험 2 응답 2) — *"환불 절차에 들어갈 예정"* 두 번째 발언 → 이중 환불 기대
3. **"조리 시작도 안 됐는데 왜 조리 시작이라고?"** (실험 1) — 거짓 메시지로 인한 사실 혼란
4. **"왜 또 사유를 적었지? 처음 적은 사유는 사라진 건가?"** (실험 2 D-2) — canceledReason 덮어쓰임이 고객 화면에 보이면 *"내가 처음 적은 이유가 시스템에서 사라졌다"* 인상
5. **"배달 받았는데 취소되었다고 알림이 와?"** (실험 2 1236) — 이미 완료된 주문 강제 취소가 후속 알림으로 흐르면 고객·매장 모두 혼란

## 프로덕션이라면 발생 가능한 장애 (실험 2 기반, 5개)

1. **결제 환불 이중 처리** — 첫 취소에서 환불 처리 → 두 번째 취소에서 *재환불 시도* → 결제 PG 사 측 *"중복 환불 거절"* 또는 *"같은 거래 2번 환불 발행"* (PG 정책에 따라)
2. **사장님 알림 이중 발송** — 매장 POS 에 *"취소 알림"* 이 같은 주문에 대해 두 번 발송. 매장 운영자 *"내가 보낸 음식이 두 번 취소된 건가?"* 혼란
3. **포인트·쿠폰 환급 이중** — *"취소 시 포인트 자동 환급"* 정책이 있다면 같은 포인트가 두 번 환급. 또는 *"취소 시 사용한 쿠폰 복원"* 도 마찬가지
4. **데이터 정합성 붕괴 (실험 2 1236 케이스)** — DELIVERED 상태 주문이 CANCELED 로 변경되면, 후속 시스템 (정산·세금·매장 매출 집계) 가 *"배달 완료 → 매출"* 로 잡았던 데이터를 *"취소"* 로 다시 처리 시도. 회계 정합성 사고
5. **라이더·매장 비용 정산 이슈** — 배달 완료된 주문이 취소 처리되면 라이더 수수료·매장 매출 보전 정산 로직이 *"이미 끝난 정산을 되돌리려는 시도"* 발생. 일부 시스템은 immutable history 라 불가 → 데이터 불일치

## Outcome enum 설계 결정 (quest 명세 3가지)

### Q1. 현재 Outcome 4개 (`CANCELED / ALREADY_CANCELED / NOT_CANCELABLE / NOT_FOUND`) — 왜 4개? `UNKNOWN`·`FAILED` 안 넣은 이유?

각 Outcome 의 의미:
- `CANCELED`: 이번 호출에서 처리 성공
- `ALREADY_CANCELED`: 이미 처리됨 (멱등 — 에러 아님)
- `NOT_CANCELABLE`: 상태 때문에 불가 (조리 시작 후)
- `NOT_FOUND`: 식별자 자체 없음

**`UNKNOWN` / `FAILED` 안 넣은 이유**:
- `UNKNOWN` 은 *"우리도 모른다"* — LLM 이 *"확인해 보겠습니다"* 식 회피 응답 유도. 고객 화면에 그대로 노출되면 *"확인 못 한다"* 인상 → 신뢰 ↓
- `FAILED` 는 *"실패했다"* — 어떤 실패인지 모호. *"네트워크 실패"* 인지 *"권한 부족"* 인지 *"동시성 충돌"* 인지 구분 불가
- **각 Outcome 은 *고객 또는 다음 시스템이 취해야 할 행동* 이 다를 때만 분리** — UNKNOWN/FAILED 는 그 정보를 안 줌

**원칙**: Outcome enum 값 = *"이 결과를 받은 호출자가 다음에 어떤 분기로 가야 하는가"* 의 분기점. 분기 안 되는 값은 enum 에 넣지 않는다.

### Q2. 운영에서 추가될 법한 Outcome 2개 이상

**(1) `REQUIRES_AGENT`** — 자동 처리 불가, 상담사 인계 필요
- 시나리오: 보상 검토가 필요한 케이스 (예: 라이더 사고 + 부분 환불). cancelOrder 의 결과 만으로는 처리 불가 → 사람 검토 결정 라우팅
- LLM 응답 예: *"이 건은 담당 상담사가 확인 후 안내드리겠습니다."*

**(2) `COOLING_OFF`** — 일정 시간 내 같은 요청 빈도 제한
- 시나리오: 같은 고객·같은 주문에 5분 내 3회 이상 cancelOrder 호출 (악의·실수 보호)
- LLM 응답 예: *"잠시 후 다시 시도해주세요. 같은 주문에 반복 요청은 5분 간격으로만 가능합니다."*

**(3) `PAYMENT_LOCK_FAILED`** — 결제 시스템 측 동시성 락 실패 (실제 환불 처리 단계 실패)
- 시나리오: cancelOrder 의 *"우리 DB" 상태* 는 CANCELED 가 됐는데 결제 PG 사 응답이 늦거나 실패 → 보상 트랜잭션 필요
- LLM 응답 예: *"취소 처리 중 일시적 오류가 발생했습니다. 잠시 후 자동 재시도합니다."*

**(4) `STORE_CONFIRM_REQUIRED`** — 매장 측 동의 필요 (COOKING 상태에서 매장 재량으로 취소 허용 시)
- 시나리오: COOKING 이라도 매장 동의 시 부분 취소·환불 가능
- LLM 응답 예: *"매장 측에 취소 가능 여부를 확인 중입니다. 5분 내 결과를 안내드리겠습니다."*

### Q3. 멱등성 3가지 수준 (에러 / 무시 / 같은 응답 재전달) — *"같은 응답 재전달"* 을 택한 이유

3가지 수준:

| 수준 | 의미 | cancelOrder 적용 시 |
|---|---|---|
| **에러** | 이미 처리됨 → `Conflict` 같은 에러 응답 | *"이미 취소됨"* HTTP 409 |
| **무시** | 같은 호출 무시, 어떤 응답도 안 줌 | (Tool 결과 없음 — LLM 이 무엇을 답해야 할지 모름) |
| **같은 응답 재전달** | 첫 처리와 같은 응답 (Outcome + reason 유지) | `ALREADY_CANCELED` + 첫 reason 유지 ← **본 구현** |

**우리가 "같은 응답 재전달" 을 택한 이유**:
1. **LLM 친화성**: Tool 결과로 *"이미 취소됨 + 첫 사유"* 가 일관되게 오면 LLM 이 *"이미 취소되었습니다. 사유는 X였습니다"* 라고 자연 응답. 에러로 throw 하면 LLM 이 Fallback 못 함 (1단계의 *"예외 그대로 throw 하지 말 것"* 원칙)
2. **고객 친화성**: 고객이 같은 액션을 두 번 시도해도 *"같은 결과"* 를 받음. 에러 받으면 *"내가 잘못한 건가?"* 자기 의심
3. **시스템 추적성**: 첫 호출의 reason 이 유지됨 → 운영팀이 *"이 주문이 왜 취소됐는가"* 추적할 때 *처음 사유* 가 남음

**"에러" 가 더 적절한 다른 예 — 결제 트랜잭션**:
- 같은 결제번호에 두 번째 결제 시도 → `ALREADY_PAID` (단순 재전달) 보다는 `DUPLICATE_PAYMENT_BLOCKED` (에러) 가 더 적절
- 이유: 결제는 *돈* 이 움직임. *"같은 응답 재전달"* 패턴이면 고객이 *"안 됐나?"* 하고 또 시도할 위험. 명확한 에러로 *"이건 위험한 중복 시도다"* 신호
- → cancelOrder 는 *되돌리는* 동작이라 멱등 안전, 결제는 *지급하는* 동작이라 멱등 위험

**일반 원칙**: 같은 응답 재전달 ↔ 에러의 선택은 *부작용의 방향* 에 의존:
- 부작용이 *복구* (cancel·refund·rollback) → 같은 응답 재전달 OK
- 부작용이 *생성* (payment·order create·notification send) → 에러로 명확 차단

## 결론 + 메타 발견

### 핵심 발견 6가지

1. **(B) 결정적 채널 (admin API) + (A) 자연 채널 (LLM) 분리가 평가 검증에 필수** — qwen2.5 Tool 호출 불안정성 때문에 *결정적* 검증과 *자연 응답* 인용은 다른 채널 필요.
2. **Outcome 별 LLM Tool 호출률이 다름** — *"안전한 거부"* (NOT_FOUND/ALREADY_CANCELED) 는 80~100%, *"실제 상태 변경"* (CANCELED) 은 50%, *"모호한 거부"* (NOT_CANCELABLE) 는 20%. LLM 이 행동 회피 경향 보유.
3. **분기 제거의 *비단조* 결과** — 단순 분기 제거 (실험 1) 만으로는 quest 가 가정한 *덮어쓰임* 안 발생. `isCancelable()` 도 함께 우회해야 (실험 2) 재현 가능. *코드 사이 암묵적 계약* 의 발견.
4. **canceledReason 덮어쓰임 직접 재현** (실험 2 D-2) — 1239 첫 호출 "마음 바뀜" → 두 번째 호출 "진짜 한 번 더 취소" 로 덮어씌워짐.
5. **더 큰 위험 — DELIVERED 강제 취소** (실험 2 1236) — 분기 제거 후 *이미 배달 완료된 주문도 취소 가능*. 후속 시스템 데이터 정합성 붕괴 사고.
6. **LLM 응답에 위험 신호** (실험 2) — *"환불 절차에 들어갈 예정"* 두 번 발언 → 이중 환불 트리거 인지 어려움.

### Round 1 발견과의 연결

> Round 1 학습 기록의 결론: *"AI 신뢰는 모델 신뢰가 아니라 구조 신뢰"*

본 라운드의 멱등성 발견이 같은 패턴:
- LLM 응답은 *"방금 취소했다"* 식으로 천연덕스럽게 답함 (실험 2 응답 1·2·4)
- 진짜 안전은 **Tool 메서드 안의 4-Outcome 분기** 에서 옴
- 분기가 빠지면 LLM 은 결과를 그대로 받아 *거짓 응답*

→ **AI 시스템의 안전은 LLM 의 *지능* 이 아니라 시스템 *분기* 에서 온다**. Round 1 의 `*_REVIEW` 라우팅·`CLAIM` 위임도 같은 패턴.
