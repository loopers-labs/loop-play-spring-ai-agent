# 1단계 — RAG 기본 구현 + 시나리오 5종 검증 (평가축 ★)

> PgVector + qwen3-embedding + `QuestionAnswerAdvisor` 로 RAG 파이프라인을 만들고,
> 5종 시나리오로 검색·Fallback·Memory 협업을 검증한다.
> 측정 환경: Ollama `qwen2.5`(chat) + `qwen3-embedding:0.6b`(1024차원), temp 0.3, PgVector(pg16, Docker), CPU 추론.

## 구현 요약

| 요소 | 값 / 위치 | 근거 |
|---|---|---|
| `TOP_K` | 4 (`RagConfig`) | 정책 7건 기준 1은 누락 위험·10은 토큰 폭증 → 출발점 4 (1/4/10 비교는 3단계) |
| `SIMILARITY_THRESHOLD` | 0.5 (`RagConfig`) | qwen3 임베딩 출발점. 미만은 "관련 없음" 버림 (0.3/0.5/0.7 비교는 3단계) |
| `TokenTextSplitter` | `(800, 350, 5, 10_000, true)` | 배달 정책은 조항 단위로 이미 짧아 대부분 1청크 |

| # | 시나리오 | 결과 | 핵심 |
|---|---|---|---|
| 1 | "비 오는 날 배달이 늦으면 보상 받을 수 있나요?" | ✅ | weather-delay 정책 인용 |
| 2 | "결제 후 바로 취소하면 환불되나요?" | ✅ | refund-basic 인용 + 주문번호 요청 |

| 5 | Memory+RAG 2턴 | ❌ | 2회 모두 실패 (방식 다름) |

### 시나리오 1 — 정상 RAG (Context 주입 확인)

응답:
> "비 오는 날"이라는 이유만으로 ... 보상 받을 수 있는 것은 아닙니다. 기상 특보 여부와 실제 지연 시간을 확인해야 합니다. ... 폭우/호우 경보, 폭설/대설 경보 ... 보상은 기상 특보가 사전 고지되지 않은 경우 ...

DEBUG 로그 — QA Advisor 가 USER 메시지 뒤에 Context 를 주입 (`PerformanceLoggingAdvisor` dump):
```
#1 [USER] 비 오는 날 배달이 늦으면 보상 받을 수 있나요?

Context information is below, surrounded by ---------------------
---------------------
# 배달 지연 보상 기준
배달이 예상 시간보다 지연된 경우 아래 기준으로 보상을 안내합니다.
## 지연 시간별 기준
| 지연 범위 | 보상 |
| 예상 시간 + 10분 이내 | 보상 대상 아님 (정상 범위) | ...
```
→ Top-K(4)가 delivery-delay 2건(delay-compensation + weather-delay)을 끌어왔고, 응답은 weather-delay 원문("기상 특보", "사전 고지")을 인용. **"그거가 마법이 아니라 주입의 결과"** 를 로그로 확인.

### 시나리오 4 — 정직한 관찰: RAG 미히트, `[금지]` 가 막음

응답:
> 저는 배달 서비스의 고객 상담 AI 에이전트라서 사장님의 전화번호를 알려드리지 못합니다. ...

그런데 DEBUG 로그의 Context 블록이 **비어 있다**:
```
#1 [USER] 사장님 전화번호 알려주세요

Context information is below, surrounded by ---------------------
---------------------
---------------------
Given the context and provided history information and not prior knowledge, ...
```
- quest 기대는 "`account/privacy` 정책 히트 + `[금지]` 거절"이었지만, **실제로는 privacy 문서가 0.5 임계값을 못 넘어 Context 가 비었다**. 입력 토큰도 3932 로 다른 시나리오(4096)보다 작다(= 주입된 정책 없음).
- 즉 전화번호 거절은 RAG 가 아니라 **순전히 `[금지]` 시스템 프롬프트 규칙**이 막은 것이다.
- 해석: "사장님 전화번호"는 *고객 계정 개인정보* 를 다루는 privacy 문서와 의미적으로 충분히 가깝지 않았다(privacy 문서는 사장님 연락처가 아니라 고객 본인 정보 보호가 주제). → **임계값 0.5 의 필터링이 도메인 밖에 가까운 질문을 떨어뜨리는 동작을 의도치 않게 관찰**. Fallback 2중 방어(임계값 + 프롬프트) 중 이번엔 프롬프트만 작동한 셈.

## 시나리오 5 — Memory+RAG 협업 실패 (실패 관찰 ★)

2턴 대화를 2회(서로 다른 세션) 실행. **turn 1 은 둘 다 1234 정상 해결**(`getDeliveryStatus(2024-1234)` → 역삼역 사거리). 문제는 turn 2 `"아까 그 주문 환불 돼요?"`:

| 실행 | "아까 그 주문" 해석 | LLM 동작 | 환불 정책 인용 |
|---|---|---|---|
| run 1 (`memo-rag`) | **2024-1239** (오해) | `getOrderDetail(2024-1239)` Tool 우선 | ❌ 주문 상세만 덤프 |
| run 2 (`memo-rag2`) | 해석 안 함 | "주문번호를 알려주시면 확인해볼 수 있습니다" 되물음 | ❌ |

**Memory 는 정상 작동했다.** run 1 turn 2 의 프롬프트 dump:
```
#0 [USER]      주문번호 2024-1234 배달 어디쯤이에요?
#1 [ASSISTANT] 주문 2024-1234는 현재 배달 중이며 라이더가 역삼역 사거리 부근 ...
#3 [USER]      아까 그 주문 환불 돼요?  (+ Context 주입)
```
→ 1234 가 프롬프트 `#0/#1` 에 그대로 있는데도, Tool 호출 로그는 `getOrderDetail(orderId=2024-1239)`. **Memory 가 준 1234 를 무시하고 1239 로 빗나갔다.**

### 디버깅 — "어디서 깨지는지" 통제 실험으로 위치 특정 (★ 핵심)

처음엔 원인을 여러 번 잘못 짚었다(모델 한계 / QA 템플릿 / RAG advisor — 전부 ablation 으로 기각됨).
**비결정 시스템에서 n=2~3 실패로 "모델이 못한다"는 부정 명제는 증명할 수 없다** — 변수를 하나씩
격리해 성공률을 재야 한다(Round 2·3 교훈). 프롬프트를 고정하고 입력만 바꿔 각 하위 능력을 N회 측정:

| 측정 | 입력 시퀀스 | 성공률 |
|---|---|---|
| C1 지시 대명사 해결만 | "2024-1234 어디?" → "그거 몇 분 남았어?" | 구성별 0~5/5 (아래) |
| C2 정책만 | (단일턴) "배달 완료 후 환불 돼요?" | **3/3 ✅** |
| C4 지시 대명사 해결+정책 | "2024-1234 어디?" → "아까 그 주문 환불 돼요?" | **0/5 ❌** |

→ **각 능력은 따로면 완벽(지시 대명사 해결·정책)인데, 한 턴에 합치면 0/5.** 합치는 게 문제다.

단일변수 ablation — 프롬프트만 바꿔 지시 대명사 해결(C1)를 깬 범인 특정:

| 구성 (프롬프트만 변경, RAG 상태 명시) | C1 지시 대명사 해결 |
|---|---|
| 내 추가 규칙(맥락+정책) + RAG 제거 | 0/5 |
| Round3 프롬프트 + RAG 제거 | **5/5** |
| Round3 프롬프트 + RAG 복원 | **5/5** |
| Round3 + `[정책 인용 규칙]`만 + RAG | **0/3** |

읽는 법:
- RAG advisor 를 빼도 지시 대명사 해결 0/5 → **RAG 가 원인 아님**(가설 기각).
- Round3 프롬프트면 RAG 있든 없든 5/5 → 지시 대명사 해결 능력 자체는 멀쩡.
- `[정책 인용 규칙]`만 다시 넣어도 0/3 → **범인은 내가 추가한 프롬프트 규칙**. 모델도 RAG advisor 도 아니다.
- (참고: Round 3 보고서가 기록한 실제 baseline 은 "Tool 호출 20~30%"였다. "~80%"는 내 잘못된 기억이었고, 그것도 검증해서 바로잡았다.)

### 헤드라인 발견 — Fallback 지시 ↔ Memory 지시 대명사 해결 상충

`[정책 인용 규칙]`의 *"Context 에 없으면 확인이 필요합니다 / 상담원 연결"* 같은 **되묻기·보류 지시**가,
같은 모델에서 "그거→1234" 지시 대명사 해결까지 *되묻기*로 끌어버린다. 정책 질문을 안전하게 막으려고
넣은 지시가, 정책과 무관한 지시 대명사 해결 턴에서도 "모르면 되물어라"로 오작동하는 것.

- 지시 대명사 해결 **5/5**(정책 규칙 無) ↔ 지시 대명사 해결 **0/3**(정책 규칙 有). 정책 규칙이 사는 순간 지시 대명사 해결이 죽는다.
- 시나리오 5(C4)가 0/5인 진짜 이유: turn2 "아까 그 주문 환불 돼요?"는 **지시 대명사 해결(Memory)+정책(RAG)을 한 턴에**
  요구하는데, 정책 처리에 필요한 프롬프트 지시가 지시 대명사 해결을 무력화한다 — **Memory∩RAG 교차 지점의 구조적 긴장**.
- "1239 오염"(예시값)·"Tool 우선"은 이 긴장 위에 얹힌 부차 증상이었다.

### 최종 구성 결정 + 진짜 해법

`[정책 인용 규칙]`을 **유지**한다 — quest 필수 산출물(TODO-J)이고, 2단계에서 이걸 제거해 환각을 관찰하는 게
평가 항목이다. 지시 대명사 해결 비용(C1 0/3, C4 0/5)은 위 상충의 직접 증거로 문서화한다.
`[대화 맥락 사용 규칙]`은 재도입하지 않는다 — 지시 대명사 해결을 더 악화시켜 Round 3 가 이미 제거했던 규칙이다.
(QA Advisor 는 기본 템플릿의 "not prior knowledge / 답 없으면 거절" 문구가 빈 Context 질문에서 Memory/Tool 을
억제하는 게 로그로 보여 — 시나리오 4 의 빈 Context+거절 — 커스텀 템플릿으로 교체했다. 단 이 교체가 지시 대명사 해결 에
필수인지는 단독 측정하지 않았다.)

**진짜 해법은 프롬프트가 아니라 아키텍처** (Round 5 Guardrail 방향):
- `activeOrderId` 를 LLM 지시 대명사 해결이 아니라 **코드 세션 상태**로 관리해 프롬프트에 결정적으로 주입 (← Round 3 의문점의 답).
- 정책 질문을 **Tool 없는 RAG 전용 경로**로 라우팅해, Tool/Fallback 지시와 지시 대명사 해결이 한 프롬프트에서 충돌하지 않게 분리.
- 또는 더 큰 chat 모델.

## 설계 결정 (요지 — 반영 근거)

1. **청크 800/350**: 배달 정책 문서는 조항 단위로 이미 짧아(각 1청크) 800 으로 거의 분할 안 됨. "블로그/장문 PDF"라면 의미 단위가 길어 더 작게(300~500) + 오버랩을 키워야 한다.
2. **Top-K=4**: 문서 7건에서 1은 복합 질문("환불+지연")에서 누락 위험, 10은 7건 대부분을 프롬프트에 밀어넣어 토큰 폭증. 4 는 균형값. **K sweep 으로 실측**(아래 ★) — 문서가 7건뿐이라 K=7=K=10(상한), K>7 은 무의미, K=4 가 토큰↔커버리지 균형.
3. **`order(20)`**: 시나리오 5 가 근거다 — Memory(10)가 "아까 그 주문"→1234 를 *먼저* 프롬프트에 복원해야 RAG(20)가 그 복원된 질문을 임베딩한다. (이번엔 복원 자체가 빗나가 실패했고, 순서를 뒤바꾸면 더 나빠지는지 3단계에서 관찰.)
4. **`similarityThreshold=0.5`**: 시나리오 4 가 보여주듯 0.5 는 privacy 문서를 떨어뜨릴 만큼 빡빡하다 — 너무 높으면 정답도 탈락(Fallback만), 너무 낮으면 도메인 밖에도 무관 정책이 끼어 환각.

### Top-K sweep — 실측 (★)

threshold 를 끄고(0.0, K 효과만 격리) Tool 안 부르는 질문("쿠폰은 어떻게 적용되나요?")으로 K 별 입력 토큰 측정 (num_ctx 8192):

| K | 입력 토큰 |
|---:|---:|
| 1 | 4481 |
| 4 | 5782 |
| 7 | 6979 |
| 10 | **6979** (= K=7) |

- K↑마다 문서가 추가돼 토큰 상승(문서당 ~400). **K=7 = K=10 = 6979 — 문서가 7건뿐이라 K 를 7 넘게 키워도 더 못 가져와 토큰 동일.** → K>7 은 순수 무의미, K=4 는 토큰을 K=7 의 ~83%로 줄이며 상위 4건 확보.
- ⚠️ 단 이건 **threshold 를 끈 격리 측정**이다. 운영 threshold 0.5 에선 어떤 질문이든 0.5 넘는 문서가 1~2건뿐이라(시나리오 4 관찰) **K 가 검색을 거의 안 바꾼다** — 운영에선 K=4↔10 토큰 차이도 미미하고, K 의 진짜 비용은 threshold 를 낮춰야 드러난다.
- 정답률(quality) 축의 K 효과는 Tool 호출 노이즈 + LLM 비결정성으로 깨끗이 격리하지 못해 **토큰 비용 축만** 실측했다(정직한 한계 — 다른 PR 처럼 K=7 정답률 하락까지 보려면 Tool 없는 RAG 전용 경로가 필요).
