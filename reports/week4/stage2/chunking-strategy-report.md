# 2단계 — 청킹 전략 실험 + 실패 관찰 (평가 핵심 ★)

> `TokenTextSplitter` 의 chunkSize 를 A(800)/B(100)/C(2000) 세 값으로 바꿔 가며 동일 5질문을 돌려
> row 수·입력 토큰·답변 품질을 정량 비교하고, 문맥 조각남과 Fallback 없는 환각을 관찰한다.
> 각 실험 전 `TRUNCATE TABLE vector_store;` 후 재기동 재적재. temp 0.3, qwen2.5 + qwen3-embedding:0.6b.

동일 5질문 (5번은 도메인 밖 — Fallback 기대):
```
1) 비 오는 날 배달이 늦으면 보상 받을 수 있나요?
2) 결제 후 바로 취소하면 환불되나요?
3) 쿠폰 중복 사용되나요?
4) 배달 완료 후에도 환불 받을 수 있나요?
5) 오늘 점심 뭐 먹을까요?     ← 도메인 밖
```
품질 기준(자체 정의): **만족**=원문 수치/조건 정확 인용 · **애매**=정책 언급하나 수치 누락/뭉갬 또는 되물음 · **불만족**=환각/무관 응답.

## 정량 비교 표

| 실험 | chunkSize / min | vector_store row 수 | 평균 입력 토큰(5턴) | 답변 품질 |
|---|---|---:|---:|---|
| A | 800 / 350 | **7** (doc=1청크) | ~4096 | 만족3 / 애매1 / 불만족1 |
| B | 100 / 40 | **49** (doc당 6~8청크) | ~4096 | 만족2 / 애매2 / 불만족1 (Q1 조각남) |
| C | 2000 / 800 | **7** (doc=1청크, A와 동일) | ~4096 | 만족3 / 애매1 / 불만족1 |

질문별:

| Q | A(800) | B(100) | C(2000) |
|---|---|---|---|
| 1 비날씨 | ✅ 기상특보·보상기준 인용 | ⚠️ **조각남 → 수치 없이 뭉갬** | ✅ |
| 2 결제취소 | ❌ 1239 환각+주문덤프 | ✅ CREATED/ACCEPTED 인용 | ✅ |
| 3 쿠폰 | ✅ | ❌ 1235 환각+주문덤프 | ⚠️ 횡설수설 |
| 4 배달완료환불 | ⚠️ 되물음 | ⚠️ 부분 | ❌ raw tool-call JSON 누출 |
| 5 점심(도메인밖) | ✅ Fallback | ✅ Fallback | ✅ Fallback |

## 핵심 발견 1 — chunk knob 은 "문서 크기보다 작을 때만" 효과

- **C(2000) ≡ A(800)**: 둘 다 row 7. 배달 정책 문서가 **각 800토큰 미만**이고 `KnowledgeLoader` 가
  문서 단위로 `tokenTextSplitter.apply(List.of(doc))` 하므로, 800이든 2000이든 **doc=1청크**로 동일하다.
  (문서를 가로질러 병합하지 않으므로 청크를 키워도 변화 없음.)
  → quest 가 기대한 "C 가 A 보다 row 적고 유사도 뭉툭"은 **우리 문서가 이미 작아서 나타나지 않았다.**
  큰 효과는 **작은 쪽(B=100)에서만** 발생: 7 → 49 row 로 조각남.
- 즉 **최적 청크 = 문서(조항) 크기 이상이면서 과하지 않게.** 우리 도메인에선 800이 적정(문서를 안 자르면서
  여러 조항을 한 청크에 안 욱여넣음). "블로그/장문 PDF"처럼 문서가 길면 그때 비로소 800↔2000 차이가 난다.

쿠폰 금액)가 든 청크가 top-4 밖으로 밀려났다.** Top-4 엔 "예상 시간 기준" 같은 *조각*만 올라오고 그 뒤의 숫자는
다른 청크에 갈려 떨어졌다. A(800)는 같은 질문에 보상 기준표("+10분 이내", "+11~29분 1,000원 쿠폰")까지 인용했던 것과 대비.
이것이 "청크가 너무 작으면 문맥(특히 수치)이 조각나 LLM 이 뭉개진 답을 한다"의 실물.

> chunkSize 와 무관하게 A/B/C 전부에서 산발한다 — 1단계에서 위치 특정한 "Tool 우선 + 예시값 오염" 증상이며
> 청킹 실험의 교란 변수다. 청크 고유 효과는 위 **B 의 수치 조각남**이 깨끗한 신호다.

## 핵심 발견 3 — 입력 토큰이 조건 무관 ~4096 (num_ctx 천장)

세 조건 모두 비-Tool 질문의 입력 토큰이 **정확히 4096**. B(작은 청크 4개 ≈ 400토큰)는 A(큰 청크 4개)보다
Context 가 작아 토큰이 적어야 하는데 동일하다. 원인: system prompt(~3500) + Tool 정의가 프롬프트를 지배해
어차피 Ollama `num_ctx` 기본값 **4096 천장**에 닿기 때문(초과분은 절단). → **청크 크기로 인한 토큰 차이가
num_ctx 천장에 가려 측정되지 않았다.** 토큰 비용을 제대로 보려면 num_ctx 를 키우거나 system prompt 를 줄여야 함(4단계 연결).

## 핵심 발견 4 — Fallback 없는 환각 (실패 관찰 ★)

`BaedalPrompt` 의 `[정책 인용 규칙]` 전체를 임시 제거 후 "오늘 점심 뭐 먹을까요?" 3회:

| 구성 | 응답 (3/3 일관) |
|---|---|
| 규칙 **있음** | "저는 주문·배달·환불 관련 상담을 도와드리는 역할이라..." (상담 범위 안내, 거절) |
| 규칙 **없음** | "오늘 점심 메뉴 추천해드릴게요! 중식·양식·일식..." / **"햄버거, 파스타, 비빔밥..."** (범위 벗어난 환각) |

→ 규칙을 빼자 3/3 전부 **상담 범위를 벗어나 메뉴를 추천**(quest 예측 "비빔밥"까지 등장). 시스템 프롬프트의
Fallback 규칙이 환각을 막는 직접 증거.

## 설계 결정 (README)

1. **최적 청크 크기**: 우리 도메인 = **800**. 정책 문서가 조항 단위로 이미 짧아(<800토큰) 800이면 문서를 안 자르고
   1청크로 담는다. 더 키워도(2000) 동일(doc=1청크), 작게(100) 하면 수치가 조각나 손실(발견 2). 즉 "문서 크기 이상,
   과하지 않게"가 기준. 큰 문서(리뷰/PDF)면 의미 단위로 더 작게 + 오버랩을 키워야.
2. **오버랩 0이면?**: 청크 경계에서 문장·수치가 갈린다. B 에서 이미 관찰됐듯 "예상 시간 +"와 "30분"이 서로 다른
   청크로 갈리면 둘 중 하나만 검색돼 의미가 깨진다. 오버랩은 경계에 걸친 맥락을 양쪽 청크에 중복 보존해 이를 완화한다.
   (TokenTextSplitter 는 chunkSize 토큰을 채우되 minChunkSizeChars 로 너무 작은 꼬리를 앞 청크에 병합 — 명시적
   overlap 파라미터는 없어, 경계 손실은 chunkSize 를 문서 크기 이상으로 잡아 회피하는 게 우리 도메인의 현실적 답.)
3. **"사용자 리뷰 10만 건"이면?**: 문서가 짧고(리뷰 1건 = 수십 토큰) 수가 많다 → 리뷰 1건 = 1청크(자르지 말 것),
   중복 방지는 faqId 대신 **내용 해시(SHA-256)**(같은 사용자가 비슷한 리뷰 반복), 재인덱싱은 전량이 아니라
   **증분(신규/수정 리뷰만)** + 주기 배치. Top-K 도 키워야(관련 리뷰가 분산).
4. **similarityThreshold 만으로 환각을 막을 수 있나? → NO** (발견 4 가 증거).
   - 임계값은 **검색 단계** 방어 — "무관 문서를 Context 에서 뺀다"(도메인 밖 질문은 Context 가 빔).
   - 그런데 Context 가 비어도 LLM 은 **생성 단계**에서 상상으로 답한다(점심 메뉴 추천).
   - 즉 임계값(검색)과 Fallback 프롬프트(생성)는 **다른 층의 방어**이며, 환각 차단엔 2중 방어가 모두 필요하다.
     ("오늘 점심"은 임계값을 넘는 정책이 없어 Context 가 비었지만, 프롬프트 규칙이 없으면 그래도 환각함.)
