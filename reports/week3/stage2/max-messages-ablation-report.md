# 2단계 (메인) — `MAX_MESSAGES` 정량 비교 (평가축 ★)

> Round 3 평가축 중 하나: **`MAX_MESSAGES` 양 옆 값(2 / 20 / Integer.MAX_VALUE) 정량 비교.**
> 슬라이딩 윈도우 크기가 (1) 입력 토큰 (2) 지시 대명사 해결에 어떻게 영향하는지 측정한다.

## 측정 조건

- `ChatMemoryConfig.MAX_MESSAGES` 를 **2 / 20 / Integer.MAX_VALUE** 로 바꿔 recompile·restart.
- 12턴 시퀀스: T1(주문번호 언급) → filler 10턴 → T12("맨 처음 주문번호 뭐였죠?")
- 입력 토큰은 `PerformanceLoggingAdvisor` 의 **1차 LLM 호출 `inputTokens`**(Memory 누적이 반영된 프롬프트)로 집계.
- `/api/v1/assistant`(memory O), 조건마다 새 세션.

## 측정 설계의 함정 — orderId 선택 (오염 2종 발견)

지시 대명사 측정에는 *"T1 에서 말한 주문번호를 T12 에서 복창하는가"* 를 쓰려 했는데, **orderId 선택에서
두 번 오염됐다.**

| 시도 | orderId | 오염 |
|---|---|---|
| 1차 | `2024-1234` | **system prompt 예시값** — Memory 가 비어도 LLM 이 예시에서 1234 를 끌어다 복창 |
| 재설계 | `9999-0001` | **mock 에 없어 NOT_FOUND** — LLM 이 "유효하지 않은 번호"로 취급해 Memory 에 있어도 복창 거부 |

→ 1차에서 MAX=2(윈도우 밖)인데도 "1234" 가 나와 측정이 무효였다. 재설계로 예시에 없는 `9999-0001` 을
썼더니 이번엔 NOT_FOUND 라서 MAX_VALUE(전체 누적)에서도 복창을 거부했다. **둘 다 윈도우 크기와 무관한
이유로 결과가 오염됐다.**

이는 1단계의 *"역삼역 언급 ≠ Tool 호출"* 함정과 같은 계열이다 — **응답 텍스트를 지표로 쓸 때 그 값이
system prompt(예시)나 Tool 결과(NOT_FOUND)에 오염되지 않는지 먼저 확인해야 한다.**

> **깨끗한 orderId 조건**: mock 에 존재(유효) + 예시에 없음(비환각). → `2024-1235/1236/1237/1238` 중 하나.
> (예시는 `2024-1234`·`2024-1239` 뿐.) **지시 대명사 깨끗한 측정은 `2024-1237` 로 재측정 예정 (TODO).**

## 결과 1 — 입력 토큰 (깨끗하게 측정됨) ✅

12턴 동안 1차 `inputTokens` 추세 (tool 2차 호출·로그 누락 턴 제외):

| 조건 | T2~T11 inputTokens 추세 | 패턴 |
|---|---|---|
| **MAX=2** | ~3557 → 3759 (3557·3636·3672·3677·3693·3759·3669·3658) | **평평** — 누적 없음 |
| **MAX=20** | 3634 → 4090 (3634·3750·3848·3981·4041·4090·3956·3950) | **우상향** 후 상한 |
| **MAX_VALUE** | 3636 → 4093 (3636·3742·3822·3917·4014·4054·4095·4089·4093) | **우상향** |

**해석:**

- **MAX=2 는 입력 토큰이 누적되지 않는다** (~3600 고정). 윈도우가 직전 1턴(2메시지)뿐이라, 대화가
  길어져도 프롬프트에 들어가는 이력이 항상 같은 크기. → 비용은 싸지만 맥락을 거의 못 들고 간다.
- **MAX=20·MAX_VALUE 는 턴이 진행될수록 입력 토큰이 증가** (3600 → 4100). Memory 누적이 프롬프트를
  키운 직접 증거. **강의 노트의 *"무제한이면 입력 토큰이 선형 증가"* 를 우리 데이터로 확인.**
- **12턴(24메시지)에서 MAX=20 과 MAX_VALUE 는 거의 동일**하다 (둘 다 ~4090). 윈도우 20 을 살짝만
  초과해서다. **차이는 대화가 더 길어질 때 벌어진다** — MAX=20 은 상한(20메시지)에서 평평해지고
  MAX_VALUE 만 계속 증가. (강의 노트: 30턴 5,400 토큰 / 100턴 18,000 토큰.)

> 기저값 ~3,500 의 대부분은 system prompt + Tool 정의 JSON 이다 (Round 2 4단계에서 측정한 구조).
> Memory 가 더하는 건 그 위의 증분(턴당 수십~수백 토큰).

## 결과 2 — 지시 대명사 해결 (`2024-1237` 깨끗한 측정) ✅

오염 없는 orderId `2024-1237`(mock 유효 + 예시 아님)로 5턴 미니 시퀀스를 다시 돌렸다.
T1 에서 1237 언급 → filler 3턴 → T5 "맨 처음 제가 말한 주문번호가 뭐였죠?".

| 조건 | T5 응답 | 1237 복창 |
|---|---|:---:|
| **MAX=2** | "주문번호를 알려주세요... 예를 들어 2024-1234" (되묻기 + 예시 흘림) | ✗ |
| **MAX=20** | "2024-1237 을 확인하겠습니다" | ✅ |
| **MAX_VALUE** | "처음에 말씀해주신 주문번호는 2024-1237입니다" | ✅ |

**해석:**

- **MAX=2 는 먼 참조 실패** — 5턴째엔 윈도우(직전 1턴=2메시지)에 T1 의 1237 이 이미 밀려나, 모델이
  맥락을 잃고 "주문번호를 알려달라"고 되묻는다. (그리고 *예시값 2024-1234 를 또 흘렸다* — 오염 재확인.)
- **MAX=20·MAX_VALUE 는 성공** — 5턴(10메시지)이 윈도우 안이라 T1 이 생존, 1237 을 정확히 복창.
- 5턴 길이에선 20 과 MAX_VALUE 가 동일하게 성공한다. 차이는 *윈도우(20)를 넘는 거리의 참조*에서만
  나타난다 (그때는 MAX_VALUE 만 성공). → **윈도우 크기 = "몇 턴 전까지 기억하느냐"의 직접 상한.**

이로써 토큰 축과 지시 대명사 축이 같은 방향을 가리킨다: **MAX=2 는 토큰은 싸지만(평평) 맥락을 잃고,
MAX≥20 은 토큰을 쓰는 대신(누적) 맥락을 들고 간다.** 비용과 맥락의 trade-off 가 윈도우 크기로 조절된다.

## 설계 결정 — `MAX_MESSAGES = 20` 채택 근거 (데이터 확정)

- **2 는 너무 작다** — 입력 토큰은 절감되나(평평) 직전 1턴만 들고 가므로, 배달 상담의 흔한
  "두세 턴 전 주문번호 참조"를 놓친다. 1단계 시나리오 1·3의 "그거→주문번호" 류가 깨질 위험.
- **Integer.MAX_VALUE 는 너무 크다** — 대화가 길어지면 입력 토큰이 선형 증가(비용·지연·컨텍스트 초과).
  배달 상담은 무한히 이어지지 않으므로 무제한 보존은 낭비.
- **20(=약 10턴)** 은 배달 상담 1회 평균 길이를 덮으면서, 토큰이 상한에서 평평해져 비용이 유계.
  → **단일 상담 세션 + 단기 맥락** 전제에서 20 이 sweet spot. (세션이 길어지는 운영이라면 요약 전략 검토.)

### MessageWindowChatMemory vs Summarization

| 전략 | 강점 | 약점 | 적합 |
|---|---|---|---|
| **Window (최근 N개)** | 단순·결정적, 구현 0 | N 밖 맥락 완전 소실 | 짧은 단일 상담 (배달) |
| **Summarization** | 오래된 맥락도 압축 보존 | 요약 호출 비용·요약 손실·시점 판단 필요 | 길고 누적되는 상담 |

배달 상담은 한 세션이 짧고 *"그 주문"* 류 참조가 직전 수 턴에 몰려 있어 Window 로 충분하다. 요약은
"수십 턴 이어지며 앞부분 결정이 뒤에 계속 영향"하는 도메인(예: 장기 기술 상담)에서 값을 한다.

## 결론 + 다음

- **토큰 축**: MAX=2 평평 / MAX≥20 누적, 무제한은 선형 증가 — 슬라이딩 윈도우의 비용 효과 확인.
- **지시 대명사 축**: `2024-1237` 깨끗한 측정으로 MAX=2 실패 / MAX≥20 성공 확인 — 윈도우 크기 = 참조 가능 거리의 상한.
- **두 축이 같은 결론**: 윈도우 크기가 *비용(토큰) ↔ 맥락(지시 대명사)* trade-off 를 조절. 20 이 sweet spot.
- 측정 부산물: **orderId 지표 오염 2종**(예시값·NOT_FOUND) — 1단계 "역삼역" 함정과 같은 계열.
- 3단계: InMemory → JDBC 영속화 + 재시작 실험 + 의사결정 트리.
