# 2단계 (추가) — temperature 테스트: "모델 탓" 결론의 재고

> 이 보고서는 1·2단계에서 내렸던 **"Tool 호출 불안정은 qwen2.5 모델 탓"** 이라는 결론을
> 다시 의심하고 검증한 기록이다. 결론부터: **그 결론은 틀렸다.** 모델은 병목이 아니었다.

## 왜 "모델 탓"을 다시 의심했나

1단계 보고서는 Tool 호출률 20~30% 를 보고 *"모델(qwen2.5) 차원에서 불안정하다"* 고 적었다.
그런데 2단계 ablation 에서 **prompt 의 `[대화 맥락 사용 규칙]` 한 블록을 제거하자 20% → 80% 로
4배가 됐다.** 모델은 그대로인데 출력이 4배 변했다면, *변수는 모델이 아니라 우리가 통제하는 무언가* 다.

→ "모델 탓"은 **통제 변수(prompt·temperature)를 고정하지 않은 채 내린 성급한 결론**일 수 있다.
prompt 는 ablation 으로 이미 잡았으니, 남은 통제 변수 **temperature** 를 격리 측정하기로 했다.

## 왜 0.3 을 "놔두고" 0.0 을 테스트했나

`temperature: 0.3` 은 Round 1 부터 이어온 프로젝트 기본값이다. 이번 측정의 목적은 *temperature 를
영구히 바꾸려는 게 아니라*, **temperature 가 Tool 호출에 주는 영향만 격리(ceteris paribus)** 하는 것이다.

- tool 호출은 본질적으로 *결정적 행동 선택* 이다. temperature 가 높을수록 "호출할까/말까"가 무작위로 흔들린다.
- 따라서 다른 조건(prompt 0줄)을 그대로 둔 채 temperature 만 0.0 으로 내려 한 번 측정하고, **측정 후 즉시 0.3 으로 원복**했다. 0.0 채택 여부는 측정 결과를 보고 따로 판단한다 (아래 "temperature 결정").

## 측정

- 조건: prompt 0줄(2단계에서 채택된 상태) + `temperature: 0.0`
- 질문: `"2024-1234 배달 어디쯤이에요?"` (정답 = getDeliveryStatus 호출)
- `/api/v1/assistant` 10회, Tool 호출은 `[Tool]` 로그로 결정적 카운트, JSON 누출도 카운트.

| 측정 | 결과 |
|---|---|
| Tool 호출 | **10/10** |
| JSON 텍스트 누출 | **0/10** |
| 응답 일관성 | 10회 전부 "역삼역 사거리 부근"(Mock 정확값)으로 동일 — 결정적 |

## 종합 — 세 조건의 누적 효과

| prompt | temperature | Tool 호출 | 비고 |
|---|---|---:|---|
| 5줄 (`[대화 맥락 사용 규칙]` 포함) | 0.3 | 2~3/10 | 1단계 baseline ("모델 탓"이라 본 지점) |
| 0줄 (블록 제거) | 0.3 | 8~9/10 | ablation — prompt 레버 |
| 0줄 | **0.0** | **10/10** | + temperature 레버 |

**모델(Q4 양자화 7.6B)은 세 조건 모두 동일하다. 그런데 20% → 100%.**

## 결론 — 모델은 병목이 아니었다

1·2단계에서 "모델 탓"이라 본 Tool 호출 불안정은 사실 **prompt 설계 + temperature 라는 두 통제 변수의
복합 효과**였다. 둘 다 우리가 *무료로* 쥔 레버다:

- **prompt**: 경쟁 섹션(`[대화 맥락 사용 규칙]`) 제거 → 20% → 80%
- **temperature**: 0.3 → 0.0 → 80% → 100% (+ JSON 누출 0)

Q4 7B 로도 같은 질문 **100% Tool 호출**이 가능했다. 즉 *"qwen2.5 가 약해서 안 된다"* 가 아니라
*"우리가 변수를 고정하지 않아서 흔들려 보였다"* 가 정확하다.

> 1·2단계 보고서의 "모델 차원 불안정" 서술은 **수정하지 않고 그대로 둔다.** 그 결론은 당시 통제 변수를
> 고정하기 전의 관찰이었고, 본 보고서가 그것을 재고·반박하는 *사고의 진화 과정* 자체가 기록의 가치다.
> (결론을 덮어쓰면 "왜 처음엔 모델 탓이라 봤는지"의 맥락이 사라진다.)

## temperature 결정 — 0.3 유지

측정상 0.0 이 Tool 호출엔 최적(10/10)이지만, **0.3 을 유지**한다.

| | temperature 0.0 | temperature 0.3 |
|---|---|---|
| Tool 호출 | 100% | 80~90% |
| JSON 누출 | 0 | 가끔 |
| 자연어 응답 | 결정적 (10회 글자까지 동일) | 다양성 유지 |

배달 상담은 Tool 정확도뿐 아니라 *공감·자연스러운 문장 변주* 도 중요하다. 응답이 매번 토씨까지 같으면
상담 톤이 기계적으로 느껴진다. 또한 Round 1~2 가 0.3 으로 일관해온 측정 기준선을 유지하는 게
비교 가능성에 좋다. **Tool 호출이 절대 목표인 별도 엔드포인트가 필요하다면 그때 0.0~0.1 을 국소 적용**하면 된다
(Spring AI 는 호출 단위 options 오버라이드 가능).

## 더 큰 교훈

- **"모델 탓"은 통제 변수를 다 고정하기 전엔 성급한 결론.** ablation(prompt) + temperature 로 변수를
  하나씩 격리하니, 모델의 순수 기여분은 거의 없었다.
- **JSON 텍스트 누출도 temperature 에 반응했다** (0.3 가끔 → 0.0 zero). 이는 누출이 *모델의 절대적
  한계* 라기보다 *샘플링 무작위성* 의 산물임을 시사한다 (Q4 양자화 한계와 겹치되, temperature 로 억제 가능).
- 측정 방법론: 한 번에 한 변수만 바꿔 누적 효과를 본 게 핵심 — prompt 고정 → temperature 만 변경.
