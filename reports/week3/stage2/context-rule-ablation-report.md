# 2단계 (선행) — `[대화 맥락 사용 규칙]` ablation

> 이 보고서는 1단계에서 발견한 **Tool 호출률 회귀**(Round 2 80% → Round 3 20~30%)의
> 원인을 ablation 으로 규명한 기록이다. 2단계의 메인 과제인 `MAX_MESSAGES` 정량 비교(평가축 ★)는
> 별도 보고서로 다룬다.

## 동기

Round 3 에서 `BaedalPrompt` 에 `[대화 맥락 사용 규칙]` 5줄을 추가했다 (upstream/round3 starter 가
넣어둔 것을 그대로 채택). 1단계 정량 측정에서 같은 질문(`"2024-1234 배달 어디쯤이에요?"`)의
Tool 호출률이 **Round 2 의 4/5(80%) → 2~3/10(20~30%)** 으로 급락했다. plan 의 "위험·함정"에
*"이 5줄이 호출률을 떨어뜨리지 않는지 측정"* 이라 적어둔 가설을 데이터로 검증한다.

추가한 5줄:
```
[대화 맥락 사용 규칙]
- 이전 대화에서 고객이 주문번호를 언급했다면, "그거", "방금 그 주문", "아까 말한 주문" 같은
  지시 대명사는 가장 최근에 언급된 주문번호로 해석합니다.
- 맥락상 여러 주문번호가 언급되었다면, 가장 마지막에 언급된 주문번호를 우선 사용합니다.
- 맥락이 모호하면 추측하지 말고 "어떤 주문을 말씀하시는 건가요?"라고 다시 확인합니다.
- 이전 턴에서 이미 Tool로 조회한 정보는 다시 Tool을 호출하지 말고 대화 이력에서 재사용합니다.
```

## 측정 방법

- 질문: `"2024-1234 배달 어디쯤이에요?"` (정답 = `getDeliveryStatus` 호출)
- 경로 2개: `/api/v1/chat`(memory X) · `/api/v1/assistant`(memory O, 매 호출 새 세션)
- **Tool 호출은 `[Tool] getDeliveryStatus` 콘솔 로그 카운트로 결정적 측정** (1단계의 자기수정 —
  "역삼역 언급" 같은 응답 텍스트 지표는 환각에 오염되므로 쓰지 않는다)
- 각 조건 10회 반복. prompt 만 바꿔 recompile·restart 후 동일 측정.

## 가설의 정정 (정직한 기록)

처음 세운 가설은 *"마지막 줄(이미 조회한 정보 재사용)이 진범"* 이었다. LLM 이 그 지시를 첫 턴에도
과잉 적용해 Tool 을 회피한다고 봤다. → **이 가설은 4줄 조건에서 기각됐다.** 마지막 줄만 빼도
호출률이 회복되지 않았다. 진범은 특정 한 줄이 아니라 **블록 전체(프레이밍)** 였다.

## 결과 — 3조건 비교

| 조건 | prompt | chat (memory X) Tool | assistant (memory O) Tool | "그거" 해결 |
|---|---|---:|---:|:---:|
| **A** baseline | 5줄 전체 | 2/10 | 3/10 | ✅ |
| **B** | 마지막 "재사용" 줄만 제거 (4줄) | 1/10 | 2/10 | ✅ |
| **C** | 블록 전체 제거 (0줄) | **8/10** | **9/10** | ✅ |

- A→B: 마지막 줄 제거는 효과 없음 (오히려 비슷하게 낮음). **진범은 마지막 줄이 아니다.**
- A,B→C: 블록을 **통째로** 빼야 Tool 호출률이 80~90% 로 회복. Round 2 수준 복귀.
- "그거" 해결은 **세 조건 모두 성공** (C 는 새 세션 3회 모두 1234 정확 참조).

부수 관찰: Tool 호출률이 오를수록 위치 환각도 사라졌다. C 조건은 거의 다 "역삼역 사거리 부근"(Mock 정확값),
A/B 조건은 "서초역·현대백화점·경복궁·용산역" 등 환각이 무작위로 섞였다. **Tool 호출 ↑ = 환각 ↓ 동반.**

## 결론 — 블록은 trade-off 없는 순수 해악이었다

`[대화 맥락 사용 규칙]` 블록은 *지시 대명사 해결을 도우려고* 넣었다. 그러나:

1. **그 일은 이미 Memory 가 하고 있었다** — `MessageChatMemoryAdvisor` 가 이전 USER/ASSISTANT 메시지를
   프롬프트에 넣어주므로, 명시적 지시 없이도(C 조건) 모델이 "그거"=1234 를 맥락에서 추론한다.
2. **블록은 Tool 호출만 억제했다** — *"이전 대화에서 주문번호를 해석하라"* 는 맥락 해석 우선 프레이밍이
   *"주문번호 보이면 Tool 을 호출하라"* 는 `[Tool 사용 규칙]` 과 경쟁하며 Tool 확률을 끌어내렸다.

즉 **기대한 이득(맥락 해결)은 Memory 가 이미 제공하고 있었고, 블록은 부작용(Tool 억제)만 남겼다.**
지시 대명사 해결과 Tool 호출률 사이의 trade-off 는 *존재하지 않았다* — 블록을 빼면 둘 다 얻는다.

→ **`[대화 맥락 사용 규칙]` 블록을 영구 제거한다.**

## 더 큰 교훈

- **Round 2 의 *"prompt 는 전역 확률 분포, 한 섹션이 다른 섹션의 상대 확률을 흔든다"* 가 정확히 재현됐다.**
  한 섹션을 *추가* 한 것이 손대지 않은 다른 섹션(Tool 호출)의 동작을 바꿨다.
- **"명시적 지시가 항상 돕지 않는다."** 모델이 이미(여기선 Memory 덕에) 하는 일을 prompt 로 다시 명시하면,
  토큰만 늘 뿐 아니라 *다른 능력을 억제* 할 수 있다. 좋은 의도의 추가가 비단조 부작용을 낳은 사례.
- **이 블록은 upstream/round3 starter 가 넣어둔 것**이었다. ablation 은 *우리 코드뿐 아니라 starter 설계의
  함정*도 드러낼 수 있다 — "starter 가 넣었으니 맞겠지" 가 아니라 측정으로 검증해야 한다.
- **지표 신뢰성**: 1단계에서 자기수정한 *"역삼역 언급 ≠ Tool 호출"* 원칙을 이번에도 유지 —
  `[Tool]` 로그만으로 카운트했기에 환각에 속지 않고 8~9/10 회복을 결정적으로 확인할 수 있었다.
