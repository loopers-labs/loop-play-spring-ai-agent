## 시나리오 1 — Memory 기본 동작 ✅ (지시 대명사 해결)

같은 세션(`live-demo`)으로 2턴. 두 번째 발화의 "그거" 가 직전 주문번호를 가리키는지 검증.

```
[T1] "2024-1234 배달 어디쯤이에요?"
 →  "주문 2024-1234는 현재 배달 중이며 라이더가 서초역 인근에서 운행 중입니다. 약 15분 후 도착 예정이에요."

[T2] "그거 몇 분 남았어요?"
 →  "주문 2024-1234는 현재 배달 중이며 ... 정확한 도착 시간은 조금 더 기다려보시면 확인 가능합니다."
```

`GET /api/v1/session/live-demo/messages` 결과:
```json
[
  {"type":"USER","content":"2024-1234 배달 어디쯤이에요?"},
  {"type":"ASSISTANT","content":"주문 2024-1234는 현재 배달 중이며 라이더가 서초역 인근에서 운행 중입니다. 약 15분 후 도착 예정이에요."},
  {"type":"USER","content":"그거 몇 분 남았어요?"},
  {"type":"ASSISTANT","content":"주문 2024-1234는 현재 배달 중이며 ... 정확한 도착 시간은 조금 더 기다려보시면 확인 가능합니다."}
]
```

**관찰 — 두 가지 일이 분리되어 일어났다:**

1. **Memory 는 작동했다** — T2 의 "그거" 가 1234 로 정확히 해석됨. USER×2 + ASSISTANT×2 누적 확인. 이게 1단계의 목표.
2. **그러나 Tool 은 호출되지 않았다** — Mock 의 실제 라이더 위치는 `"역삼역 사거리 부근"` 인데 응답은 `"서초역 인근"`. 콘솔에 `[Tool] getDeliveryStatus` 로그 없음. **즉 "그거→1234" 지시 대명사는 풀었지만, 그 1234 로 Tool 을 부르지 않고 위치를 환각했다.**

→ **Memory 검증과 Tool 검증은 별개 축이다.** 이 분리가 이번 단계에서 가장 중요한 깨달음이고, 아래 정량 측정으로 이어졌다.

## 시나리오 2 — 지시 대명사 우선순위 + Tool 누출 관찰

세션 `pron-test` 로 3턴. 서로 다른 주문번호를 언급한 뒤 "아까 그거" 가 무엇을 가리키는지.

```
[T1] "2024-1234 취소해주세요"          (1234 = 배달중, NOT_CANCELABLE 기대)
[T2] "아 그거 말고 2024-1235 취소해주세요" (1235 = CREATED, CANCELED 기대)
[T3] "아니 아까 그거, 상담원 연결도 같이 해주세요"
```

T1·T2 응답에서 **Tool call JSON 이 본문 텍스트로 누출**됐다:
```
주문 2024-1234가 취소될 예정입니다. 주문 상태를 확인한 뒤 취소 처리를 진행하겠습니다.

{"name": "cancelOrder", "arguments": {"orderId": "2024-1234", "reason": "고객 요청"}}
```

- LLM 이 `cancelOrder` 를 *실제 호출* 하지 않고 호출 의도를 텍스트로 뱉음 (`[Tool] cancelOrder` 로그 없음).
- 게다가 `"취소될 예정입니다"` 라는 가짜 약속까지 함 — Outcome 을 받지 않았는데도.
- **이것은 Round 2 1단계 보고서의 *"S3 JSON Tool call 텍스트 누출"* 과 동일한 실패가 Round 3 에서 재현된 것.** (`reports/week2/stage1` 참조)

T3 "아까 그거" → **1234**(처음 언급) 로 해석. 강의 노트의 규칙은 *"가장 마지막에 언급된 주문번호 우선"*(=1235)인데 어긋났다. qwen2.5 가 맥락상 *처음 강조된 건* 을 고른 케이스 — 강의 노트가 말한 *80% 정확도* 의 실패 20% 에 해당할 수 있다.

## 시나리오 3 — 세션 분리 ✅ (평가축 ★)

서로 다른 두 고객이 동시에 다른 주문을 얘기할 때 Memory 가 섞이지 않는지. quest 평가축
*"세션 분리 누락 시 다른 고객 대화가 새는 실패 시뮬레이션"* 의 정상 측(분리되는 경우).

```
[T1] customer-A : "2024-1234 지금 어디쯤이에요?"   → getDeliveryStatus(1234) 실호출, "역삼역 사거리"
[T2] customer-B : "2024-1239 주문 취소해주세요"     → cancelOrder(1239) 실호출, CANCELED
[T3] customer-A : "아 그거 말고 다시 확인해주세요"   → 1234 재안내 (1239 안 샘)
```

세션별 저장 분리 검증:
```
GET /session/customer-A/messages → 1234 관련만 (1239 흔적 0)
GET /session/customer-B/messages → 1239 관련만 (1234 흔적 0)
GET /session/ids                 → customer-A, customer-B 분리 등록
```

**관찰 2가지:**

1. **세션 격리 완벽** — A·B Memory 가 서로 0 오염. `.advisors(a -> a.param(CONVERSATION_ID, sessionId))` 가
   의도대로 동작. (이번엔 Tool 도 2/2 실호출 — 비결정성의 반대쪽 끝, 운 좋은 케이스.)
2. **T3 가 `[대화 맥락 사용 규칙]` 의 의도된 동작** — A 의 "그거 다시"에서 `getDeliveryStatus` 를 *다시 부르지
   않고* Memory 에 쌓인 이전 ASSISTANT 응답을 재사용 (`[Tool]` 로그 없음). 우리가 추가한 5줄 중
   *"이전 턴에서 이미 Tool 로 조회한 정보는 재사용"* 이 작동 → 토큰 절약. **역설적으로, 이 "재사용" 유도가
   시나리오 1·2 의 Tool 호출률 저하의 원인일 수 있다** (아래 회귀 의심의 또 다른 단서).

## 시나리오 4 — clear 후 망각 ✅

`live-demo`(시나리오 1 잔존, 4건) → `DELETE` → 같은 "그거" 재질문.

| 단계 | 결과 |
|---|---|
| clear 전 "그거" | → 1234 정확 참조 |
| `DELETE /session/live-demo` | status 200 |
| clear 후 messages | `[]` |
| clear 후 "그거" | "주문번호를 알려주시면..." → **맥락 완전 상실, 되묻기** |

의도된 망각 재현 성공.

**부수 — 중국어 누출**: clear 후 첫 응답에 중국어가 섞여 나왔다.
> 客户提供的是最近一次的订单，我们可以通过查询该订单的状态来估算剩余时间。请提供一下订单号码哦。

`[규칙] 모든 자연어 응답은 한국어로` 가 있는데도 누출 — Round 2 보고서의 *"qwen2.5 다국어 모델 한계"* 재현.
**가설**: Memory 가 있을 땐 앞에 쌓인 한국어 ASSISTANT 응답들이 언어 일관성의 *닻* 역할을 했는데, clear 로
그 닻이 사라지자 모델 본연의 다국어 불안정이 드러난 것일 수 있다. (Memory 가 맥락 해결 외 *언어 고정*
부수효과도 가졌을 가능성 — 표본이 필요한 추측 단계.)

## 시나리오 5 — default 폴백 보안 사고 ✅ 재현 (평가축 ★)

`defaultValue="default"` 의 위험을 직접 재현. 두 "고객"이 **헤더 없이** 차례로 요청 → 같은 `default` 세션 공유.

```
[고객1, 헤더 없음] "제 주문 2024-1234 배달 어디쯤이에요?"   → "주문 2024-1234는 배달 중..."
[고객2, 헤더 없음] "방금 제가 말한 주문번호 뭐였죠?"        → "...订单号码是2024-1234..."
```

**고객2 는 1234 를 한 번도 말한 적 없다.** 그런데 시스템이 1234 를 알려줬다 — 고객1 의 개인정보가
고객2 에게 누출됐다. `default` 세션 messages 에 두 사람 대화가 한 곳에 섞여 있다:
```
USER(고객1)  : 제 주문 2024-1234 배달 어디쯤이에요?
ASSISTANT    : 주문 2024-1234는 현재 배달 중...
USER(고객2)  : 방금 제가 말한 주문번호 뭐였죠?
ASSISTANT    : 订单号码是2024-1234   ← 누출
```

### 시나리오 3 ↔ 5 의 대비 — 평가축의 핵심

| | 헤더 | conversationId | 결과 |
|---|---|---|---|
| **시나리오 3** | `X-Session-Id: customer-A/B` | 분리 | **격리** ✅ |
| **시나리오 5** | 없음 | 둘 다 `default` | **누출** ❌ |

**같은 코드, 헤더 유무 하나로 격리/사고가 갈린다.** quest 가 강조한 *"테스트(시나리오 3)는 통과하고
운영(시나리오 5)에서 발견되는 사고"* 를 직접 만든 케이스다. → 프로덕션에선 헤더 누락 시 `default` 폴백이
아니라 400 Bad Request 로 막아야 한다는 결론의 살아있는 증거. (중국어 누출도 3번째 재현.)

## 실패 관찰 (핵심) — Tool 호출률 정량 측정

### 측정 동기 + 가설의 정정 과정 (정직한 기록)

시나리오 1·2 에서 Tool 호출이 안 보여서, 처음엔 `/api/v1/chat`(memory 없음) vs `/api/v1/assistant`(memory 있음)
**1:1 단발 비교**를 했다. 그 1회 결과만 보고 *"memoryAdvisor 가 Tool calling 을 깨뜨린다"* 고 단정했다.

**이 단정은 틀렸다.** 표본을 10회로 늘리자 그림이 뒤집혔다. 단발 비교는 qwen2.5 의 비결정성에 속은 착시였다.

### 정량 측정 — 동일 질문 10회씩

질문: `"2024-1234 배달 어디쯤이에요?"` (getDeliveryStatus 를 부르는 게 정답)
Tool 호출 여부는 **`[Tool] getDeliveryStatus` 콘솔 로그 카운트**로 결정적 측정.
assistant 는 매 호출 새 세션 ID(`q-1`~`q-10`)로 Memory 오염 차단.

| 경로 | Memory | **Tool 호출 (결정적)** | "역삼역" 언급 (보조) |
|---|---|---:|---:|
| `/api/v1/chat` (SupportService) | ❌ | **2/10** | 3/10 |
| `/api/v1/assistant` (memory advisor) | ✅ | **3/10** | 6/10 |

### 발견 1 — memoryAdvisor 는 Tool calling 을 깨뜨리지 않는다

memory 경로(3/10)가 오히려 약간 *높다*. 표본이 작아 통계적 유의성은 없지만, 최소한
*"memory 가 Tool 을 막는다"* 는 가설은 **기각**된다. 같은 system prompt + 같은 `defaultTools(orderTools)`
이고 차이는 advisor 체인의 `memoryAdvisor` 하나뿐인데, Tool 호출률에 의미 있는 하락이 없다.

### 발견 2 — qwen2.5 의 Tool 호출 자체가 극도로 불안정 (20~30%)

같은 질문을 10회 반복했는데도 Tool 호출률이 2~3할에 그친다. memory 유무와 무관하게 낮다.
Round 2 plan 에서 관찰한 *"시나리오마다 20~100% 변동"* 의 **하단(20~30%)**을 이번에 재확인했다.
**Tool 호출 불안정의 주 원인은 advisor 구성이 아니라 모델 자체다.**

### 발견 3 — "역삼역 언급" 은 Tool 호출의 신뢰 지표가 아니다 ⚠️

표에서 *"역삼역" 언급 횟수*(3·6)가 *Tool 호출 횟수*(2·3)보다 **많다**. 즉 Tool 을 부르지 않고도
`"역삼역 사거리 부근"` 을 답한 케이스가 있다. qwen2.5 가 *배달=강남/역삼* 을 흔히 환각하기 때문이다.
(10회 응답에 "서초역", "현대백화점 분당점", "경복궁", "경희대학교 정문", "서대문구 북아현동" 등
환각 위치가 무작위로 섞여 나왔다.)

→ **Round 2 3단계 description A/B/C 실험에서 *"역삼역 사거리 포함 횟수"* 를 성공 지표로 썼는데,
그 지표는 사실 신뢰할 수 없었다.** 환각으로도 역삼역이 나오므로 실제 Tool 호출률을 과대평가했을 수 있다.
**결정적 지표는 오직 `[Tool]` 콘솔 로그뿐**이라는 걸 이번에 확인했다. (Round 2 결론의 자기수정)

### 미해결 의심 — 회귀 (Round 2 80% → 지금 20~30%)

Round 2 에서 같은 질문이 4/5(80%) 호출됐는데 지금 20~30% 로 급락했다. 의심 1순위는 Round 3 에서
새로 추가한 **`[대화 맥락 사용 규칙]` 5줄**(BaedalPrompt). plan 의 "위험·함정"에 *"이 5줄이 호출률을
떨어뜨리지 않는지 측정"* 이라 적어둔 바로 그 회귀 가능성이다.
→ **2단계에서 이 5줄 ablation(빼고 재측정)으로 데이터 확정 예정.** (단순 비결정성일 가능성도 남아 있음)

## 설계 결정

### MAX_MESSAGES = 20 (출발점)

배달 상담 1회를 평균 5~10턴으로 가정하면, USER+ASSISTANT 가 한 턴에 2개씩 쌓이므로 20개는 약 10턴 분량.
지시 대명사가 보통 직전 1~3턴을 참조하므로 10턴 윈도우면 충분하다는 가정. **2단계에서 2 / 20 / MAX_VALUE
세 값으로 정량 비교하여 이 가정을 검증한다.**

### advisor order — memory(10) < performance(100)

memory advisor 가 먼저 실행되어 *프롬프트 조립 시점에* 이전 대화를 끼워 넣고, performance advisor 가
가장 바깥에서 *완성된 프롬프트의* 토큰·응답 시간을 집계해야 한다. 순서를 뒤집으면 performance 가
Memory 주입 *이전* 의 토큰을 재므로 측정값이 과소 집계된다.

### `defaultValue = "default"` 폴백의 위험 (시나리오 5 에서 재현됨)

헤더가 없으면 모든 클라이언트가 `"default"` 세션을 공유한다 → 서로 다른 고객의 대화가 한 Memory 에
섞인다. 이는 개인정보 사고다. 개발 편의용으로만 허용하고, 프로덕션에선 400 Bad Request 로 막아야 한다.

### 세션 식별 — HTTP 헤더(`X-Session-Id`)를 택한 이유

| 전략 | 단점 | 비고 |
|---|---|---|
| 쿠키/HTTP Session | Sticky Session 필요 | 웹 UI 한정 |
| **HTTP 헤더** | 클라이언트가 직접 관리 | **앱/웹/API 모두 통용 ← 채택** |
| JWT 클레임 | 인증 인프라 전제 | 이미 JWT 있으면 권장 |
| URL 경로 | URL 오염 | 운영 비추천 |
