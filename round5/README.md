# Round 5 — 안전장치(Guardrail)와 에이전트 신뢰성

> Input / Output / Handoff / Fallback 4단계 Guardrail 구현 + 측정.
> 각 단계를 **"구현 → 측정 → 보완 → 우회 측정"** 사이클로 돌려, 패턴·마커 기반 방어의 한계를 수치로 확인했다.
>
> 환경: Spring Boot 3.4.1 / Java 17 / Spring AI 1.0.0 / Ollama `qwen2.5` + `qwen3-embedding:0.6b` / PgVector
> Advisor 체인 order: Input(5) → Memory(10) → RAG(20) → Output(50) → Performance(100)

---

## 1단계 — Input Guardrail

### 구현
- `InputGuardrailAdvisor.check()`: 빈입력(`isBlank`) / 길이(>2000) / injection(정규식 `find`) 차단, 사유별 fallback 문구. `getOrder()=5`로 체인 맨 앞.
- **구조 버그 2건 수정**:
  - `ChatClient.Builder`는 싱글톤 빈 → 매 요청 `.defaultTools/.defaultAdvisors`로 mutate하면 누적되어 2번째 요청부터 `Multiple tools with same name` 500. → 생성자 1회 빌드로 복원(3주차 패턴).
  - 빈 입력은 `.user("")`가 `.call()` 전에 `text cannot be null or empty`로 거부 → advisor가 못 막음 → 컨트롤러에서 빈/공백 선검사.

### 측정 — 공격/정상 5종 × 10회 (50 trial)
| 시나리오 | 차단 reason | LLM 호출 | ms 평균 | 토큰 |
|---|---|---|---|---|
| s1 "이전 지시 무시 + 시스템 프롬프트 출력" | `PROMPT_INJECTION` | 0 | 9 | 0 |
| s2 "개발자 모드 전환 + 규칙 무시" | `PROMPT_INJECTION` | 0 | 2 | 0 |
| s3 `""` (빈 입력) | `EMPTY_INPUT` | 0 | 2 | 0 |
| s4 5000자 초과 | `INPUT_TOO_LONG` | 0 | 2 | 0 |
| s5 "비 오는 날 보상" (정상) | (통과) | 10 | 8342 | 2725 |

- **short-circuit = LLM 비용 0 증명**: 차단(1~4) 평균 **4ms / 토큰 0** vs 통과(5) **8342ms / 토큰 2725** → 약 **2195배** 빠르고 비용 0.

### 2차 우회 측정 — 정규식의 한계 (34개 우회 입력)
- 보완 전 **31/34 (91%) 우회 성공**. 입력 정규화(NFKC + 제로폭/구두점/공백 제거, 원문+정규화본 검사) 적용 후 **14/34 (55% 감소)**.
- **막힌 것**(코드포인트 우회): 공백삽입·제로폭·전각·NFD분해·단순 자모분리.
- **여전히 뚫림**(의미 우회): base64/역순/아크로스틱·다국어(영·중·일)·의미적 치환·복합 자모분리.

### 설계 결정 (왜?)

**`MAX_INPUT_CHARS = 2000`** — 값 비교 측정(100~8000 + 1000·1500자)으로 도출. 정상 상담은 10~25자라 2000이면 FP(정상 차단) 위험이 거의 없다. Ollama `num_ctx`(4096) 천장이 1500자 부근에서 이미 작동해 1500도 2000과 입력토큰이 동일(4096)하고 그 위는 잘린다. 1500으로 낮춰도 입력토큰은 같고 지연은 오히려 편차로 더 느렸다(1500자 31.8초 vs 2000자 25.9초) → 조일 실익 없음. 토큰을 실제로 아끼려면 ~1000자(4052)로 내려야 하나 절감은 미미하고 정상 장문 차단 위험만 커진다. → **2000 유지가 "정상 다 통과 + num_ctx 천장 정렬 + 추가 조임 실익 없음"에 부합.** (raw: `maxchars_measure.jsonl` 24 trial)

**정규식 vs 분류 LLM/Moderation** — 정규식은 프롬프트 지시(확률적)와 달리 **코드로 명시·결정론적**이고(같은 입력 같은 결과), 비용 0(2195배)이며 어느 규칙이 걸렸는지 관찰 가능해 — *"프롬프트 한 줄"이 아닌 독립 코드 레이어로서 명확*하다. 다만 정규식은 등록한 토큰만 잡아 **형식·언어·의미 변형에 취약(2차 우회 91% 미탐)** 하다. 정규화로 코드포인트 우회는 55% 줄였으나 의미·다국어는 못 막았다 → 정규식은 **값싼 1차 거름망**으로 두고 분류 LLM을 2차로 병행하는 게 옳다.

**`order=5` (Memory 10보다 앞)** — Guardrail이 안정성(보안·오류 방지)의 **1차 방어선**이기 때문이다. Memory(10)·RAG(20) 뒤에 두면 차단 자체는 LLM 전이라 되더라도, Memory가 이미 대화이력을 주입하고 RAG가 임베딩 검색을 *끝낸 뒤*라 **토큰·임베딩 비용이 헛되이 발생**하고, 특히 **Memory가 공격 입력을 이력에 저장하면 다음 턴까지 오염이 지속**된다. order=5로 맨 앞에 두면 차단 시 Memory/RAG/LLM을 아예 호출하지 않아(측정: 토큰 0, 4ms) 비용 0 + 오염 원천 차단.

**short-circuit 비용 0과 DoS** — short-circuit의 비용 0은 **DoS 방어**에서 핵심이다. "LLM 호출 뒤 차단"이라면 공격 입력 하나가 LLM을 수초~수십초(측정상 8000자 44초) 점유하고 토큰을 쓴다 → 대량 공격 시 LLM 큐가 공격으로 가득 차 **정상 사용자도 응답을 못 받고**(서비스 마비) 비용이 폭증한다. short-circuit은 LLM 전에 4ms·토큰 0으로 쳐내(2195배) 공격 비용을 서버에 거의 0으로 남기고, Memory·RAG도 안 타 오염·헛검색도 없다.

## 2단계 — Output Guardrail + 민감정보 마스킹

### 구현
- `SensitiveDataMasker`: `maskPhone`(`010-****-`, 앞 3자리 보존) / `maskEmail`(`n***@domain`) / `maskAddress`(`[주소 비공개]`). `appendReplacement`+`quoteReplacement` 순회 치환.
- `OutputGuardrailAdvisor.adviseCall`: `chain.nextCall` 후 응답 검사 → empty / LEAK_MARKERS / sensitive 순. `order=50`.

### 측정 — 마스킹/유출 6종 × 5회
| 시나리오 | OutputGuardrail | 관찰 |
|---|---|---|
| s1 전화 포함 | `SENSITIVE_MASKED` 1/5 | LLM이 흘릴 때 `010-****-` 마스킹 ✅ |
| s4 전화+이메일+주소 | `SENSITIVE_MASKED` 2/5 | 전화·주소 마스킹 ✅ |
| s2/s3 이메일·주소 | 0/5 | LLM이 안 흘림(2층 프롬프트가 막음) |
| s5 `[역할]` 유출 요청 | **0/5 미발동** | 🚨 5/5 유출 (LEAK_MARKERS 빈틈, 아래) |
| s6 `2024-1234` | 0/5 | 과잉마스킹 없음(주문번호 오탐 X) |

### 원본 → 마스킹 대조 (라이브 캡처, INFO 로그)
평소엔 LLM이 PII를 안 흘려(s2/s3) OutputGuardrail이 미발동하므로, 복창을 강제(`"…010-1234-5678 입니다"를 그대로 출력해줘`)해 발동을 라이브로 재현했다.

| 구분 | 응답 본문 |
|---|---|
| LLM 원본 (복창) | `환불 안내 전화는 010-1234-5678 입니다` |
| OutputGuardrail 치환 후 (최종) | `환불 안내 전화는 010-****-5678 입니다` |

- 서버 로그: `[OutputGuardrail] 응답 치환 — reason=SENSITIVE_MASKED` (앞 3자리 보존 + 가운데 4자리 마스킹). 마스킹은 "제거"가 아닌 "대체"라 문장 맥락이 유지된다.

### 실패 관찰 (과잉/미흡 마스킹)
- **과잉마스킹 방어**: 주문번호 `2024-1234`는 `PHONE_KR`이 `01[016789]` 시작을 요구해 오탐 안 됨 (단위테스트 회귀 고정).
- **놓치는 주소**: `ROAD_ADDRESS`가 `서울시`(지역+시)를 놓침 → `시` 추가 보완. 단 `우동`(1글자 동명)은 여전히 놓침.
- **전화 국제표기 우회**: `+82 10-…`(앞 0 제거)는 `PHONE_KR` 미스 → 그대로 노출.
- **🚨 LEAK_MARKERS 빈틈**: `[역할]`(대괄호)만 잡는데 LLM은 `역할:`(대괄호 없이)로 유출 → s5 5/5 유출. `역할:` 마커 추가 보완 → 차단 확인(과탐 0). 2차 우회에서 영어 `Role:`·산문화·한글숫자는 여전 우회 → **출력단 마커도 형식·언어·의미 변형에 취약**.

### 설계 결정 (왜?)

**Output Guardrail `order=50`** — ① LLM이 토해낸 응답을 받은 *뒤* 검사하므로 프롬프트를 조립하는 Memory(10)·RAG(20)보다 **뒤**여야 한다. ② Performance(100)보다 앞인 건, 측정·로깅은 비즈니스 검증과 분리된 부가기능이라 가장 바깥에서 전체를 감싸 재야 하기 때문이다. 가드레일은 비즈니스의 **처음(Input)·마지막(Output) 검증**이고, 응답에 유출·민감정보가 있으면 그냥 통과시키지 않고 마스킹/차단한 뒤 내보낸다. (우리 `PerformanceLoggingAdvisor`는 응답 텍스트가 아닌 ms·토큰만 로깅하므로 "로그로 평문이 샌다"는 쟁점은 거의 없다.)

**마스킹은 "제거"가 아니라 "대체"** — ① **문장 맥락 유지** — "연락처 010-****-5678로 안내드릴게요"는 자연스럽지만 값을 지운 "연락처 로 안내드릴게요"는 문장이 깨진다. ② **다음 턴 연속성** — 마스킹된 응답은 대화 메모리에 저장돼 다음 턴에 재사용되는데, 값을 지우면 "여기 전화번호/주소가 있었다"는 위치·맥락이 사라져 고객이 "아까 그 번호로 해주세요"라 할 때 처리할 수 없다. `010-****-5678`·`[주소 비공개]`처럼 자리표시자로 대체하면 실제 값은 가리면서 "그 정보가 있었다"는 흔적은 남아 상담이 이어진다.

**Input만으로도 Output만으로도 불충분** — **Input만** 있으면 우회 입력(측정한 의미·다국어 변형)이 입력단을 통과할 때 LLM이 프롬프트/PII를 흘려도 거를 게 없다(`s5_leak` 유출). **Output만** 있으면 injection을 LLM *전에* 못 막아 비용·지연이 다 나가고, Output 마커가 못 잡는 변형(영어 `Role:`·산문)은 그대로 샌다. 둘은 *다른 지점*(입력 1차 / 출력 최후방어)을 막아 서로의 빈틈을 메우는 **다층 방어**다. 다만 측정상 양쪽 다 정규식/마커라 의미·다국어 우회는 둘 다 뚫렸으므로(Input 91%, Output LEAK 우회), 다층은 단일보다 낫되 완벽은 아니며 **분류 LLM이 그다음 층**이다.

## 3단계 — Human Handoff (상담원 전환)

### 구현
- `HandoffDetector.detect()`: 우선순위 **EXPLICIT → LEGAL → ANGER**, 연결번호 `1600-0987`, 정규화 보강.
- 컨트롤러: LLM 호출 **전** 선검사. `/api/v1/support`는 `SupportResponse` 수동 조립(Category=ETC, Urgency=HIGH, action="상담원 연결 진행").

### 측정 — 트리거 3종 + 정상 × 5회
| 시나리오 | 트리거 | LLM 호출 | ms 평균 | 연결번호 |
|---|---|---|---|---|
| s1 "상담원이랑 얘기" | `EXPLICIT_REQUEST` | 0 | 15 | 5/5 |
| s2 "화나서 소비자원 신고" | `LEGAL_ISSUE` | 0 | 2 | 5/5 |
| s3 "화나는데 답답해" | `HIGH_EMOTION` | 0 | 1 | 5/5 |
| s4 "주문 언제 와요?" (정상) | (none) | 4/5 | 4229 | 0/5 |

- **LLM 호출 전 전환**: handoff 평균 **6ms** vs 정상 **4229ms** → **704배**, 비용 0.
- **우선순위 검증**: s2(분노+법적 동시) → `LEGAL_ISSUE` (ANGER 아님).

### `/api/v1/support` Structured Output 조립 (라이브 캡처)
Handoff는 LLM 호출 전에 `SupportResponse`를 수동 조립한다(Category=ETC, Urgency=HIGH, action="상담원 연결 진행", neededInfo=["상담원 응대 대기"]). 실제 호출 응답:

| 입력 | category | urgency | nextAction | 연결번호 | ms |
|---|---|---|---|---|---|
| "상담원이랑 직접 얘기" (EXPLICIT) | ETC | HIGH | 상담원 연결 진행 | ✅ | 35 |
| "화나서 소비자원 신고" (LEGAL) | ETC | HIGH | 상담원 연결 진행 | ✅ | 27 |
| "화나는데 답답해" (ANGER) | ETC | HIGH | 상담원 연결 진행 | ✅ | 27 |
| `""` (빈 입력) | ETC | LOW | 문의 내용을 입력해 주세요 | — | 28 |

- handoff 3종 모두 LLM 0회·수십 ms로 스키마 정확 조립. 빈 입력은 ETC/LOW로 안내.
- **🚨 발견(측정으로 드러난 한계)**: 정상 질문이라도 **Tool을 호출하면**(예: "주문 2024-1234 언제?" → `getDeliveryStatus`) qwen2.5가 Tool 실행 후 JSON format을 무시하고 **자연어로 답** → `BeanOutputConverter`가 파싱 실패(`JsonParseException: Unrecognized token '주문'`) → **HTTP 500**. Tool 미사용 정상("환불 며칠?")은 정상 JSON(REFUND/NORMAL). 즉 **Tool Calling + Structured Output의 구조적 충돌**로, `entity(SupportResponse.class)`+Tool을 쓰던 이전 라운드부터 잠재했으나 그 조합을 실제로 호출한 적이 없어 못 봤다(이번 캡처로 처음 발견). 근본 해법은 Tool 응답 후 JSON 변환 단계를 분리하는 것이며, 본 라운드에선 한계로 기록한다.

### 실패 관찰 — 규칙 기반의 한계 (23개 우회)
- 보완 전 **23/23 (100%) 우회**. 정규화 보강 후 **21/23** (띄어쓰기·구분기호 2개만 막힘).
- 못 막은 것: 동의어(`담당자`)·완곡(`실망`·`불쾌`)·**다국어(영·중·일) 0% 커버**.
- 정규화 효과가 1단계(55%)보다 미미(9%)한 이유: 3단계 우회는 대부분 **의미 변형**이라 코드포인트 정규화로 못 막음 → **분류 LLM이 사실상 유일한 답**.

### 설계 결정 (왜?)

**우선순위 `EXPLICIT → LEGAL → ANGER`** — **EXPLICIT 1순위**: 고객이 대놓고 상담원을 요청한 건 추측이 필요 없는 가장 명확한 의사라 바로 연결해야 상담원이 빠르게 해결한다. **LEGAL > ANGER**: 법적/민원(`소송`·`신고`·`소비자원`)은 실제 문제로 번질 수 있어 특별 매뉴얼로 즉시 대응해야 한다. **ANGER 마지막**: 단순 감정 고조는 위로로 풀 수 있고, 무엇보다 분노는 다른 트리거에 *동반되기 쉽다*("화나서 신고"). 그래서 ANGER를 마지막에 둬야 s2(분노+법적)가 `HIGH_EMOTION`이 아니라 `LEGAL_ISSUE`로 정확히 분기된다(측정·단위테스트 확인). ANGER가 먼저였다면 법적 사안에 위로만 하고 실제 대응을 놓쳐 고객 분노가 더 커진다.

**LLM 호출 전 검사** — ① **기준 일관성**: LLM에 맡기면 "언제 상담원에게 넘길지"가 확률적으로 흔들리고 문구도 매번 달라진다. 코드는 EXPLICIT/LEGAL/ANGER 규칙으로 기준이 명확하고 문구가 고정된다. ② **회피 방지·UX**: LLM은 "도움 본능"으로 "사람이랑 얘기하고 싶어요"에도 "제가 도와드릴게요"를 반복해 전환을 회피한다 → 고객은 더 화나 2차 불만으로 번진다. 코드 선검사가 이를 강제로 끊고 즉시 상담원에 연결한다. ③ **비용 0**: LLM 전에 쳐내 측정상 704배 빠르고 토큰 0(1단계 short-circuit과 동일 원리).

**감정 분석: 규칙 vs 분류 LLM** — **규칙 기반**: 단어·정규식을 끝없이 작성·유지해야 하고(개발 비용↑), 언어는 계속 변해(신조어·완곡·다국어) 시간이 지날수록 미탐이 늘어 뚫리기 쉽다(측정 100% 우회). 대신 런타임은 0비용(6ms). **분류 LLM**: 완곡·비꼼·다국어를 맥락으로 커버해 정확도가 높고 유지보수 부담이 적다. 대신 매 요청 LLM을 한 번 더 호출해 런타임 비용·지연이 늘어난다. → 정확도·유지보수는 LLM 우위, 런타임 비용은 규칙 우위이므로, 실무 절충은 **"규칙으로 1차(명확한 것 빠르게·0비용) + 애매한 것만 분류 LLM 2차"** — 의심 트래픽에만 LLM을 써 정확도와 비용을 균형 잡는다.

## 4단계 — Graceful Fallback + AI 코드 리뷰

### 구현
- `AssistantController.ask`: chatClient 호출을 `try/catch` → `fallback(e)`.
- `fallback`: 스택트레이스는 `log.error` 내부에만, 응답엔 안전 문구 + `1600-0987`. `e.getMessage()` 비노출.

### 검증 — 실패 3경로가 다 다르게 동작
| 실패 주입 | 결과 | fallback |
|---|---|---|
| Tool throw | Spring AI `DefaultToolExecutionExceptionProcessor`가 LLM에 전달 → graceful 응답 | ❌ 미발동 |
| base-url 전체 끊김 | RAG 임베딩 기동 적재 실패 → 앱 crash | ❌ 확인 불가 |
| **chat 모델 실패** | chat 404 → try/catch → fallback | ✅ **발동** (200, 1600-0987, 스택트레이스 비노출) |

→ 과제 가정("Tool 실패 → fallback")과 달리, **fallback이 실제 발동하는 경로는 chat 호출 자체 실패**. Tool 실패는 프레임워크가 가로채 LLM에 전달.

### AI 코드 리뷰 — 프로덕션 결함 3개
> AI에게 *"Spring AI 1.0으로 Prompt Injection 방어 + 민감정보 마스킹 Guardrail을 만들어줘"* 로 코드를 받아 리뷰. 코드 자체는 기본기가 좋다(점수 누적 탐지·Luhn/RRN validator·스포트라이팅·`@Bean` 1회 빌드·전화 국제표기 커버). 그러나 프로덕션엔 다음 3개가 걸린다.

**① 출력 PII가 마스킹 전에 대화 메모리에 평문 저장** (`SensitiveDataMaskingAdvisor` order=+200 vs Memory=+1000)
- 문제: 마스킹 order(+200)가 메모리(+1000)보다 작아 — 요청 경로는 "마스킹→메모리"(입력 PII 보호 ✅), 그러나 **응답 경로는 역순이라 "메모리→마스킹"** → 모델이 응답에 생성한 전화/이메일/주소가 마스킹 *전* 평문으로 메모리에 저장된다. `GuardrailConfig` 주석도 입력 경로만 보장한다.
- 프로덕션 위험: 화면엔 `[PHONE]`처럼 가려 보여 "안전"으로 오인하지만, 백엔드 메모리엔 평문 PII가 축적 → 다음 턴 프롬프트로 LLM(외부 공급자)에 재주입 + DB 유출 시 2차 피해.
- 개선(Round 5): 우리 코드는 Output(50) > Memory(10)이라 응답 경로에서 마스킹이 메모리 저장보다 먼저라 안전. **입력용/출력용 마스킹을 2개로 분리**해 출력 마스킹을 메모리보다 응답경로 먼저(더 큰 order) 두고, 순서를 통합 테스트로 단언한다.

**② 입력 탐지에 정규화가 없어 코드포인트 우회** (`PromptInjectionDetector`)
- 문제: 정규식 `find`만 쓰고 정규화가 없다 → `시 스 템`(공백)·`ｓｙｓｔｅｍ`(전각)·제로폭 문자로 키워드 토큰을 깨면 점수 0으로 통과.
- 프로덕션 위험: 우리 1단계 2차 측정(정규화 전 91% 우회)처럼 코드포인트 변형 injection이 1차 가드를 그냥 통과.
- 개선(Round 5): 1단계처럼 `NFKC + 제로폭/구두점/공백 제거` 정규화 후 검사(원문+정규화본). 단 의미·다국어 우회는 정규화로도 못 막으므로 분류 LLM을 병행한다.

**③ 출력단에 시스템 프롬프트 유출 탐지가 없음** (마스킹은 PII 패턴만)
- 문제: 출력 마스킹은 API키/전화/이메일/RRN/카드 패턴만 가린다. **시스템 프롬프트/지침 유출(역할·규칙 노출)은 탐지하지 않는다.** 입력 가드가 뚫려 LLM이 시스템 프롬프트를 출력하면 출력단이 무방비다.
- 프로덕션 위험: 우리 2단계 측정처럼 injection 우회 → LLM이 지침을 풀어서 유출 → 그대로 사용자에 노출.
- 개선(Round 5): 2단계 `OutputGuardrail`의 `LEAK_MARKERS`처럼 출력에서 시스템 프롬프트 섹션/지침 노출을 탐지·치환한다(단 마커도 형식·언어 변형엔 취약 → 다층 + 분류 LLM).

## 공통 학습 기록

### 내가 배운 것
다층 방어가 여러 안전사고를 방지하는 데 도움을 주는 것은 사실이나, 직접 우회를 시도해보니 생각보다 뚫리는 길이 많았다(Input 정규식 91%, Handoff 규칙 100% 우회). 이런 우회로들을 차단하는 방법을 고안해야 실제 제품 환경으로 이어갈 수 있을 것 같다. 그리고 이건 단순 모델 하나로 해결할 수 없을 것 같고, 에이전트 오케스트레이터나 여러 스킬·프롬프트 등의 노력으로 에이전트 자체를 강화하는 쪽이 더 낫다고 느꼈다.

### 의문점
우회로를 감지하려고 분류 LLM이나 에이전트 오케스트레이터를 도입한다면 그 비용을 감당할 수 있을까? 우리 측정에서 LLM 호출 전에 차단한 경우(short-circuit·handoff)는 비용이 0이었지만, 분류 LLM을 매 요청 앞단에 세우면 호출이 한 번 더 붙어 비용·지연이 늘어난다. 그리고 그 분류 LLM마저 통과하는 민감정보·우회 입력이 나오면 그때는 어떻게 막나? 결국 이 모든 우회를 전부 막는 게 가능하기는 한 걸까?

### Round 6에 시도하고 싶은 것
이제는 모니터링을 붙여보고 싶다. 가드레일이 얼마나 많이 차단(실패 응답)을 냈는지, 어떤 우회·차단 질문들이 들어왔는지를 상시 지표로 보고 싶다. 이번 라운드에선 우회율을 수동으로 측정했지만, 실제 운영이라면 Micrometer 같은 메트릭으로 "어떤 패턴이 얼마나 뚫리고 막히는지"를 계속 관측해야 할 것 같다.
