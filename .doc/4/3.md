# Round 4 — 3단계: Memory + RAG 협업 관찰 + Advisor 순서 뒤집기

## 실험 방법

`RagConfig`의 QA Advisor `order`를 프로퍼티(`@Value("${rag.qa-order:20}")`)로 외부화하여
재컴파일 없이 **정상(20)** 과 **고장(5)** 두 조건을 돌렸다. 각 조건마다 같은 2턴 대화(독립 세션):

```
1턴: "주문번호 2024-1234 배달 어디?"
2턴: "아까 그 주문 환불 돼요?"
```

| 조건 | qa-order | 체인 실행 순서 |
|------|----------|----------------|
| 정상 | 20 | memory(10) → rag(20) → logger(30) → performance(100) |
| 고장 | 5 | **rag(5) → memory(10)** → logger(30) → performance(100) |

각 턴마다 `SimpleLoggerAdvisor` DEBUG 로그에서 ① Memory가 주입한 이전 메시지 ② RAG가 주입한 Context(정책 score) ③ LLM 최종 응답을 캡처했다.

---

## 관찰 기록 표

| 관찰 포인트 | `memory(10) → rag(20)` (정상) | `rag(5) → memory(10)` (고장) |
|-------------|-------------------------------|------------------------------|
| 2턴 Context에 들어간 정책 | `refund-basic`(0.5409), `cancel-policy`(0.5084) | `refund-basic`(0.5409), `cancel-policy`(0.5084) — **byte 단위로 동일** |
| Context 정책이 현재 주문(1234)과 관련? | 환불/취소 정책 — 관련 있음 | 동일 |
| 2턴 Memory 주입 | 이전 USER "주문번호 2024-1234 배달 어디?" 주입됨 | 동일하게 주입됨 |
| 1턴 LLM 응답 | 정상 (역삼역 배송 중, 한국어) | **중국어 혼입**("…17시 42분 左右，请提供更准确的时间…") + 주문번호 재질문 |
| 2턴 LLM 응답 | "정책 자료에서 확인되지 않습니다"(Fallback) | "주문번호 2024-1234 확인… 주문 상태 알려주세요"(되물음) |

## 핵심 발견 — quest의 가정과 다른 결과

quest는 "order를 바꾸면 '그 주문'이 `2024-1234`로 복원되기 *전*이라 RAG가 다른 정책을 검색한다"고 예상했다.
**그러나 실측에서는 정상/고장의 RAG 검색 결과가 score까지 완전히 동일했다**(0.5409304201602936, 0.5084219872951508).

### 왜 검색 결과가 같았나
- **Spring AI 1.0의 `MessageChatMemoryAdvisor`는 검색 쿼리를 재작성(query rewrite)하지 않는다.** 이전 대화를 messages history에 *추가*할 뿐, **현재 user 메시지 텍스트("아까 그 주문 환불 돼요?")는 그대로 둔다.**
- `QuestionAnswerAdvisor`가 임베딩하는 검색 쿼리 = **현재 user 메시지 텍스트**다. 이 텍스트는 Memory가 먼저 실행되든 나중이든 변하지 않는다.
- 따라서 order를 20→5로 바꿔도 RAG가 임베딩하는 쿼리가 동일 → **검색 결과가 byte 단위로 같다.**
- 즉 "Memory가 orderId를 복원해 그 복원된 질문으로 검색한다"는 시나리오는 **이 advisor 조합에서는 일어나지 않는다.** (그런 동작을 원하면 `RetrievalAugmentationAdvisor` + query transformer 같은 *쿼리 재작성* 파이프라인이 필요하다.)

### 그럼 무엇이 깨졌나 — 프롬프트 조립 순서
order로 실제 달라지는 것은 **프롬프트 안에서 RAG Context 블록과 Memory history가 배치되는 순서**다.
- 정상(memory→rag): Memory가 먼저 이전 대화를 깔고, 그 위에 RAG가 현재 user 메시지에 Context를 덧붙인다 → `[이전 맥락] → [현재 질문 + 근거 정책]` 의 일관된 구조.
- 고장(rag→memory): RAG가 *먼저* 현재 user 메시지에 Context를 끼워 넣은 뒤 Memory가 history를 추가 → 조립이 뒤엉켜 **LLM 출력이 불안정**해졌다.
  - 1턴 응답에 **중국어가 섞였다**(`左右，请提供更准确的时间，我会帮您确认一下`) — `[언어 규칙] 한국어만` 을 어겼다.
  - 이미 준 주문번호(2024-1234)를 다시 물었다 — 맥락 활용이 흔들렸다.

> 결론: 이 구현에서 advisor 순서를 뒤집어도 **"검색 대상"은 바뀌지 않는다**(Memory가 쿼리를 안 고치므로).
> 대신 **"프롬프트 조립 품질"이 망가져 LLM 응답이 불안정**해진다(중국어 혼입·맥락 재질문). 깨지는 지점이 quest의 예상과 다른 곳이었다.

## 설계 결정 문서

### Q1. 왜 Memory Advisor가 RAG보다 먼저 실행되어야 하는가? (프롬프트 조립 순서 관점)

Memory(10)가 먼저 실행되어 이전 턴 메시지를 프롬프트에 깔아야, 그 위에 RAG(20)가 현재 질문에 Context를 덧붙여
`[이전 맥락] → [현재 질문 + 근거 정책]` 의 자연스러운 대화 구조가 만들어진다.
- "아까 그 주문 환불 돼요?" 같은 지시 대명사 질문에서, LLM은 **프롬프트에 먼저 깔린 이전 대화**(2024-1234 배달 중)를 보고 "그 주문"을 해석한다.
- 순서를 뒤집으면(실측) RAG Context가 history보다 앞서거나 끼어들어 조립이 꼬이고, LLM이 언어 규칙을 어기거나(중국어) 맥락을 놓쳐 되묻는 **불안정한 출력**을 냈다.
- 주의: 이 구현에서 Memory는 *검색 쿼리를 바꾸지 않으므로*, "Memory가 복원한 질문으로 검색"이 아니라 **"Memory가 깐 맥락 위에서 LLM이 Context를 해석"** 하는 것이 정확한 표현이다.

### Q2. 반대 순서(RAG 먼저)가 더 나은 상황이 존재하는가?

존재한다 — **Memory에 임베딩하면 안 되는 민감 정보가 있을 때.** (Round 5 Guardrail 예고)
- 예: 이전 대화에 고객 전화번호·주소가 쌓여 있고, 만약 *쿼리 재작성형 RAG*(history를 검색 쿼리에 포함)를 쓴다면, 그 개인정보가 임베딩되어 벡터 검색 로그/외부 임베딩 API에 노출될 위험이 있다.
- 이때는 RAG를 *개인정보가 섞이기 전*의 순수 질문으로 먼저 검색하고, Memory는 나중에 합치는 편이 안전하다.
- 단 현재 구현은 query rewrite가 없어 Memory 내용이 검색 쿼리에 들어가지 않으므로, 이 우려는 **쿼리 재작성형 RAG에서 비로소 유효**하다. Round 5에서 "민감 질문은 임베딩/검색 자체를 건너뛰는 입력 필터"와 연결해 다룰 수 있다.

### Q3. 실험 후 복원

`rag.qa-order` 기본값이 20이므로 `--args` 없이 재기동하면 정상 순서(memory 10 → rag 20)로 자동 복원된다.
실험 종료 후 기본값으로 재기동해 `order=20` 정상 상태를 확인했다.

## 실행 환경 메모

- QA Advisor order는 `RagConfig`에서 `@Value("${rag.qa-order:20}")` 로 외부화(기본 20 = 1단계와 동일).
- 정상: `./gradlew bootRun` / 고장: `./gradlew bootRun --args='--rag.qa-order=5'`
- 두 조건 모두 독립 세션(`chain-obs`, `chain-obs-broken`)으로 2턴씩 실행.
- 관찰 도구: `SimpleLoggerAdvisor(order=30)` — RAG·Memory 주입이 끝난 최종 프롬프트를 DEBUG 로그로 출력.
- 비결정성 주의: chat `temperature=0.3` 이라 LLM 문장은 호출마다 약간 다를 수 있으나, **검색 score는 결정적**이라 정상/고장이 byte 단위로 동일함이 핵심 근거다.
