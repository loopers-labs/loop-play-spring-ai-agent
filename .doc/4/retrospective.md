# Round 4 — 공통 학습 기록

> 진행: 1단계(RAG 기본 구현 + 시나리오 5종) · 2단계(청킹 A/B/C + 실패 관찰) · 3단계(Advisor 순서 뒤집기)까지 완료. 4단계(토큰 비용 관찰 + AI 코드 리뷰)는 시간 관계상 스킵. `./gradlew build` 통과, 커밋에 API Key 등 민감정보 없음(Ollama 로컬 `api-key: ollama` 더미).

## 내가 배운 것

**RAG의 두 파이프라인은 "다른 시점에 도는 별개의 루프"였다.**
인덱싱(`KnowledgeLoader`가 기동 시 7개 문서를 임베딩→`vector_store` INSERT)과 검색(매 질문마다 `QuestionAnswerAdvisor`가 질문을 임베딩→유사도 Top-K)은 코드도 트리거도 완전히 분리돼 있었다. 기동 로그의 `신규 7건 / 스킵 7건`은 인덱싱 루프, DEBUG의 `Context:` 블록은 검색 루프 — 둘을 같은 임베딩 모델(qwen3, 1024차원)로 맞춰야 벡터 공간이 일치한다는 게 추상이 아니라 `dimensions: 1024` 한 줄로 체감됐다.

**설정이 틀려도 에러가 안 나고 조용히 기본값으로 폴백한다 — 가장 무서운 실패다.**
`application.yml`의 임베딩 모델을 `spring.ai.openai.embedding.model`로 적으면 Spring AI 1.0은 그 줄을 **무시**하고 기본값 `text-embedding-ada-002`로 폴백한다. 올바른 경로는 `embedding.options.model`. 기동 시 `HTTP 404 model not found`로 터져서야 알았다. "차원 불일치로 조용히 쓰레기 결과"라는 강의 경고가, 사실은 그 전에 "모델 지정 자체가 무시되는" 더 은밀한 함정이 있다는 걸 직접 밟아봤다.

**문맥 조각남은 "row 수"라는 숫자로 먼저 드러났다.**
chunkSize를 800→100으로 줄이자 `vector_store` row가 7→**49**로 7배 늘었다. 그런데 입력 토큰은 오히려 줄었다(2162→1838). "토큰이 줄었으니 효율적"이 아니라, 보상 정책 표가 쪼개져 `| 11~29분 → 1,000원 쿠폰 |` 행이 표 헤더 청크와 **분리되어 Top-K에서 누락**됐고, 그래서 답변이 "60분 이상만 보상"으로 뭉개졌다. 같은 질문인데 800은 단계별 보상을 정확히 인용하고 100은 중간 단계를 통째로 빠뜨렸다 — 청크 경계가 표의 행을 끊으면 검색은 되는데 답이 비는 현상을 Context 블록 캡처로 눈으로 봤다.

**"실패 관찰이 불발하는 것"도 관찰이다 — C(2000)=A(800).**
chunkSize 2000으로 "유사도 뭉툭/토큰 낭비"를 보려 했지만, 이 도메인 정책 문서는 모두 800토큰 이내라 2000으로 키워도 문서당 1청크 → row·score·토큰이 A와 **byte 단위로 동일**했다. quest의 기대 시나리오가 *문서가 클 때만* 성립한다는 걸, "안 나타남"을 확인함으로써 배웠다. 가정을 도메인에 맞춰 검증하는 게 실험이다.

**Fallback은 임계값과 다른 "층위"의 방어선이다.**
`[정책 인용 규칙]`을 지우고 "오늘 점심 뭐 먹을까요?"(검색 0건)를 보내자, 임계값이 무관 문서를 다 걸러 Context가 비었는데도 LLM은 "메뉴를 추천해 드리겠습니다"라며 범위를 이탈했다. 임계값 = 입력(검색) 통제, Fallback = 출력(생성) 통제. 검색을 0건으로 막아도 LLM은 빈손으로도 지어낸다는 걸, 규칙 제거 전후 응답을 나란히 놓고 확인했다.

**Advisor 순서 실험은 quest의 예상과 다른 곳이 깨졌다.**
order를 20→5로 뒤집어도 RAG 검색 결과는 score까지 동일했다(0.5409…, 0.5084…). `MessageChatMemoryAdvisor`가 **검색 쿼리를 재작성하지 않고** 현재 질문 텍스트를 그대로 RAG에 넘기기 때문이다. "Memory가 복원한 질문으로 검색"은 이 advisor 조합에선 일어나지 않았다. 대신 프롬프트 조립이 꼬여 고장 조건의 1턴 응답에 **중국어가 섞였다**(`左右，请提供更准确的时间…`). 순서가 바꾸는 건 "검색 대상"이 아니라 "프롬프트 조립 품질"이었다.

## 의문점

- **한국어 임베딩 품질을 어떻게 측정할까?** qwen3-embedding 기준 정답 문서 score가 0.50~0.64의 **좁은 띠**에 몰려 있어, 임계값 0.5가 정답/오답을 가르는 경계가 아주 빠듯했다(시나리오 4의 privacy는 0.5 바로 아래로 떨어져 0건). 이 좁은 분포가 한국어 임베딩의 한계인지, 모델 선택의 문제인지, 정답셋을 만들어 recall@k로 정량화해보고 싶다.

- **쿼리 재작성형 RAG라면 3단계 결과가 달라질까?** `RetrievalAugmentationAdvisor` + query transformer로 "이전 대화를 반영해 검색 쿼리를 재작성"하면, 그때는 order가 검색 결과를 실제로 바꿀 것이다. 그 경우 "Memory의 개인정보가 검색 쿼리에 섞이는" 위험이 비로소 현실이 된다 — 어디까지가 안전한 query rewrite인가?

- **검색 결과의 출처를 응답에 어떻게 자동으로 노출할까?** 적재 시 metadata에 `title`을 심어 뒀고(`faqId=delay-compensation, title=배달 지연 보상 기준`) Context 블록에도 들어가지만, 정작 **고객 응답에는 "어느 정책을 근거로 답했는지"가 안 보인다.** "[배달 지연 보상 기준] 정책에 따르면…" 처럼 출처를 답변에 자동으로 붙이려면, 프롬프트로 강제할지 / 응답 후처리로 metadata.title을 추출해 각주를 달지 — 어느 쪽이 환각 없이 안정적인지 모르겠다.

- **정책 문서가 자주 바뀌면 재인덱싱을 언제 트리거할까?** 현재 `alreadyLoaded()`는 `faqId` 존재 여부만 보므로 **내용이 바뀌어도 감지 못 한다**. 내용 해시를 metadata에 넣어 변경 감지 + 변경분만 재임베딩하는 증분 전략이 필요한데, "언제(웹훅? 스케줄?)" 트리거할지가 미해결이다.

## Round 5(Guardrail)에 시도하고 싶은 것

**검색 0건을 "Fallback 문구"가 아니라 "행동"으로 연결하고 싶다.**
지금은 Context가 비면 "상담원 연결을 도와드릴까요?"라고 *말만* 한다. RAG 검색이 0건일 때 바로 `connectToAgent` 같은 Tool을 호출하는 Guardrail Advisor를 만들면, 환각을 막는 데서 나아가 실제 다음 액션으로 넘어갈 수 있다.

**`[금지]` 질문은 임베딩/검색 자체를 건너뛰는 입력 필터를 두고 싶다.**
"사장님 전화번호"는 어차피 임계값에 걸려 0건이었지만, 더 깔끔하게는 검색을 *시작하기 전에* 입력 가드가 차단하는 게 맞다. 3단계에서 본 "민감정보가 검색 쿼리에 섞이면 안 되는" 문제와도 직결된다 — Memory에 쌓인 전화번호·주소가 (쿼리 재작성형 RAG에서) 임베딩되지 않도록, 검색 전 단계에서 마스킹/차단하는 Guardrail을 RAG 앞에 배치해보고 싶다.
