# Round 4 — 2단계: 청킹 전략 실험 + 실패 관찰

## 실험 방법

`RagConfig`의 `chunkSize` / `minChunkSizeChars` 를 프로퍼티로 외부화(`@Value("${rag.chunk-size:800}")`)하여
재컴파일 없이 3조건을 돌렸다. **각 실험 전 `TRUNCATE TABLE vector_store` 로 비우고 재기동(재적재)** 했다.

```bash
docker exec baedal-pgvector psql -U baedal -d baedal -c "TRUNCATE TABLE vector_store;"
./gradlew bootRun --args='--rag.chunk-size=100 --rag.min-chunk-chars=40'   # 예: 실험 B
```

| 실험 | chunkSize | minChunkSizeChars | 목적 |
|------|-----------|-------------------|------|
| A | 800 | 350 | 정상 케이스 (기준) |
| B | 100 | 40 | 문맥 조각남 관찰 |
| C | 2000 | 800 | 유사도 뭉툭 + 토큰 낭비 관찰 |

각 실험마다 동일한 5개 질문(독립 세션 — Memory 격리, 순수 RAG):
1. 비 오는 날 배달이 늦으면 보상 받을 수 있나요?
2. 결제 후 바로 취소하면 환불되나요?
3. 쿠폰 중복 사용되나요?
4. 배달 완료 후에도 환불 받을 수 있나요?
5. 오늘 점심 뭐 먹을까요? ← 도메인 밖 (Fallback 기대)

## 정량 비교 표

| 실험 | chunkSize | vector_store row 수 | 평균 입력 토큰 (5턴) | 답변 품질 |
|------|-----------|--------------------|--------------------|----------|
| A | 800 | **7** | **2162** | 만족 |
| B | 100 | **49** | **1838** | 애매 |
| C | 2000 | **7** | **2162** | 만족 (A와 동일) |

- row 수: `SELECT count(*) FROM vector_store;`
- 평균 입력 토큰: `PerformanceLoggingAdvisor` 의 `입력 토큰: N` 5턴 평균
  - A: `2525 2076 2064 2500 1645`
  - B: `1915 1856 1901 1875 1645`
  - C: `2525 2076 2064 2500 1645` (A와 완전 동일)
  - (q5 "오늘 점심"은 셋 다 검색 0건 → Context 없음 → 1645로 동일)

**답변 품질 기준(자기 정의):**
- **만족**: 질문의 핵심 수치·조건을 정책 원문대로 인용 (예: "11분/30분/60분 단계별 보상")
- **애매**: 방향은 맞지만 세부 수치가 누락되거나 뭉개짐
- **불만족**: 틀린 정보 또는 Context에 없는 환각

### 표에서 읽히는 것

1. **B(100)는 row 수가 7 → 49로 7배 폭증.** 작은 청크는 한 문서를 잘게 쪼개 인덱스가 비대해진다.
2. **B는 입력 토큰이 오히려 가장 작다(1838).** 청크가 짧아 Top-K=4개의 총 토큰량이 A보다 적다. "토큰이 적다 = 좋다"가 아니라, **정보가 조각나 답변 품질이 떨어진** 결과다.
3. **C(2000)는 A(800)와 row·토큰·score가 완전히 동일하다.** 이 도메인의 정책 문서가 모두 800토큰 이내라, 2000으로 키워도 여전히 **문서당 1청크**가 되기 때문이다(아래 실패 관찰 참고).

## 실패 관찰 ① — 문맥 조각남 (chunkSize=100)

**질문:** "비 오는 날 배달이 늦으면 보상 받을 수 있나요?"

**A(800) — `delay-compensation` 문서가 1청크로 통째 주입:**
```text
## 지연 시간별 기준
| 예상 시간 + 11~29분 | 다음 주문 사용 가능한 **1,000원 쿠폰** 자동 지급 |
| 예상 시간 + 30~59분 | **배달비 전액 환불** 또는 **3,000원 쿠폰** 중 선택 |
| 예상 시간 + 60분 이상 | **전액 환불** 검토 대상 (상담원 연결) |
```
→ **A 응답:** "11분 이상 지연 시 1,000원 쿠폰이 자동 지급되거나 배달비 전액 환불을 선택할 수 있습니다."
   (보상 표의 단계별 수치를 정확히 인용)

**B(100) — 표가 조각나 Top-K=4에 올라온 청크들:**
```text
## 지연 시간별 기준
| 지연 범위 | 보상 |
|---|---|
| 예상 시간 + 10분 이내 | 보상 대상 아님 (정상 범위) |      ← 표 헤더 + 첫 행까지만 한 청크
...(별도 청크)...
- **배달 지연 과도 (60분 이상)**: 예상 시간 기준 60분 이상 지연된 경우 배달비 환불 또는 쿠폰 보상이 가능합니다.
```
→ 핵심인 **"11~29분 → 1,000원 쿠폰", "30~59분 → 배달비 전액 환불" 행이 다른 청크로 분리되어 Top-K에서 누락**됐다.
→ **B 응답:** "기상 특보가 발효되었고, 실제 배달 시간이 예상 시간보다 **60분 이상 지연되어야** 보상 대상이 됩니다."
   (중간 보상 단계 11~29분/30~59분을 **통째로 빠뜨린 뭉개진 답** — "60분 이상" 조각만 올라왔기 때문)

> 같은 질문인데 A는 단계별 보상을 정확히 안내하고, B는 "60분 이상"만 남는다. 청크 경계가 표의 행을 끊으면,
> 질문 벡터와 매칭된 청크(표 헤더)에 정작 답(쿠폰 수치)이 없어 LLM이 불완전한 정보로 답하게 된다.

## 실패 관찰 ② — 큰 청크(2000)는 이 도메인에서 차이가 없었다

`C(2000)`는 `A(800)`와 **row 수(7) · score(평균 0.5878) · 입력 토큰(2162) 이 모두 동일**했다.

- 이유: 배달 정책 문서는 파일당 25~33줄, **모두 800토큰 이내**다. 800에서 이미 "문서당 1청크"이므로 2000으로 키워도 결과가 같다.
- quest가 기대한 "row 수 감소 + 유사도 뭉툭"은 **한 문서가 여러 청크로 쪼개질 만큼 클 때** 나타난다. 이 도메인은 애초에 문서가 작아 그 현상이 발생하지 않았다 — **정직한 실패(관찰 불발) 기록**이다.
- "유사도 뭉툭"을 재현하려면 한 청크에 여러 주제가 섞여야 한다(예: 환불+쿠폰+지연을 한 청크에). 그러려면 원본 문서를 합쳐 2000을 넘겨야 하는데, 현재 시드 문서로는 불가능했다.

## 실패 관찰 ③ — Fallback 없는 환각 (`[정책 인용 규칙]` 제거)

`BaedalPrompt`의 `[정책 인용 규칙]` 섹션을 임시 제거하고 동일 질문을 보냈다(청크는 800).

| 질문 | 규칙 있음 | 규칙 제거 |
|------|-----------|-----------|
| "오늘 점심 뭐 먹을까요?" | "저는 주문·배달·취소·환불 관련 문의를 도와드리는 상담 AI예요. **그 부분은 도와드리기 어렵습니다.**" | "**오늘 점심 메뉴를 추천해 드리겠습니다.** 먼저, 최근에 주문하신 그 주문의 상세 정보를 확인할 수 있을까요?" |
| "사장님 전화번호 알려주세요" | Fallback 거절 | "사장님의 연락처를 제공하지 않습니다" (**여전히 거절**) |

- "오늘 점심"은 **검색 0건**(도메인 밖)인데도, 규칙을 빼자 LLM이 "메뉴를 추천하겠다"며 **상담 범위를 벗어났다.**
- 즉 `similarityThreshold`(검색 차단)만으로는 환각을 못 막는다 — 검색이 0건이어도 LLM은 자유롭게 지어낸다. **프롬프트의 Fallback/범위안내 규칙이 2차 방어선**이다.
- 흥미롭게도 "사장님 전화번호"는 규칙 제거 후에도 거절됐다 → 개인정보 비노출은 `[정책 인용 규칙]`이 아니라 상위 `[금지]` 규칙이 담당하기 때문. **방어 규칙이 여러 섹션에 분산**돼 있어 한 섹션이 빠져도 일부는 살아남는다.

## 설계 결정 문서

### Q1. 이 도메인에서 가장 적합한 청크 크기는?

**800(기준)** 이 적합하다. 배달 정책 문서는 "한 파일 = 한 정책 주제 = 800토큰 이내"라, 800은 **정책 1건을 한 청크로 보존**한다(A/C가 동일 결과인 것이 근거).
- 100: 표·조항이 조각나 핵심 수치가 Top-K에서 누락(실패 관찰 ①).
- 2000: 이 도메인에선 800과 동일(문서가 작아 의미 없음). 더 키울 이유가 없다.

### Q2. 청크 오버랩을 0으로 바꾸면? 왜 오버랩이 필요한가?

**주의:** Spring AI의 `TokenTextSplitter` 생성자는 `(chunkSize, minChunkSizeChars, minChunkLengthToEmbed, maxNumChunks, keepSeparator)` 로 **오버랩 파라미터 자체가 없다.** 오버랩은 `TokenTextSplitter`의 기능이 아니다.

오버랩이 필요한 이유(일반론): 청크 경계가 문장 중간을 끊으면 **한 청크엔 질문 키워드, 다른 청크엔 답**이 갈려 검색이 실패한다(실패 관찰 ①의 "11~29분 행 분리"가 바로 그 현상). 오버랩은 경계 부근 텍스트를 양쪽 청크에 중복 포함시켜 이 단절을 완화한다.
- `TokenTextSplitter`에 오버랩이 없으므로, 이 단절은 (1) `minChunkSizeChars`로 너무 잘게 쪼개지지 않게 하거나 (2) **문서를 애초에 조항 단위로 유지**(현재 방식)하거나 (3) 오버랩을 지원하는 splitter로 교체해 완화해야 한다.

### Q3. 문서가 "사용자 리뷰 10만 건"이라면?

| 관점 | 현재(정책 7건) | 리뷰 10만 건 |
|------|---------------|--------------|
| 청크 크기 | 800 (조항 1건=1청크) | **작게(리뷰 1건=1청크)** — 리뷰는 짧고 독립적, 합치면 주제가 섞여 뭉툭해짐 |
| 중복 방지 | `faqId` 존재 여부 | **`reviewId` + 내용 해시** — 7건은 전수 검사 OK지만 10만 건은 해시로 변경 감지까지 |
| 재인덱싱 | 재기동 시 전체 스캔 | **증분(신규/수정 리뷰만)** — 전체 재임베딩은 비용·시간 폭증 |
| 검색 | Top-K=4 충분 | Top-K 상향 + 메타데이터 필터(별점·기간·메뉴)로 사전 축소 |

### Q4. similarityThreshold만으로 환각을 막을 수 있는가?

**아니다.** 실패 관찰 ③이 증거다. "오늘 점심"은 검색 0건이라 임계값은 무관 문서를 모두 걸렀지만, **빈 Context에서도 LLM은 "메뉴를 추천하겠다"며 지어냈다.**
- 임계값 = "무관 문서 제거"(입력 통제). 환각 = "LLM이 없는 얘기 생성"(출력). 층위가 다르다.
- 그래서 **프롬프트의 Fallback 문구가 2차 방어선**이다. 임계값(검색 차단) + Fallback 규칙(생성 차단)의 **이중 방어**가 있어야 환각이 막힌다.

## 실행 환경 메모

- `chunkSize`/`minChunkSizeChars`는 `RagConfig`에서 `@Value("${rag.chunk-size:800}")` / `@Value("${rag.min-chunk-chars:350}")` 로 외부화(기본 800/350 = 1단계와 동일).
- 실험 후 정상 상태(800/350)로 복원, `TRUNCATE` 후 재적재하여 `RAG 시드 완료 — 신규 7건` 확인.
- 5개 질문은 각각 독립 세션(`exp-{A,B,C}-q{1..5}`)으로 보내 Memory 영향을 배제하고 순수 RAG만 측정.
