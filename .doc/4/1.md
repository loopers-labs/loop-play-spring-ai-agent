# Round 4 — 1단계: RAG 기본 구현 + 시나리오 5종 검증

## 구현 요약

### RAG 설정 (`RagConfig.java`)

| 요소 | 값 / Bean | 역할 |
|------|-----------|------|
| `TOP_K` | `4` | `similaritySearch`가 반환할 상위 N건 |
| `SIMILARITY_THRESHOLD` | `0.5` (COSINE) | 이 값 미만 검색 결과는 "관련 없음"으로 폐기 |
| `TokenTextSplitter` | `(800, 350, 5, 10000, true)` | 청크 800토큰 / min 350자 / 임베딩 최소 5 / 최대 10000청크 / 구분자 유지 |
| `QuestionAnswerAdvisor` | `order(20)` | 질문으로 VectorStore 검색 → Top-K를 프롬프트에 주입 |

```java
@Bean
public TokenTextSplitter tokenTextSplitter() {
    return new TokenTextSplitter(800, 350, 5, 10_000, true);
}

@Bean
public QuestionAnswerAdvisor questionAnswerAdvisor(VectorStore vectorStore) {
    SearchRequest searchRequest = SearchRequest.builder()
            .topK(TOP_K)
            .similarityThreshold(SIMILARITY_THRESHOLD)
            .build();
    return QuestionAnswerAdvisor.builder(vectorStore)
            .searchRequest(searchRequest)
            .order(20)   // Memory(10) 뒤, Performance(100) 앞
            .build();
}
```

### 인덱싱 적재 + 중복 방지 (`KnowledgeLoader.java`)

```java
// E) FaqDocument → Document(metadata 심기) → 청킹 → 적재
Document doc = new Document(faq.id(), faq.content(),
        Map.of("faqId", faq.id(), "title", faq.title(), "category", faq.category()));
List<Document> chunks = tokenTextSplitter.apply(List.of(doc));
vectorStore.add(chunks);  // 내부적으로 EmbeddingModel 호출 → 벡터 + metadata INSERT

// F) 중복 방지: faqId 필터로 이미 있으면 스킵
SearchRequest req = SearchRequest.builder()
        .query("정책").topK(1).similarityThresholdAll()
        .filterExpression("faqId == '" + faqId + "'").build();
return !vectorStore.similaritySearch(req).isEmpty();
```

- metadata에 `faqId`(중복 방지 키) / `title`(출처 표기) / `category`(카테고리 필터) 3개를 심는다.
- `tokenTextSplitter.apply()`로 쪼개는 이유: 검색 단위를 조항 단위로 맞춰 유사도를 또렷하게 한다(원본 1건으로 넣으면 한 벡터에 여러 주제가 섞여 뭉툭해짐).

### Advisor 체인 (`AssistantController` / `SupportController`)

```java
.defaultAdvisors(memoryAdvisor, ragAdvisor, new SimpleLoggerAdvisor(30), performanceAdvisor)
//               order=10        order=20    order=30                     order=100
```

| order | Advisor | 역할 |
|-------|---------|------|
| 10 | `MessageChatMemoryAdvisor` | 이전 턴 메시지 주입(지시 대명사 복원) |
| 20 | `QuestionAnswerAdvisor` | 복원된 질문으로 정책 검색 → Context 주입 |
| 30 | `SimpleLoggerAdvisor` | (관찰용) RAG 증강 직후의 최종 프롬프트를 DEBUG 로그로 출력 — 토큰 영향 없음 |
| 100 | `PerformanceLoggingAdvisor` | 전체 왕복 시간 / 입력·출력 토큰 집계 |

### Fallback 시스템 프롬프트 (`BaedalPrompt.java` — `[정책 인용 규칙]`)

- Context에 근거가 없으면 **고정 Fallback 문구**로만 답한다("…정책 자료에서 확인되지 않습니다. …상담원 연결을 도와드릴까요?").
- 수치·조건은 **원문 그대로** 인용(반올림·단순화 금지).
- 상담 범위 밖 질문은 Context를 인용하지 않고 범위 안내.
- 복수 정책은 고객의 현재 상황(주문 상태·결제 시점·기상 특보)에 맞는 것을 우선, 일반 규칙보다 구체적 예외 우선.
- 개인정보/[금지] 질문은 정책이 검색돼도 원문 비노출.

## 설계 결정 문서

### Q1. 왜 청크 크기 800 / min 350 인가?

배달 정책 문서는 이미 **조항 단위로 짧게 쪼개져 있다**(파일당 25~33줄, 모두 800토큰 이내). 실측에서 **문서당 1청크**로 적재됐다. 즉 800은 "한 정책 문서 = 한 검색 단위"를 보존하는 크기다. `min 350`(chars)은 잘게 나뉜 꼬리 조각을 앞 청크에 병합해 의미 없는 미니 청크의 임베딩을 막는다.

- 다른 도메인(블로그/장문 PDF)이라면? 한 문서에 여러 주제가 섞이므로 800보다 작게(300~500) 쪼개 주제 단위로 검색되게 한다. 단 너무 작으면 문맥이 조각나므로(2단계 B 실험) 오버랩으로 보강한다.

### Q2. 왜 Top-K = 4 인가?

정책 문서가 **7건**뿐이라 K를 키울 여지가 적다.

- `K=1`: 복합 질문("환불 + 지연")에서 한 정책만 잡혀 다른 축을 놓친다. 실제 시나리오 5-2는 `refund-basic` + `cancel-policy` **2건**이 함께 필요했다 — K=1이면 실패했을 것.
- `K=10`: 7건 전부 + 무관 문서까지 들어가 입력 토큰 폭증, 임계값의 의미 소멸.
- `K=4`: 7건의 절반가량. 복합 질문은 커버하되(임계값이 무관 문서 추가 차단) 토큰은 절제. 실측에서 한 질문당 0~2건이 통과했다.

### Q3. 왜 `QuestionAnswerAdvisor.order(20)` 인가? (memory 10 → rag 20 → performance 100)

프롬프트 **조립 순서** 때문이다. Memory(10)가 먼저 이전 턴 메시지를 프롬프트에 넣어야, RAG(20)가 그 **"복원된 질문"** 을 임베딩해 검색한다.

- 시나리오 5-2 *"아까 그 주문 환불 돼요?"* 에서, Memory가 `2024-1234` 맥락을 먼저 깔아주면 RAG는 "환불" 의도로 `refund-basic`/`cancel-policy` 를 정확히 검색한다.
- RAG가 Memory보다 먼저라면 *"아까 그 주문 환불 돼요?"* 문장 그 자체로만 검색하게 된다(3단계에서 order 20→5로 뒤집어 직접 관찰 예정).
- Performance(100)는 가장 바깥이라 Memory·Tool·RAG 왕복을 모두 포함한 전체 시간/토큰을 집계한다.

### Q4. `similarityThreshold = 0.5` 의 근거

qwen3-embedding 실측 점수는 정답 문서가 **0.50~0.64**, 무관 질문(시나리오 4)은 **0.5 미만**으로 갈렸다. 0.5가 둘을 가르는 자연스러운 경계였다.

- 너무 낮으면(0.3): 시나리오 4 같은 도메인 밖 질문에도 무관 정책이 Top-K에 끼어 LLM이 근거로 오해 → 환각.
- 너무 높으면(0.7): 정답 문서(0.52~0.53)까지 걸러져 Context가 비고 모든 질문이 Fallback.
- 임계값만으로 환각을 100% 막을 수는 없다(임계값은 "무관 문서 제거"만 한다). 그래서 `[정책 인용 규칙]`의 Fallback 문구가 2차 방어선으로 "없는 얘기 생성"을 막는다(시나리오 4가 증거). 정량 실험은 3단계.
