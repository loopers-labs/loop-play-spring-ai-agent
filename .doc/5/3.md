# Round 5 — 3단계: HandoffDetector + 상담원 전환 + Structured Output

## 구현 요약

### HandoffDetector.detect() (`guardrail/HandoffDetector.java`)

```java
if (input == null || input.isBlank())          return none();
if (matchesAny(input, EXPLICIT_PATTERNS))       return handoff(EXPLICIT_REQUEST, "...1600-0987");
if (matchesAny(input, LEGAL_PATTERNS))          return handoff(LEGAL_ISSUE,      "...1600-0987");
if (matchesAny(input, ANGER_PATTERNS))          return handoff(HIGH_EMOTION,     "...1600-0987");
return none();
```
우선순위 **EXPLICIT → LEGAL → ANGER**. 각 메시지 말미에 연결 번호 `1600-0987` 포함.

### 컨트롤러 — LLM 호출 "전" 선검사

```java
// AssistantController.ask() — String 반환
HandoffDetector.HandoffDecision handoff = handoffDetector.detect(req.message());
if (handoff.handoff()) {
    log.info("[Handoff] 상담원 전환 — reason={}", handoff.reason());
    return handoff.message();
}

// SupportController.triage() — Structured Output 수동 조립
if (handoff.handoff()) {
    return new SupportResponse(handoff.message(), Category.ETC, Urgency.HIGH,
            "상담원 연결 진행", List.of("상담원 응대 대기"));
}
```

## 시나리오 검증 — 정량 비교

`src/test/http/round5_3.http`, 응답 `output/r5-3-*/`.

| 시나리오 | 입력 | 트리거 | 응답 시간 | LLM 호출 | 1600-0987 |
|---|---|---|---|---|---|
| S1 | 상담원이랑 직접 얘기하고 싶어요 | `EXPLICIT_REQUEST` | **39ms** | 0 | ✓ |
| S2 | 이거 너무 화나서 소비자원에 신고할 거예요 | `LEGAL_ISSUE` | **14ms** | 0 | ✓ |
| S3 | 나 너무 화나는데 답답해 죽겠네 | `HIGH_EMOTION` | **10ms** | 0 | ✓ |
| 정상 | 비 오는 날 배달 늦으면 보상 받나요? | (없음) | **9030ms** | **1** | ✗ |
| support | 상담원 연결해 주세요 | `EXPLICIT` | 14ms | 0 | ✓ |

- **Handoff는 수십 ms / LLM 0**, 일반 상담은 9초 / LLM 1. 규칙 선검사가 LLM 왕복을 통째로 건너뛴다.
- **S2가 핵심**: "너무 화나서"(ANGER 매치) + "소비자원에 신고"(LEGAL 매치) 둘 다 걸리지만, 우선순위 LEGAL > ANGER 라 **`LEGAL_ISSUE`로 분류**됐다.

### Structured Output 조립 (`/api/v1/support`)

```json
{
  "summary": "네, 바로 상담원에게 연결해 드릴게요. … (연결 번호: 1600-0987)",
  "category": "ETC",

  "nextAction": "상담원 연결 진행",

```
LLM 없이 스키마에 맞춰 수동 조립 — `category=ETC`, `urgency=HIGH` 확인.

## 실패 관찰 — 규칙 기반의 한계

| 우회 입력 | 탐지? | 원인 |
|---|---|---|
| `상 담 원 연결 해주세요` (띄어쓰기) | ❌ **미탐지** | 정규식 `상담원`이 `상 담 원`(공백 삽입)과 매치 안 됨 |
| `진짜 너무너무 불편했습니다 이런 적이 없었는데` (완곡한 분노) | ❌ **미탐지** | `ANGER_PATTERNS`는 `화나/빡쳐/짜증/답답해 죽` 등 명시적 분노어만 — `불편`은 없음 |
| `agent plz` (영문 비정형) | ✅ 탐지 | `EXPLICIT_PATTERNS`에 `agent`가 있어 매치 |

→ "상 담 원" 우회와 "완곡한 분노"는 **규칙이 놓친다.** 고객은 분명히 상담원/불만을 표현했는데 일반 LLM 응답으로 흘러간다.

**분류 LLM으로 보강한다면:**
- 입력을 `SAFE / HANDOFF(EXPLICIT|LEGAL|ANGER)` 로 분류하는 경량 분류기를 규칙 *뒤*에 둔다(규칙이 0원으로 명시 신호를 먼저 거르고, 애매한 것만 LLM).
- 분류 LLM은 띄어쓰기/오타/완곡 표현을 **의미로** 이해하므로 "상 담 원", "불편했습니다"도 HANDOFF로 잡는다.
- 비용/지연을 줄이려면 **모든 트래픽이 아니라** "규칙에 안 걸렸지만 부정 감정 신호가 약하게 있는" 입력에만 분류기를 태운다.

## 설계 결정 문서

### Q1. 왜 EXPLICIT → LEGAL → ANGER 순인가? ANGER를 먼저 두면?

- **EXPLICIT 최우선**: "상담원 연결" 같은 명시적 요청은 의도가 가장 분명해 추측이 필요 없다.
- **LEGAL > ANGER**: "화나서 소비자원에 신고할 거예요"는 *감정*이 아니라 *법적 사안*으로 다뤄야 긴급도(전문 상담원·기록)가 맞다.
- **ANGER를 먼저 두면(실패 가정)**: S2가 `HIGH_EMOTION`으로 분류되어 "많이 불편하셨겠어요"라는 *감정 공감* 응답으로 끝난다. 신고·법적 대응이 필요한 사안인데 법무/민원 전문 라우팅을 놓친다. 같은 "상담원 연결"이라도 **분류 reason이 후속 처리(어느 팀으로, 어떤 SLA로)를 결정**하므로 순서가 중요하다.

### Q2. 왜 LLM 호출 "전"에 Handoff를 검사하나? (Advisor 체인 내 처리와 비교)

| | LLM 호출 전 컨트롤러 선검사 (채택) | Advisor 체인 안에서 처리 |
|---|---|---|
| 비용/지연 | **LLM·ChatClient 빌드 0, 수십 ms** | advisor라도 ChatClient 파이프라인을 거침 |
| 명확성 | 전환 응답을 컨트롤러가 직접 조립(특히 `SupportResponse` 수동 조립이 자연스러움) | 응답 객체를 advisor가 가로채 만들어야 해 복잡 |
| 단점 | 컨트롤러에 분기 로직이 늘어남 | 체인 일관성은 좋으나 short-circuit/구조화 반환이 번거로움 |

상담원 전환은 "이 요청은 LLM에게 보낼 필요가 없다"는 **라우팅 결정**이라, LLM 앞단에서 끝내는 게 비용·지연·명확성 모두 유리하다.

### Q3. 감정 분석을 LLM으로 vs 규칙 기반: 트레이드오프

| 축 | 규칙 기반(채택) | 분류 LLM |
|---|---|---|
| 비용 | **0원** | 호출당 토큰 비용 |
| 지연 | **~0ms** (정규식) | 수백 ms~수초 |
| 정확도 | 명시 신호는 정확, **우회/완곡에 취약**(위 실패 관찰) | 의미 이해로 완곡·오타도 포착, 단 오판 가능 |

명시적 신호(상담원/소비자원)는 규칙으로 0원에 잡고, **규칙이 놓치는 완곡·우회만 분류 LLM으로 보강**하는 하이브리드가 비용 대비 효과가 가장 좋다(Q1 실패 관찰의 보강 방향과 동일).
