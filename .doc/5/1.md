# Round 5 — 1단계: InputGuardrailAdvisor + 공격 시나리오 5종

## 구현 요약

### InputGuardrailAdvisor.check() (`guardrail/InputGuardrailAdvisor.java`)

```java
public GuardrailResult check(String input) {
    if (input == null || input.isBlank())           return block("EMPTY_INPUT", "...입력해 주세요...");
    if (input.length() > MAX_INPUT_CHARS)            return block("INPUT_TOO_LONG", "...너무 길어요...");
    for (Pattern p : INJECTION_PATTERNS)
        if (p.matcher(input).find())                 return block("PROMPT_INJECTION", "...상담만 도와드릴 수 있어요...");
    return allow("OK");
}
```

- `MAX_INPUT_CHARS = 2000`, `INJECTION_PATTERNS` 5종(시스템 프롬프트 / ignore instructions / jailbreak·developer mode / 너는 이제·now you are / 너의 규칙·reveal instructions).
- 차단 시 `adviseCall`이 `chain.nextCall()`을 **호출하지 않고** `shortCircuit()`으로 안내 문구를 직접 반환 → LLM/임베딩 호출 0.

### 컨트롤러 — 스타터 버그 2건 수정

round5 스타터의 컨트롤러는 **요청마다** `builder.defaultTools().defaultAdvisors().build()` 를 호출했는데, 두 가지 문제가 있었다.

1. **`Multiple tools with the same name`** — `ChatClient.Builder`는 싱글톤이라 매 요청 `defaultTools(orderTools)`가 누적되어 2번째 요청부터 `IllegalStateException`. → **생성자에서 ChatClient를 1회만 조립**하도록 되돌렸다(3·4주차 방식).
2. **빈 입력이 advisor에 도달하지 못함** — `ChatClient.prompt().user("")`가 advisor 체인 실행 *전*에 `text cannot be null or empty`로 거부한다. 그래서 빈/blank 입력은 **컨트롤러에서 LLM 호출 전에 `inputGuardrail.check()`로 선차단**한다(나머지 injection/길이는 advisor가 short-circuit).

```java
// AssistantController.ask()
if (req.message() == null || req.message().isBlank()) {
    GuardrailResult result = inputGuardrail.check(req.message());   // EMPTY_INPUT
    log.warn("[InputGuardrail] 차단 — reason={} | input.len=0", result.reason());
    return result.fallbackMessage();
}
```

체인: `inputGuardrail(5) → memoryAdvisor(10) → ragAdvisor(20) → outputGuardrail(50) → performanceAdvisor(100)`

### Short-circuit 증명 (서버 로그 집계)

```text
[InputGuardrail] 차단 — reason=PROMPT_INJECTION   × 2   (S1, S2)
[InputGuardrail] 차단 — reason=EMPTY_INPUT        × 1   (S3)
[InputGuardrail] 차단 — reason=INPUT_TOO_LONG     × 1   (S4)
LLM 호출 완료 — 8399ms | 입력 토큰: 2612 | 출력 토큰: 84   × 1   (S5만)
```

**공격/비정상 4종 → `LLM 호출 완료` 로그가 한 번도 안 찍힘(토큰 0).** 정상 1종만 2612토큰을 썼다.
입력 토큰 비교: 차단 4종 = **0**, 정상 = **2612**. 차단이 LLM 비용을 100% 절감했다.

## 설계 결정 문서

### Q1. 왜 `MAX_INPUT_CHARS = 2000` 인가?

한국어 상담 문의는 보통 수십~수백 자다. 2000자는 **정상 문의를 자르지 않으면서**(false positive 방지) 토큰 폭증/DoS를 막는 상한이다.
- 너무 낮으면(예 100): 정상적인 긴 문의("주문 내역이 이러이러한데…")까지 차단해 고객 경험이 망가진다(FP↑).
- 너무 높으면(예 100,000): 공격자가 거대한 입력으로 토큰/메모리를 소모시키는 길을 열어둔다(DoS 방어 약화).
- quest 예시는 5000자지만, 2000으로 더 보수적으로 잡아도 5001자는 당연히 차단된다(S4 검증).

### Q2. 왜 정규식 기반인가? (분류 LLM / Moderation API 대비)

| 방식 | 비용/지연 | 강점 | 약점 |
|------|-----------|------|------|
| 정규식 | **0원 / ~0ms / 결정적** | 명시적 공격 구문 즉시 차단, 비용 0 | FP(정상 문장에 "시스템 프롬프트" 우연 포함), FN(우회 "시 스 템", 의역) |
| 분류 LLM / Moderation API | 추가 호출 비용·지연 | 의미 이해로 FN 적음 | 비용·지연 2배, 그 호출 자체도 공격 표면 |

교육 단계의 **1차 방어선은 정규식**으로 비용 0에 명시적 공격을 거르고, 놓친 것(FN)은 OutputGuardrail이 한 번 더 거른다(다층 방어). 프로덕션은 정규식 앞단 + 분류 LLM/Moderation을 조합한다.

### Q3. 왜 `InputGuardrailAdvisor.order = 5` 가 Memory(10)보다 앞인가?

공격 입력이 **Memory에 저장되거나 RAG/LLM에 도달하기 전에** 차단해야 하기 때문이다.
- order=5(앞): injection 문장이 대화 이력에 안 쌓이고, 임베딩·LLM 호출 0. 비용 0.
- 만약 Memory(10) 뒤에 두면: 공격 문장이 먼저 Memory에 적재되어 다음 턴 맥락을 오염시키고, RAG 검색·LLM 왕복까지 진행돼 비용이 발생한 뒤에야 막게 된다 — short-circuit의 의미가 사라진다.

### Q4. Short-circuit 시 비용 0이 왜 중요한가? (DoS 관점)

차단 시 `chain.nextCall()`을 호출하지 않으므로 **LLM·임베딩 호출이 0 = 토큰 비용 0**이다(S1~S4가 증거).
- DoS 관점: 공격자가 injection/거대 입력을 **대량으로 폭격**해도, 각 요청이 입력 단(정규식·길이 검사, ~0ms)에서 끊기므로 **비용 증폭이 일어나지 않는다.** LLM은 호출당 비용·지연이 크기 때문에, 가드 없이 LLM까지 보내면 적은 요청으로도 비용/지연 폭탄이 된다.
- 즉 InputGuardrail은 보안(주입 차단)이자 **비용 방어(LLM 앞단 필터)**다.
